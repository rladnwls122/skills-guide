# 실습 축 전환 — 재현에서 변동 대응으로

날짜: 2026-08-11
상태: 검토 중
범위: PART-1 · PART-2 · PART-4 의 `lab.mdx` 12편

## 왜 이 문서를 쓰나

지금 실습은 두 가지 중 하나다. 모듈 01 은 정답지 스펙을 백지에서 다시 쓰고, 나머지는 런북의
명령을 순서대로 실행한다. 둘 다 **완성된 과제 한 편을 재현하는 훈련**이다.

대회 당일에 재현할 것은 없다. 과제지가 채점 점수의 30% 범위 안에서 바뀐 채로 나온다
([`reference/variation-drill`](../../../src/content/docs/reference/variation-drill.mdx) 의 협의회
확인 내용). 필요한 것은 재현 능력이 아니라 **바뀐 요구를 읽고 기존 구성을 어디까지 고쳐야
하는지 판단하는 능력**이다.

실습이 묻는 질문을 바꾼다. "이 스택을 어떻게 만드나"에서 "**이 스택이 있는데 요구가 이렇게
바뀌었다. 어디를 고치나**"로.

## 지금 상태 — 실측

| 항목 | 실측 |
|---|---|
| `lab.mdx` 총 편수 | 18 |
| 변동을 다루는 절이 있는 편수 | 6 (`변형 셀프 체크`) |
| 그 절의 형식 | **재배포 없이 답만 맞춰 보는 지면 문제** — "각 질문에 먼저 답한 뒤 펼쳐 확인한다" |
| 손으로 하는 변동 훈련 | PART-6 모듈 15 하나. 고정 일차 없음 |
| 변동 소재의 출처 | 모듈 15 는 "친구 또는 AI에게 변형 과제지 제작을 의뢰" — 학습자가 스스로 조달 |

즉 변동 대응은 사이트에 **부록으로만** 있고, 그 부록조차 소재를 학습자가 구해 와야 한다.

## 협의회가 확인한 실제 변경 범위

근거는 `reference/variation-drill.mdx` 서두다. 이 범위가 설계 전체를 규정한다.

| 과제 | 변경 범위 |
|---|---|
| 1과제 | **아키텍처 교체 없음.** EKS→ECS 같은 서비스 교체 불가. 기존 구성 위에 모니터링·Lambda 를 얹는 추가 |
| 2과제 | **모듈 최대 2개 추가 출제.** 추첨된 세트의 4개 + 2개 = 최대 6개. **추가 시간 없음** |
| 3과제 | 전면 변경 없이 배점 수정과 추가 문제. 추가 바이너리 배포, 새 Lambda 개발 후 운영이 예시 |

1과제의 변동이 "이름·값·개수"에 그치지 않는다는 점이 중요하다. 아키텍처는 안 바뀌지만
**구성 요소가 추가되고 제약이 바뀐다.** `sed` 치환 훈련만으로는 부족하다.

2과제의 "추가 모듈 2개, 추가 시간 없음"이 이번 설계에서 후보 밖 세트를 쓰는 근거다.

## 결정

1. **`lab.mdx` 를 변동 이행 실습으로 재작성한다.** 기초 구축 절차는 사이트가 다시 쓰지 않고
   정답지 레포 런북으로 넘긴다.
2. **변동 소재는 후보 세트 간의 실제 차이에서 가져온다.** 지어내지 않는다. 타깃 세트의
   `mark.sh`·`mark.md` 가 그대로 채점기가 되므로 검증이 함께 풀린다.
3. **통과 기준은 코드 이행과 `plan` 까지다.** 배포와 `mark.sh` 실행은 선택 절로 둔다.
4. **범위는 PART-1·2·4 의 12편.** PART-3·5·6 은 이번에 손대지 않는다.
5. **`theory.mdx` 는 손대지 않는다.** 원리와 채점 관점은 그대로 유효하다.

### 왜 기초 구축을 레포로 넘기나

정답지 레포에 세트별 런북이 이미 있다 — `set-02/task-1/README.md` 359줄, `set-03/task-1` 398줄,
`set-07/task-1` 468줄, 2과제는 모듈마다 `README.md`. 사이트가 같은 절차를 다시 쓰면 두 벌을
유지해야 하고, 지금 lab 의 분량 대부분이 그 중복이다.

레포는 공개돼 있고(`github.com/ishs-cloud-computing/skills-2026`) Day 0 에서 이미 클론한다.
모듈↔경로 매핑도 [`reference/links`](../../../src/content/docs/reference/links.mdx) 에 있다.

### 왜 `plan` 까지만 필수인가

12편을 전부 배포하면 모듈마다 EKS·NAT 비용이 든다. 반복 훈련이 불가능해진다.

변동 대응에서 실제로 어려운 것은 **바뀐 값이 숨어 있는 곳을 전부 찾는 일**이고, 그것은
`grep` 잔존 검사와 `terraform plan` 의 리소스 목록으로 판정된다. 배포해야만 드러나는 변동
(KEDA 스케일 동작, DocumentDB 접속, 이벤트 자동복구)은 선택 절에 두고 그 사실을 명시한다.

## 문서 구조

모듈당 파일 수는 3개 그대로다. 역할만 바뀐다.

| 파일 | 지금 | 바뀐 뒤 |
|---|---|---|
| `index.mdx` | 개요·목표 | 유지. 학습 목표 문장만 변동 대응 기준으로 교체 |
| `theory.mdx` | 원리·채점 관점 | **손대지 않는다** |
| `lab.mdx` | 백지 작성 / 런북 따라하기 | **변동 이행 실습**으로 재작성 |

`lab.mdx` 골격:

```
## 0. 기준본 세우기        레포 런북 링크 + 섰는지 확인하는 명령 한 줄. 10줄 내외
## 1. 변동 과제지          타깃 세트의 스펙 차이만 산문으로. 정답 코드는 보여주지 않는다
## 2. 이행 (타이머 N분)    학습자가 직접. 절차 지시 없음
## 3. 통과 기준            grep 잔존 · validate/plan · 타깃 mark 항목 대응표
## 4. 복기                타깃 세트 정답과 diff, 놓친 곳 분류
## 5. 배포 확인 (선택)     여유 있을 때만. 타깃 mark.sh
```

**2절에 절차를 쓰지 않는 것이 이 설계의 핵심이다.** 명령을 순서대로 주면 학습자는 읽고
붙여넣지, 찾지 않는다. 대신 모든 lab 에 이미 있는 `실전 참조 — 막히면 여는 곳` 블록을
그 모듈의 변동에 맞게 다시 쓴다.

문서 유형은 `tutorial` 을 유지한다. 절차를 지시하지 않지만 학습자를 정해진 결과로 데려가는
훈련이고, 목표·통과 기준·복기가 있는 구조다.

### 모듈 01 의 변동이 어떤 것인지 — 대표 예

| | set-02 (기준본) | set-07 (변동) |
|---|---|---|
| VPC CIDR | `172.16.0.0/16` | `10.97.0.0/16` |
| 서브넷 | 2 AZ × 2계층 = 4개. **표로 CIDR 지급** | 3 AZ × 2계층 = 6개. **"Public 이 0·1·2번째, Private 이 10·11·12번째" 규칙만 주고 직접 계산** |
| 이름 | 전부 나열 | `unicorn-subnet-{pub,priv}-{a,b,c}` — 중괄호를 선수가 전개 |
| 프라이빗 외부 통신 | NAT Gateway 2개 | **"인터넷을 경유하지 않아야 한다"** → NAT 삭제, VPC Endpoint |

`sed` 치환으로 풀리지 않는다. 표를 규칙으로 바꾸고 NAT 를 걷어내려면 코드 구조를 봐야 한다.
이 성격이 12편 전체가 목표로 하는 난이도다.

### 후보 밖 세트를 쓰는 것에 관하여

`CLAUDE.md` 는 **수상 후보만 근거로 쓴다**고 규정한다 — 1과제 set-02·03·07, 2과제 set-02·07·08.
set-05·09 는 후보가 아니다. 이 설계는 모듈 10·12 에서 set-05 를 쓴다.

충돌하지 않는다. **정답의 근거로 쓰지 않고 변동 소재로만 쓰기 때문이다.** 협의회가 2과제에
모듈 2개가 추가되고 그것이 후보 밖에서 올 수 있다고 확인했으므로, 후보 밖 세트는 "출제될 수
있는 변동"의 실물이다. `reference/variation-drill` 이 이미 같은 논리로 set-05·set-06 을 쓰고 있다.

문서에 이 구분을 명시한다 — 해당 lab 의 변동 과제지 절에 "**후보 밖 세트에서 가져온 변동
소재다. 이 스펙 자체가 출제된다는 뜻이 아니라 추가 모듈이 이런 모양으로 온다는 뜻이다**"를
적는다.

## 통과 기준

세 층이고, 셋 다 배포 없이 판정된다.

1. **잔존 검사** — 옛 값 전부에 대해 `grep -rn --exclude-dir=.terraform '옛값' .` 이 0건.
   숨는 곳은 모듈 15 가 정리한 8종을 따른다: `terraform.tfvars` · YAML 리터럴 · JS 코드 ·
   Grafana dashboard JSON · `mark.sh` · `eksctl/cluster.yaml` · userdata 템플릿 · Lambda 환경 변수.
2. **`terraform validate` + `plan`** — 통과할 뿐 아니라 `plan` 이 만드는 리소스의 **개수와
   이름이 변동 스펙과 일치**해야 한다. 모듈 01 이면 서브넷 6개, 라우팅 테이블 개수, NAT 0개다.
3. **채점 항목 대응표** — 타깃 세트 `mark.md` 를 열어 "이 변동이 어느 항목을 건드리나"를
   **학습자가 직접 채운다.** 표의 정답은 접어서 제공한다.

타이머는 모듈당 20~40분으로 잡는다. 정확한 값은 각 모듈 작성 시 변동 규모를 보고 정한다.

## 미확인

- **모듈 03 의 변동 짝.** set-02 의 컨테이너·Lambda·DynamoDB 구성과 set-03·set-07 의 차이를
  실측하지 않았다. 차이가 얕으면 이 모듈은 자체 제작 변동으로 돌린다.
- **모듈 12 의 Lattice 짝.** `set-05/task-2/module-2-vpc-lattice` 디렉터리가 있는 것만 확인했고
  `set-08/task-2/module-2-lattice` 와 요구사항을 대조하지 않았다.
- **모듈 13 은 짝이 없다.** CDN Function 은 set-07 모듈2 에만 있다. 변동을 자체 제작해야 하는데,
  그러면 "지어내지 않는다"는 결정 2번의 예외가 된다. 리전 이동과 KVS 키·쿠키명 변경처럼
  근거가 확실한 축으로만 만든다.
- **타이머 값.** 모듈당 20~40분은 추정이다. 실제로 풀어 보고 정한다.
- **PART-3·5·6.** 이번 범위 밖이다. PART-5(3과제)는 근거가 예상 풀이 하나뿐이라 이행할 상대가
  없다 — 협의회가 말한 "추가 바이너리·새 Lambda" 유형으로 자체 제작해야 하고, 별도 spec 이 필요하다.
