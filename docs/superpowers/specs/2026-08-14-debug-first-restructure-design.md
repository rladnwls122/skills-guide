## 0. 앞선 설계와의 관계

`2026-08-11-variation-first-labs-design.md` 가 실습 축을 "재현"에서 "변동 이행"으로 옮겼고, 모듈 01 의 `lab.mdx` 가 그 골격으로 이미 재작성됐다(`f577318`). 구현은 형식 검토 게이트에서 멈춰 있다.

이 문서가 그 설계를 **대체한다.** 다만 되돌리지 않는다. 08-11 의 결정 중 다음은 그대로 승계한다.

- 실습의 질문은 "이 스택을 어떻게 만드나"가 아니라 "요구가 바뀌었다, 어디를 고치나"다.

- 모듈별 변동 짝 표를 쓴다.
- `변형 셀프 체크` 는 흡수해 삭제한다. 지면 문제가 손으로 하는 훈련으로 바뀌었으므로 남기면 같은 질문에 답을 두 번 준다.

## 1. 문제

지금 문서에 없는 것이 둘이다.

- **과제지 오독 복구.** 이름 접두사·리전·CIDR·버전을 연습본 기준으로 **이미 만들어 놓고** 나중에 과제지가 다른 값을 요구한다는 것을 안다. 그 시점의 질문은 "고쳐서 살리나, 부수고 다시 만드나, 몇 분 걸리나"다. `plan` 단계에서는 이 질문이 나오지 않는다.
- **장애 진단.** 파드가 안 뜨고 타깃그룹이 unhealthy 인 상태에서 원인을 좁혀 가는 순서. `reference/troubleshooting` 은 증상별 처방 목록이라 참조 문서이고, 증상을 이미 특정한 사람을 전제한다. 좁혀 가는 훈련이 없다.

`part-6/16-break-fix` 에 시나리오 표가 있으나 고장을 실제로 주입하는 명령이 없어 혼자 재현할 수 없다.

### theory.mdx — explanation + 접이식 실행

문서 유형은 `explanation` 을 유지한다. 각 개념 절 끝에 접이식 블록을 하나 붙인다.

```
> 문서 유형: explanation

## 1. 개념 A
   (산문 설명 — 현행 유지)
   <details class="build-step"><summary>지금 띄우기 — A</summary>
     실행 명령(PowerShell·bash 두 탭) + 기대 출력 + 기대와 다를 때 볼 곳 한 줄
   </details>

## 2. 개념 B
   <details class="build-step"><summary>지금 띄우기 — B</summary> ... </details>
...
## n. 전체 검증 — mark 항목 대응
## 정리 — 이 문서에서 띄운 것 지우기
## 자기 점검 퀴즈   (현행 유지)
```

블록은 **누적**된다. 1절 블록을 열고 따라오면 2절 블록이 그 위에 쌓여, 마지막 절에서 기준본 세트의 인프라가 완성된다. 블록을 열지 않는 사람에게는 현행 theory 와 같은 문서다. 이 접힘이 Diátaxis 유형 혼재를 막는 장치다 — 기본 읽기 흐름은 설명 그대로다.

블록 안의 형식은 셋으로 고정한다. 실행 명령, 기대 출력, 기대와 다를 때 볼 곳 한 줄. 진단 절차를 여기에 쓰지 않는다 — lab 소관이다.

`class="build-step"` 을 쓴다. 스타일은 `src/styles/diagram-note.css` 의 형제로 `src/styles/build-step.css` 를 만들고 `astro.config.mjs` 의 `customCss` 에 등록한다.

theory 가 띄우는 것은 **기준본 세트**다(모듈 01 이면 set-02). 타깃 세트로의 이행은 lab 이 한다.

`2.` 에 절차를 쓰지 않는 08-11 의 결정은 그대로 지킨다. 대신 `실전 참조 — 막히면 여는 곳` 블록을 그 모듈의 변동에 맞게 다시 쓴다.

### 5절 — 과제지 오독 복구

소재를 지어내지 않는다. **2절 이행에서 학습자가 실제로 놓치기 쉬운 항목**을 골라, 그것을 놓친 채 apply 한 상태에서 시작한다. 변동 짝이 실제 세트 차이이므로 소재도 실측이다.

각 항목은 다섯 부분이다.

1. **상황** — "타깃은 3AZ 6서브넷인데 너는 기준본대로 2AZ 4서브넷을 apply 했다"
2. **판정** — `terraform plan` 출력에서 `# forces replacement` 가 붙는 줄을 직접 찾게 한다. 콘솔·CLI 로 만든 것은 대응하는 `modify` API 가 있는지로 판정한다. 추측으로 넘어가지 않는 것이 이 절의 규율이다.
3. **파급** — 그 리소스가 재생성되면 같이 깨지는 것(S3 버킷명이면 CloudFront OAC 와 KMS 키 정책)
4. **복구 명령** — 순서대로
5. **소요 시간** — 실측값

판정 축은 네 단계다. 모듈마다 해당하는 것만 쓴다.

| 판정 | 예 | 비용 |
|---|---|---|
| in-place | 태그, 라벨, 인스턴스 타입, SG 규칙, Lambda 환경변수 | 초 |
| ForceNew, 의존 없음 | 서브넷 CIDR, Lambda 런타임 | 분 |
| ForceNew, 의존 딸림 | S3 버킷명 → OAC·KMS 키 정책 동반 | 십분 |
| 전면 재생성 | EKS 클러스터명, 리전 | 20분 이상 — 당일 치명 |

마지막 줄이 핵심 교훈이다. 리전과 클러스터 이름은 만들기 전에 두 번 확인해야 하는 값이고, 그 이유를 몸으로 알게 하는 것이 이 절의 목적이다.

### 6절 — 장애 진단

정상 상태에서 고장을 주입하고 좁혀 간다. 각 항목은 넷이다.

1. **주입 명령** — 재현 가능해야 한다. `kubectl set image ... :nosuchtag` 처럼 한 줄로
2. **관측되는 증상** — 사용자가 먼저 보게 되는 출력
3. **좁히는 순서** — 계층을 좁혀 가는 명령 순서. `reference/troubleshooting` 의 해당 항목을 링크하되 순서 자체는 여기에 쓴다
4. **복구** — 되돌리는 명령과 확인

모듈당 5절 2~3건, 6절 1~2건을 기준으로 한다. 문서가 길어지는 것은 허용한다.

## 5. 콘솔 배포 문서 (신규)

`src/content/docs/part-N/console-deploy.mdx`. PART 1~4 에 하나씩, 총 4개. `> 문서 유형: how-to`, `sidebar.order: 99` 로 파트 끝에 놓는다. 사이드바는 `autogenerate` 라 파일만 추가하면 잡힌다.

클릭 순서 나열은 쓸모가 없다. 네 가지를 담는다.

1. **같은 리소스, 두 경로** — 그 파트의 핵심 리소스를 콘솔로 만들고 Terraform 산출물과 대조한다.
2. **콘솔이 몰래 만드는 것** — 마법사가 기본 보안그룹, 기본 라우팅 테이블 연결, 기본 로그그룹을 끼워 만든다. `reference/cleanup-check` 의 잔존 리소스 점검에 걸리는 지점.
3. **drift** — 콘솔로 고친 뒤 `terraform plan` 이 되돌리려 든다. `terraform import` 와 코드 수정과 방치, 각각이 옳은 때. 이 절이 문서의 존재 이유다. 지금 사이트 어디에도 없고 대회 당일 반드시 만난다.
4. **판단표** — 콘솔이 옳은 때(1회성 수정, Terraform 이 막힘, 채점 직전 분 단위)와 코드가 옳은 때(반복, 이름 일괄 변경, 재현 필요).

### 구현 결과 (2026-08-14)

**파트마다 drift 의 성격이 다르다는 것이 실제로 써 보고 드러났다.** 같은 내용을 네 번 쓰는 것이 아니라 네 종류를 하나씩 맡는다.

| 파트 | drift 의 성격 | 정본 |
|---|---|---|
| 1 | 코드에 있는데 값이 다르다 | Terraform 상태 |
| 2 | **되돌리는 주체가 다르다** — 탐지가 자동이 아니고 되돌려 주지도 않는다 | CloudFormation 스택 |
| 3 | **코드에 아예 없다** — `plan` 이 조용한 것이 안전하다는 뜻이 아니다 | 없다 — 사람이 목록을 적어야 한다 |
| 4 | **다른 리전에 있다** — 코드도 상태도 모르고 채점도 못 찾는데 과금은 된다 | 없다 — 리전을 바꿔 가며 조회하는 수밖에 |

4 가 가장 나쁘다. 점수는 안 나오는데 돈은 나가고 도구는 아무 말도 안 한다. 복구가 전면 재배포뿐이라 **예방이 유일한 대응**이다.

`terraform plan -generate-config-out` 은 도구 도움말에 `(Experimental)` 로 표시된다(1.15.8 확인). 대회 당일 의존하지 말라는 근거로 문서에 그대로 옮겼다.

- 비용은 **트래픽을 처리하는 2시간 동안만** 집계해 채점에 반영한다.
- 대시보드 반영은 최대 1분 걸린다. 조치 직후 값이 안 변해도 고장이 아니다.
- 인스턴스 비용 ratio 는 단순 평균 인스턴스 수가 아니라 별도 계산식이다. N분마다 집계한 데이터로 대회 시간 동안 평균 몇 대를 썼는지를 활용한다.
- 절대 계산식이다. 모든 선수가 만점일 수도, 모두 0점일 수도 있다.
- 언급되지 않은 인스턴스를 쓰면 패널티가 부과된다.
- 트래픽 발생 시점과 대응 시간은 과제지에 명시된 바를 따른다(사전 공개 없음).

여기서 파생되는 운영 지침을 lab 에 넣는다. 대시보드 1분 지연을 모르면 조치를 겹쳐 넣어 과잉 대응하게 되므로, 조치 후 최소 1분은 기다리고 판단한다. 비용이 2시간만 집계되므로 구축 단계의 인스턴스 수는 점수에 들어가지 않는다. 절대 평가이므로 남과 비교할 이유가 없고 자기 목표치만 본다.

모듈 14 는 how-to 유형을 유지한다. 3절 문서 계약을 적용하지 않는다 — 부하 발생 환경을 개인이 재현할 수 없기 때문이다. 대신 부하 중 운영 디버깅(스케일 지연, 502/503, 파드 Pending) 절을 늘린다.
