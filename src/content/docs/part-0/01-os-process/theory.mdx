## 1. 프로그램과 프로세스는 다른 것이다

**프로그램**은 디스크에 있는 파일이다. 명령어가 순서대로 적힌 죽은 바이트 덩어리다.

**프로세스**는 그 파일을 메모리에 올려 실행 중인 상태다. 살아 있고, 자기만의 주소 공간과 열어 둔 파일 목록과 신원(어떤 사용자로 도는가)을 가진다.

같은 프로그램에서 프로세스를 열 개 만들 수 있다. 열 개는 서로 남남이라 한쪽이 죽어도 나머지는 산다. 3과제에서 앱 파드를 여러 개 띄우는 것이 바로 이것이다 — 같은 바이너리, 다른 프로세스.

**스레드**는 한 프로세스 안에서 갈라진 실행 흐름이다. 주소 공간을 **공유**한다. 그래서 스레드 하나가 메모리를 망가뜨리면 같은 프로세스의 다른 스레드도 같이 죽는다. Go 로 짠 웹 서버가 요청 하나당 고루틴을 만드는 것은 프로세스가 아니라 이쪽에 가깝다 — 싸게 만들고 싸게 버린다.

| | 프로세스 | 스레드 |
|---|---|---|
| 주소 공간 | 각자 따로 | 공유 |
| 하나가 죽으면 | 나머지는 산다 | 같이 죽을 수 있다 |
| 만드는 비용 | 크다 | 작다 |
| 대회에서 보는 자리 | 파드, EC2 위의 systemd 서비스 | 앱 안의 동시 요청 처리 |

## 2. 가상 메모리 — 모든 프로세스가 자기가 혼자라고 믿는다

프로세스는 `0x0000...` 부터 시작하는 연속된 메모리를 자기가 통째로 가진 것처럼 본다. 거짓말이다. 실제 물리 메모리는 조각나 있고, 다른 프로세스와 나눠 쓰며, 일부는 아예 디스크에 있다.

이 거짓말을 유지하는 것이 **가상 메모리**다. 커널과 CPU 의 MMU 가 프로세스가 보는 주소(가상 주소)를 실제 주소(물리 주소)로 그때그때 바꿔 준다.

여기서 대회에 직접 걸리는 결론 둘이 나온다.

**첫째, "이 프로세스가 메모리를 얼마나 쓰나"에 답이 여러 개다.**

| 지표 | 뜻 | 언제 보나 |
|---|---|---|
| 가상 크기(VSZ) | 프로세스가 예약한 주소 공간 전체 | 거의 안 본다. 실제로 안 쓰는 영역이 잔뜩 들어 있다 |
| 상주 크기(RSS) | 지금 물리 메모리에 실제로 올라와 있는 양 | 보통 이것을 본다 |
| 공유분 | 다른 프로세스와 함께 쓰는 라이브러리 등 | 여러 프로세스의 RSS 를 더하면 실제보다 커지는 이유 |

파드의 메모리 사용량이라고 표시되는 값도 결국 이 계열이다. **RSS 를 더한 값이 물리 메모리보다 클 수 있다**는 사실을 모르면 "메모리가 200% 사용 중"이라는 이상한 결론에 도달한다.

**둘째, 메모리는 "쓸 때" 진짜로 할당된다.** 프로그램이 1GB 를 달라고 해도 커널은 일단 약속만 하고, 실제로 그 주소에 값을 쓰는 순간에 물리 페이지를 붙인다. 그래서 컨테이너가 뜰 때는 멀쩡하다가 트래픽이 들어온 뒤에야 메모리 한도에 부딪히는 일이 생긴다.

## 3. 메모리가 모자라면 누가 죽는가

두 개의 층이 있고, 대회에서 만나는 것은 대개 아래쪽이다.

**호스트 층 — OOM Killer.** 물리 메모리가 진짜로 바닥나면 커널이 프로세스를 골라 죽인다. 고르는 기준은 "메모리를 많이 쓰고 덜 중요한 것"이다. 이건 노드 전체가 위태로울 때의 최후 수단이다.

**cgroup 층 — 한도 초과.** 컨테이너에 "메모리 512Mi 까지" 라고 걸어 두면, 그 컨테이너의 프로세스 합이 512Mi 를 넘는 순간 **그 컨테이너 안에서만** 죽인다. 노드에 메모리가 남아 있어도 죽는다. 쿠버네티스가 `OOMKilled` 라고 표시하는 것이 이쪽이다.

:::danger[메모리 한도는 CPU 한도와 성질이 다르다]
CPU 는 한도를 넘으면 **느려진다**(스로틀링). 기다리면 처리된다.

메모리는 한도를 넘으면 **죽는다**. 메모리에는 "조금씩 나눠 준다"가 없다 — 페이지를 주거나 못 주거나 둘 중 하나다.

그래서 같은 "한도"라는 말을 써도 대응이 정반대다. CPU 한도 초과는 지연 지표에서 보이고, 메모리 한도 초과는 재시작 횟수에서 보인다.
:::

`OOMKilled` 를 만났을 때 물을 것은 순서대로 셋이다.

1. **한도가 너무 낮은가** — 앱이 정상적으로 그만큼 쓰는데 한도가 작았다.
2. **앱이 새는가** — 시간이 갈수록 사용량이 단조 증가하면 누수다. 한도를 올려도 시간만 벌 뿐이다.
3. **한 요청이 너무 크게 먹는가** — 평소엔 멀쩡한데 특정 요청에서 튄다. 3과제의 `stress` API 가 정확히 이 모양이다.

## 4. CPU 는 나눠 쓰는 것이지 소유하는 것이 아니다

CPU 코어 하나는 한 순간에 한 스레드만 돌린다. 여러 프로세스가 동시에 도는 것처럼 보이는 것은 커널이 아주 짧은 간격으로 번갈아 실행하기 때문이다. 이 전환을 **컨텍스트 스위치**라고 한다.

그래서 "CPU 1 코어"라는 말은 소유가 아니라 **시간 배분의 몫**이다. 쿠버네티스가 CPU 를 `500m`(0.5 코어) 처럼 소수로 적을 수 있는 이유가 이것이다 — 시간의 절반이라는 뜻이지 코어 반쪽이 아니다.

CPU 를 기다리는 상태와 입출력을 기다리는 상태는 다르다. 이 구분이 진단에서 갈린다.

| 상태 | 뜻 | 지표에서 보이는 모습 |
|---|---|---|
| 실행 중 | CPU 를 지금 쓰고 있다 | CPU 사용률이 오른다 |
| 실행 대기 | 일할 준비는 됐는데 CPU 차례가 안 왔다 | 사용률은 100% 인데 처리량이 안 는다 |
| 대기(블록) | 디스크·네트워크·DB 응답을 기다린다 | **CPU 사용률은 낮은데 응답이 느리다** |

세 번째 줄이 3과제 성능 축의 핵심이다. 응답이 0.2초를 넘는데 CPU 가 한가하면 원인은 앱이 아니라 **기다리는 대상**(대개 DB)이다. CPU 를 늘려도 안 낫는다.

## 5. 컨테이너는 새로운 것이 아니다 — 격리된 프로세스다

가상 머신은 운영체제를 통째로 하나 더 돌린다. 컨테이너는 그렇지 않다. **호스트의 커널을 그대로 쓰는 보통의 프로세스**이고, 다만 두 가지 커널 기능으로 시야와 몫이 제한돼 있다.

**네임스페이스 — 무엇을 볼 수 있는가.** 프로세스 목록, 네트워크 인터페이스, 마운트된 파일시스템, 호스트 이름 같은 것들을 각각 따로 가질 수 있다. 컨테이너 안에서 `ps` 를 쳤을 때 자기 프로세스만 보이는 이유가 PID 네임스페이스다. 컨테이너가 자기만의 IP 를 갖는 것은 네트워크 네임스페이스다.

**cgroup — 얼마나 쓸 수 있는가.** CPU 시간, 메모리, 입출력 대역을 그룹 단위로 제한하고 계량한다. 쿠버네티스의 `limits` 가 최종적으로 도착하는 곳이 여기다.

이 둘의 조합이 컨테이너의 전부다. 이미지는 그 프로세스가 볼 파일시스템을 미리 말아 둔 것이고, 런타임은 위 설정을 대신 걸어 주는 도구다.

:::note[여기서 따라 나오는 결론들]
- 컨테이너는 부팅하지 않는다. 그래서 **뜨는 데 초 단위**면 되고, 그래서 오토스케일링의 단위가 될 수 있다.
- 컨테이너는 호스트 커널을 공유한다. 그래서 **리눅스 이미지를 리눅스 노드에서만** 돌린다.
- 컨테이너 안의 `top` 이 호스트 전체 메모리를 보여 주는 일이 있다. 격리는 커널이 보여 주는 만큼만이고, 모든 도구가 cgroup 을 읽도록 만들어져 있지는 않다.
:::

## 6. requests 와 limits — 미리 만나 두기

쿠버네티스에서 컨테이너마다 두 값을 적는다. 이름이 비슷해서 자주 섞이는데 **하는 일이 완전히 다르다.**

**`requests` 는 배치를 정한다.** 스케줄러는 노드의 남은 용량과 파드가 요청한 양만 보고 어느 노드에 놓을지 정한다. 실제 사용량은 보지 않는다. `requests` 를 크게 적으면 실제로 놀고 있어도 노드가 꽉 찬 것으로 계산돼 **새 노드가 뜬다.**

**`limits` 는 상한을 정한다.** cgroup 에 걸리는 값이고, 실행 중에 넘으면 CPU 는 느려지고 메모리는 죽는다.

3과제 비용 축이 여기 걸린다. 노드 수는 실사용량이 아니라 **`requests` 의 합**이 정한다. 그래서 비용을 줄이는 첫 손질은 앱 최적화가 아니라 `requests` 를 실제 사용량에 맞게 낮추는 일이다. 동시에 너무 낮추면 한 노드에 파드가 몰려 서로를 방해한다 — 이 균형이 [22. 3과제 부하 운영](/part-5/22-task3-tuning/)에서 다시 나온다.

<details class="build-step">
<summary>지금 띄우기 — CPU 를 기다리는 것과 입출력을 기다리는 것 구분하기</summary>

<Tabs syncKey="shell">

  ```powershell
  # CPU 를 태우는 작업 - 사용률이 오른다

  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  # CPU 를 태우는 작업
  time (i=0; while [ $i -lt 3000000 ]; do i=$((i+1)); done)

  # 기다리는 작업
  time sleep 3
  ```
  </TabItem>
</Tabs>

기대: 둘 다 몇 초가 걸리지만 첫 번째만 작업 관리자·`top` 에서 CPU 사용률을 올린다. **걸린 시간이 같아도 원인이 다르다**는 것이 이 블록의 전부다.

</details>

## 정리

- 프로세스는 실행 중인 프로그램이고, 스레드는 그 안에서 주소 공간을 공유하는 실행 흐름이다.
- 메모리 사용량에는 답이 여럿이다. 보통 보는 것은 상주 크기이고, 예약과 실제 사용은 다르다.
- 메모리 한도 초과는 죽음이고 CPU 한도 초과는 지연이다. 증상이 다르니 지표도 다른 곳을 본다.
- 컨테이너는 네임스페이스(시야)와 cgroup(몫)으로 제한된 보통의 프로세스다.
- `requests` 는 배치를, `limits` 는 상한을 정한다. 노드 수와 비용은 `requests` 가 정한다.

## 자기 점검 퀴즈

<Quiz title="OOMKilled 의 층">
컨테이너에 메모리 `limits: 512Mi` 를 걸었다. 노드에는 메모리가 8GB 남아 있는데 컨테이너가 `OOMKilled` 되었다. 왜인가?

- [x] cgroup 한도를 넘어 그 컨테이너 안에서 죽었다 — 노드의 여유와 무관하다
- [ ] 노드의 물리 메모리가 부족해 커널 OOM Killer 가 골라 죽였다
  > 그것도 OOM 이지만 다른 층이다. 노드에 8GB 가 남아 있으므로 호스트 층은 아직 위태롭지 않다.
- [ ] 스케줄러가 파드를 다른 노드로 옮기려고 죽였다
  > 스케줄러는 배치만 정한다. 실행 중인 컨테이너를 메모리 때문에 죽이는 것은 커널이다.
- [ ] `requests` 가 `limits` 보다 커서 거부됐다
  > 그 경우는 파드가 아예 뜨지 않는다. `OOMKilled` 는 떠서 돌던 것이 죽은 상태다.

**cgroup 한도 초과다.** `limits` 는 노드 전체가 아니라 그 컨테이너에만 걸리는 상한이고, 커널은 그 그룹 안에서 프로세스를 죽인다. 그래서 노드 메모리를 늘려도 이 증상은 안 사라진다 — 한도를 올리거나, 앱이 그만큼 안 쓰게 만들어야 한다.
</Quiz>

<Quiz title="느린데 CPU 는 한가하다">
응답 시간이 목표를 넘는데 파드의 CPU 사용률은 20% 대다. 가장 먼저 의심할 것은?

- [x] 무언가를 기다리는 중이다 — 대개 데이터베이스나 외부 호출
- [ ] CPU `limits` 가 낮아 스로틀링이 걸렸다
  > 스로틀링이면 사용률이 한도에 붙어 있다. 20% 대면 CPU 를 달라고 하지도 않은 것이다.
- [ ] 노드가 모자라 파드가 대기 중이다
  > 그 경우 파드가 `Pending` 이라 응답 자체가 없다. 느린 것과 다르다.
- [ ] 메모리가 부족해 스왑이 일어났다
  > 쿠버네티스 노드는 보통 스왑을 끈다. 메모리가 모자라면 느려지는 게 아니라 죽는다.

**기다리는 것이다.** CPU 를 쓰지 않으면서 시간이 흐른다는 것은 실행이 아니라 대기 상태라는 뜻이고, 웹 앱에서 그 대상은 대개 DB 다. 이때 CPU 를 늘리거나 파드를 늘려도 낫지 않고, 오히려 DB 커넥션만 더 소모해 악화된다.
</Quiz>

<Quiz title="노드 수를 정하는 값">
비용을 줄이려고 노드 수를 낮추고 싶다. 실사용량은 그대로일 때 가장 직접적으로 효과가 있는 손질은?

- [x] `requests` 를 실제 사용량에 맞게 낮춘다 — 노드 수는 요청량의 합이 정한다
- [ ] `limits` 를 낮춘다
  > `limits` 는 배치 계산에 들어가지 않는다. 낮추면 죽거나 느려질 뿐 노드 수는 그대로다.
- [ ] 이미지 크기를 줄인다
  > 디스크와 당겨 오는 시간이 줄 뿐 스케줄러의 계산은 바뀌지 않는다.
- [ ] `limits` 를 올려 파드가 덜 죽게 한다
  > 안정성에는 도움이 될 수 있으나 노드 수와는 무관하다.

**`requests` 다.** 스케줄러는 실사용량을 보지 않고 요청량만 더해 노드의 남은 자리를 계산한다. 그래서 실제로 놀고 있는 파드도 요청량이 크면 노드를 한 대 더 부른다. 이 관계가 [22. 3과제 부하 운영](/part-5/22-task3-tuning/)의 비용 축 전체를 지배한다.
</Quiz>
