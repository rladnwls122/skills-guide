## 1. 주소는 두 부분이다

IP 주소 `10.0.12.5` 는 점으로 나뉜 네 덩어리이고 각 덩어리는 0~255 다. 컴퓨터에게는 32비트 숫자 하나일 뿐이다.

중요한 것은 이 주소가 혼자 다니지 않는다는 점이다. 항상 짝이 되는 값이 붙는다 — 어디까지가 "동네 이름"이고 어디부터가 "집 번호"인지 알려 주는 값이다. 그것이 **서브넷 마스크**이고, 요즘은 `/24` 처럼 비트 수로 적는다(**CIDR 표기**).

`10.0.12.5/24` 를 풀면 이렇다.

| | 값 | 뜻 |
|---|---|---|
| 앞 24비트 | `10.0.12` | 네트워크 부분 — 같은 동네 |
| 나머지 8비트 | `5` | 호스트 부분 — 그 동네에서의 번호 |

같은 네트워크 부분을 가진 주소끼리는 **라우터 없이 직접** 이야기한다. 다르면 반드시 중간 장치를 거친다. 이 한 줄이 뒤의 모든 것을 만든다.

## 2. CIDR 을 손으로 쪼갠다

`/24` 는 호스트 비트가 8개이므로 주소가 256개다. `/26` 은 호스트 비트가 6개라 64개다. **숫자가 커질수록 네트워크가 작아진다** — 여기서 헷갈리는 사람이 많다.

`10.0.0.0/24` 를 `/26` 네 개로 쪼개면 이렇다.

| 조각 | 범위 |
|---|---|
| `10.0.0.0/26` | `10.0.0.0` ~ `10.0.0.63` |
| `10.0.0.64/26` | `10.0.0.64` ~ `10.0.0.127` |
| `10.0.0.128/26` | `10.0.0.128` ~ `10.0.0.191` |
| `10.0.0.192/26` | `10.0.0.192` ~ `10.0.0.255` |

계산 요령은 하나다. **`/26` 의 블록 크기는 `256 - 192 = 64`.** 마스크의 마지막 옥텟 값을 256에서 빼면 그 블록의 크기가 나오고, 시작 주소는 그 크기의 배수여야 한다.

| CIDR | 마지막 옥텟 마스크 | 블록 크기 | 시작 주소가 될 수 있는 값 |
|---|---|---|---|
| `/24` | 0 | 256 | 0 |
| `/25` | 128 | 128 | 0, 128 |
| `/26` | 192 | 64 | 0, 64, 128, 192 |
| `/27` | 224 | 32 | 0, 32, 64 ... |
| `/28` | 240 | 16 | 0, 16, 32 ... |

:::danger[AWS 는 서브넷마다 5개를 가져간다]
서브넷의 주소가 전부 내 것은 아니다. AWS 는 각 서브넷에서 **처음 4개와 마지막 1개**를 예약한다 — 네트워크 주소, 라우터, DNS, 예비, 브로드캐스트 자리다.

그래서 `/28`(16개)은 실제로 **11개**만 쓸 수 있다. 파드마다 IP 를 주는 EKS 구성에서 서브넷을 너무 작게 잡으면 노드가 늘다가 주소가 모자라 파드가 `Pending` 에 걸린다. 과제지가 `/24` 를 주는 데는 이유가 있다.
:::

## 3. 패킷은 표를 보고 길을 고른다

프로세스가 데이터를 보내면 커널이 목적지 주소를 보고 **라우팅 테이블**에서 경로를 찾는다. 규칙은 두 줄이다.

1. 목적지와 **가장 길게 일치하는** 항목을 고른다. 더 구체적인 쪽이 이긴다.
2. 아무것도 안 맞으면 기본 경로(`0.0.0.0/0`)로 보낸다.

그래서 라우팅 테이블에 `0.0.0.0/0` 이 없으면 **바깥으로 나갈 방법이 아예 없다.** AWS 에서 퍼블릭 서브넷과 프라이빗 서브넷을 가르는 것도 결국 이 한 줄이다.

| | 라우트 테이블의 기본 경로 | 결과 |
|---|---|---|
| 퍼블릭 서브넷 | `0.0.0.0/0` → 인터넷 게이트웨이 | 공인 IP 가 있으면 양방향 통신 |
| 프라이빗 서브넷 | `0.0.0.0/0` → NAT 게이트웨이 | 나갈 수는 있고 밖에서 먼저 들어올 수는 없다 |
| 완전 격리 | 기본 경로 없음 | VPC 안에서만 |

**서브넷이 퍼블릭인지는 서브넷 자체의 속성이 아니라 붙어 있는 라우트 테이블이 정한다.** 이름을 `public` 이라고 지어도 라우트가 NAT 를 가리키면 프라이빗이다. 채점 스크립트가 라우트 테이블과 서브넷의 연결을 직접 읽는 이유가 이것이다.

첫 홉이 안 보이거나 별표만 나오는 것은 정상이다 — 장비가 응답을 안 할 뿐 경로는 살아 있다.

</details>

## 4. NAT — 사설 주소로 공인망에 나가는 법

사설 대역(`10.`, `172.16~31.`, `192.168.`)은 인터넷에서 라우팅되지 않는다. 전 세계 누구나 같은 주소를 쓰기 때문이다. 그런데도 집 컴퓨터가 인터넷을 쓰는 것은 중간 장치가 **출발지 주소를 자기 공인 주소로 바꿔치기**하기 때문이다. 이것이 NAT 다.

NAT 는 바꿔치기하면서 표를 남긴다 — 내 공인 주소의 포트 40001 로 온 응답은 사설 `192.168.0.7` 의 포트 5555 로 돌려준다는 식이다. 그래서 **먼저 나간 대화의 응답만** 돌아올 수 있고, 밖에서 아무 때나 먼저 들어오는 것은 불가능하다.

여기서 AWS 의 세 가지가 갈린다.

| | 밖으로 나가기 | 밖에서 먼저 들어오기 | 비용 |
|---|---|---|---|
| 인터넷 게이트웨이 + 공인 IP | 가능 | **가능** | 게이트웨이 자체는 무료 |
| NAT 게이트웨이 | 가능 | 불가능 | **시간당 + 처리량당 과금** |
| VPC 엔드포인트 | AWS 서비스로만 | — | 종류에 따라 다름 |

:::caution[NAT 게이트웨이는 이 과정에서 가장 비싼 상시 과금 리소스다]
떠 있는 내내 시간당 요금이 붙고, 지나가는 데이터에도 요금이 붙는다. 실습을 끝내고 지우지 않으면 그대로 비용이다. 이 사이트가 모듈마다 정리 절을 두는 첫 번째 이유가 NAT 게이트웨이다.

프라이빗 서브넷에서 S3 같은 AWS 서비스만 부르면 되는 경우가 있다. 그때는 NAT 대신 **VPC 엔드포인트**로 트래픽을 AWS 내부로 돌린다 — 비용과 지연이 함께 준다. 1과제 후보 세트들이 엔드포인트를 요구하는 이유다.
:::

## 5. 방화벽 두 종류 — 상태를 기억하는가

AWS 에는 성격이 다른 문지기가 둘 있다. 시험에 자주 나오고 실전에서도 자주 헷갈린다.

**보안 그룹은 상태를 기억한다.** 인스턴스 단위로 붙는다. 나간 요청의 응답은 규칙이 없어도 자동으로 통과한다. 그래서 **허용 규칙만** 있고 거부 규칙이 없다.

**네트워크 ACL 은 상태를 기억하지 않는다.** 서브넷 단위로 붙는다. 나가는 것과 들어오는 것을 각각 적어야 한다. 허용과 거부가 모두 있고 번호 순으로 평가한다.

| | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| 붙는 곳 | 인스턴스·ENI | 서브넷 |
| 상태 기억 | 한다 | 안 한다 |
| 규칙 종류 | 허용만 | 허용 + 거부 |
| 응답 트래픽 | 자동 통과 | **직접 열어야 한다** |
| 기본값 | 인바운드 전부 차단 | 전부 허용 |

HTTP 응답을 위해 아웃바운드 80번을 열어야 하는가. 보안 그룹에서는 아니다. 네트워크 ACL 에서는 그렇다 — 그것도 80번이 아니라 응답이 돌아오는 **높은 번호 포트 범위**를 열어야 한다. 이 비대칭이 네트워크 ACL 을 손대는 것을 위험하게 만든다.

보안 그룹의 또 하나의 힘은 **다른 보안 그룹을 출발지로 지정할 수 있다**는 점이다. 이 데이터베이스는 웹 서버 보안 그룹에서 오는 것만 받는다고 쓰면, 웹 서버가 몇 대로 늘든 규칙을 안 고쳐도 된다. IP 로 쓰면 늘어날 때마다 규칙을 고쳐야 한다.

## 6. 나갈 수 없다를 좁히는 순서

실전 장애의 가장 흔한 형태다. 순서를 지키면 대개 세 번 안에 끝난다.

1. **경로가 있나** — 라우팅 테이블에 기본 경로가 있는가. 프라이빗인데 NAT 를 안 만들었거나, 만들고 라우트를 안 붙인 경우가 압도적으로 많다.
2. **문지기가 막나** — 보안 그룹 아웃바운드, 그리고 네트워크 ACL 의 **양방향**.
3. **이름은 풀리나** — 주소는 나가는데 이름을 못 찾는 경우다. 이것은 [03. DNS · HTTP · TLS](/part-0/03-dns-http-tls/)의 주제다.

**순서가 중요한 이유**는 증상이 똑같기 때문이다. 셋 다 안 된다로 보인다. 경로부터 확인하는 것은 그것이 가장 자주 원인이면서 가장 빨리 확인되기 때문이다.

<details class="build-step">
<summary>지금 띄우기 — 세 단계를 명령으로</summary>

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  Get-NetRoute -DestinationPrefix '0.0.0.0/0' | Select-Object -First 1 NextHop
  Test-NetConnection -ComputerName 1.1.1.1 -Port 443 -InformationLevel Detailed
  Resolve-DnsName aws.amazon.com | Select-Object -First 2 Name, IPAddress
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  ip route show default
  curl -sS -m 5 -o /dev/null -w '%{http_code}\n' https://1.1.1.1
  getent hosts aws.amazon.com
  ```
  </TabItem>
</Tabs>

세 명령이 각각 경로·도달·이름을 본다. 기대: 셋 다 성공한다. **둘째는 되는데 셋째가 안 되면 네트워크가 아니라 DNS 문제**다 — 이 구분이 진단 시간을 절반으로 줄인다.

</details>

## 7. VPC 를 여럿 잇는 법

VPC 하나로 끝나지 않는 과제가 있다. [2025 실기출 1과제](/reference/past-exams/#3-1-2025-1과제--solution-architecture-4시간-30점)는 Hub VPC 와 App VPC 둘을 만들고 그 둘이 통신하게 하라고 요구했다.

VPC 는 기본적으로 서로 격리돼 있다. 잇는 방법이 둘이다.

### 7-1. 피어링 — 둘을 직접 잇는다

```
VPC A  <---->  VPC B
```

한 쌍마다 연결을 하나 만들고, 양쪽 라우트 테이블에 상대 CIDR 경로를 넣는다.

문제는 셋 이상일 때다. VPC 가 넷이면 필요한 연결이 여섯 개, 다섯이면 열 개다. **연결 수가 VPC 수의 제곱에 가깝게 는다.** 라우트 테이블도 그만큼 늘어난다.

그리고 피어링은 **전이되지 않는다.** A-B 가 연결되고 B-C 가 연결돼도 A 는 C 와 통신하지 못한다. B 를 거쳐 가는 경로를 만들 수 없다.

### 7-2. Transit Gateway — 가운데 허브를 둔다

```
VPC A ──┐
VPC B ──┼── Transit Gateway
VPC C ──┘
```

각 VPC 를 허브에 한 번씩 붙이면 서로 통신할 수 있다. VPC 가 넷이면 연결이 넷이다. **선형으로 는다.**

| | 피어링 | Transit Gateway |
|---|---|---|
| 연결 수 | 쌍마다 하나 | VPC 마다 하나 |
| 전이 통신 | 안 된다 | 된다 |
| 비용 | 연결 자체는 무료 | **시간당 + 데이터 처리량당 과금** |
| 라우팅 제어 | 각 VPC 의 라우트 테이블 | **TGW 라우트 테이블로 중앙에서** |

### 7-3. 붙이는 두 층

Transit Gateway 를 쓸 때 라우팅이 두 층이라는 점이 처음에 헷갈린다.

**첫째 층 — VPC 의 라우트 테이블.** "이 대역으로 가려면 TGW 로 보내라"를 적는다.

```
gj2025-app-private-rtb-a
  0.0.0.0/0  ->  Transit Gateway
```

**둘째 층 — TGW 의 라우트 테이블.** "TGW 에 들어온 이 대역은 어느 연결로 내보내라"를 적는다.

```
gj2025-app-tgw-rtb
  10.0.0.0/16  ->  hub-tgw-attachment
```

:::danger[한 층만 채우면 통신이 안 된다]
VPC 라우트만 넣고 TGW 라우트를 비워 두면 패킷이 TGW 까지는 가고 거기서 버려진다. **양쪽 VPC 모두** 두 층을 채워야 왕복이 성립한다.

증상이 "한쪽에서만 되고 반대는 안 됨"이면 반대편 두 층 중 하나가 비어 있는 것이다.
:::

### 7-4. 연결에도 이름이 필요하다

2025 실기출 채점 스크립트가 연결 이름까지 확인한다.

```bash
TGW_ID=$(aws ec2 describe-transit-gateways --filters "Name=tag:Name,Values=$TGW_NAME" \
  --query "TransitGateways[0].TransitGatewayId" --output text)
aws ec2 describe-transit-gateway-attachments --filters "Name=transit-gateway-id,Values=$TGW_ID" \
  --query "TransitGatewayAttachments[*].{Name:Tags[?Key=='Name'].Value|[0]}" --output json
```

연결과 라우트 테이블에 이름 태그를 붙이지 않으면 이 조회가 `null` 을 낸다. 통신이 되더라도 채점 항목을 잃는다.

## 8. 흐름 로그 — 지나간 것을 남긴다

지금까지는 "왜 안 통하나"를 설정에서 찾았다. **실제로 무엇이 오갔는지**를 보려면 기록이 필요하다.

VPC Flow Logs 가 그 기록이다. VPC·서브넷·ENI 단위로 켤 수 있고 CloudWatch Logs 나 S3 로 보낸다.

### 8-1. 한 줄이 하나의 흐름이다

기본 형식은 이렇게 생겼다.

```
2 123456789012 eni-abc123 10.0.1.5 52.95.110.1 43210 443 6 12 1580 1720000000 1720000060 ACCEPT OK
```

| 자리 | 뜻 |
|---|---|
| `srcaddr` · `dstaddr` | 출발지·목적지 주소 |
| `srcport` · `dstport` | 출발지·목적지 포트 |
| `protocol` | 6 은 TCP, 17 은 UDP, 1 은 ICMP |
| `packets` · `bytes` | 양 |
| `action` | **`ACCEPT` 또는 `REJECT`** |
| `log-status` | `OK` · `NODATA` · `SKIPDATA` |

**`action` 이 진단의 핵심이다.** `REJECT` 가 보이면 보안 그룹이나 네트워크 ACL 이 막은 것이고, 아예 기록이 없으면 패킷이 그 ENI 까지 오지도 않은 것 — 곧 라우팅 문제다.

:::note[없다는 것도 정보다]
"안 통한다"를 좁힐 때 흐름 로그를 이렇게 읽는다.

| 로그에 | 뜻 | 다음에 볼 곳 |
|---|---|---|
| 기록이 없다 | 패킷이 도달하지 않았다 | 라우트 테이블 |
| `REJECT` 가 있다 | 도달했고 막혔다 | 보안 그룹 · 네트워크 ACL |
| `ACCEPT` 인데 응답이 없다 | 나갔고 돌아오지 못했다 | 반대 방향 경로 · NACL |
:::

### 8-2. 형식을 지정할 수 있다

기본 형식 대신 원하는 필드만 골라 순서까지 정할 수 있다. 2024 실기출이 그것을 요구했다.

```
${region} ${vpc-id} ${action} ${instance-id}
```

네 필드만 이 순서로 남기라는 뜻이다. 채점 스크립트가 형식 문자열 자체를 조회한다.

```bash
aws ec2 describe-flow-logs --query "FlowLogs[0].LogFormat"
```

**필드 하나만 빠져도, 순서만 달라도 불일치다.** 요구된 문자열을 그대로 옮긴다.

:::caution[`instance-id` 는 비어 있을 수 있다]
ENI 가 인스턴스에 붙어 있지 않으면(로드밸런서·NAT 게이트웨이 등) 이 필드가 `-` 로 남는다. 값이 없다고 설정이 틀린 것은 아니다.
:::

### 8-3. 기록에는 지연이 있다

흐름 로그는 실시간이 아니다. 기본 집계 간격이 **10분**이고 1분으로 줄일 수 있다. 방금 보낸 패킷을 바로 찾으려 하면 없어서 당황한다.

```
집계 간격 10분 -> 최대 10분 뒤에 나타난다
```

대회에서 시간이 급할 때는 1분으로 줄여 두는 편이 낫다.

## 정리

- 주소는 네트워크 부분과 호스트 부분으로 나뉘고, 그 경계를 CIDR 이 정한다.
- 마스크 숫자가 클수록 네트워크는 작아진다. 블록 크기는 256 에서 마지막 옥텟 마스크를 뺀 값이다.
- 서브넷이 퍼블릭인지는 이름이 아니라 **라우트 테이블의 기본 경로**가 정한다.
- NAT 는 나간 대화의 응답만 돌려준다. 그래서 밖에서 먼저 들어올 수 없다.
- 보안 그룹은 상태를 기억하고 허용만 쓴다. 네트워크 ACL 은 기억하지 않아 양방향을 다 적어야 한다.
- 안 나갈 때는 경로 → 방화벽 → 이름 순으로 좁힌다.
- VPC 를 여럿 이을 때 피어링은 쌍마다 하나이고 전이되지 않는다. Transit Gateway 는 허브를 두어 연결이 선형으로 늘고 전이 통신이 된다.
- Transit Gateway 는 **라우팅이 두 층**이다. VPC 라우트와 TGW 라우트를 양쪽 다 채워야 왕복이 성립한다.
- 흐름 로그는 지나간 것을 남긴다. **기록이 없으면 라우팅, `REJECT` 면 방화벽**이다.

## 자기 점검 퀴즈

<Quiz title="서브넷 쪼개기">
`10.0.0.0/24` 를 `/26` 으로 넷으로 쪼갤 때, 세 번째 조각의 시작 주소는?

- [x] `10.0.0.128`
- [ ] `10.0.0.96`
  > `/26` 의 블록 크기는 64 다. 96 은 64 의 배수가 아니라 시작 주소가 될 수 없다.
- [ ] `10.0.0.192`
  > 그것은 네 번째 조각이다.
- [ ] `10.0.0.64`
  > 그것은 두 번째 조각이다.

**`10.0.0.128`.** 블록 크기 64 로 0 / 64 / 128 / 192 네 조각이 나온다. 시작 주소는 항상 블록 크기의 배수다.
</Quiz>

<Quiz title="퍼블릭과 프라이빗을 가르는 것">
서브넷 이름을 `public-subnet-a` 로 짓고 공인 IP 자동 할당도 켰다. 그런데 그 안의 인스턴스가 인터넷에 못 나간다. 가장 먼저 볼 곳은?

- [x] 그 서브넷에 붙은 라우트 테이블의 기본 경로가 인터넷 게이트웨이를 가리키는지
- [ ] 인스턴스의 운영체제 방화벽
  > 가능성은 있지만 순서가 뒤다. 경로가 없으면 방화벽을 다 열어도 못 나간다.
- [ ] 서브넷 이름을 규칙에 맞게 고쳤는지
  > 이름은 통신에 아무 영향이 없다. 채점에는 영향이 있다.
- [ ] 공인 IP 가 탄력적 IP 인지 아닌지
  > 종류는 상관없다. 경로가 먼저다.

**라우트 테이블이다.** 서브넷의 성격은 이름이나 공인 IP 가 아니라 라우트 테이블의 `0.0.0.0/0` 이 어디를 가리키는지가 정한다. 공인 IP 가 있어도 경로가 없으면 나갈 수 없다.
</Quiz>

<Quiz title="상태 저장의 의미">
보안 그룹으로 웹 서버의 인바운드 443 만 열었다. 아웃바운드 규칙은 아무것도 없다. 클라이언트가 HTTPS 로 접속하면?

- [x] 정상 동작한다 — 나가는 응답은 상태 추적으로 자동 허용된다
- [ ] 응답이 못 나가 타임아웃된다
  > 그것은 네트워크 ACL 의 동작이다. 보안 그룹은 상태를 기억한다.
- [ ] 첫 요청만 되고 그다음부터 막힌다
  > 연결마다 같은 규칙이 적용된다. 횟수와 무관하다.
- [ ] 아웃바운드 443 을 열어야만 된다
  > 응답은 443 에서 나가지만, 상태 저장 방화벽에서는 규칙이 필요 없다.

**동작한다.** 보안 그룹은 들어온 연결의 응답을 기억해 자동으로 내보낸다. 같은 상황을 네트워크 ACL 로 만들면 응답이 돌아가는 높은 번호 포트 범위를 아웃바운드에 직접 열어야 한다.
</Quiz>

<Quiz title="한쪽에서만 통하는 Transit Gateway">
Hub VPC 와 App VPC 를 Transit Gateway 로 이었다. Hub 에서 App 으로는 통하는데 App 에서 Hub 로는 응답이 없다. 어디를 먼저 보나?

- [x] App 쪽 라우트 두 층 중 비어 있는 곳 — VPC 라우트 테이블과 TGW 라우트 테이블
- [ ] 보안 그룹의 아웃바운드 규칙
  > 한 방향만 되는 증상은 경로가 비대칭이라는 신호다. 보안 그룹은 상태를 기억하므로 응답만 막히는 일이 드물다.
- [ ] Transit Gateway 를 하나 더 만들어 반대 방향에 붙인다
  > 허브는 하나면 된다. 방향마다 만드는 것이 아니다.
- [ ] 피어링으로 바꾼다
  > 원인을 찾지 않고 구성을 바꾸는 것이다. 피어링에서도 양쪽 라우트 테이블을 다 채워야 한다.

**App 쪽 라우트 두 층이다.** Transit Gateway 는 층이 둘이다 — VPC 라우트 테이블이 "이 대역은 TGW 로"를, TGW 라우트 테이블이 "TGW 에 들어온 이 대역은 이 연결로"를 정한다. 한 층만 채우면 패킷이 TGW 까지 가고 거기서 버려진다. **양쪽 VPC 가 각각 두 층을 채워야 왕복이 성립한다.**
</Quiz>

<Quiz title="흐름 로그에 기록이 아예 없다">
프라이빗 인스턴스가 외부 API 를 못 부른다. 그 ENI 의 흐름 로그를 봤더니 해당 시간대에 `ACCEPT` 도 `REJECT` 도 없이 **기록 자체가 없다.** 무엇을 뜻하나?

- [x] 패킷이 그 ENI 까지 오지 않았다 — 라우트 테이블을 본다
- [ ] 보안 그룹이 막았다
  > 막힌 것은 `REJECT` 로 남는다. 기록이 없다는 것은 막힌 것과 다르다.
- [ ] 네트워크 ACL 이 막았다
  > 마찬가지로 `REJECT` 로 남는다. 보안 그룹과 ACL 은 둘 다 도달한 뒤에 판단한다.
- [ ] 응답만 돌아오지 못했다
  > 그 경우는 나가는 `ACCEPT` 가 기록으로 남는다. 지금은 그것조차 없다.

**라우팅이다.** 기록이 없다 = 도달하지 않았다, `REJECT` = 도달했고 막혔다, `ACCEPT` 인데 응답이 없다 = 나갔고 돌아올 경로가 없다. 세 갈래가 다음에 볼 곳을 갈라 준다.

다만 기본 집계 간격이 **10분**이다. 방금 보낸 패킷이라면 아직 안 나왔을 수 있으니 간격을 1분으로 줄여 두고 판단한다.
</Quiz>
