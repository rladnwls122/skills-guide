## 1. 이름은 여러 곳에서 풀린다

`aws.amazon.com` 을 치면 컴퓨터는 순서대로 찾는다.

1. **프로세스 안의 캐시** — 브라우저나 런타임이 최근 결과를 들고 있다.
2. **운영체제 캐시** — 방금 다른 프로그램이 물어본 답이 남아 있다.
3. **호스트 파일** — 손으로 적어 둔 고정 매핑. 여기 있으면 DNS 를 아예 안 본다.
4. **DNS 서버** — 위에서 다 못 찾으면 물어본다.

이 순서가 진단에서 중요한 이유는 **한 단계만 오래된 값을 들고 있어도 나만 다른 결과를 본다**는 점이다. 동료는 새 주소를 보는데 나만 옛 주소로 붙는 상황이 여기서 나온다.

DNS 서버도 혼자 답하지 않는다. 모르면 루트 → 최상위 도메인 → 해당 도메인의 권한 서버 순으로 물어 내려간다. 이 과정을 **재귀 조회**라 하고, 중간의 서버들이 답을 캐시한다.

기대: 이름·종류·TTL·주소가 나온다. **같은 명령을 두 번 치면 TTL 이 줄어 있다** — 캐시에서 오고 있다는 뜻이다.

TTL 이 안 줄면 매번 서버에 묻는 설정이거나 캐시를 안 쓰는 도구다.

</details>

## 2. 레코드 종류 — 무엇을 가리키는가

| 종류 | 가리키는 것 | 특징 |
|---|---|---|
| A | IPv4 주소 | 가장 기본 |
| AAAA | IPv6 주소 | |
| CNAME | **다른 이름** | 도메인 최상위(`example.com` 자체)에는 쓸 수 없다 |
| ALIAS(AWS 전용) | AWS 리소스 | 최상위에도 쓸 수 있고 조회가 무료다 |
| TXT | 임의의 문자열 | 소유권 증명·정책 공표에 쓴다 |

**CNAME 은 최상위 도메인에 못 붙는다.** 규격상 CNAME 이 있는 이름에는 다른 레코드가 함께 있을 수 없는데, 최상위에는 반드시 있어야 하는 다른 레코드들이 있기 때문이다. 그래서 AWS 는 겉으로는 CNAME 처럼 동작하되 응답할 때는 주소를 직접 돌려주는 ALIAS 를 따로 만들었다.

로드밸런서나 CDN 앞에 이름을 붙일 때는 **주소를 직접 적지 않는다.** 그 주소는 언제든 바뀌기 때문이다. 이름으로 가리켜 두면 뒤에서 주소가 바뀌어도 그대로 동작한다.

## 3. TTL — 바꾼 값이 언제 퍼지는가

레코드마다 "이 답을 몇 초 동안 재사용해도 된다"는 값이 붙는다. 그게 TTL 이다.

TTL 이 길면 조회가 줄어 빠르고 싸지만, **값을 바꿨을 때 옛 값이 그만큼 오래 살아 있다.** 짧으면 반대다.

:::caution[전환을 계획한다면 TTL 을 먼저 줄인다]
주소를 바꿀 예정이면 **바꾸기 하루 전에 TTL 부터 짧게** 내려 둔다. 바꾸는 순간에 TTL 을 줄이는 것은 늦다 — 이미 퍼진 캐시는 옛 TTL 만큼 남아 있다.

이 순서를 모르면 "레코드를 바꿨는데 절반의 사용자만 새 서버로 온다"는 상황을 겪는다. 잘못된 것은 없고 그냥 캐시가 아직 안 끝난 것이다.
:::

## 4. HTTP — 요청과 응답은 텍스트다

HTTP 요청은 사람이 읽을 수 있는 텍스트다. 세 부분이다.

```
GET /v1/user?email=a@example.org HTTP/1.1     <- 시작 줄: 메서드, 경로, 버전
Host: api.example.org                          <- 헤더들
Accept: application/json

(본문 - GET 은 보통 비어 있다)
```

응답도 같은 모양이다.

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 57

{"username":"dbdump500001","email":"a@example.org"}
```

메서드는 의도를 나타낸다. 이 과정에서 만나는 것은 넷이다.

| 메서드 | 뜻 | 3과제에서 |
|---|---|---|
| GET | 가져온다. 서버 상태를 바꾸지 않는다 | 사용자·상품 조회, 이미지 다운로드 |
| POST | 새로 만든다 | 사용자·상품 생성, 부하 발생 |
| PUT | 통째로 바꾼다 | 상품 이미지 교체 |
| DELETE | 지운다 | |

**GET 은 상태를 바꾸지 않는다**는 약속이 캐시를 가능하게 한다. 같은 GET 요청은 같은 답을 준다고 가정할 수 있으니 중간에서 저장해 두고 재사용한다. POST 를 캐시하지 않는 이유도 같다.

### 상태 코드는 계열로 읽는다

| 계열 | 뜻 | 자주 보는 것 |
|---|---|---|
| 2xx | 성공 | 200 OK, 201 Created |
| 3xx | 다른 곳을 보라 | 301 영구 이동, 304 안 바뀜 |
| 4xx | **요청한 쪽 잘못** | 400 잘못된 요청, 403 금지, 404 없음, 429 너무 많음 |
| 5xx | **받은 쪽 잘못** | 500 내부 오류, 502 게이트웨이 오류, 503 사용 불가, 504 시간 초과 |

4xx 와 5xx 의 경계가 진단의 첫 갈림길이다. **4xx 는 보낸 요청을 고쳐야 하고, 5xx 는 서버를 고쳐야 한다.**

502·503·504 는 특히 로드밸런서가 자주 내는 답이고 각각 원인이 다르다.

| 코드 | 로드밸런서가 말하는 것 | 볼 곳 |
|---|---|---|
| 502 | 뒤에서 이상한 응답이 왔다 | 앱이 죽었거나 프로토콜이 안 맞는다 |
| 503 | 보낼 대상이 없다 | 정상 대상이 0개 — 헬스체크를 본다 |
| 504 | 뒤가 제때 답을 안 했다 | 앱이 느리다 — 대개 DB 대기 |

## 5. TLS — 언제, 무엇을 감싸는가

TLS 는 HTTP 밑에 깔린다. 연결이 맺어진 **직후, 첫 HTTP 요청을 보내기 전에** 핸드셰이크를 한다.

핸드셰이크에서 하는 일은 셋이다.

1. **신원 확인** — 서버가 인증서를 내민다. 클라이언트는 그것이 신뢰하는 기관이 서명했는지, 그리고 **내가 부른 이름과 일치하는지** 본다.
2. **암호 방식 합의** — 어떤 알고리즘을 쓸지 정한다.
3. **열쇠 교환** — 이후 대화를 암호화할 열쇠를 만든다.

여기서 자주 나오는 오해 둘을 정리한다.

**인증서는 "안전한 사이트"를 증명하지 않는다.** 증명하는 것은 **이름의 소유**뿐이다. 공격자의 사이트도 자기 도메인의 인증서를 정상적으로 받을 수 있다.

**이름이 안 맞으면 인증서가 유효해도 실패한다.** 로드밸런서의 기본 주소로 접속하면서 내 도메인 인증서를 기대하면 실패한다. 이름과 인증서는 짝이다.

TLS 가 어디서 끝나는지도 중요하다. **끝나는 지점 = 평문이 되는 지점**이다.

| 구성 | TLS 가 끝나는 곳 | 뒤쪽 구간 |
|---|---|---|
| CDN 에서 종료 | CDN | CDN → 원본은 별도 설정 |
| 로드밸런서에서 종료 | 로드밸런서 | LB → 앱은 보통 평문(VPC 안) |
| 앱까지 통과 | 앱 | 로드밸런서가 내용을 못 본다 |

세 번째를 고르면 로드밸런서는 **경로를 보고 판단할 수 없다.** 암호화된 바이트만 보이기 때문이다. 이것이 다음 절의 L4·L7 차이다.

## 6. L4 와 L7 — 무엇을 보고 판단하는가

| | L4 | L7 |
|---|---|---|
| 보는 것 | 주소와 포트 | 경로·헤더·메서드까지 |
| 할 수 있는 것 | 어디로 보낼지 고르기 | 경로별 분기, 헤더 추가, 응답 직접 생성 |
| AWS | Network Load Balancer | Application Load Balancer |
| 지연 | 더 낮다 | 조금 더 든다 |

**경로에 따라 다른 곳으로 보내려면 L7 이어야 한다.** 1과제가 "POST 는 EKS 로, GET 은 Lambda 로" 같은 요구를 하는 것이 그래서다. 3과제가 정의되지 않은 경로에 404 를 요구하는 것도 L7 이어야 가능하다. L4 는 경로를 아예 볼 수 없다.

L7 로드밸런서는 **뒤로 안 보내고 자기가 답할 수도 있다.** 고정 응답이라고 부르고, 3과제의 404 가 정확히 이것이다 — 아무 대상에도 안 맞는 요청에 로드밸런서가 직접 404 를 낸다.

:::danger[403 과 404 는 다른 장비가 낸다]
방화벽이 CDN 앞단에 붙으면 **평가 순서가 방화벽 먼저**다. 그래서 정의되지 않은 경로로 온 공격 문자열은 로드밸런서까지 못 가고 방화벽에서 403 이 된다. 과제지가 그 자리에 404 를 요구한다면 그대로 오답이다.

해법의 방향은 **방화벽이 아는 경로만 평가하게 하는 것**이다. 알려진 API 경로가 아니면 방화벽 규칙에 아예 걸리지 않게 만들고, 로드밸런서의 기본 응답으로 떨어뜨린다. 실제 구현과 기각된 대안들은 [22. 부하 운영 이론](/part-5/22-task3-tuning/theory/)에 있다.
:::

<details class="build-step">
<summary>지금 띄우기 — 응답을 만든 것이 누구인지 헤더로 보기</summary>

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  $r = Invoke-WebRequest -Uri 'https://aws.amazon.com/' -Method Head
  $r.Headers.GetEnumerator() | Where-Object { $_.Key -match 'server|via|x-cache|x-amz' }
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  curl -sI https://aws.amazon.com/ | grep -iE 'server|via|x-cache|x-amz'
  ```
  </TabItem>
</Tabs>

기대: `server`·`via`·`x-cache` 같은 헤더가 나온다. `x-cache` 에 `Hit` 이나 `Miss` 가 보이면 **CDN 이 답한 것**이고, 원본까지 갔는지 아닌지가 그 값에 적혀 있다.

헤더가 없어도 정상이다 — 서비스마다 내보내는 헤더가 다르다.

</details>

## 정리

- 이름은 캐시 → 호스트 파일 → DNS 서버 순으로 풀린다. 한 곳만 오래된 값을 들고 있어도 나만 다른 결과를 본다.
- CNAME 은 최상위 도메인에 못 붙는다. AWS 는 그 자리를 ALIAS 로 메운다.
- 값을 바꿀 예정이면 TTL 을 미리 줄인다. 바꾸는 순간에 줄이는 것은 늦다.
- 4xx 는 요청을, 5xx 는 서버를 고친다. 502·503·504 는 각각 다른 곳을 가리킨다.
- 인증서는 이름의 소유를 증명할 뿐이고, 이름이 안 맞으면 유효해도 실패한다.
- 경로로 분기하려면 L7 이어야 한다. L4 는 주소와 포트만 본다.

`example.com` 자체(하위 이름 없이)를 로드밸런서로 보내려 한다. 옳은 것은?

- [x] ALIAS 레코드를 쓴다 — CNAME 은 최상위에 붙일 수 없다
- [ ] CNAME 으로 로드밸런서 이름을 가리킨다
  > CNAME 이 있는 이름에는 다른 레코드가 공존할 수 없는데, 최상위에는 반드시 있어야 하는 레코드들이 있다.
- [ ] A 레코드에 로드밸런서의 현재 IP 를 적는다
  > 그 IP 는 예고 없이 바뀐다. 바뀌는 순간 서비스가 끊긴다.
- [ ] TXT 레코드로 주소를 적어 둔다
  > TXT 는 임의 문자열일 뿐 라우팅에 쓰이지 않는다.

**ALIAS 다.** 겉으로는 이름을 가리키지만 응답할 때는 주소를 직접 돌려주므로 최상위에도 붙는다. 조회 비용도 들지 않는다.
</Quiz>

<Quiz title="503 이 뜻하는 것">
로드밸런서가 503 을 낸다. 가장 먼저 볼 곳은?

- [x] 대상 그룹에 정상 대상이 0개인지 — 헬스체크를 본다
- [ ] 앱의 애플리케이션 로그에서 예외를 찾는다
  > 앱이 답을 하긴 했다면 502 나 500 이 뜬다. 503 은 보낼 곳 자체가 없다는 뜻이다.
- [ ] DB 커넥션 풀이 가득 찼는지 본다
  > 그 경우는 느려지거나 504 다.
- [ ] 클라이언트가 보낸 헤더가 규격에 맞는지 본다
  > 그것은 4xx 계열의 원인이다.

**정상 대상이 없는 것이다.** 파드가 아직 안 떴거나, 헬스체크 경로·포트가 틀렸거나, 보안 그룹이 헬스체크를 막고 있다. 앱 로그를 뒤지기 전에 대상 그룹의 상태부터 본다.
</Quiz>

<Quiz title="TLS 를 어디서 끝낼 것인가">
로드밸런서가 경로에 따라 서로 다른 대상으로 요청을 나눠야 한다. TLS 를 앱까지 통과시키면?

- [x] 로드밸런서가 경로를 볼 수 없어 경로 기반 분기가 불가능하다
- [ ] 문제없다. 로드밸런서는 항상 경로를 볼 수 있다
  > 암호화된 바이트만 지나가므로 볼 수 없다. 그래서 L4 처럼 동작한다.
- [ ] 인증서를 로드밸런서에 올릴 필요가 없어 더 안전하다
  > 안전성의 문제가 아니라 기능의 문제다.
- [ ] 지연이 늘어 응답 시간만 나빠진다
  > 지연도 영향이 있지만 핵심은 분기가 불가능해진다는 점이다.

**경로를 못 본다.** TLS 가 끝나는 지점이 곧 평문이 되는 지점이고, 거기서부터만 경로·헤더로 판단할 수 있다. 경로 분기가 필요하면 로드밸런서에서 종료한다.
</Quiz>
