## 1. 파일 권한 — 세 주체, 세 동작

리눅스의 모든 파일에는 소유자와 그룹이 있고, 권한이 세 벌 붙는다.

```
-rwxr-xr--  1 ec2-user  ec2-user  8402  user
 ^^^ ^^^ ^^^
  |   |   +-- 그 외 모두: 읽기만
  |   +------ 그룹: 읽기, 실행
  +---------- 소유자: 읽기, 쓰기, 실행
```

각 자리는 읽기(r)·쓰기(w)·실행(x) 세 비트다. 숫자로 쓰면 읽기 4, 쓰기 2, 실행 1 이고 더해서 한 자리로 적는다. `755` 는 소유자 7(4+2+1), 그룹 5(4+1), 그 외 5 다.

**실행 권한이 없으면 프로그램이 아니다.** 파일 내용이 완벽한 실행 파일이어도 x 비트가 없으면 커널이 실행을 거부한다. 배부된 바이너리를 받아 바로 실행했을 때 나오는 `Permission denied` 의 대부분이 이것이다.

:::caution[권한을 777 로 열지 않는다]
막히면 전부 열어 버리고 싶어지지만, 채점에 보안 항목이 있는 세트에서는 그 자체가 감점이다. 실행하려면 **x 만** 주면 된다.

- 실행 권한만: 소유자에게 `+x`
- 스크립트라면 읽기도 필요하다 — 해석기가 파일을 읽어야 하니까
:::

## 2. 환경 변수 — 프로세스마다 따로다

환경 변수는 프로세스가 시작될 때 부모에게서 **복사받는** 값이다. 복사이므로 셋이 따라온다.

1. 자식이 값을 바꿔도 **부모는 모른다.**
2. 이미 실행 중인 프로세스의 환경 변수는 **밖에서 바꿀 수 없다.**
3. 새 터미널을 열면 그 터미널의 부모에게서 다시 복사받는다 — 그래서 아까 셸에서 설정한 값이 새 창에는 없다.

3과제 앱이 데이터베이스 주소를 환경 변수로 받는다는 것은, **값이 바뀌면 프로세스를 다시 시작해야 한다**는 뜻이기도 하다. 쿠버네티스에서 ConfigMap 을 고쳤는데 파드가 옛 값을 쓰고 있는 이유가 정확히 이것이다.

:::note[설정을 파일이 아니라 환경 변수로 받는 이유]
같은 이미지를 개발·운영에 그대로 쓰고 값만 바꿔 끼우기 위해서다. 이미지 안에 설정을 넣으면 환경마다 이미지를 따로 만들어야 하고, 그러면 "테스트한 그 이미지"와 "배포한 이미지"가 달라진다.

그래서 비밀번호 같은 값도 이미지에 넣지 않는다. 3과제가 데이터베이스 자격 증명을 비밀 저장소에서 꺼내 쓰는 구조인 것도 같은 이유다.
:::

## 3. 표준 스트림 — 출력이 두 갈래인 이유

모든 프로세스는 시작할 때 세 개의 통로를 받는다.

| 번호 | 이름 | 쓰임 |
|---|---|---|
| 0 | 표준 입력 | 받는 곳 |
| 1 | 표준 출력 | 정상 결과 |
| 2 | 표준 오류 | 오류 메시지, 진단 |

**둘로 나뉜 이유는 섞이면 안 되기 때문이다.** 결과를 다른 프로그램에 넘길 때 오류 메시지가 섞이면 그 프로그램이 오작동한다. 그래서 결과는 1번으로, 사람이 볼 메시지는 2번으로 보낸다.

리디렉션 기호가 그래서 두 벌이다.

| 표기 | 뜻 |
|---|---|
| `> file` | 표준 출력을 파일로. 덮어쓴다 |
| `>> file` | 표준 출력을 파일에 이어 붙인다 |
| `2> file` | 표준 오류만 파일로 |
| `2>&1` | 표준 오류를 표준 출력과 **같은 곳으로** 합친다 |
| `> /dev/null` | 버린다 |

`command > out.log 2>&1` 은 "출력을 파일로 보내고, 오류도 같은 곳으로" 라는 뜻이다. 순서가 중요하다 — `2>&1 > out.log` 는 의도와 다르게 동작한다. 오류를 **그 시점의** 표준 출력(화면)에 붙인 뒤 표준 출력만 파일로 바꾸기 때문이다.

## 4. 파이프라인 — 작은 도구를 잇는다

`|` 는 앞 명령의 표준 출력을 뒤 명령의 표준 입력에 붙인다. 로그를 다루는 일 대부분이 이 조합이다.

| 도구 | 하는 일 |
|---|---|
| `grep` | 패턴이 있는 줄만 남긴다 |
| `awk` | 줄을 칸으로 쪼개 원하는 칸만 뽑는다 |
| `sed` | 치환한다 |
| `sort` · `uniq -c` | 정렬하고 같은 것을 세어 준다 |
| `head` · `tail` | 앞·뒤 몇 줄만 |
| `wc -l` | 줄 수를 센다 |
| `jq` | JSON 을 다룬다 |

**가장 자주 쓰는 조합은 "세어서 많은 순으로 보기"다.**

```
grep ERROR app.log | awk '{print $5}' | sort | uniq -c | sort -rn | head
```

오류 줄만 남기고, 다섯 번째 칸을 뽑고, 정렬해서 세고, 많은 순으로 앞부분만 본다. 3과제에서 방화벽 로그 수십만 줄을 분석할 때 쓰는 것이 정확히 이 형태다.

:::tip[PowerShell 은 텍스트가 아니라 객체를 넘긴다]
같은 일을 PowerShell 에서 하면 칸을 번호로 뽑을 필요가 없다. 속성 이름으로 바로 접근한다.

대신 리눅스 서버 안에서는 PowerShell 이 없다. **두 벌을 다 손에 익혀 둔다** — 대회에서 본 PC 는 Windows 이고 서버와 CloudShell 은 리눅스다.
:::

## 5. 서비스 — 꺼져도 다시 뜨게 만든다

터미널에서 실행한 프로그램은 터미널을 닫으면 같이 죽는다. 서버에서 계속 돌아야 하는 프로그램은 **서비스**로 등록한다.

리눅스의 서비스 관리자는 대개 systemd 이고, 유닛 파일 하나를 적어 등록한다. 적는 내용은 넷이다.

| 항목 | 뜻 |
|---|---|
| 실행할 명령 | 어떤 바이너리를 어떤 인자로 |
| 환경 변수 | 값 또는 값이 담긴 파일 경로 |
| 재시작 정책 | 죽으면 다시 띄울지, 몇 초 뒤에 |
| 실행 사용자 | 어떤 신원으로 |

서비스로 등록하면 **로그가 시스템 저널로 간다.** 프로그램이 표준 출력에 찍은 것을 systemd 가 받아 저장하고, `journalctl` 로 꺼내 본다.

:::note[컨테이너에서는 이 층이 사라진다]
컨테이너는 프로세스 하나를 띄우고, 그 프로세스가 죽으면 컨테이너가 끝난다. 재시작은 systemd 가 아니라 **쿠버네티스가** 맡는다. 로그도 저널이 아니라 컨테이너 런타임이 걷어 간다.

그래서 컨테이너 안에서는 앱이 **로그를 파일이 아니라 표준 출력으로** 뱉어야 한다. 파일에 쓰면 컨테이너 밖에서 볼 방법이 없어진다. 3과제 앱이 표준 출력으로 접근 로그를 내는 것도 이 관례를 따른 것이다.
:::

## 6. 로그를 어디서 보는가

| 상황 | 보는 곳 |
|---|---|
| 터미널에서 직접 실행 | 화면 |
| systemd 서비스 | `journalctl -u <서비스이름>` |
| 컨테이너(도커) | `docker logs <컨테이너>` |
| 쿠버네티스 파드 | `kubectl logs <파드>` |
| 클라우드로 수집한 뒤 | CloudWatch Logs 등 |

층이 하나 올라갈 때마다 **로그를 꺼내는 명령이 바뀔 뿐 원리는 같다** — 프로그램이 표준 출력에 찍은 것을 누군가 받아 보관한다.

`kubectl logs` 는 **지금 살아 있는 컨테이너의 로그**만 보여 준다. 파드가 죽고 새로 떴다면 이전 것은 `--previous` 를 붙여야 나오고, 그마저도 노드에서 회수되면 사라진다. **재시작을 반복하는 파드의 원인을 잡으려면 로그를 밖으로 내보내 두어야 한다** — 관측성 모듈이 하는 일이 이것이다.

## 정리

- 실행 권한이 없으면 프로그램이 아니다. 필요한 비트만 준다.
- 환경 변수는 시작할 때 복사된다. 값이 바뀌면 다시 시작해야 반영된다.
- 표준 출력과 표준 오류는 섞이면 안 되므로 따로다. 합칠 때는 `2>&1` 을 **뒤에** 쓴다.
- 파이프라인의 기본형은 걸러서 뽑고 세어서 정렬하는 것이다.
- 서비스로 등록하면 재시작과 로그 보관을 시스템이 맡는다. 컨테이너에서는 그 역할을 오케스트레이터가 가져간다.
- 컨테이너 앱은 로그를 파일이 아니라 표준 출력으로 낸다.

## 자기 점검 퀴즈

<Quiz title="Permission denied">
배부받은 바이너리를 실행했더니 `Permission denied` 가 났다. 파일은 정상적으로 내려받아졌다. 가장 먼저 할 일은?

- [x] 실행 권한이 있는지 보고, 없으면 소유자에게 실행 비트를 준다
- [ ] 권한을 `777` 로 열어 확실히 해 둔다
  > 실행은 되겠지만 필요 이상으로 연 것이고, 보안 항목이 있는 채점에서는 감점이다.
- [ ] 관리자 권한으로 다시 실행한다
  > 권한 상승은 실행 비트가 없는 문제를 해결하지 못한다. 원인이 다르다.
- [ ] 파일을 다시 내려받는다
  > 내용이 온전하다면 다시 받아도 권한은 같다.

**실행 비트를 준다.** 파일 내용이 완전한 실행 파일이어도 x 비트가 없으면 커널이 실행을 거부한다. 필요한 비트만 주는 것이 원칙이다.
</Quiz>

<Quiz title="설정을 바꿨는데 반영이 안 된다">
앱이 데이터베이스 주소를 환경 변수로 받는다. 값을 새로 설정했는데 앱은 여전히 옛 주소로 붙는다. 왜인가?

- [x] 환경 변수는 프로세스 시작 시점에 복사된다 — 실행 중인 프로세스에는 반영되지 않는다
- [ ] 환경 변수 이름을 대문자로 써야 한다
  > 관례일 뿐 강제가 아니다. 이름이 틀렸다면 애초에 옛 값도 못 읽었을 것이다.
- [ ] 값에 따옴표를 빠뜨렸다
  > 그 경우 값 자체가 잘못 들어간다. 옛 값을 계속 쓰는 것과는 증상이 다르다.
- [ ] 셸을 다시 시작하면 자동으로 반영된다
  > 셸이 아니라 **앱 프로세스**를 다시 시작해야 한다.

**프로세스를 다시 시작해야 한다.** 환경 변수는 시작할 때 복사되는 값이고 밖에서 밀어 넣을 수 없다. 쿠버네티스에서 ConfigMap 을 고친 뒤 파드를 다시 굴리는 이유가 같다.
</Quiz>

<Quiz title="컨테이너 앱의 로그">
컨테이너로 도는 앱이 로그를 `/var/log/app.log` 파일에 쓴다. 무엇이 문제인가?

- [x] 컨테이너 밖에서 그 로그를 걷어 갈 수 없다 — 표준 출력으로 내야 한다
- [ ] 파일 크기가 커져 디스크가 찬다
  > 실제로 문제가 되지만 핵심은 아니다. 표준 출력이어도 회전 설정은 필요하다.
- [ ] 파일에 쓰면 성능이 나빠진다
  > 유의미한 차이가 아니다.
- [ ] 권한 때문에 쓰기가 실패한다
  > 그럴 수도 있지만 그건 별개 문제다.

**밖에서 못 본다.** 컨테이너 런타임과 쿠버네티스는 프로세스의 표준 출력을 걷어 간다. 파일에 쓰면 그 파일은 컨테이너 안에만 있고, 컨테이너가 죽으면 같이 사라진다.
</Quiz>
