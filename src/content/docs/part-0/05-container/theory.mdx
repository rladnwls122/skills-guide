## 1. 세 낱말을 먼저 가른다

| 낱말 | 무엇인가 |
|---|---|
| 이미지 | 파일시스템의 스냅숏 + 실행 방법이 적힌 설정. **읽기 전용** |
| 컨테이너 | 그 이미지를 바탕으로 실제로 도는 프로세스. 쓰기 가능한 층이 하나 얹힌다 |
| 레지스트리 | 이미지를 보관하고 나눠 주는 저장소. AWS 에서는 ECR |

이미지와 컨테이너의 관계는 프로그램과 프로세스의 관계와 같다. 이미지 하나로 컨테이너를 열 개 만들 수 있고, 열 개는 서로 남남이다.

**컨테이너에 쓴 내용은 컨테이너가 사라지면 같이 사라진다.** 이미지가 바뀌는 것이 아니다. 그래서 데이터베이스 파일이나 업로드된 이미지를 컨테이너 안에 두면 안 된다 — 파드가 재시작하는 순간 없어진다. 3과제가 상품 이미지를 객체 저장소에 넣는 이유가 이것이다.

## 2. 이미지는 레이어의 쌓임이다

Dockerfile 의 지시어 하나가 대체로 레이어 하나를 만든다. 레이어는 **이전 레이어와의 차이**만 담는다.

```
FROM golang:1.22        <- 레이어 1: 베이스
COPY go.mod go.sum ./   <- 레이어 2: 파일 두 개 추가
RUN go mod download     <- 레이어 3: 받은 의존성
COPY . .                <- 레이어 4: 소스 전체
RUN go build -o app     <- 레이어 5: 빌드 결과
```

레이어는 **캐시된다.** 다시 빌드할 때 앞에서부터 훑다가 바뀐 지점을 만나면 거기서부터 다시 만든다. 그래서 순서가 성능을 정한다.

:::tip[자주 바뀌는 것을 뒤에 둔다]
위 예에서 의존성 목록(`go.mod`)을 소스보다 **먼저** 복사한 것이 요령이다. 소스만 고쳤다면 레이어 1~3 은 캐시에서 그대로 오고 4~5 만 다시 만든다.

반대로 `COPY . .` 를 맨 앞에 두면 소스 한 글자만 바꿔도 의존성을 매번 다시 받는다. 빌드가 몇 분씩 걸리는 이유의 대부분이 이 순서다.
:::

레이어에는 또 하나의 성질이 있다. **지운 것도 남는다.** 어떤 레이어에서 파일을 만들고 다음 레이어에서 지우면, 보이지는 않지만 앞 레이어에는 그대로 있다. 그래서 비밀번호를 넣었다가 지우는 방식은 **누출**이다.

## 3. 베이스 이미지가 정하는 것

`FROM` 한 줄이 뒤의 많은 것을 정한다.

| 베이스 | 크기 | 특징 |
|---|---|---|
| 배포판 전체(`ubuntu`, `amazonlinux`) | 크다 | 도구가 다 있어 디버깅이 쉽다 |
| 경량(`alpine`) | 작다 | 표준 C 라이브러리가 달라 일부 바이너리가 안 돈다 |
| 최소(`distroless`, `scratch`) | 가장 작다 | 셸조차 없어 컨테이너 안에 들어가 볼 수 없다 |

**작을수록 좋은 것이 아니다.** 노드가 새로 뜰 때 내려받는 시간은 줄지만, 문제가 생겼을 때 안에서 확인할 도구가 없다.

경량 이미지에서 자주 걸리는 함정 둘을 미리 안다.

**시간대.** 최소 이미지에는 시간대 정보가 없다. 그러면 앱이 무슨 설정을 하든 시각이 UTC 로 찍힌다. 채점이 로그 시각을 한국 시간으로 요구하면 아홉 시간 어긋나 그대로 오답이다. 시간대 데이터를 설치하고 환경 변수로 지정해야 한다.

**C 라이브러리.** `alpine` 은 다른 C 라이브러리를 쓴다. 일반 배포판에서 빌드한 바이너리를 그대로 넣으면 실행이 안 되는 경우가 있다. 3과제 배부물처럼 **이미 빌드된 바이너리**를 받는 경우 특히 조심한다 — 그 바이너리가 어디서 빌드됐는지가 과제지에 적혀 있다.

## 4. 태그와 다이제스트

이미지를 가리키는 방법이 둘이다.

| | 예 | 성질 |
|---|---|---|
| 태그 | `myapp:1.2.0` | 사람이 붙이는 이름표. **옮겨 붙일 수 있다** |
| 다이제스트 | `myapp@sha256:abc...` | 내용에서 계산된 값. **절대 안 바뀐다** |

:::danger[latest 는 태그가 아니라 습관이다]
`latest` 는 "최신"을 뜻하는 특별한 기능이 아니다. 그냥 흔히 쓰는 이름일 뿐이고, 아무 이미지에나 붙일 수 있다.

문제는 **무엇이 배포됐는지 알 수 없게 된다**는 점이다. 파드가 `myapp:latest` 를 쓰고 있을 때, 그 파드 안의 이미지가 오늘 올린 것인지 어제 것인지 확인할 방법이 없다. 노드마다 다른 시점에 내려받았다면 **파드마다 다른 코드가 돌 수도 있다.**

이 과정의 채점에서도 `latest` 는 감점 사유로 나온다. 태그는 버전이나 커밋 해시처럼 **한 번 붙이면 안 옮기는 값**으로 준다.
:::

## 5. Dockerfile — 빌드 시점과 실행 시점

지시어를 이 기준으로 나누면 헷갈리지 않는다.

| 지시어 | 언제 | 하는 일 |
|---|---|---|
| `FROM` | 빌드 | 베이스를 고른다 |
| `RUN` | **빌드** | 이미지를 만드는 중에 명령을 실행한다 |
| `COPY` · `ADD` | 빌드 | 파일을 이미지에 넣는다 |
| `ENV` | 빌드 + 실행 | 환경 변수를 이미지에 새긴다. 실행할 때 덮어쓸 수 있다 |
| `EXPOSE` | 문서 | **아무것도 열지 않는다.** 이 이미지가 쓰는 포트를 적어 두는 메모다 |
| `USER` | 실행 | 어떤 사용자로 돌지 |
| `WORKDIR` | 빌드 + 실행 | 기본 디렉터리 |
| `CMD` · `ENTRYPOINT` | **실행** | 컨테이너가 시작될 때 무엇을 돌릴지 |

혼동이 잦은 둘을 짚는다.

**`RUN` 은 빌드할 때 한 번, `CMD` 는 실행할 때마다.** `RUN` 에 앱 시작 명령을 적으면 빌드 중에 앱이 떠서 빌드가 끝나지 않는다.

**`EXPOSE` 는 포트를 열지 않는다.** 실제로 밖에서 닿게 하는 것은 컨테이너를 띄울 때의 설정이나 쿠버네티스의 Service 다. `EXPOSE` 를 적었는데 안 된다고 그 줄을 의심하는 것은 시간 낭비다.

### 루트로 돌리지 않는다

기본값은 루트다. 컨테이너가 뚫렸을 때 피해가 커지고, 보안 항목이 있는 채점에서는 감점이다. 사용자를 하나 만들어 `USER` 로 지정한다.

부작용을 하나 알아 둔다. **1024 미만 포트는 루트만 열 수 있다.** 그래서 루트가 아닌 사용자로 돌리면 80번 대신 8080 같은 포트를 쓴다. 3과제 앱이 8080 에 붙는 것도 이 관례다.

## 6. 이미지가 도착하기까지

파드가 뜰 때 노드는 이미지를 내려받아야 한다. 이 경로에서 자주 막힌다.

1. **권한** — 프라이빗 레지스트리라면 노드에 인증이 필요하다. AWS 에서는 노드 역할에 붙은 권한이 그 일을 한다.
2. **경로** — 프라이빗 서브넷의 노드가 레지스트리에 닿으려면 NAT 나 VPC 엔드포인트가 있어야 한다. 완전히 닫힌 클러스터에서 이미지를 못 받는 사고가 여기서 난다.
3. **이름** — 태그가 틀리면 `ImagePullBackOff` 다. 대소문자와 계정 번호까지 정확해야 한다.

세 가지 모두 증상이 비슷하다. **파드가 `ImagePullBackOff` 로 멈춘다.** 순서대로 권한 → 경로 → 이름을 본다.

## 정리

- 이미지는 읽기 전용 스냅숏, 컨테이너는 그것으로 도는 프로세스, 레지스트리는 보관소다.
- 레이어는 캐시된다. 자주 바뀌는 것을 뒤에 두면 빌드가 빨라진다.
- 지운 파일도 앞 레이어에 남는다. 비밀을 넣었다 지우는 것은 누출이다.
- 베이스가 시간대·C 라이브러리·디버깅 도구의 유무를 정한다. 작다고 좋은 것이 아니다.
- `latest` 는 무엇이 배포됐는지 모르게 만든다. 태그는 안 옮기는 값으로 준다.
- `RUN` 은 빌드, `CMD` 는 실행. `EXPOSE` 는 아무것도 열지 않는다.

소스 한 줄만 고쳤는데 매번 의존성을 처음부터 다시 받는다. Dockerfile 의 무엇을 고쳐야 하나?

- [x] 의존성 목록 파일을 소스 전체보다 **먼저** 복사하고 그 다음에 의존성을 받는다
- [ ] 캐시를 끄는 옵션을 붙인다
  > 반대다. 캐시가 안 듣는 것이 문제인데 끄면 더 느려진다.
- [ ] 베이스 이미지를 더 작은 것으로 바꾼다
  > 내려받는 시간은 줄겠지만 의존성을 다시 받는 것과 무관하다.
- [ ] `RUN` 을 여러 줄로 쪼갠다
  > 레이어 수만 늘고 원인은 그대로다.

**복사 순서다.** 레이어는 앞에서부터 비교하다 바뀐 지점에서 캐시가 끊긴다. 소스를 먼저 복사하면 그 뒤 모든 레이어가 매번 다시 만들어진다.
</Quiz>

<Quiz title="EXPOSE 의 역할">
Dockerfile 에 `EXPOSE 8080` 을 적었는데 밖에서 접속이 안 된다. 왜인가?

- [x] `EXPOSE` 는 문서용 메모다 — 실제 노출은 컨테이너를 띄울 때나 Service 가 정한다
- [ ] 포트 번호가 1024 미만이어야 한다
  > 오히려 반대다. 1024 미만은 루트만 열 수 있다.
- [ ] `EXPOSE` 다음에 `RUN` 이 와야 적용된다
  > 순서와 무관하다. 애초에 여는 기능이 없다.
- [ ] 방화벽이 막고 있다
  > 그럴 수도 있지만 이 경우의 직접 원인은 아니다.

**`EXPOSE` 는 아무것도 열지 않는다.** 이 이미지가 어떤 포트를 쓰는지 사람과 도구에게 알려 주는 메모다. 실제로 트래픽이 닿게 하는 것은 그 바깥의 설정이다.
</Quiz>

<Quiz title="시각이 아홉 시간 어긋난다">
경량 베이스 이미지로 만든 앱의 로그 시각이 한국 시간보다 아홉 시간 이르다. 원인은?

- [x] 이미지에 시간대 정보가 없어 UTC 로 찍힌다 — 시간대 데이터를 넣고 지정해야 한다
- [ ] 앱이 시각을 잘못 계산한다
  > 앱은 시스템 시간대를 따를 뿐이다.
- [ ] 노드의 시계가 틀렸다
  > 그렇다면 아홉 시간이라는 정확한 차이가 나오지 않는다.
- [ ] 로그 수집기가 시각을 변환한다
  > 변환한다면 방향과 값이 일정하지 않다. 정확히 아홉 시간이면 시간대 문제다.

**시간대 데이터가 없는 것이다.** 정확히 아홉 시간 차이는 UTC 와 한국 시간의 차이이고, 최소 이미지에 시간대 파일이 빠져 있을 때 나온다. 채점이 로그 시각을 보는 세트에서는 그대로 실점이다.
</Quiz>
