**방식**: set-02 의 1과제 Terraform 구성이 서 있는 상태에서 시작한다. set-07 변동 과제지를 읽고 **절차 안내 없이 직접** 고친 뒤, 통과 기준으로 스스로 판정한다. 막히면 실전 참조를 연다.

대회 당일 과제지는 30% 범위에서 바뀐 채로 나온다. 손이 필요한 능력은 VPC 를 처음부터 다시 쓰는 속도가 아니라, 바뀐 요구를 읽고 기존 코드에서 고칠 자리를 찾아내는 능력이다.

## 실습 목표

- [ ] `10.97.0.0/16` 과 3 AZ·6 서브넷 요구를 반영한다 — CIDR 은 표가 아니라 규칙으로 주어지므로 직접 계산한다
- [ ] `unicorn-*` 이름 체계로 VPC·IGW·NAT·라우트 테이블을 이행한다
- [ ] VPC Endpoint 와 VPC Flow Log 를 새로 놓는다 — set-02 에 블록 자체가 없는 요구다
- [ ] 옛 값 `grep` 잔존 0건을 만든다
- [ ] `terraform plan` 의 리소스 개수·이름이 변동 스펙과 일치한다
- [ ] 이행본을 `apply` 하고, 값을 잘못 읽었을 때 무엇이 in-place 로 고쳐지고 무엇이 재생성인지 `plan` 출력으로 판정한다
- [ ] 라우트 테이블 연결이 끊긴 상태에서 증상만 보고 원인을 좁힌다

## 1. 변동 과제지

set-07 요구다. **정답 코드를 먼저 열지 않는다.**

| 항목 | set-02 (기준본) | set-07 (변동) |
|---|---|---|
| VPC CIDR | `172.16.0.0/16` | `10.97.0.0/16` |
| VPC 이름 | `wskorea26-vpc` | `unicorn-vpc` |
| AZ | 2개 (c, d) | 3개 (a, b, c) |
| 서브넷 수 | 4개 (public 2 + private 2) | 6개 (public 3 + private 3) |
| 서브넷 이름 | `wskorea26-pub-subnet-c` 식으로 전부 나열 | `unicorn-subnet-{pub,priv}-{a,b,c}` |
| 서브넷 CIDR | 표로 지급 | 규칙만 지급 |
| IGW | `book-igw` | `unicorn-igw` |
| 퍼블릭 RTB | `wskorea26-public-rtb` 1개 | `unicorn-rt-pub` 1개 |
| NAT | `book-ngw-{c,d}` 2개 + EIP 2개 | `unicorn-nat-{a,b,c}` 3개 + EIP 3개 |
| 프라이빗 RTB | `wskorea26-private-rtb-{c,d}` 2개 | `unicorn-rt-priv-{a,b,c}` 3개 |
| VPC Endpoint | 없음 | S3 Gateway + `ecr.api`·`ecr.dkr`·`logs` Interface |
| VPC Flow Log | 없음 | 활성화 |
| 채점용 SG | `wskorea26-vpc-environment-sg` | `unicorn-mark-sg` |

과제지 유의사항 10 에 따라 중괄호는 동일 패턴의 축약 표기다. `unicorn-subnet-{pub,priv}-{a,b,c}` 는 선수가 여섯 개 이름으로 전개해서 쓴다.

서브넷 마스크는 24bit 고정이고 Zero Subnet 을 허용한다. CIDR 을 표로 주지 않고 배정 규칙만 준다 — VPC CIDR 기준으로 Public 이 0·1·2번째, Private 이 10·11·12번째다. 여섯 개 대역을 직접 계산해서 넣는다.

<details>
<summary>계산 결과 확인</summary>

Public 은 `10.97.0.0/24` · `10.97.1.0/24` · `10.97.2.0/24`, Private 은 `10.97.10.0/24` · `10.97.11.0/24` · `10.97.12.0/24` 다. Zero Subnet 허용이 `10.97.0.0/24` 를 쓸 수 있다는 뜻이라 0번째부터 세기 시작한다.

</details>

프라이빗 서브넷은 AZ별 NAT 게이트웨이 `unicorn-nat-{a,b,c}` 로 인터넷에 나간다. 여기에 조건이 하나 더 붙는다 — App 이 도는 서브넷은 컨테이너 이미지 다운로드와 로그·메트릭 export 때 외부 인터넷을 경유하면 안 된다. NAT 를 지우는 것이 아니라, 그 트래픽만 VPC 안에서 끝나도록 S3 Gateway Endpoint 와 `ecr.api`·`ecr.dkr`·`logs` Interface Endpoint 를 놓고 private DNS 로 해석되게 만든다. VPC Flow Log 도 함께 켠다.

## 2. 이행 (타이머 30분)

타이머를 걸고 시작한다. 아래는 절차가 아니라 **놓치기 쉬운 자리 목록**이다.

- `terraform.tfvars` — `vpc_cidr` 한 줄만 있다. **AZ 목록은 여기 없다.** tfvars 만 치환하고 끝내면 AZ 가 c·d 로 남는다
- `variables.tf` 의 `subnets` map — 4개에서 6개로. map key 가 곧 서브넷 이름이고, `az` 필드가 AZ 를 담는다
- `variables.tf` 의 이름 변수 — `vpc_name` · `igw_name` · `nat_name_prefix` · `public_rtb_name` · `private_rtb_name_prefix`. 접두어 체계 자체가 바뀐다 (`wskorea26-private-rtb` → `unicorn-rt-priv`)
- `variables.tf` 의 `environment_sg_name` — 채점용 CloudShell VPC Environment 가 붙을 보안 그룹 이름이다. 네트워크 표 밖에 있어 잘 넘어간다
- `vpc.tf` 의 `local.private_az_suffix` — `substr(v.az, -1, 1)` 로 AZ 끝 글자를 뽑아 NAT·RTB 이름 뒤에 붙인다. AZ 를 바꾸면 접미사가 따라오므로 **고칠 자리가 아니다**. 여기를 건드리면 이름이 틀어진다
- NAT·EIP·프라이빗 RTB 의 개수 — 전부 `for_each = toset(local.private_subnet_keys)` 다. 서브넷을 늘리면 2개에서 3개로 자동으로 따라온다. 고치는 자리가 아니라 `plan` 에서 세는 자리다
- VPC Endpoint 와 Flow Log — set-02 에 리소스 블록 자체가 없다. Gateway Endpoint 는 프라이빗 RTB 의 ID 목록을, Interface Endpoint 는 서브넷 ID 목록과 보안 그룹을 받는다. Flow Log 는 로그 그룹과 IAM 역할이 함께 필요하다
- `outputs.tf` 의 `private_subnet_ids` · `public_subnet_ids` — map key 가 서브넷 이름이라 출력 개수와 **키 문자열이 통째로** 바뀐다
- 뒤 모듈이 읽는 `.env.ps1` / `.env.sh` 생성 블록 — set-02 런북 §1 이 `wskorea26-priv-subnet-c` 를 키로 직접 지목한다. 키 이름이 바뀌고 개수가 셋이 된다

`endpoints.tf` 와 `flowlog.tf` 는 기준본에 짝이 없으므로 diff 대신 통째로 읽는다.

놓친 것을 세 갈래로 분류한다.

- **값만 바뀐 것** — CIDR·이름 문자열. 변수 기본값 한 줄로 끝나는 자리다
- **구조가 바뀐 것** — AZ 2개에서 3개, 서브넷 4개에서 6개. `for_each` 가 이미 개수를 따라가게 돼 있어 map 항목만 늘리면 되는지, 아니면 손으로 늘려야 하는 자리가 남았는지 확인한다
- **새로 생긴 요구** — VPC Endpoint 와 Flow Log. 기준본에 리소스 블록이 없어 "고칠 자리"를 찾는 방식으로는 나오지 않는다. 과제지를 문장 단위로 읽어야 잡히는 종류다

정답이 `aws_subnet` 에 붙인 `kubernetes.io/role/elb`·`kubernetes.io/cluster/<이름>` 태그도 같이 본다. AWS Load Balancer Controller 의 서브넷 자동 디스커버리가 이 태그를 읽는다 — PART-2 로 넘어갈 때 걸리는 자리다.

## 5. 배포와 채점 확인

이행한 코드를 실제로 올린다. 6·7절이 배포된 상태를 전제한다.

`apply` 전에 `plan` 출력의 `# forces replacement` 줄이 어디에 붙는지 먼저 읽는다. 기준본에서 이행본으로 가는 것이라 전량 신규 생성이 아니다 — VPC CIDR 이 `172.16.0.0/16` 에서 `10.97.0.0/16` 으로 바뀌므로 VPC 부터 통째로 다시 만들어지고 그 안의 모든 것이 따라온다. 6절이 이 판정을 다룬다.

```bash
terraform apply
```

기대: `Apply complete!` NAT 3개를 새로 만드느라 3~5분 걸린다.

배포했다면 [set-07 채점 스크립트](https://github.com/ishs-cloud-computing/skills-2026/blob/main/set-07/task-1/mark.sh)를 CloudShell VPC Environment `unicorn-mark` 에서 실행해 1-1-A ~ 1-3-A 를 확인한다.

## 6. 과제지 오독 복구

이행을 마치고 apply 까지 했는데 과제지를 다시 읽어 보니 값이 다르다. 대회 당일 가장 자주 오는 순간이다. 이때 물어야 할 것은 하나다 — **고쳐서 살리나, 부수고 다시 만드나, 몇 분 걸리나.**

판정 축은 넷이다. 아래 세 상황을 각각 어디에 넣을지 먼저 답하고 실행한다.

| 판정 | 무엇으로 아나 | 비용 |
|---|---|---|
| in-place | `plan` 에 `~ update in-place` | 초 |
| 재생성, 의존 없음 | `plan` 에 `-/+ destroy and then create` 와 `# forces replacement` | 분 |
| 재생성, 의존 딸림 | 위와 같되 다른 리소스가 함께 `-/+` 로 끌려온다 | 십분 |
| 전면 재생성 | 최상위 리소스에 `forces replacement` — 하위가 전부 따라온다 | 20분 이상 |

### 6-1. 이름 접두어를 잘못 읽었다

**상황.** 라우트 테이블 이름을 `unicorn-rt-priv` 가 아니라 `unicorn-rtb-priv` 로 만들어 apply 했다. mark 1-2-A 가 `Name` 태그로 필터링하므로 조회 자체가 빈다.

**판정.** 이름을 고치고 `plan` 을 낸다.

```bash
terraform plan
```

기대: `~ update in-place` 로 `tags.Name` 한 줄만 바뀐다. `forces replacement` 는 나오지 않는다. 라우트 테이블의 `Name` 은 식별자가 아니라 태그이기 때문이다.

**복구.** `terraform apply` 로 끝난다. 수 초다.

**교훈.** 이름이 태그로만 쓰이는 리소스는 언제든 고칠 수 있다. 라우트 테이블·서브넷·VPC·NAT 의 `Name` 이 전부 여기 해당한다. 시간이 없으면 뒤로 미뤄도 되는 종류다.

### 6-2. CIDR 을 잘못 계산했다

**상황.** Zero Subnet 허용을 못 읽고 Public 을 `10.97.1.0/24`·`10.97.2.0/24`·`10.97.3.0/24` 로 1번부터 세어 apply 했다. 과제지는 0번부터다.

**판정.** 올바른 CIDR 로 고치고 `plan` 을 낸다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  terraform plan -no-color | Select-String -Pattern 'forces replacement|^  # aws_' | Select-Object -First 20
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  terraform plan -no-color | grep -E 'forces replacement|^  # aws_' | head -20
  ```
  </TabItem>
</Tabs>

기대: `cidr_block` 줄 옆에 `# forces replacement` 가 붙고, 해당 `aws_subnet` 세 개가 `-/+` 로 잡힌다. 서브넷 CIDR 은 변경 불가 속성이다.

**파급.** 서브넷만 지워지지 않는다. `aws_route_table_association` 이 그 서브넷을 참조하므로 함께 재생성되고, 퍼블릭 서브넷을 지목하는 `aws_nat_gateway` 와 그 EIP 도 끌려온다. `plan` 출력에서 `-/+` 가 붙은 리소스를 전부 센다.

**복구.** `terraform apply`. NAT 재생성이 있어 3~5분 걸린다.

**교훈.** 재생성이지만 VPC 는 살아 있다. 위 표의 "재생성, 의존 딸림" 이다. 아프지만 당일에 감당할 수 있다.

### 6-3. VPC CIDR 자체를 잘못 읽었다

**상황.** `10.97.0.0/16` 을 `10.79.0.0/16` 으로 뒤집어 읽고 apply 했다.

**판정.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  terraform plan -no-color | Select-String -Pattern 'Plan: |forces replacement'
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  terraform plan -no-color | grep -E 'Plan: |forces replacement'
  ```
  </TabItem>
</Tabs>

기대: `aws_vpc.this` 의 `cidr_block` 에 `forces replacement` 가 붙고, `Plan:` 줄의 destroy 수가 지금 떠 있는 리소스 전량과 같다. VPC 가 재생성되면 그 안의 모든 것이 따라 죽는다.

**복구.** `terraform apply` 로 되기는 한다. 다만 NAT 3개를 새로 만드느라 오래 걸리고, 뒤 모듈이 이 VPC 를 쓰고 있다면 EKS 클러스터까지 전부 다시다.

**교훈.** 위 표의 "전면 재생성"이다. **VPC CIDR·리전·클러스터 이름은 만들기 전에 두 번 확인한다.** 이 셋은 틀리면 되돌리는 시간이 처음부터 다시 만드는 시간과 같다. 과제지를 받으면 이 셋부터 `terraform.tfvars` 에 적고 시작한다.

## 7. 장애 진단

정상으로 선 상태에서 일부러 고장을 내고 증상만 보고 좁혀 간다. **주입 명령과 복구 명령이 짝으로 있다** — 주입만 하고 덮어 두지 않는다.

### 7-1. 프라이빗 서브넷에서 외부로 나가지 못한다

**주입.** 프라이빗 라우트 테이블 하나에서 기본 라우트를 지운다. `<rtb-id>` 는 첫 명령이 알려준다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws ec2 describe-route-tables --filters "Name=tag:Name,Values=unicorn-rt-priv-a" --query 'RouteTables[].RouteTableId' --output text
  aws ec2 delete-route --route-table-id <rtb-id> --destination-cidr-block 0.0.0.0/0
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws ec2 describe-route-tables --filters "Name=tag:Name,Values=unicorn-rt-priv-a" --query 'RouteTables[].RouteTableId' --output text
  aws ec2 delete-route --route-table-id <rtb-id> --destination-cidr-block 0.0.0.0/0
  ```
  </TabItem>
</Tabs>

**증상.** 그 서브넷에 뜨는 파드가 이미지를 못 받아 `ImagePullBackOff` 가 되거나, EC2 가 `yum`·`apt` 에서 멈춘다. PART-2 로 넘어가면 이 증상으로 먼저 만난다.

**좁히는 순서.** 위에서 아래로, 한 계층씩만 확인한다.

<Steps>

1. **어느 서브넷인가** — 문제 자원의 서브넷 ID 를 먼저 확정한다. 다른 AZ 는 멀쩡하다는 사실이 첫 단서다.

2. **그 서브넷에 붙은 라우트 테이블을 찾는다.**

   ```bash
   aws ec2 describe-route-tables --filters "Name=association.subnet-id,Values=<subnet-id>"
   ```

3. **그 테이블의 기본 라우트를 본다** — 출력의 `Routes` 에 `DestinationCidrBlock: 0.0.0.0/0` 항목이 있는지. 없으면 여기가 원인이다.

4. 있는데도 안 나가면 그때 NAT 상태와 보안 그룹으로 내려간다.

</Steps>

이 순서를 건너뛰고 보안 그룹부터 보는 것이 가장 흔한 시간 낭비다. **라우팅이 없으면 보안 그룹은 볼 필요가 없다.**

**복구.** Terraform 이 실제 상태와 코드의 차이를 알아서 메운다.

```bash
terraform plan
terraform apply
```

기대: `plan` 이 `aws_route.private_nat["..."]` 하나를 `+ create` 로 잡는다. 콘솔·CLI 로 지운 것을 코드가 되돌리는 이 동작이 drift 복구다.

### 7-2. 서브넷 태그가 사라져 로드밸런서가 안 붙는다

**주입.** 퍼블릭 서브넷에서 디스커버리 태그를 지운다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws ec2 describe-subnets --filters "Name=tag:Name,Values=unicorn-subnet-pub-a" --query 'Subnets[].SubnetId' --output text
  aws ec2 delete-tags --resources <subnet-id> --tags Key=kubernetes.io/role/elb
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws ec2 describe-subnets --filters "Name=tag:Name,Values=unicorn-subnet-pub-a" --query 'Subnets[].SubnetId' --output text
  aws ec2 delete-tags --resources <subnet-id> --tags Key=kubernetes.io/role/elb
  ```
  </TabItem>
</Tabs>

**증상.** PART-2 에서 `Ingress` 를 만들어도 ALB 가 안 생기고, AWS Load Balancer Controller 로그에 서브넷을 못 찾는다는 줄이 남는다. 여기서는 태그 조회로 먼저 본다.

**좁히는 순서.**

<Steps>

1. **태그가 실제로 있나** — 태그 키로 서브넷을 뽑는다.

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws ec2 describe-subnets --filters "Name=tag-key,Values=kubernetes.io/role/elb" --query "Subnets[].Tags[?Key=='Name'].Value" --output text
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     aws ec2 describe-subnets --filters "Name=tag-key,Values=kubernetes.io/role/elb" --query "Subnets[].Tags[?Key=='Name'].Value" --output text
     ```
     </TabItem>
   </Tabs>

2. 기대는 퍼블릭 서브넷 3개 전부다. 하나라도 빠지면 그 AZ 에 로드밸런서가 못 선다.

3. **코드와 대조한다.** 코드에 태그가 있는데 실제에 없으면 콘솔에서 지워진 것이다. 코드에도 없으면 애초에 안 쓴 것이다 — 이쪽이면 6절 오독 복구 문제로 넘어간다.

</Steps>

**복구.**

```bash
terraform apply
```

기대: `~ update in-place` 로 `tags` 한 줄만 되돌아온다.

**교훈.** 태그는 in-place 라 복구가 싸다. 그런데 없으면 **다른 서비스가 조용히 실패한다.** 실패 지점과 원인 지점이 멀어서 좁히기가 어렵다. PART-2 에서 ALB 가 안 생기면 여기부터 본다.

```bash
terraform destroy
```

기대: `Destroy complete!`
