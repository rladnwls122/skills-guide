   직접 쓰는 파일: `variables.tf`, `kms.tf`, `s3.tf`, `cloudfront.tf`, `outputs.tf`

   - **변수화 대상 (tfvars 주입)**: `player_number`(비번호), `region`(리전), `prefix`(이름 접두사)는 하드코딩하지 않고 변수로 주입한다. 버킷 이름의 비번호나 리소스 이름 접두사(`wskorea26`)가 이 변수들로 치환되어야 한다.

   | 항목 | 스펙 (set-02 실측) |
   |---|---|
   | CMK | `wskorea26-s3-key`, `wskorea26-dynamodb-key` — rotation 활성, 삭제 대기 7일, alias `alias/<이름>` |
   | s3 키 정책 | root 전체 위임 + CloudFront 서비스 principal 에 Decrypt/GenerateDataKey (`aws:SourceAccount` 조건) |
   | dynamodb 키 정책 | root 전체 위임만 |
   | 버킷 | `wskorea26-concert-bucket-<비번호>`, 퍼블릭 차단 4종, SSE-KMS(s3키)+BucketKey |
   | 객체 | `web/main/index.html`(`text/html`), `web/main/main.jpeg`(`image/jpeg`) — for_each |
   | OAC | `wskorea26-s3-oac`, s3 타입, always/sigv4 |
   | CloudFront | comment `wskorea26-concert-cf`, S3 오리진(OAC, origin_path `/web/main`), default behavior GET/HEAD + redirect-to-https + Managed-CachingOptimized, default_root_object `index.html`, 기본 인증서 |
   | 버킷 정책 | cloudfront.amazonaws.com + `AWS:SourceArn` = 배포 ARN, `s3:GetObject` |
   | output | `s3_bucket_name`, `cloudfront_domain` |

   관리형 캐시 정책은 data source 로 조회한다: `data "aws_cloudfront_cache_policy" "caching_optimized" { name = "Managed-CachingOptimized" }`.

2. **순환 참조를 일부러 체험 (5분)**

   s3 키 정책의 CloudFront statement 에 SourceAccount 대신 아래를 넣고 plan:

   ```hcl title="kms.tf (일부러 깨뜨리는 버전)"
   condition {
     test     = "StringEquals"
     variable = "aws:SourceArn"
     values   = [aws_cloudfront_distribution.cdn.arn]   # 순환!
   }
   ```

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   일부러 순환 참조를 만드는 조각이다. 키 정책이 CloudFront 배포 ARN 을 참조하고, 그 배포는 다시 이 키로 암호화된 버킷을 오리진으로 삼는다. Terraform 은 이 고리를 풀 수 없어 apply 를 거부한다 — 그래서 키 정책 쪽 조건은 배포 ARN 대신 `aws:SourceAccount` 로 느슨하게 잡는다.

   </details>

   기대: `Error: Cycle: aws_kms_key.s3, aws_cloudfront_distribution.cdn, aws_s3_bucket..., ...` — key→distribution→bucket→key 순환을 확인 후 `aws:SourceAccount = local.account_id` 로 되돌린다.

3. **apply & 검증**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     terraform init
     terraform fmt
     terraform validate
     terraform apply
     # CloudFront 배포 완료까지 수 분 소요

     $BUCKET = terraform output -raw s3_bucket_name
     $CF     = terraform output -raw cloudfront_domain

     # (1) alias 역조회 — mark 방식
     aws kms describe-key --key-id alias/wskorea26-s3-key --query 'KeyMetadata.[KeyState,KeyManager]'
     # 기대: ["Enabled", "CUSTOMER"]

     # (2) 퍼블릭 차단 4종 — mark 2-2
     aws s3api get-public-access-block --bucket $BUCKET
     # 기대: 4개 필드 모두 true
     aws s3api get-bucket-policy-status --bucket $BUCKET --query 'PolicyStatus.IsPublic'
     # 기대: false  (버킷 정책이 없으면 이 호출 자체가 에러 — OAC 정책이 있어야 함)

     # (3) 암호화 — SSE-KMS + BucketKey
     aws s3api get-bucket-encryption --bucket $BUCKET `
       --query 'ServerSideEncryptionConfiguration.Rules[0]'
     # 기대: SSEAlgorithm aws:kms + KMSMasterKeyID(s3키 ARN) + BucketKeyEnabled true

     # (4) 객체 키 — mark 2-1
     aws s3api list-objects-v2 --bucket $BUCKET --query 'Contents[].Key'
     # 기대: ["web/main/index.html", "web/main/main.jpeg"]

     # (5) 접근 경로: CloudFront 만 허용
     curl.exe -s -o NUL -w "%{http_code}`n" "https://$CF/"          # 기대: 200
     curl.exe -s -o NUL -w "%{http_code}`n" "https://$BUCKET.s3.ap-northeast-2.amazonaws.com/web/main/index.html"  # 기대: 403
     curl.exe -s -o NUL -w "%{http_code}`n" "http://$CF/" -L        # http → 301 후 200 (redirect-to-https)
     ```

4. **(심화) root-less 키 정책으로 재작성**

   set-03 유의사항을 가정하고 s3 키 정책에서 root statement 를 제거:

   - `aws_caller_identity` 로 계정 ID 를 조회
   - principal 을 `["*"]` 로 두고 `condition { test = "StringEquals", variable = "kms:CallerAccount", values = [local.account_id] }` 로 계정을 못 박기
   - `kms:*` 없이 admin 액션을 개별 나열한 `kms_admin` 문서 작성 (lockout 검사 통과를 위해 `kms:Put*` 필수)
   - apply 후 정책 텍스트 자가 grep:

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws kms get-key-policy --key-id alias/wskorea26-s3-key --policy-name default --output text | Select-String -Pattern ':root|kms:\*'
     # 기대: 출력 없음 (있으면 set-03 mark 실격)
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     aws kms get-key-policy --key-id alias/wskorea26-s3-key --policy-name default --output text | grep -E ':root|kms:\*'
     # 기대: 출력 없음 (있으면 set-03 mark 실격)
     ```
     </TabItem>
   </Tabs>

   `kms:Put*` 를 빼고 apply 해 보면 `MalformedPolicyDocumentException: ... will prevent you from managing the key`(lockout safety check) 를 볼 수 있다.

6. **(보너스) WAF Web ACL 부착 — CLOUDFRONT scope**

   set-02 에는 WAF 가 없다. set-03·set-07 후보를 대비한 보너스 스텝이다 — 개념(scope·override 계층)은 [이론 7절](/part-1/02-kms-s3-cloudfront/theory/)을 먼저 읽는다. 여기서는 3번에서 만든 CloudFront 배포에 set-03 방식(관리형 규칙 그룹 없이 커스텀 매치)으로 Web ACL 을 붙인다.

   작성/수정 파일: 복사해 둔 `versions.tf` 에 `us-east-1` provider alias 한 블록만 더하고, `waf.tf` 를 신설한다. alias 추가는 부트스트랩 파일에서 실제로 손이 가는 유일한 자리다.

   | 항목 | 스펙 (set-03 실측) |
   |---|---|
   | provider | `alias = "use1"`, `region = "us-east-1"` |
   | Web ACL | `scope = "CLOUDFRONT"`(provider `aws.use1`), `default_action` allow |
   | SQLi 규칙 | priority 1, `sqli_match_statement`(query_string, `sensitivity_level = "HIGH"`, text_transformation `URL_DECODE`) → block |
   | XSS 규칙 | priority 2, `xss_match_statement`(query_string, text_transformation `URL_DECODE`→`HTML_ENTITY_DECODE`) → block |
   | Rate 규칙 | priority 3, `rate_based_statement`(`aggregate_key_type = "IP"`, `limit = 200`, `evaluation_window_sec = 60`) → block |
   | 연결 | `aws_cloudfront_distribution.cdn` 의 `web_acl_id = aws_wafv2_web_acl.this.arn` |

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">

     ```powershell
     curl.exe -s -o NUL -w "%{http_code}`n" "https://$CF/?probe=1%27%20OR%201=1--"       # SQLi 페이로드 → 403 기대
     curl.exe -s -o NUL -w "%{http_code}`n" "https://$CF/?probe=<script>alert(1)</script>" # XSS 페이로드 → 403 기대
     curl.exe -s -o NUL -w "%{http_code}`n" "https://$CF/"                                 # 정상 요청 → 200 기대
     ```

     ```bash
     curl -s -o /dev/null -w "%{http_code}\n" "https://$CF/?probe=1%27%20OR%201=1--"         # SQLi 페이로드 → 403 기대
     curl -s -o /dev/null -w "%{http_code}\n" 'https://'"$CF"'/?probe=<script>alert(1)</script>' # XSS 페이로드 → 403 기대
     curl -s -o /dev/null -w "%{http_code}\n" "https://$CF/"                                  # 정상 요청 → 200 기대
     ```
     </TabItem>
   </Tabs>

   **오탐 대응 훈련(Count → 검증 → Block 복구)**:

   1. SQLi 규칙의 `action`을 `block{}`에서 `count{}`로 바꿔 `apply`한다.
   2. 같은 SQLi 페이로드 요청이 200으로 통과하는지 확인한다. 차단은 안 되지만 CloudWatch 메트릭·sampled requests엔 여전히 잡힌다.
   3. `action`을 다시 `block{}`으로 되돌려 `apply`한다.

   관리형 규칙 그룹(set-07 방식)이었다면 2번 자리에 `rule_action_override`가 들어간다.

## :badge[함정]{variant=danger} 목록

| 함정 | 증상 / 결과 |
|---|---|
| PowerShell 5.1 에서 `&&` 로 명령 연결 | `'&&' 연산자는 예약되어 있습니다` 파서 에러 — 줄을 나눠 실행 |
| 키 정책에 배포 ARN 직접 참조 | `Error: Cycle` — SourceAccount 조건으로 우회 |
| 버킷 정책 없이 퍼블릭 차단만 | `get-bucket-policy-status` 호출 에러 → mark 2-2 실패 |
| 객체 content_type 누락 | 브라우저가 html 을 다운로드 (기본 octet-stream) |
| origin_path 누락 | `https://<cf>/` 가 403/404 — 루트가 web/main/index.html 로 안 감 |
| alias 오타 (`alias/` 접두 누락 포함) | mark 가 키를 역조회 못 함 — 암호화 항목 전멸 |
| root-less 정책에 `kms:Put*` 누락 | lockout safety check 로 apply 자체 실패 |
| root-less 키를 다른 신원으로 사용 | AccessDenied — terraform 과 같은 자격증명으로만 작업 |
| ECR 등 이름 없는 서비스에 CMK 생성 | 불필요 리소스 감점 (set-02 유의사항 10) |
| CloudFront 전파 전 채점/검증 | 간헐 403 — `wait distribution-deployed` 후 확인 |
| WAF Web ACL을 서울 리전에 생성 | apply 실패 또는 CloudFront가 연결을 거부 — CLOUDFRONT scope는 us-east-1 고정 |
| 관리형 규칙 그룹 전체를 override_action count로 전환 | 오탐 규칙 하나 때문에 그룹 전체 보호가 무력화 — RuleActionOverrides로 해당 규칙만 좁힐 것 |

## 변형 셀프 체크

당일 과제의 약 30% 가 수정된다. 재배포 없이, 각 질문에 먼저 답한 뒤 펼쳐 확인한다.

1. 비번호가 `103` 에서 `217` 로 바뀌면 무엇을 고치나?

   <details>
   <summary>답 확인</summary>

   `terraform.tfvars` 의 `player_number` 한 곳이다. 버킷 이름은 `data.tf` 의 `local.bucket_name` 이 접두어와 이어 붙인다. `grep -rn '"103"' *.tf` 가 `variables.tf` 의 기본값 한 건만 내야 하드코딩이 없는 것이다. mark.sh 는 버킷을 접두어로 찾지만 mark 2-1-A 의 기대 출력은 비번호까지 포함한 이름이다.

   </details>

2. 객체 경로가 `web/main` 에서 `web/2026` 으로 바뀌면 어디를 고치나?

   <details>
   <summary>답 확인</summary>

   `variables.tf` 의 `object_prefix` 한 곳이다. `s3.tf` 의 객체 key 와 `cloudfront.tf` 의 `origin_path` 가 같은 변수를 쓴다. `grep -rn "web/main" *.tf` 가 `variables.tf` 한 건이면 된다. 경로를 바꾸면 mark 2-1-A 의 객체 키와 8-5-A 의 루트 응답이 함께 움직인다.

   </details>

3. 정적 파일에 `style.css` 가 하나 더 지급되면 어디를 고치고, 어디를 그대로 두나?

   <details>
   <summary>답 확인</summary>

   `s3.tf` 두 곳이다. `aws_s3_object.static` 의 `for_each` 목록에 파일명을 넣고, `local.content_types` 에 `css = "text/css"` 를 더한다. 버킷·퍼블릭 차단·암호화·OAC·버킷 정책은 그대로 둔다 — 버킷 정책이 `버킷ARN/*` 전체를 허용하기 때문이다. `content_type` 인자 이름이 막히면 [검색 가이드](/reference/search-guide/)의 Registry 동선으로 `aws_s3_object` 문서를 연다.

   </details>

4. CMK 별칭을 `wskorea26-s3-key` 대신 `wskorea26-s3-cmk` 로 만들면 어느 체크가 깨지나?

   <details>
   <summary>답 확인</summary>

   mark 2-2-A 다. 이 항목은 객체의 `SSEKMSKeyId` 로 키를 역조회해 별칭 이름을 두 줄 출력하고 `alias/wskorea26-s3-key` 와 정확히 비교한다. DynamoDB 별칭은 같은 방식으로 mark 4-1-A 가 본다. `alias/` 접두어는 `kms.tf` 가 붙이므로 변수에는 이름만 넣는다.

   </details>

5. 배포 comment 를 `wskorea26-concert-cf` 에서 다른 값으로 바꾸면 어디까지 영향이 가나?

   <details>
   <summary>답 확인</summary>

   mark.sh 는 맨 앞에서 comment 로 배포 ID 를 찾고, 그 ID 로 도메인까지 얻는다. comment 가 다르면 ID 가 `None` 이 되어 mark 8-1-A 부터 8-5-A 까지, 그리고 도메인을 쓰는 9-1-A~9-3-A 까지 함께 무너진다. 고칠 곳은 `variables.tf` 의 `cloudfront_name` 한 곳이다.

   </details>

`apply` 가 실패하면 [01 실습의 apply 실패 세 갈래](/part-1/01-terraform-vpc/lab/)를 먼저 본다. 증상별 확인 명령은 [트러블슈팅](/reference/troubleshooting/), 실습을 끝냈으면 [잔존 리소스 점검](/reference/cleanup-check/)을 돌린다.
