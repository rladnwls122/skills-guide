## 실습 목표

- [ ] alpine 고정 + tzdata/TZ + 비루트 Dockerfile 작성, (CloudShell 에서) 빌드·push·스캔 확인

- [ ] PK/GSI/PITR/삭제방지/SSE-KMS DynamoDB 테이블 tf 작성
- [ ] ALB 통합 응답 포맷 Lambda + 최소권한 실행역할 + env 주입 tf 작성

선행 지식과 목표는 [모듈 개요](/part-1/03-container-lambda-dynamodb/)에.

## 단계별 절차

<Steps>

1. **Dockerfile 직접 작성 (정답지 최대한 보지않기, Amazon Q 사용 가능)**

   스펙:

   - 베이스: 최신 안정 **고정 버전** alpine
   - 타임존: tzdata 설치 + `TZ=Asia/Seoul`
   - 사용자: uid 10001 비루트 유저 생성·전환
   - 바이너리: `book` 을 `/book` 으로 755 복사
   - 포트·진입점: EXPOSE 8080, ENTRYPOINT

   실제 book 바이너리가 없으므로 로컬 검증용 더미를 만든다. 줄 끝은 **LF** 여야 한다.

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     $dummy = "#!/bin/sh`ndate `"+%Y-%m-%d %H:%M:%S %Z`"; sleep 3600`n"
     [IO.File]::WriteAllText("$PWD\book", $dummy)
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     printf '#!/bin/sh\ndate "+%%Y-%%m-%%d %%H:%%M:%%S %%Z"; sleep 3600\n' > book
     ```
     </TabItem>
   </Tabs>

   :::caution[CRLF 함정]
   리눅스·CloudShell 에서 만들면 줄 끝이 LF 라 이 함정이 없다. Windows 기본 도구(`Set-Content`·메모장)는 줄 끝에 CR 을 붙인다. 셔뱅이 `#!/bin/sh\r` 이 되면 컨테이너가 `no such file or directory` 로 죽는다 — 실패 원인이 셔뱅이라는 표시가 어디에도 안 나와서 찾기 어렵다. 위처럼 `WriteAllText` 로 쓰거나 CloudShell 에서 직접 만든다. 실행 권한은 Dockerfile 의 `COPY --chmod=755` 가 붙이므로 Windows 쪽에서 신경 쓸 것이 없다.
   :::

2. **빌드·타임존 검증 (Docker 가능 환경 — CloudShell 권장)**

   대회 조건 그대로 연습하려면 기본 CloudShell(인터넷 O, docker 내장, amd64)에 Dockerfile+book 만 올려 빌드한다. 업로드는 CloudShell 우측 상단 **Actions → Upload file** 이고, 올린 파일은 홈(`~`)에 떨어진다.

   ```bash
   docker build -t book-test .
   docker run --rm book-test        # 기대: ... KST  (UTC 가 나오면 tzdata/TZ 누락)
   docker run --rm --entrypoint id book-test   # 기대: uid=10001(book) — 비루트 확인
   ```

3. **tf 작성 — ECR + DynamoDB (`ecr.tf`·`dynamodb.tf`)**

   CMK 는 복사해 온 `kms.tf` 의 `wskorea26-dynamodb-key` 를 참조한다 — 다시 정의하지 않는다.

   - **변수화 대상 (tfvars 주입)**: `player_number`(비번호), `region`(리전), `prefix`(이름 접두사). ECR 리포지토리 이름, DynamoDB 테이블 이름, Lambda 함수 이름 등의 접두사(`wskorea26`)를 이 변수로 치환한다.

   | 리소스 | 스펙 (set-02 실측) |
   |---|---|
   | ECR | `wskorea26-book-repo`, scan_on_push, encryption_type KMS(키 미지정=aws/ecr), force_delete |
   | 테이블 | `wskorea26-data-table`, PAY_PER_REQUEST, hash_key `client_id`(S), deletion_protection, attribute 3개(client_id/concert_name/created_at 전부 S), GSI `concert_name-created_at-index`(HASH concert_name + RANGE created_at, ALL), SSE-KMS(CMK), PITR |

4. **push & 스캔 확인 (CloudShell)**

   ```bash
   # 리포지토리 URI 는 계정 ID 를 조립하지 말고 조회해서 받는다
   ECR=$(aws ecr describe-repositories --repository-names wskorea26-book-repo \
     --query 'repositories[0].repositoryUri' --output text)
   aws ecr get-login-password | docker login --username AWS --password-stdin "${ECR%%/*}"
   docker build -t "$ECR:stable" .
   docker push "$ECR:stable"              # stable 만! latest 추가 push 금지

   aws ecr wait image-scan-complete --repository-name wskorea26-book-repo --image-id imageTag=stable
   aws ecr describe-image-scan-findings --repository-name wskorea26-book-repo --image-id imageTag=stable \
     --query 'imageScanFindings.findingSeverityCounts'
   # 기대: {} 또는 CRITICAL/HIGH 키 없음. High 발견 시 RUN apk upgrade --no-cache 추가 후 재빌드
   aws ecr describe-images --repository-name wskorea26-book-repo --query 'imageDetails[].imageTags'
   # 기대: [["stable"]] — 태그 1개뿐
   ```

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   이미지를 올리고 스캔 결과까지 확인한다. 첫 줄은 리포지토리 URI 를 계정 ID 로 조립하는 대신 `describe-repositories` 로 받아 온다 — 계정 ID 를 따로 알 필요가 없고 오타도 안 난다. `${ECR%%/*}` 는 리포지토리 경로를 잘라 레지스트리 주소만 남기는 셸 문법이라 로그인 대상이 된다. `wait image-scan-complete` 로 스캔이 끝나기를 기다린 뒤 심각도 집계를 보고, 마지막 `describe-images` 로 태그가 `stable` 하나뿐인지 확인한다 — `latest` 가 함께 붙으면 감점이다.

   </details>

5. **Lambda 작성 (index.py + lambda.tf)**

   index.py 스펙 (정답지 최대한 보지않기, Amazon Q 사용 가능, theory §4 의 사실 목록만 보고):

   - env `TABLE_NAME`/`INDEX_NAME` 읽기 (하드코딩 금지)
   - `queryStringParameters` 에서 `concert_name` — 없으면 400 `{"msg": "concert_name is required"}`
   - `unquote_plus` 디코딩 (ALB 는 `2ND%20TINY_CON` 그대로 전달)
   - GSI Query + `ScanIndexForward=False` + LastEvaluatedKey 페이지네이션
   - 결과 없으면 `[]` + 200
   - 응답: statusCode / headers / isBase64Encoded 는 필수, body 는 선택. statusDescription("200 OK")은 필수가 아니지만 함께 넣는다
   - body 는 `json.dumps(..., ensure_ascii=False, default=str)`, 키 순서 `username, created_at, email, booking_id, client_id, concert_name`

   `lambda.tf` 파일 스펙:

   - 패키징: `archive_file` zip
   - 로그그룹: `/aws/lambda/wskorea26-book-lambda`, 보존 30일
   - 실행역할: 3-statement (`dynamodb:Query` 테이블+`/index/*` / logs 2액션 / CMK `kms:Decrypt`)
   - 런타임: python3.14, 불가하면 python3.13
   - 기타: timeout 10, env 주입

6. **데이터 주입 & 검증**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     # Decimal 함정은 CLI put-item 은 문자열 "N" 타입이라 안 밟지만, 파이썬 스크립트로 넣을 땐 Decimal 필수

       "username":{"S":"akaね"},"email":{"S":"a@b.c"},"booking_id":{"S":"b1"}}'

       "client_id":{"S":"c2"},"concert_name":{"S":"2ND TINY_CON"},"created_at":{"S":"2026-07-25 12:00:00"},
       "username":{"S":"kim"},"email":{"S":"k@b.c"},"booking_id":{"S":"b2"}}'

     Get-Content out.json
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">

     ```bash
       "username":{"S":"kim"},"email":{"S":"k@b.c"},"booking_id":{"S":"b2"}}'

     cat out.json
     ```

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   조회할 항목 두 건을 넣고 Lambda 를 ALB 없이 호출한다. CLI 의 `put-item` 은 값을 타입 표기(`{"S": ...}`)로 주므로 숫자를 문자열로 다루고, 그래서 boto3 의 float 제한을 밟지 않는다. 호출은 ALB 이벤트 모양의 JSON 을 파일로 만들어 `--payload fileb://` 로 넘기는 방식이다 — `concert_name` 값이 `%20` 으로 인코딩돼 있는 것이 ALB 가 넘겨주는 형태를 그대로 흉내 낸 것이다.

   </details>

   기대 출력 검증 포인트:

   - `"statusCode": 200`, `"statusDescription": "200 OK"`
   - body 배열이 **12:00 항목이 먼저** (최신순)
   - 각 항목 키 순서가 username → created_at → email → booking_id → client_id → concert_name
   - `akaね` 가 이스케이프 없이 그대로 (`\u` 가 보이면 ensure_ascii 실패)

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">

   <summary>이 블록이 하는 일</summary>

   실패 경로와 테이블 속성을 확인한다. (2)는 파라미터가 없을 때 400 과 정해진 메시지가 나오는지, (3)은 결과가 없을 때 404 가 아니라 `[]` 와 200 이 나오는지를 본다. (4)는 삭제방지·SSE 종류·GSI 이름을 한 번에 뽑고, 이어서 PITR 상태를 따로 조회한다 — PITR 은 `describe-table` 이 아니라 `describe-continuous-backups` 에 있다.

   </details>

   직접 쓴 파일 다섯 개를 정답지와 나란히 비교한다. Dockerfile·tf 3종·핸들러 코드 순이라 컨테이너부터 애플리케이션까지 한 바퀴가 된다. 차이가 나면 어느 쪽이 채점 항목을 만족하는지 기준으로 판단한다 — 정답지와 다르다고 전부 틀린 것은 아니다.

   </details>

   확인 관점: 비키 attribute 를 정의하지 않았는가, 실행역할이 3-statement 최소권한인가, 페이지네이션 루프가 있는가, `_KEYS` 재조립 방식인가.

</Steps>

## 변형 셀프 체크

당일 과제의 약 30% 가 수정된다. 재배포 없이, 각 질문에 먼저 답한 뒤 펼쳐 확인한다.

1. GSI 이름이 `concert_name-created_at-index` 에서 다른 값으로 바뀌면 무엇을 고치나?

   <details>
   <summary>답 확인</summary>

   두 곳이다. `dynamodb.tf` 의 `global_secondary_index.name` 과 `lambda.tf` 의 `INDEX_NAME` 환경 변수다. `INDEX_NAME` 은 변수가 아니라 리터럴이라 한쪽만 고치면 Query 가 `ValidationException` 으로 죽는다. `grep -rn "concert_name-created_at-index" .` 로 두 건이 다 잡히는지 본다.

   </details>

2. Lambda 런타임 요구가 `python3.14` 에서 `python3.13` 으로 바뀌면?

   <details>
   <summary>답 확인</summary>

   `variables.tf` 의 `lambda_runtime` 한 곳이다. `lambda.tf` 는 그 변수를 참조만 한다. mark 6-1-A 는 함수 이름·런타임·`TABLE_NAME` 세 값을 한 줄로 뽑아 정확히 비교하므로 런타임 문자열이 하나라도 다르면 그 항목이 통째로 실패한다.

   </details>

3. 조회 결과를 최신순이 아니라 오래된 순으로 내라면 어디를 고치고, 어디를 그대로 두나?

   <details>
   <summary>답 확인</summary>

   `lambda/index.py` 의 Query 인자 `ScanIndexForward` 를 `True` 로 바꾼다. 테이블·GSI·실행역할은 그대로 둔다 — 정렬 방향은 인덱스 구조가 아니라 조회 옵션이기 때문이다. 인자 이름이 막히면 `aws dynamodb query help` 나 boto3 문서를 열고, 찾는 순서는 [검색 가이드](/reference/search-guide/)에 있다.

   </details>

4. 이미지를 `stable` 대신 `latest` 태그로 올리면 어느 체크가 깨지나?

   <details>
   <summary>답 확인</summary>

   mark 3-1-A 다. 이 항목은 `--image-ids imageTag=stable` 로 이미지를 지목해 태그 목록과 스캔 결과를 뽑는다. `stable` 이 없으면 조회부터 실패하고, `stable` 에 `latest` 를 덧붙이면 태그 목록이 두 개로 나와 기대 출력과 어긋난다.

   </details>

`apply` 가 실패하면 [01 실습의 apply 실패 세 갈래](/part-1/01-terraform-vpc/lab/)를 먼저 본다. 증상별 확인 명령은 [트러블슈팅](/reference/troubleshooting/), 실습을 끝냈으면 [잔존 리소스 점검](/reference/cleanup-check/)을 돌린다.
