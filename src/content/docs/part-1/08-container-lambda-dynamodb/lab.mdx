## 실습 목표

- [ ] 조회 패턴이 뒤집힌 요구를 읽고 파티션 키와 GSI 축을 다시 정한다
- [ ] 파티션 키가 왜 이 모듈에서 가장 비싼 값인지, 삭제 방지가 왜 그 비용을 더 키우는지 확인한다
- [ ] 태그 덮어쓰기 정책에 **예외**를 두는 요구를 반영한다 — 코드가 아니라 도구 버전이 걸리는 경우를 판정한다
- [ ] 로그 그룹 이름을 기본 규칙에서 지정 이름으로 옮긴다
- [ ] `plan` 출력으로 in-place 와 재생성을 판정하고 파급을 센다
- [ ] 함수가 실패할 때 권한 문제와 호출 차단을 구분해 좁힌다

선행 지식과 목표는 [모듈 개요](/part-1/08-container-lambda-dynamodb/)에.

## 1. 변동 과제지

set-07 요구다. **정답 코드를 먼저 열지 않는다.**

| 항목 | set-02 (기준본) | set-07 (변동) |
|---|---|---|
| 테이블 이름 | `wskorea26-data-table` | `unicorn-concert-db` |
| 예약 하나를 찾는 기준 | 고객 | **예약 번호** |
| 최신순으로 묶어 보는 기준 | 콘서트 | **고객** |
| PITR | 없음 | 켠다 |
| 테이블 암호화 키 | DynamoDB 전용 키 | 02 에서 만든 **애플리케이션 데이터용 키** |
| 리포지토리 이름 | `wskorea26-book-repo` | `unicorn-concert-app` |
| 태그 덮어쓰기 | 자유 | **금지 — 단 `latest` 는 예외** |
| 리포지토리 암호화 키 | 관리형 `aws/ecr` | 02 에서 만든 **저장소용 키** |
| 이미지 태그 | `stable` | `v1.0.0` 과 `latest` |
| 함수 이름 | `wskorea26-book-lambda` | `unicorn-get-booking-func` |
| 함수 로그 그룹 | 기본 규칙에 맡김 | **`/unicorn/lambda/get-booking` 으로 지정** |
| 함수 권한 | 인덱스 Query | **항목 하나 직접 읽기 + 인덱스 Query** |

### 요구에서 파생되는 것

**조회 기준 두 줄이 이 모듈의 전부다.** 표에 "예약 번호로 찾는다"와 "고객별로 최신순"이라고만 적혀 있지만, 그것이 테이블 설계를 결정한다. 무엇이 파티션 키가 되고 무엇이 인덱스로 가는지 스스로 배치한다. [08 이론 3절](/part-1/08-container-lambda-dynamodb/theory/)이 두 세트를 나란히 놓는다.

**"단 `latest` 는 예외"** 가 두 번째다. 예외 없는 금지와 예외 있는 금지는 쓰는 값 자체가 다르고, 예외를 적는 자리가 따로 있다. 그리고 **이 요구는 코드만으로 해결되지 않을 수 있다** — 이론 2절 확인 블록이 그 이유를 보여 준다.

**로그 그룹 이름을 지정하라는 요구**는 두 곳을 건드린다. 로그 그룹 리소스 자체와, 함수가 어디에 쓸지 정하는 설정이다. 한쪽만 고치면 그룹은 만들어졌는데 로그는 옛 자리에 쌓인다.

**권한이 하나 늘었다.** 인덱스를 훑는 것과 항목 하나를 직접 집는 것은 다른 액션이다. 요구가 "예약 번호로 찾는다"이므로 어느 쪽이 늘어야 하는지는 요구에서 나온다.

## 2. 이행 (타이머 30분)

타이머를 걸고 시작한다. `~/set07-lab` 의 `ecr.tf` · `dynamodb.tf` · `lambda.tf` 를 고친다. 아래는 절차가 아니라 **스스로 답해야 할 질문 목록**이다.

- 파티션 키를 바꾸면 `attribute` 블록은 몇 개가 되나. 늘어나나 줄어드나
- GSI 의 HASH 가 될 속성이 테이블 파티션 키 자리에서 빠진다. 그래도 `attribute` 에 남겨야 하나
- 태그 덮어쓰기에 예외를 두는 값의 이름은 무엇이고, 예외 대상을 적는 자리는 인자인가 블록인가
- 로그 그룹 이름을 함수에 알려 주는 인자는 어디에 있나. 함수 리소스 안인가 밖인가
- 항목 하나를 키로 직접 읽는 DynamoDB 액션 이름은 무엇인가
- 02 에서 만든 키들의 참조 이름이 바뀌었다. 이 파일들이 그 키를 어떻게 부르고 있나
- 애플리케이션 코드(`lambda/index.py`)는 손대야 하나. 무엇을 보고 판단하나

**마지막 질문이 중요하다.** 인프라만 고치고 코드를 안 고치면 배포는 되는데 응답이 틀린다.

## 6. 과제지 오독 복구

배포까지 했는데 값이 다르다. 판정은 01·02 와 같은 축이고, **여기에 한 종류가 더 있다.**

| 판정 | 무엇으로 아나 | 비용 |
|---|---|---|
| in-place | `plan` 에 `~ update in-place` | 초 |
| 재생성, 의존 없음 | `plan` 에 `forces replacement` | 분 |
| 재생성, 의존 딸림 | 위와 같되 다른 리소스가 함께 `-/+` | 십분 |
| **도구가 모른다** | `plan` 이 아예 안 돈다 — `validate` 에서 막힌다 | 분 — **코드를 고치면 안 된다** |

마지막 줄이 이 모듈에서 처음 나온다.

### 6-1. 로그 그룹을 지정하는 것을 빼먹었다

**상황.** 로그 그룹 리소스는 만들었는데 함수가 그것을 쓰도록 연결하지 않았다. 채점 `7-1-A` 의 세 번째 값이 `/aws/lambda/unicorn-get-booking-func` 로 나온다.

**판정.** 연결 인자를 넣고 `plan` 을 낸다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  terraform plan -no-color | Select-String -Pattern 'logging_config|log_group|forces replacement'
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  terraform plan -no-color | grep -E 'logging_config|log_group|forces replacement'
  ```
  </TabItem>
</Tabs>

기대: 함수가 `~ update in-place` 로 잡히고 `forces replacement` 는 없다. 로그 대상은 함수의 설정이지 정체성이 아니다.

**복구.** `terraform apply`. 초 단위다.

**파급.** 리소스는 안 죽지만 **이미 쌓인 로그는 옛 그룹에 남는다.** 새 그룹은 다음 호출부터 채워지므로, 채점 전에 함수를 한 번 호출해 새 그룹에 스트림이 생기게 해야 한다. 빈 로그 그룹은 조회는 되지만 내용이 없다.

**교훈.** 값은 싼데 **시간 축이 붙는다.** "고쳤다"와 "채점이 볼 수 있다" 사이에 호출 한 번이 필요한 항목이 있다.

### 6-2. 태그 정책 인자를 프로바이더가 모른다

**상황.** 이론 2절대로 썼는데 `validate` 가 막는다.

```
Error: Unsupported block type
Blocks of type "image_tag_mutability_exclusion_filter" are not expected here.
```

**판정.** **여기서 코드를 고치기 시작하면 시간을 버린다.** 먼저 프로바이더가 그 블록을 아는지 묻는다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  $s = terraform providers schema -json | ConvertFrom-Json
  $s.provider_schemas.'registry.terraform.io/hashicorp/aws'.resource_schemas.aws_ecr_repository.block.block_types.PSObject.Properties.Name
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  terraform providers schema -json |
    jq -r '.provider_schemas["registry.terraform.io/hashicorp/aws"].resource_schemas.aws_ecr_repository.block.block_types | keys[]'
  ```
  </TabItem>
</Tabs>

목록에 `image_tag_mutability_exclusion_filter` 가 **없으면 코드가 아니라 도구가 낡은 것이다.**

**복구.**

```bash
terraform init -upgrade
terraform validate
```

`.terraform.lock.hcl` 이 버전을 고정하고 있으므로 `-upgrade` 없이는 안 올라간다. 올린 뒤 같은 조회를 다시 해 목록에 생겼는지 확인한다.

**교훈.** **문법 오류처럼 보이는 에러가 항상 문법 문제는 아니다.** 과제지가 최신 기능을 요구하면 도구 버전이 먼저다. 판정 순서는 이렇다 — `validate` 가 막으면 ① 오타인가 ② 프로바이더가 아는가 ③ 그래도 아니면 문서를 본다. ②를 건너뛰면 맞는 코드를 계속 고치게 된다.

### 6-3. 파티션 키를 잘못 읽었다

**상황.** 조회 기준 두 줄을 뒤집어 읽어 고객을 파티션 키로 두고 만들었다. set-02 와 같은 배치다.

**판정.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  terraform plan -no-color | Select-String -Pattern 'forces replacement|# aws_' | Select-Object -First 20
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  terraform plan -no-color | grep -E 'forces replacement|# aws_' | head -20
  ```
  </TabItem>
</Tabs>

기대: `hash_key` 줄 옆에 `# forces replacement`. 파티션 키는 테이블의 정체성이라 바꿀 수 없다.

**여기서 apply 하면 막힌다.** 삭제 방지가 켜져 있기 때문이다.

```
Error: deleting DynamoDB Table: ValidationException:
Resource cannot be deleted because deletion protection is enabled.
```

**복구 순서가 있다.** 이 순서를 모르면 위 에러에서 멈춘다.

<Steps>

1. **삭제 방지를 먼저 끈다** — 코드에서 `deletion_protection_enabled` 를 `false` 로 두고 apply 한다. 이때는 테이블이 안 죽는다. `~ update in-place` 다

2. **그다음 파티션 키를 바꿔 apply 한다** — 이제 재생성이 통과한다

3. **삭제 방지를 다시 켠다** — 채점 항목이므로 꺼 둔 채로 두면 감점이다

</Steps>

**파급.** 테이블만 죽지 않는다.

- **항목이 전부 사라진다.** 검증 데이터를 다시 넣어야 한다
- GSI 도 함께 다시 만들어진다
- Lambda 실행 역할의 리소스 ARN 이 테이블 ARN 을 참조한다
- 애플리케이션 코드가 파티션 키 이름을 문자열로 쓴다면 그것도 함께 고친다

**교훈.** 01 의 VPC CIDR, 02 의 버킷 이름과 같은 자리다. 다만 여기엔 **삭제 방지라는 한 겹이 더 있다.** 비싼 값을 되돌리는 데 드는 시간에 "안전장치를 푸는 시간"이 더해진다는 것이 이 모듈이 더하는 교훈이다.

과제지를 받으면 **테이블 이름과 파티션 키부터 확정하고 시작한다.**

## 7. 장애 진단

정상으로 선 상태에서 일부러 고장을 내고 증상만 보고 좁혀 간다. **주입 명령과 복구 명령이 짝으로 있다.**

### 7-1. 함수가 500 을 낸다

**주입.** 실행 역할에서 인라인 정책을 지운다. 정책 이름은 첫 명령이 알려준다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws iam list-role-policies --role-name unicorn-get-booking-func-role --output text
  aws iam delete-role-policy --role-name unicorn-get-booking-func-role --policy-name <정책이름>
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws iam list-role-policies --role-name unicorn-get-booking-func-role --output text
  aws iam delete-role-policy --role-name unicorn-get-booking-func-role --policy-name <정책이름>
  ```
  </TabItem>
</Tabs>

**증상.** 함수 호출이 500 을 내거나 오류 응답이 온다. 함수 자체는 존재하고 상태도 정상이다.

**좁히는 순서.**

<Steps>

1. **함수가 실행은 됐나** — `aws lambda get-function-configuration --function-name <함수> --query "[State,LastUpdateStatus]"`. `Active` 면 배포는 정상이다. 배포 문제와 실행 문제를 여기서 가른다

2. **로그를 읽는다** — 로그 그룹의 최신 스트림에서 마지막 메시지를 본다. `AccessDeniedException` 이면 신원·권한 문제이고, `ValidationException` 이면 요청 자체가 잘못된 것이다. **여기서 방향이 갈린다**

3. **역할에 정책이 붙어 있나** — `aws iam list-role-policies --role-name <역할>`. 비었으면 여기가 원인이다

4. **정책이 있는데도 거부되면 리소스 ARN 을 본다** — 인덱스를 쓰는데 `/index/*` 가 빠지면 테이블은 되고 인덱스만 막힌다. **부분적으로만 되는 실패**라 알아채기 어렵다

</Steps>

로그를 안 읽고 코드부터 보는 것이 가장 흔한 시간 낭비다. **함수는 자기가 왜 실패했는지 로그에 적어 둔다.**

**복구.** 코드가 실제 상태와의 차이를 메운다.

```bash
terraform plan
terraform apply
```

기대: `plan` 이 `aws_iam_role_policy` 하나를 `+ create` 로 잡는다. drift 복구다.

### 7-2. 함수가 아예 호출되지 않는다

**주입.** 예약 동시성을 0 으로 내린다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws lambda put-function-concurrency --function-name unicorn-get-booking-func --reserved-concurrent-executions 0
  aws lambda get-function-concurrency --function-name unicorn-get-booking-func --output json
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws lambda put-function-concurrency --function-name unicorn-get-booking-func --reserved-concurrent-executions 0
  aws lambda get-function-concurrency --function-name unicorn-get-booking-func --output json
  ```
  </TabItem>
</Tabs>

기대(주입 확인): `ReservedConcurrentExecutions` 가 `0`.

**증상.** 요청이 전부 실패하는데 **로그 그룹에 새 로그가 하나도 안 생긴다.** 7-1 과 증상이 겉으로 비슷하지만 결정적으로 다르다.

**좁히는 순서.**

<Steps>

1. **로그에 새 스트림이 생기나** — 호출한 뒤 로그 그룹을 본다. **새 로그가 아예 없으면 함수 안으로 못 들어간 것이다.** 7-1 은 들어가서 실패했으므로 로그가 남는다. 이 한 가지로 두 고장이 갈린다

2. **호출이 거부되고 있나** — `aws lambda invoke --function-name <함수> --payload '{}' out.json` 을 직접 던져 본다. `TooManyRequestsException` 이나 스로틀 관련 메시지가 오면 호출 단계에서 막힌 것이다

3. **동시성 설정** — `aws lambda get-function-concurrency --function-name <함수>`. `0` 이면 여기가 원인이다

4. 설정이 정상인데도 막히면 그때 호출하는 쪽(ALB 타깃 등록, 권한)을 본다

</Steps>

**복구.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws lambda delete-function-concurrency --function-name unicorn-get-booking-func
  aws lambda get-function-concurrency --function-name unicorn-get-booking-func --output json
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws lambda delete-function-concurrency --function-name unicorn-get-booking-func
  aws lambda get-function-concurrency --function-name unicorn-get-booking-func --output json
  ```
  </TabItem>
</Tabs>

기대: `ReservedConcurrentExecutions` 항목이 사라진다. 곧 정상으로 돌아온다.

**교훈.** **"로그가 있느냐 없느냐"가 진단의 첫 갈림이다.** 로그가 있으면 함수 안에서 실패한 것이라 권한·코드·데이터를 보고, 로그가 없으면 함수 밖에서 막힌 것이라 호출 경로·동시성·트리거를 본다. 이 둘을 구분하지 않으면 엉뚱한 계층을 뒤진다.

예약 동시성 0 은 실수로도 만들어진다 — 다른 함수에 동시성을 몰아 주다 보면 계정 한도가 남지 않아 같은 증상이 난다.
