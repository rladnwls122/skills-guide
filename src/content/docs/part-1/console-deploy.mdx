> 문서 유형: how-to

01~03 은 전부 코드로 만드는 훈련이다. 그런데 **대회 당일에 콘솔을 아예 안 쓰는 일은 없다.** 급히 한 번 고칠 때, Terraform 이 막혔을 때, 채점 직전 분 단위로 손볼 때 콘솔이 가장 빠르다.

문제는 그다음이다. 콘솔로 고친 뒤 `terraform plan` 을 돌리면 **되돌리려 든다.** 그때 무엇을 해야 하는지가 이 문서다.

:::note[클릭 순서는 적지 않는다]
콘솔 화면은 자주 바뀐다. 버튼 이름과 위치를 적어 두면 문서가 금방 낡는다.

대신 **무엇을 만들려는지**와 **만든 뒤 무엇을 확인하는지**를 적는다. 확인은 CLI 로 한다 — 채점도 CLI 로 하므로 같은 눈으로 보는 셈이다.
:::

## 1. 같은 리소스, 두 경로

VPC 하나를 콘솔로 만들고 [06 실습](/part-1/06-terraform-vpc/lab/)이 코드로 만든 것과 대조한다.

### 만들 것

CIDR `10.99.0.0/16` 짜리 VPC 하나. 이름 태그는 `console-lab-vpc` 로 둔다. **서브넷·게이트웨이는 만들지 않는다** — 마법사가 아니라 VPC 만 만드는 쪽을 고른다.

### 만든 뒤 확인

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" `
    --query "Vpcs[].{Id:VpcId,Cidr:CidrBlock,Tenancy:InstanceTenancy,Dns:IsDefault}" --output table
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" \
    --query 'Vpcs[].{Id:VpcId,Cidr:CidrBlock,Tenancy:InstanceTenancy,Dns:IsDefault}' --output table
  ```
  </TabItem>
</Tabs>

기대: VPC 하나가 표로 나온다.

### 코드로 만든 것과 무엇이 다른가

같은 조회를 [06](/part-1/06-terraform-vpc/lab/)의 VPC 에 걸어 비교하면, **리소스 자체는 구분이 안 된다.** 콘솔로 만들었다는 표시가 어디에도 없다.

차이는 리소스가 아니라 **기록**에 있다.

| | 콘솔로 만든 것 | 코드로 만든 것 |
|---|---|---|
| AWS 가 아는 것 | VPC 가 있다 | VPC 가 있다 (같다) |
| Terraform 이 아는 것 | **아무것도 모른다** | 상태 파일에 기록돼 있다 |
| 다시 만들 수 있나 | 사람이 같은 순서를 기억해야 한다 | `apply` 한 번 |
| 지울 때 | 사람이 찾아서 지운다 | `destroy` 가 챙긴다 |

**이 표가 이 문서의 전부다.** 콘솔이 나쁜 것이 아니라, 콘솔로 만든 것은 코드의 시야 밖에 있다는 사실이 뒤에서 문제를 만든다.

## 2. 콘솔이 몰래 만드는 것

VPC 하나를 만들었는데 실제로는 셋이 더 생겼다. 세어 본다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  $V = aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" --query "Vpcs[0].VpcId" --output text
  aws ec2 describe-route-tables --filters "Name=vpc-id,Values=$V" --query "RouteTables[].{Id:RouteTableId,Main:Associations[0].Main}" --output table
  aws ec2 describe-security-groups --filters "Name=vpc-id,Values=$V" --query "SecurityGroups[].{Id:GroupId,Name:GroupName}" --output table
  aws ec2 describe-network-acls --filters "Name=vpc-id,Values=$V" --query "NetworkAcls[].{Id:NetworkAclId,Default:IsDefault}" --output table
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  V=$(aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" --query 'Vpcs[0].VpcId' --output text)
  aws ec2 describe-route-tables --filters "Name=vpc-id,Values=$V" --query 'RouteTables[].{Id:RouteTableId,Main:Associations[0].Main}' --output table
  aws ec2 describe-security-groups --filters "Name=vpc-id,Values=$V" --query 'SecurityGroups[].{Id:GroupId,Name:GroupName}' --output table
  aws ec2 describe-network-acls --filters "Name=vpc-id,Values=$V" --query 'NetworkAcls[].{Id:NetworkAclId,Default:IsDefault}' --output table
  ```
  </TabItem>
</Tabs>

기대: 라우트 테이블 하나(메인), 보안 그룹 하나(`default`), 네트워크 ACL 하나(기본)가 각각 나온다. **아무것도 안 만들었는데 있다.**

### 무엇이 함께 사라지고 무엇이 남나

이 셋은 VPC 에 딸린 것이라 **VPC 를 지우면 함께 사라진다.** 그래서 이것들 자체는 잔존 리소스 문제가 아니다.

문제가 되는 것은 성격이 다른 셋이다.

| 콘솔이 만드는 것 | VPC 삭제 시 | 잔존 위험 |
|---|---|---|
| 메인 라우트 테이블 · 기본 보안 그룹 · 기본 NACL | 함께 사라진다 | 없다 |
| **Elastic IP** (NAT 마법사가 만든다) | **남는다** | **높다 — 안 붙어 있어도 과금** |
| **NAT 게이트웨이** | 먼저 지워야 VPC 가 지워진다 | 높다 — 시간당 과금 |
| **VPC 엔드포인트** | 먼저 지워야 한다 | 중간 |

**VPC 마법사를 쓰면 이 셋이 한꺼번에 생긴다.** 그래서 이 문서는 마법사가 아니라 VPC 만 만드는 쪽을 골랐다 — 무엇이 생기는지 세기 위해서다.

전체 점검은 [잔존 리소스 점검](/reference/cleanup-check/)이 훑는다. 콘솔로 만든 뒤에는 **그것을 반드시 한 번 돌린다** — 코드로 만든 것과 달리 `destroy` 가 챙겨 주지 않는다.

## 3. drift 판단

**이 절이 이 문서의 존재 이유다.**

코드로 만든 리소스를 콘솔에서 고치면 실제 상태와 코드가 어긋난다. 그것을 drift 라고 한다. `terraform plan` 이 그 차이를 발견하고 **되돌리려 든다.**

### 눈으로 본다

[06 실습](/part-1/06-terraform-vpc/lab/)의 `~/set07-lab` 이 서 있는 상태에서 한다. 콘솔에서 VPC 의 `Name` 태그를 아무 값으로나 바꾼 뒤 돌린다.

```bash
terraform plan
```

기대: `~ update in-place` 로 태그를 **원래 값으로 되돌리는** 계획이 나온다.

**Terraform 은 "지금 이렇게 되어 있다"를 존중하지 않는다.** 코드가 정본이고 실제는 코드를 따라와야 한다고 본다. 이것이 IaC 의 전제다.

### 선택지는 셋이다

| 선택 | 무엇을 하나 | 옳은 때 |
|---|---|---|
| **코드를 고친다** | 콘솔에서 바꾼 값을 코드에도 적는다 | **바꾼 것이 옳을 때.** 대부분 이쪽이다 |
| **되돌린다** | `terraform apply` 로 코드 상태로 밀어 버린다 | 콘솔 수정이 실수였을 때 |
| **가져온다(import)** | 코드에 없는 리소스를 상태에 등록한다 | **콘솔로 만든 것**을 앞으로 코드로 관리할 때 |
| **방치한다** | 아무것도 안 한다 | 그 리소스를 다시 apply 할 일이 없을 때 |

세 번째와 네 번째가 헷갈린다. 갈림은 **그 리소스가 코드에 있느냐**다.

- 코드에 있는데 값이 다르다 → 고치거나 되돌린다. import 는 필요 없다
- **코드에 아예 없다** → import 를 고민한다

### import 를 쓸 때와 안 쓸 때

Terraform 1.5 부터 `import` 블록을 코드에 적고 `plan` 이 코드를 대신 써 주게 할 수 있다.

```bash
terraform plan -generate-config-out=generated.tf
```

:::caution[도구가 스스로 실험적이라고 말한다]
`terraform plan -help` 의 이 플래그 설명에 **`(Experimental)`** 이 붙어 있다(Terraform 1.15.8 에서 확인). :badge[실측]{variant=note}

생성된 코드가 항상 그대로 쓸 수 있는 형태는 아니고, 손봐야 하는 경우가 있다. **대회 당일 처음 써 보는 실험적 기능에 기대는 것은 위험하다.**
:::

**대회에서 import 가 옳은 경우는 드물다.** 이유는 셋이다.

1. 시간이 든다. 리소스마다 주소와 ID 를 맞춰 줘야 한다
2. 채점은 **리소스가 있는지**를 보지 코드로 만들었는지를 보지 않는다
3. 남은 시간에 할 수 있는 더 점수 되는 일이 대개 있다

그래서 실전 판단은 이렇게 좁혀진다. **콘솔로 급히 만든 것은 그냥 두고, 코드로 관리할 것은 처음부터 코드로 만든다.** import 는 연습 때 구조를 이해하려고 해 보는 것이지 당일 도구가 아니다.

### 방치가 옳을 때가 있다

방치는 게으름이 아니라 선택이다. **그 리소스를 다시 `apply` 할 일이 없다면** 코드와 실제가 달라도 아무 문제가 없다.

위험한 것은 **잊고 있다가 나중에 `apply` 를 돌리는 것**이다. 그 순간 되돌아간다. 그래서 방치를 고를 때는 **`apply` 를 다시 안 돌린다는 것까지 함께 정한다.**

## 4. 판단표 — 콘솔이 옳은 때, 코드가 옳은 때

| 상황 | 고르는 쪽 | 이유 |
|---|---|---|
| 값 하나를 급히 고친다 | **콘솔** | 코드 고치고 plan 보고 apply 하는 시간이 더 든다 |
| 채점 직전 분 단위로 손본다 | **콘솔** | apply 가 다른 것까지 건드릴 위험이 있다 |
| Terraform 이 막혔다 | **콘솔** | 원인을 찾는 것보다 우회가 빠를 때가 있다 |
| 같은 것을 여러 개 만든다 | **코드** | 콘솔은 개수만큼 반복해야 한다 |
| 이름을 일괄로 바꾼다 | **코드** | 변수 하나로 끝난다 |
| 다시 만들 일이 있다 | **코드** | 콘솔은 순서를 사람이 기억해야 한다 |
| 지울 것이 많다 | **코드** | `destroy` 가 의존 순서를 챙긴다 |
| 채점이 값을 정확 비교한다 | **코드** | 오타가 나면 콘솔은 어디서 났는지 못 찾는다 |

### 한 줄로

**만들 때는 코드, 고칠 때는 콘솔, 지울 때는 코드다.**

만드는 것은 재현이 필요하고, 고치는 것은 속도가 필요하며, 지우는 것은 빠뜨리지 않는 것이 필요하기 때문이다.

다만 **콘솔로 고친 것은 반드시 기억해 둔다.** 그날 안에 `apply` 를 다시 돌릴 계획이 있으면 코드에도 같이 적는다.

## 정리

이 문서에서 만든 VPC 를 지운다. 콘솔로 만들었으므로 `destroy` 가 챙겨 주지 않는다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  $V = aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" --query "Vpcs[0].VpcId" --output text
  aws ec2 delete-vpc --vpc-id $V
  aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" --query "Vpcs[].VpcId" --output text
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  V=$(aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" --query 'Vpcs[0].VpcId' --output text)
  aws ec2 delete-vpc --vpc-id "$V"
  aws ec2 describe-vpcs --filters "Name=tag:Name,Values=console-lab-vpc" --query 'Vpcs[].VpcId' --output text
  ```
  </TabItem>
</Tabs>

기대: 마지막 조회가 빈 출력.

`DependencyViolation` 이 나오면 그 VPC 안에 아직 뭔가 있는 것이다. 서브넷·엔드포인트·게이트웨이를 먼저 지운다 — **의존 순서를 사람이 챙겨야 한다는 것**이 콘솔 경로의 비용이다.

계정 전체 점검은 [잔존 리소스 점검](/reference/cleanup-check/)이다.
