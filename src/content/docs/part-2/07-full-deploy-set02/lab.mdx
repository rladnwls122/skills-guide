## ① Terraform + 변수 영속화

```powershell
$env:AWS_DEFAULT_REGION = "ap-northeast-2"
$env:NUM = "103"                                  # 본인 비번호로 교체 (버킷/Grafana 계정에 쓰임)
cd terraform
terraform init
terraform apply -var "player_number=$env:NUM"
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

배포의 1단계다. 리전과 비번호를 환경 변수로 먼저 고정하는 이유는 뒤의 모든 리소스 이름과 Grafana 계정이 이 값을 쓰기 때문이다. `-var` 로 넘긴 비번호가 버킷 이름 접미사가 되므로, 값이 바뀌면 버킷이 새로 만들어진다.

</details>

이어서 [04 실습의 `.env.ps1` 영속화 블록](/part-2/04-eksctl-cluster/lab/)을 그대로 실행한다. 변수 21종(ACCOUNT_ID, VPC_ID, PRIV_SUBNET_C/D, CLUSTER_EXTRA_SG_ID, NODE_SG_ID, EKS_KMS_ARN, BOOK_APP/LBC/FLUENT_BIT_POLICY_ARN, ECR, APP_TG, GRAFANA_TG, BUCKET, ALB_DNS, GRAFANA_ALB_DNS, CF, GRAFANA_ADMIN_USER/PASSWORD 등)이 `..\.env.ps1` 로 저장되고, 이어지는 ②~⑨ 가 그 파일 하나로 변수를 복원한다.

**검증**: `terraform output` 에러 없음, `.env.ps1` 존재. 새 터미널에선 `. .\.env.ps1`만 재실행.

## ② 이미지 빌드 & push — **기본 CloudShell** (VPC CloudShell 불가 — 인터넷 없음)

콘솔 기본 CloudShell에서 Actions → Upload file로 `book`(shared\provided\task-1)과 `app\Dockerfile` 업로드 후:

```bash
export AWS_DEFAULT_REGION=ap-northeast-2
ECR=$(aws ecr describe-repositories --repository-names wskorea26-book-repo --query 'repositories[0].repositoryUri' --output text)
mkdir -p ~/build && mv ~/book ~/Dockerfile ~/build/ && cd ~/build
aws ecr get-login-password | docker login --username AWS --password-stdin "${ECR%/*}"
docker build -t "$ECR:stable" .
docker push "$ECR:stable"

# 스캔 대기 + Critical/High 0 확인 (mark 3-1)
aws ecr wait image-scan-complete --repository-name wskorea26-book-repo --image-id imageTag=stable || \
  { aws ecr start-image-scan --repository-name wskorea26-book-repo --image-id imageTag=stable; \
    aws ecr wait image-scan-complete --repository-name wskorea26-book-repo --image-id imageTag=stable; }
aws ecr describe-image-scan-findings --repository-name wskorea26-book-repo --image-id imageTag=stable \
  --query 'imageScanFindings.findingSeverityCounts'
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

이미지 빌드는 인터넷이 있는 **기본 CloudShell** 에서 한다. ECR 주소는 조회해서 받고, 업로드한 파일을 한 폴더로 모아 빌드·푸시한다. 스캔 확인 줄의 `||` 뒤가 보험이다 — 스캔이 아직 시작되지 않아 `wait` 가 실패하면 직접 스캔을 걸고 다시 기다린다.

</details>

**검증**: 출력에 `CRITICAL`/`HIGH` 키가 **없어야** 함. High가 나오면 Dockerfile에 `RUN apk upgrade --no-cache` 추가 후 재빌드/재푸시.

:::danger[빌드 위치]
VPC CloudShell은 홈 디렉터리가 비영속이고 업로드/다운로드 메뉴를 쓸 수 없다. 이미지 빌드는 **기본 CloudShell**에서.
:::

## ⑧ 검증 시드 (CloudFront Deployed 대기 후)

```powershell
$CF_ID = aws cloudfront list-distributions `
  --query "DistributionList.Items[?Comment=='wskorea26-concert-cf'].Id | [0]" --output text
aws cloudfront wait distribution-deployed --id "$CF_ID"     # mark 8-1이 Deployed 검사

curl.exe -o NUL -s -w "%{http_code}`n" "https://$env:CF"                 # 200
curl.exe -o NUL -s -w "%{http_code}`n" "http://$env:CF/"                 # 301
curl.exe -o NUL -s -w "%{size_download}`n" "https://$env:CF/main.jpeg"   # 180926
curl.exe -o NUL -s -w "%{http_code}`n" "http://$env:ALB_DNS/book"        # 403

curl.exe -s -X POST -H "Content-Type: application/json" `
  -d '{"client_id":"T0001","username":"tester","email":"t@t.com","concert_name":"SEED_CON"}' `
  "https://$env:CF/book"                                                 # {"booking_id": "..."}
curl.exe -s "https://$env:CF/book?concert_name=SEED_CON"                 # 최신순 배열
curl.exe -o NUL -s -w "%{http_code}`n" "https://$env:CF/book"            # 400
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

CloudFront 가 배포 완료될 때까지 기다린 뒤 경로별 기대값을 한 번에 훑는다. https 200, http 301, 이미지 크기, ALB 직접 접근 403 을 먼저 보고, 그다음 POST 로 예매를 하나 만들고 GET 으로 최신순 조회가 되는지, 본문 없는 POST 가 400 인지 확인한다. 하나라도 다르면 다음 단계로 넘어가지 않는다 — 여기서 걸러야 채점 때 원인을 찾는 시간이 없다.

</details>

:::caution
주석의 기대값과 하나라도 다르면 여기서 멈추고 원인 추적 (아래 함정 표). 다음 단계로 넘어가지 않는다.
:::

## ⑨ 채점 — CloudShell VPC Environment

콘솔에서 VPC Environment 생성: **Subnet `wskorea26-priv-subnet-d` + SG `wskorea26-vpc-environment-sg`** (채점 항목 0). 파일 업로드가 안 되므로 mark.sh는 **heredoc 붙여넣기**:

:::danger[`rm -rf ~/.aws` 는 되돌릴 수 없다]
다음 블록의 첫 줄은 그 셸의 자격증명 설정을 통째로 지운다. 실행하기 **전에** 액세스 키 ID 와 시크릿 액세스 키를 손에 들고 있어야 한다 — 시크릿 키는 발급 화면을 벗어나면 다시 볼 수 없고, 없으면 IAM 에서 새 키를 만들어야 한다. 지운 뒤 `aws configure` 를 못 채우면 채점 셸에서 아무 명령도 안 나간다.

CloudShell 홈은 세션마다 초기화되므로 이 삭제가 본 PC 의 `~/.aws` 를 건드리지는 않는다. 그래도 명령을 본 PC 터미널에 잘못 붙여넣지 않도록 셸을 먼저 확인한다.
:::

```bash
rm -rf ~/.aws && aws configure          # default region: ap-northeast-2
cat > ~/mark.sh <<'MARKEOF'
# ← 본 PC의 mark.sh 내용 전체를 그대로 붙여넣기
MARKEOF
chmod +x ~/mark.sh && ~/mark.sh
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

VPC CloudShell 에는 파일 업로드 메뉴가 없으므로 heredoc 으로 채점 스크립트를 붙여넣는다. 앞의 `rm -rf ~/.aws && aws configure` 는 신원을 배포자와 같게 맞추는 단계다 — 생성자와 채점 신원이 다르면 클러스터 접근부터 막힌다.

</details>

**통과 기준: 자동 채점 80% 이상** (30점 만점 기준 24점+; 10번 Monitoring 3.5점은 수동 — Grafana 접속·패널로 셀프 확인).

## ⑩ 정리 (순서 엄수)

:::danger[순서 엄수]
helm → eksctl → DynamoDB 삭제방지 해제 → `terraform destroy`. 순서를 바꾸면 destroy 가 중간에 막힌다.
:::

```powershell
helm -n monitoring uninstall wskorea26-monitoring
helm -n kube-system uninstall aws-load-balancer-controller
eksctl delete cluster -f eksctl/cluster.rendered.yaml --disable-nodegroup-eviction
aws dynamodb update-table --table-name wskorea26-data-table --no-deletion-protection-enabled
cd terraform; terraform destroy -var "player_number=$env:NUM"
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

정리는 만든 역순이다. helm 릴리스 → 클러스터 → 삭제방지 해제 → `terraform destroy` 순서를 지켜야 한다. 순서를 바꾸면 destroy 가 중간에 막힌다 — LBC 가 만든 리소스가 남아 서브넷이 안 지워지거나, 삭제방지가 걸린 DynamoDB 에서 멈춘다.

</details>

**검증**: destroy 완료 + 콘솔에서 EKS/ALB/NAT/CloudFront 잔존 0.
