> 문서 유형: tutorial

원리와 채점 관점은 [09 이론 — eksctl ClusterConfig](/part-2/09-eksctl-cluster/theory/)에 있다.

**방식**: set-02 의 클러스터가 선 상태에서 시작한다. set-07 변동 과제지를 읽고 **절차 안내 없이 직접** 고친 뒤, 통과 기준으로 스스로 판정한다. 배포한 다음에는 값을 잘못 읽었을 때의 복구와 고장 진단까지 간다.

클러스터는 한 번 만들면 약 20분이 묶인다. 그래서 이 모듈에서 진짜로 익힐 것은 YAML 을 빨리 쓰는 속도가 아니라 **`create` 를 누르기 전에 무엇을 확인하는가**, 그리고 **잘못 만든 뒤에 고쳐서 살릴 수 있는 값인지 판정하는 법**이다.

## 실습 목표

- [ ] 컨트롤 플레인을 외부에서 못 닿게 하고, 그 결과 본 PC 의 `kubectl` 이 끊긴다는 사실을 스스로 마주한다
- [ ] IRSA 를 Pod Identity 로 바꾼다 — 애드온 하나가 함께 따라온다
- [ ] 프라이빗 서브넷 3 AZ, 노드 볼륨 CMK 암호화, 노드 시간대 KST 를 반영한다
- [ ] 라벨 키를 바꿀 때 따라오는 자리를 전부 센다
- [ ] `${VAR}` 잔존 0건과 `--dry-run` 통과를 만든 뒤에만 `create` 를 누른다
- [ ] 만들어 놓고 값을 잘못 읽은 것을 발견했을 때, 수정 API 가 있는지로 판정한다
- [ ] 파드가 안 뜨거나 AWS 호출이 거부될 때 계층을 좁혀 원인을 짚는다

선행 지식과 목표는 [모듈 개요](/part-2/09-eksctl-cluster/)에.

:::note[실전 참조 — 막히면 여는 곳]
- ClusterConfig 필드 이름: `eksctl utils schema` 출력, 브라우저는 [schema.eksctl.io](https://schema.eksctl.io/)
- private 클러스터 스키마: 위 목록의 `privateCluster` 항목 — `clusterEndpoints` 와 어느 쪽을 쓰는지 확인한다
- 애드온의 default 버전: `eksctl utils describe-addon-versions --kubernetes-version 1.35 --name <addon>`
- CLI 출력 필드: `aws eks describe-cluster help` · `aws eks describe-nodegroup help` · `aws eks list-pod-identity-associations help`
- 노드 배치를 보는 YAML 필드: `kubectl explain pod.spec.nodeSelector` · `kubectl explain node.metadata.labels`
- 찾는 법 자체가 막히면 [실전 문서 검색 가이드](/reference/search-guide/)
:::

## 1. 변동 과제지

set-07 요구다. **정답 `cluster.yaml` 을 먼저 열지 않는다.**

| 항목 | set-02 (기준본) | set-07 (변동) |
|---|---|---|
| 클러스터 이름 | `wskorea26-cluster` | `unicorn-eks-cluster` |
| 컨트롤 플레인 접근 | 퍼블릭·프라이빗 둘 다 열림 | **외부에서 닿으면 안 된다** |
| 파드 자격증명 | OIDC 로 위임 | **EKS 가 직접 중계** |
| 프라이빗 서브넷 | 2개 (c, d) | 3개 (a, b, c) |
| 노드 라벨 | `node-type: addon\|app` | `unicorn: addon\|app` |
| EC2 인스턴스 Name | `wskorea26-{addon,app}-node` | `unicorn-k8snode-{addon,app}-node` |
| Secret 암호화 키 | EKS 전용 키 | 플랫폼 공용 CMK |
| 노드 볼륨 암호화 | 켜짐(기본 키) | **플랫폼 공용 CMK 로** |
| 노드 시간대 | 기본(UTC) | **KST** |
| 애드온 버전 | 미지정 | 전부 고정 |
| 블록 스토리지 | 없음 | 워크로드가 EBS 볼륨을 쓴다 |

이 표는 요구를 옮긴 것이지 고칠 자리를 알려 주는 것이 아니다. 어느 필드인지는 직접 찾는다.

### 요구에서 파생되는 것

과제지는 결과만 적는다. 거기서 따라 나오는 것을 읽어 내는 것이 이 절의 훈련이다. 세 가지가 특히 그렇다.

**컨트롤 플레인이 외부에서 닿으면 안 된다**는 요구는 필드 하나로 끝나지 않는다. 그렇게 만드는 순간 본 PC 의 `kubectl` 이 API 서버에 못 닿는다. 클러스터를 만든 다음 무엇으로 조작할지를 **만들기 전에** 정해 둬야 한다. 5절에서 이 문제를 실제로 만난다.

**파드 자격증명을 EKS 가 직접 중계**하게 하면 애드온 하나가 필수로 따라온다. 그것이 없으면 연결을 걸어도 파드는 자격증명을 못 받고, 증상이 코드 오류처럼 보인다. [09 이론 2절](/part-2/09-eksctl-cluster/theory/)이 두 방식을 대조한다.

**워크로드가 EBS 볼륨을 쓴다**는 것도 애드온 요구다. set-02 는 이 애드온을 일부러 뺐고 그 이유가 있었다. set-07 에도 그 이유가 그대로 있는지 확인하고 판단한다.

## 2. 이행 (타이머 25분)

타이머를 걸고 시작한다. 아래는 절차가 아니라 **스스로 답해야 할 질문 목록**이다. 답은 적지 않는다.

- 컨트롤 플레인을 닫는 필드는 `vpc.clusterEndpoints` 인가, 다른 최상위 블록인가? 둘을 함께 쓰면 어떻게 되나
- 프라이빗 서브넷이 셋이 되면 `vpc.subnets.private` 의 키 이름과 `az` 값은 어디서 오나. `.env.ps1` 에 그 값이 이미 있나
- 라벨 키를 바꾸면 이 파일 안에서 고칠 자리가 몇 군데인가 — [09 이론 3절](/part-2/09-eksctl-cluster/theory/)의 확인 블록이 세는 법을 보여 준다
- EC2 인스턴스 Name 태그를 지정하는 필드와 `describe-nodegroup` 의 `tags.Name` 을 만드는 필드는 같은가. set-07 채점은 어느 쪽을 보나
- 노드 볼륨을 특정 CMK 로 암호화하는 필드 이름은 무엇인가. `volumeEncrypted` 만으로 되나
- 모든 노드의 시간대를 바꾸려면 노드 부팅 때 명령을 넣어야 한다. 그 필드는 무엇이고, 노드그룹 둘에 같은 내용을 두 번 쓰지 않는 YAML 문법은 무엇인가
- 애드온 버전을 고정하려면 그 버전 문자열을 어디서 얻나

새로 쓰는 파일이 아니라 `cluster.yaml` 사본을 고친다. 원본을 직접 건드리지 않는다.

2. **`${VAR}` 치환 누락 0건**

   치환한 뒤 검사한다. set-07 은 참조하는 리소스가 늘어 변수 이름 목록 자체가 바뀐다 — `.env.ps1` 에 없는 변수를 쓰면 조용히 빈 문자열이 된다.

     </TabItem>

     </TabItem>
   </Tabs>

   기대: **출력 없음.**

3. **`--dry-run` 통과**

   ```bash
   eksctl create cluster -f cluster.rendered.yaml --dry-run
   ```

   기대: eksctl 이 기본값을 채운 ClusterConfig 가 나오고 에러가 없다. 아무것도 만들지 않는다.

   `mutually exclusive` 나 `unknown field` 가 나오면 2절의 첫 질문으로 돌아간다 — 컨트롤 플레인을 닫는 두 방식을 겹쳐 쓴 것이다.

</Steps>

## 4. 복기

[set-07 `eksctl/cluster.yaml`](https://github.com/ishs-cloud-computing/skills-2026/blob/main/set-07/task-1/eksctl/cluster.yaml)과 대조한다. **3절을 통과한 뒤에 연다.**

놓친 곳을 셋으로 나눈다.

- **과제지를 못 읽은 것** — 요구가 있는 줄 몰랐다. 다음엔 과제지를 표로 옮기고 시작한다
- **읽었는데 어디를 고칠지 못 찾은 것** — 필드 이름을 몰랐다. `eksctl utils schema` 로 찾는 연습이 부족한 것이다
- **찾았는데 틀린 것** — 문법이나 값이 어긋났다. `--dry-run` 이 잡아 주는 종류인지 확인한다

셋의 처방이 다르므로 뭉뚱그리지 않는다.

## 5. 배포와 채점 확인

이행본을 실제로 올린다. 6·7절이 배포된 상태를 전제한다.

```bash
eksctl create cluster -f cluster.rendered.yaml
```

기대(말미): `EKS cluster "unicorn-eks-cluster" in "ap-northeast-2" region is ready`. **약 20분**이 걸린다.

기다리는 동안 CloudFormation 콘솔에서 `eksctl-unicorn-eks-cluster-cluster` → `-addon-...` → `-nodegroup-...` 스택 순서를 관찰해 둔다. 어느 스택에서 멈추는지가 곧 원인의 계층이다.

:::danger[생성 실패 후 같은 이름으로 재시도할 때]
`eksctl create cluster` 가 실패하면 CloudFormation 스택이 `ROLLBACK_COMPLETE` 로 남는다. 이 상태의 스택은 갱신이 안 되므로, 같은 이름으로 다시 만들면 `AlreadyExistsException` 이나 `stack ... is in ROLLBACK_COMPLETE state` 로 즉시 막힌다. 지우고 다시 만든다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws cloudformation describe-stacks `
    --query "Stacks[?starts_with(StackName,'eksctl-unicorn-eks-cluster')].[StackName,StackStatus]" --output text
  eksctl delete cluster --name unicorn-eks-cluster --disable-nodegroup-eviction --wait
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws cloudformation describe-stacks \
    --query "Stacks[?starts_with(StackName,'eksctl-unicorn-eks-cluster')].[StackName,StackStatus]" --output text
  eksctl delete cluster --name unicorn-eks-cluster --disable-nodegroup-eviction --wait
  ```
  </TabItem>
</Tabs>

`eksctl delete` 가 남은 스택까지 지운다. 그래도 스택이 남으면 콘솔에서 해당 스택을 직접 삭제한 뒤 재시도한다. 삭제 확인 없이 `create` 를 다시 던지면 또 20분을 버린다.
:::

### 여기서 `kubectl` 이 끊긴다

컨트롤 플레인을 닫았으므로 본 PC 에서 `kubectl get nodes` 가 응답하지 않는다. 1절에서 예고한 파생 결과다. 채점도 CloudShell 에서 이뤄지므로 이 상태가 정상이다.

정답지는 SSM 으로 접속하는 작업용 EC2 를 임시로 세워 거기서 `kubectl`·`helm` 을 돌린다. 절차는 [set-07 `task-1/README.md`](https://github.com/ishs-cloud-computing/skills-2026/blob/main/set-07/task-1/README.md) 의 `3) 작업용 SSM bastion 생성` 과 `4) 도구 설치·자격증명·파일 수신·환경 변수` 에 있다. 그대로 따르고, 이후 절의 `kubectl` 은 전부 거기서 실행한다.

**이 EC2 는 작업용이라 채점 전에 지워야 한다.** 과제지 유의사항의 불필요 리소스 감점 대상이다.

### 채점 명령으로 확인

`aws` 계열은 본 PC 에서도 된다. `kubectl` 계열만 bastion 에서 돌린다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws eks describe-cluster --name unicorn-eks-cluster `
    --query "cluster.resourcesVpcConfig.[endpointPublicAccess, endpointPrivateAccess]" --output text
  aws ec2 describe-instances `
    --filters Name=tag:Name,Values=unicorn-k8snode-app-node Name=instance-state-name,Values=running `
    --query "Reservations[].Instances[].PublicIpAddress" --output json
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws eks describe-cluster --name unicorn-eks-cluster \
    --query "cluster.resourcesVpcConfig.[endpointPublicAccess, endpointPrivateAccess]" --output text
  aws ec2 describe-instances \
    --filters Name=tag:Name,Values=unicorn-k8snode-app-node Name=instance-state-name,Values=running \
    --query "Reservations[].Instances[].PublicIpAddress" --output json
  ```
  </TabItem>
</Tabs>

기대: 첫 명령이 `False True`, 둘째가 **빈 배열** `[]`. 둘째에 IP 가 찍히면 노드가 퍼블릭 서브넷에 떴거나 퍼블릭 IP 자동 할당이 켜진 것이다.

## 6. 과제지 오독 복구

이행을 마치고 만들기까지 했는데 과제지를 다시 읽어 보니 값이 다르다. 물어야 할 것은 하나다 — **고쳐서 살리나, 부수고 다시 만드나.**

06 실습에서는 `terraform plan` 의 `# forces replacement` 가 답을 줬다. eksctl 에는 그 출력이 없다. 대신 **그 값을 바꾸는 API 가 존재하는지**로 판정한다.

| 판정 | 무엇으로 아나 | 비용 |
|---|---|---|
| 즉시 수정 | `aws eks update-*` 에 해당 옵션이 있다 | 초~분 |
| 짝이 있는 수정 | 수정 API 는 있는데 다른 리소스가 같은 값을 참조한다 | 분 — 짝을 못 세면 더 |
| 노드그룹 교체 | 노드그룹만 지우고 다시 만든다 | 분 |
| 클러스터 재생성 | `create` 외에 방법이 없다 | 처음 만든 시간이 그대로 다시 든다 |

판정은 추측으로 하지 않는다. `aws eks update-cluster-config help` 와 `aws eks update-nodegroup-config help` 가 **무엇을 받는지**가 곧 판정 근거다.

### 6-1. 컨트롤 플레인을 닫는 것을 빼먹었다

**상황.** 이름과 서브넷은 다 맞췄는데 엔드포인트를 기준본 그대로 두어 퍼블릭이 열린 채로 만들었다. 채점 `6-1-A` 가 `True True` 를 뱉는다.

**판정.**

```bash
aws eks update-cluster-config help
```

`--resources-vpc-config` 가 `endpointPublicAccess` · `endpointPrivateAccess` 를 받는다. **수정 API 가 있다 → 즉시 수정**이다.

**복구.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws eks update-cluster-config --name unicorn-eks-cluster `
    --resources-vpc-config endpointPublicAccess=false,endpointPrivateAccess=true
  aws eks describe-cluster --name unicorn-eks-cluster --query "cluster.status" --output text
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws eks update-cluster-config --name unicorn-eks-cluster \
    --resources-vpc-config endpointPublicAccess=false,endpointPrivateAccess=true
  aws eks describe-cluster --name unicorn-eks-cluster --query "cluster.status" --output text
  ```
  </TabItem>
</Tabs>

기대: 클러스터가 잠깐 `UPDATING` 이 됐다가 `ACTIVE` 로 돌아온다. 노드는 그대로 살아 있다.

**파급.** 리소스는 하나도 안 죽지만 **네가 죽는다.** 이 명령이 끝나는 순간 지금 쓰던 `kubectl` 이 끊긴다. bastion 을 먼저 세워 두지 않았으면 클러스터 안을 볼 방법이 없어진다.

**교훈.** 싼 수정이라고 순서가 자유로운 것은 아니다. **접근 경로를 끊는 변경은 대체 경로를 먼저 만들고 실행한다.**

### 6-2. 라벨 키를 기준본 그대로 뒀다

**상황.** 노드그룹 `labels` 를 `node-type` 으로 둔 채 만들었다. 채점 `6-2-A` 가 `unicorn=app` 노드를 못 찾아 빈 출력을 낸다.

**판정.**

```bash
aws eks update-nodegroup-config help
```

`--labels` 가 `addOrUpdateLabels` · `removeLabels` 를 받는다. 노드그룹을 지우지 않고 고칠 수 있다.

**복구.** 노드그룹 둘 다에 건다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws eks update-nodegroup-config --cluster-name unicorn-eks-cluster `
    --nodegroup-name unicorn-app-ng `
    --labels "addOrUpdateLabels={unicorn=app},removeLabels=node-type"
  kubectl get nodes -l unicorn=app --no-headers
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws eks update-nodegroup-config --cluster-name unicorn-eks-cluster \
    --nodegroup-name unicorn-app-ng \
    --labels "addOrUpdateLabels={unicorn=app},removeLabels=node-type"
  kubectl get nodes -l unicorn=app --no-headers
  ```
  </TabItem>
</Tabs>

기대: 앱 노드 두 대가 나온다.

**파급.** 여기서 끝내면 다음 날 파드가 안 뜬다. **라벨은 짝이 있는 값이다.** 이 클러스터에서 같은 키를 참조하는 자리를 전부 센다.

- 노드그룹 둘의 `labels` — 방금 고쳤다
- coredns 애드온의 `configurationValues` 안 `nodeSelector`
- [10](/part-2/10-k8s-workloads-alb/lab/)의 앱 Deployment `nodeSelector`
- 모니터링 스택의 `nodeSelector` 값들

노드 쪽만 고치면 파드가 옛 키를 찾다 `Pending` 으로 남는다. 증상이 나오는 곳과 원인이 있는 곳이 멀어서, 7절이 이 경우를 따로 다룬다.

**교훈.** 수정 API 가 있다고 값이 싼 것은 아니다. **그 값을 참조하는 곳의 개수가 진짜 비용이다.**

### 6-3. Secret 암호화 키를 기준본 것으로 뒀다

**상황.** `secretsEncryption.keyARN` 을 기준본의 EKS 전용 키로 둔 채 만들었다. 과제지는 플랫폼 공용 CMK 를 요구한다.

**판정.** 앞의 둘과 다르게 접근한다. `aws eks update-cluster-config` 에는 암호화 옵션이 없다. 암호화를 다루는 명령은 따로 있다.

```bash
aws eks associate-encryption-config help
```

이름이 `associate` 이지 `update` 가 아니다. **없는 것을 붙이는 명령이고, 이미 붙은 키를 다른 키로 바꾸거나 떼는 API 는 없다.** 판정 표의 마지막 칸이다.

**복구.** 클러스터를 지우고 다시 만든다.

```bash
eksctl delete cluster --name unicorn-eks-cluster --disable-nodegroup-eviction --wait
eksctl create cluster -f cluster.rendered.yaml
```

처음 만든 시간이 그대로 다시 든다. 05 에서 올린 워크로드도 전부 같이 죽는다.

**교훈.** 06 실습의 VPC CIDR 과 같은 자리다. **되돌리는 시간이 처음부터 다시 만드는 시간과 같은 값**이 이 모듈에도 있다.

이 클러스터에서 그런 값은 셋이다 — **클러스터 이름, 리전, Secret 암호화 키.** 과제지를 받으면 이 셋부터 확정하고 시작한다. 나머지는 만들고 나서도 고칠 수 있다.

## 7. 장애 진단

정상으로 선 상태에서 일부러 고장을 내고 증상만 보고 좁혀 간다. **주입 명령과 복구 명령이 짝으로 있다** — 주입만 하고 덮어 두지 않는다.

명령은 전부 bastion 에서 실행한다.

### 7-1. 파드가 Pending 에서 안 움직인다

**주입.** addon 노드 한 대에서 라벨을 뗀다. 6-2 가 코드에서 만든 상황을 손으로 재현하는 것이다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  $node = kubectl get nodes -l unicorn=addon -o jsonpath='{.items[0].metadata.name}'
  kubectl label node $node unicorn-
  kubectl delete pod -n kube-system -l k8s-app=kube-dns
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  node=$(kubectl get nodes -l unicorn=addon -o jsonpath='{.items[0].metadata.name}')
  kubectl label node "$node" unicorn-
  kubectl delete pod -n kube-system -l k8s-app=kube-dns
  ```
  </TabItem>
</Tabs>

**증상.** coredns 파드 일부가 `Pending` 에 머문다. 클러스터 안의 이름 해석이 흔들리기 시작하므로 다른 서비스에서 먼저 티가 나기도 한다.

**좁히는 순서.** 위에서 아래로, 한 계층씩만 본다.

<Steps>

1. **파드가 왜 안 뜨는지 파드에게 묻는다** — `kubectl describe pod <name> -n kube-system`. 맨 아래 `Events` 가 이유를 글자로 말한다. `didn't match Pod's node affinity/selector` 면 스케줄 조건 문제이고, `Insufficient cpu` 면 자원 문제다. **여기서 갈래가 갈리므로 이 줄을 먼저 읽는다**

2. **파드가 요구하는 조건** — `kubectl get pod <name> -n kube-system -o jsonpath='{.spec.nodeSelector}'`

3. **그 조건을 만족하는 노드가 있나** — `kubectl get nodes -l <키>=<값>`. 빈 출력이면 원인은 노드 쪽이다

4. **노드의 실제 라벨** — `kubectl get nodes --show-labels`. 여기서 라벨이 빠진 노드가 보인다

</Steps>

`describe` 를 건너뛰고 노드부터 보는 것이 가장 흔한 시간 낭비다. **파드는 자기가 왜 못 떴는지 이미 알고 있고 `Events` 에 적어 둔다.**

**복구.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl label node $node unicorn=addon
  kubectl get pod -n kube-system -l k8s-app=kube-dns -o wide
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl label node "$node" unicorn=addon
  kubectl get pod -n kube-system -l k8s-app=kube-dns -o wide
  ```
  </TabItem>
</Tabs>

기대: 몇 초 안에 `Running` 으로 바뀌고 addon 노드에 배치된다.

증상별 처방 목록은 [트러블슈팅](/reference/troubleshooting/)에 있다.

### 7-2. 파드는 떴는데 AWS 호출이 거부된다

**주입.** 앱의 Pod Identity 연결을 끊는다. `<association-id>` 는 첫 명령이 알려준다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws eks list-pod-identity-associations --cluster-name unicorn-eks-cluster --namespace unicorn `
    --query "associations[].[serviceAccount,associationId]" --output text
  aws eks delete-pod-identity-association --cluster-name unicorn-eks-cluster --association-id <association-id>
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws eks list-pod-identity-associations --cluster-name unicorn-eks-cluster --namespace unicorn \
    --query "associations[].[serviceAccount,associationId]" --output text
  aws eks delete-pod-identity-association --cluster-name unicorn-eks-cluster --association-id <association-id>
  ```
  </TabItem>
</Tabs>

**증상.** 파드는 `Running` 이다. 그런데 앱 로그에 `AccessDenied` 나 `is not authorized to perform` 이 찍히고, 앱을 호출하면 500 이 돌아온다. **파드 상태만 보면 정상이라 코드를 의심하게 되는 것이 이 고장의 함정이다.**

**좁히는 순서.**

<Steps>

1. **에러 문자열을 그대로 읽는다** — `kubectl logs -n unicorn -l app --tail=50`. `AccessDenied` 계열이면 코드가 아니라 신원 문제다. 여기서 방향이 정해진다

2. **파드가 어떤 신원으로 도는가** — `kubectl get pod -n unicorn <name> -o jsonpath='{.spec.serviceAccountName}'`

3. **그 서비스 계정에 연결이 걸려 있나** — `aws eks list-pod-identity-associations --cluster-name unicorn-eks-cluster --namespace unicorn`. 목록에 없으면 여기가 원인이다

4. **연결은 있는데도 거부되면** 그때 역할의 정책과 신뢰 관계로 내려간다 — `aws iam get-role --role-name <역할>`

</Steps>

**복구.** 지운 연결을 다시 만든다. `<role-arn>` 은 Terraform 이 만든 것이라 `terraform output` 에 있다.

```bash
aws eks create-pod-identity-association --cluster-name unicorn-eks-cluster \
  --namespace unicorn --service-account unicorn-book-app-sa --role-arn <role-arn>
```

기대: `associationId` 가 돌아온다. 파드는 다음 자격증명 갱신부터 정상이므로, 급하면 `kubectl delete pod -n unicorn -l app` 으로 다시 띄운다.

**교훈.** 증상이 앱에서 나와도 원인이 앱에 없을 수 있다. **`AccessDenied` 는 코드 버그가 아니라 신원 배선 문제라는 신호다.** 이 순서를 몸에 익혀 두면 코드를 읽는 데 시간을 버리지 않는다.

## 8. 정리

:::caution[05 로 바로 이어 간다면]
클러스터를 남긴다. 다시 만드는 데 20분이 들기 때문이고, 이것은 [잔존 리소스 점검](/reference/cleanup-check/)의 destroy 방침에 대한 명시적 예외다. 이어 가지 않으면 아래를 돌린다.
:::

작업용 bastion 을 먼저 지운다. 클러스터보다 먼저다 — 클러스터를 지우고 나면 접속할 이유가 없어지는데 잊어버리기 쉽다.

```bash
eksctl delete cluster -f cluster.rendered.yaml --disable-nodegroup-eviction
```

기대: 스택 삭제가 순서대로 돈다.

`eksctl delete` 가 끝났다고 다 지워졌다고 믿지 않는다. 남은 스택을 직접 센다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws cloudformation describe-stacks `
    --query "Stacks[?starts_with(StackName,'eksctl-unicorn-eks-cluster')].[StackName,StackStatus]" --output text
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws cloudformation describe-stacks \
    --query "Stacks[?starts_with(StackName,'eksctl-unicorn-eks-cluster')].[StackName,StackStatus]" --output text
  ```
  </TabItem>
</Tabs>

기대: 빈 출력. `DELETE_FAILED` 로 남은 스택이 있으면 콘솔에서 직접 지운다.

Terraform 리소스(VPC·NAT 등)는 PART-2 를 끝낼 때까지 남겨도 되지만 NAT 는 시간당 과금이다. 그날을 끝냈으면 함께 지운다.

막히면 [트러블슈팅](/reference/troubleshooting/), 계정 전체 점검은 [잔존 리소스 점검](/reference/cleanup-check/)이다.
