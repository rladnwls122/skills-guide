실습 A는 IAM만 사용(무료, 클러스터 불필요) — 반드시 수행.

## 목표 체크박스

- [ ] `:root` trust + ExternalId 조건의 audit role을 CLI로 생성
- [ ] 권한 없는 사용자로 assume **실패**(trust 통과해도 identity policy에서 거부) 재현
- [ ] 권한 있는 사용자로 ExternalId 없이 assume **실패**, ExternalId 붙여 **성공** 재현
- [ ] assume한 세션으로 허용 액션 성공 / 미허용 액션 거부 확인
- [ ] (B) private 엔드포인트 상태 확인·재차단 명령 수행
- [ ] (B) VPC CloudShell(또는 bastion) 멱등 셋업 블록 1회 왕복
- [ ] (B) CoreDNS 커스텀 도메인 양쪽 적용 확인

## 실습 A. Audit Role — assume 성공/실패 양쪽 재현

셸: 본 PC bash (admin 자격증명). `NUM`은 선수등번호 가정.

<Steps>

1. **A-1) 역할 생성** (`:root` trust + ExternalId + 3600초)

   ```bash
   export NUM=00
   ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
   EXT_ID="unicorn-audit-2026$NUM"

   cat > /tmp/audit-trust.json <<EOF
   {
     "Version": "2012-10-17",
     "Statement": [{
       "Effect": "Allow",
       "Principal": { "AWS": "arn:aws:iam::$ACCOUNT_ID:root" },
       "Action": "sts:AssumeRole",
       "Condition": { "StringEquals": { "sts:ExternalId": "$EXT_ID" } }
     }]
   }
   EOF
   aws iam create-role --role-name lab-audit-role \
     --assume-role-policy-document file:///tmp/audit-trust.json \
     --max-session-duration 3600

   # 권한: 좁힐 수 있는 것(eks:DescribeCluster)은 분리, ec2:DescribeVpcs는 ARN 미지원이라 "*" 불가피
   cat > /tmp/audit-policy.json <<EOF
   {
     "Version": "2012-10-17",
     "Statement": [
       { "Sid": "DescribeVpcs", "Effect": "Allow", "Action": "ec2:DescribeVpcs", "Resource": "*" },
       { "Sid": "DescribeCluster", "Effect": "Allow", "Action": "eks:DescribeCluster",
         "Resource": "arn:aws:eks:ap-northeast-2:$ACCOUNT_ID:cluster/*" }
     ]
   }
   EOF
   aws iam put-role-policy --role-name lab-audit-role --policy-name lab-audit-policy \
     --policy-document file:///tmp/audit-policy.json
   ROLE_ARN="arn:aws:iam::$ACCOUNT_ID:role/lab-audit-role"
   ```

2. **A-2) 실패 케이스 1 — 호출자 identity policy 부재** (이중 평가)

   ```bash
   # 정책이 하나도 없는 사용자 생성
   aws iam create-user --user-name lab-no-perm
   read -r AK SK <<< $(aws iam create-access-key --user-name lab-no-perm \
     --query 'AccessKey.[AccessKeyId,SecretAccessKey]' --output text)

   # 그 사용자로 assume 시도 — trust는 :root라 계정 내 전원이 '후보'지만…
   AWS_ACCESS_KEY_ID=$AK AWS_SECRET_ACCESS_KEY=$SK AWS_SESSION_TOKEN= \
     aws sts assume-role --role-arn "$ROLE_ARN" --role-session-name lab --external-id "$EXT_ID"
   ```

   **기대 출력**: `AccessDenied ... not authorized to perform: sts:AssumeRole`
   → **trust policy AND 호출자 identity-based sts:AssumeRole 둘 다 필요**. `:root` trust는 권한 부여가 아니다.

   ```bash
   # 사용자에게 sts:AssumeRole만 부여하면 통과하는지 확인
   aws iam put-user-policy --user-name lab-no-perm --policy-name allow-assume \
     --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Action\":\"sts:AssumeRole\",\"Resource\":\"$ROLE_ARN\"}]}"
   sleep 10   # IAM 전파
   AWS_ACCESS_KEY_ID=$AK AWS_SECRET_ACCESS_KEY=$SK AWS_SESSION_TOKEN= \
     aws sts assume-role --role-arn "$ROLE_ARN" --role-session-name lab --external-id "$EXT_ID" \
     --query 'AssumedRoleUser.Arn'
   # 기대: "arn:aws:sts::<acct>:assumed-role/lab-audit-role/lab"  ← 성공
   ```

3. **A-3) 실패 케이스 2 — ExternalId 누락/불일치** (admin 호출자여도 실패)

   ```bash
   aws sts assume-role --role-arn "$ROLE_ARN" --role-session-name lab 2>&1 | grep -oE AccessDenied
   # 기대: AccessDenied   (mark 9-2 첫 검사와 동일 패턴)
   aws sts assume-role --role-arn "$ROLE_ARN" --role-session-name lab --external-id wrong-id 2>&1 | grep -oE AccessDenied
   # 기대: AccessDenied   (문자열 정확 일치 — 대회에선 player_number와 채점 export number 일치 필수)
   ```

4. **A-4) 성공 케이스 + 세션 권한 경계 확인**

   ```bash
   read -r AK SK TK < <(aws sts assume-role --role-arn "$ROLE_ARN" --role-session-name lab \
     --external-id "$EXT_ID" \
     --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]' --output text)
   export AWS_ACCESS_KEY_ID=$AK AWS_SECRET_ACCESS_KEY=$SK AWS_SESSION_TOKEN=$TK

   aws sts get-caller-identity --query Arn --output text
   # 기대: arn:aws:sts::<acct>:assumed-role/lab-audit-role/lab
   aws ec2 describe-vpcs --query 'Vpcs[0].VpcId' --output text
   # 기대: vpc-xxxx (허용 액션 성공)
   aws ec2 describe-instances 2>&1 | grep -oE 'AccessDenied|UnauthorizedOperation'
   # 기대: UnauthorizedOperation (미허용 액션 거부 — 최소권한 확인)

   unset AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY AWS_SESSION_TOKEN
   ```

</Steps>

## 실습 B. Private EKS 운용 드릴 (PART-2 클러스터 필요)

<Steps>

1. **B-1) 엔드포인트 상태 확인·재차단**

   ```bash
   aws eks describe-cluster --name <cluster> \
     --query 'cluster.resourcesVpcConfig.[endpointPublicAccess,endpointPrivateAccess]'
   # 기대: [false, true] — true로 남았으면(생성 중단 등):
   aws eks update-cluster-config --name <cluster> --resources-vpc-config endpointPublicAccess=false
   # 전환에 수 분 소요, status ACTIVE 복귀 후 재확인
   ```

2. **B-2) VPC CloudShell 멱등 셋업 왕복**

   콘솔 CloudShell → Actions → Create VPC environment → 과제 VPC/프라이빗 서브넷/mark-sg 선택.
   아래 블록을 통째로 실행하고, **세션을 끊었다가 재접속해 같은 블록을 다시 실행**해 1~2분 내 복구되는지 체감한다.

   ```bash
   aws configure   # 배포와 같은 신원 (생성자=채점 신원 원칙)
   sudo curl -sLo /usr/local/bin/kubectl "https://dl.k8s.io/release/$(curl -sL https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl" && sudo chmod +x /usr/local/bin/kubectl
   curl -sL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
   BUCKET=<과제 버킷>
   mkdir -p ~/work && cd ~/work
   aws s3 cp "s3://$BUCKET/_transfer/outputs.json" .   # 본 PC에서 미리 업로드해둔 릴레이
   aws eks update-kubeconfig --name <cluster> --region ap-northeast-2
   kubectl get nodes   # 기대: 노드 목록 (private API 접근 성공)
   ```

3. **B-3) CoreDNS 커스텀 도메인 양쪽 확인**

   ```bash
   # kubelet clusterDomain (nodeadm NodeConfig가 적용된 노드)
   NODE=$(kubectl get nodes -o jsonpath='{.items[0].metadata.name}')
   kubectl get --raw "/api/v1/nodes/$NODE/proxy/configz" | jq -r .kubeletconfig.clusterDomain
   # 기대: wsc2026.skills.local
   # Corefile
   kubectl -n kube-system get configmap coredns -o jsonpath='{.data.Corefile}' | grep skills.local
   # 기대: wsc2026.skills.local 존 라인
   # 실동작
   kubectl run dns-test --rm -it --restart=Never --image=busybox \
     -- nslookup kubernetes.default.svc.wsc2026.skills.local
   # 기대: 해석 성공. 한쪽만 적용돼 있으면 여기서 실패한다.
   ```

</Steps>

## 프라이빗 EKS·IAM :badge[함정]{variant=danger}

- **`:root` trust를 "전원 허용"으로 오해**: A-2에서 재현했듯 호출자 identity policy가 없으면 실패. 반대로, 계정에 admin 사용자가 많으면 그들 모두 assume 가능하다는 뜻이기도 하다.
- **ExternalId 불일치**: apply 시 `player_number`와 채점 셸 export `number`가 한 글자라도 다르면 9-1 문자열 비교·9-2 assume 모두 실패. 당일 등번호 확정 즉시 tfvars 반영 → apply.
- **IAM 전파 지연**: put-user-policy 직후 assume이 실패할 수 있다 — 10초쯤 기다렸다 재시도.
- **`kms:Decrypt` 등 요구 목록 외 권한 추가**: 수동 채점에서 최소권한 위반으로 읽힐 리스크. 꼭 필요하면 키 ARN 하나로 한정 + sid 명시.
- **퍼블릭 엔드포인트 잔존**: eksctl 중단 시 열린 채 남는다 — B-1을 습관화.
- **eks/eks-auth Endpoint 생성**: Pod Identity가 깨진다(theory 주제 1). 만들지 않는다.
- **VPC CloudShell 비영속**: 홈 삭제 + 업로드 UI 없음. 셋업 블록을 멱등하게 유지하고 파일은 전부 S3 릴레이로. 채점 전 `_transfer/` 삭제(버킷이 채점 대상).
- **coredns addon 업데이트**: Corefile 초기화 → B-3 재확인.

## 통과 기준

- [ ] A-2 실패(identity policy 부재) / A-3 실패(ExternalId) / A-4 성공+권한 경계, 세 가지 출력 모두 기대와 일치
- [ ] B-1에서 `[false, true]` 확인 (또는 재차단 수행)
- [ ] B-2 재접속 후 셋업 블록 재실행으로 kubectl 복구
- [ ] B-3 kubelet·Corefile·nslookup 3중 확인 통과
