## Part A — 유형 3 · 오토스케일링 (기준본, ap-northeast-2, skm-)

### A-1. 절차 (순서 요약)

<Steps>

1. **본 PC**: `module-3-eks-scaling/terraform` apply → `outputs.json` → eksctl/k8s/mark/provided+outputs.json을 zip으로 CloudShell 반입.
2. **CloudShell**: eksctl·helm 설치 → `~/.skm-env` 환경변수 영구화 → `eksctl create cluster`(~20분, **탭 닫지 말 것**). 클러스터가 2개(모듈 3·4)가 되면 **모듈 전용 터미널에서 `KUBECONFIG`를 모듈 경로로 고정**하고 시작한다 — 터미널 1개 = 클러스터 1개. 공유 kubeconfig의 `use-context` 전환은 잊는 순간 엉뚱한 클러스터에 apply 된다.
3. 앱 이미지 빌드/푸시 (제공 Dockerfile 그대로).
4. **KEDA 2.20.1** 설치 — `serviceAccount.operator.create=false`(IRSA용 keda-operator 재사용) + addon taint `tolerations` 지정.
5. **Karpenter 1.14.0** 설치(kube-system) — `--set replicas=1`(차트 기본 2는 addon 노드 1대에서 `helm --wait` 무한 대기) + `controller.resources.requests.cpu=0.5, memory=512Mi`로 낮춤(addon 노드 용량).
6. k8s 번호 순서 apply: namespace → **NodePool 먼저** → deployment → ScaledObject. deployment 는 자리표시자 두 개를 치환해 넘긴다.

   ```bash
   sed -e "s|<ECR_IMAGE>|$ECR_IMAGE|" -e "s|<SQS_URL>|$SQS_URL|" k8s/20-deployment.yaml | kubectl apply -f -
   ```

   매니페스트 파일 자체는 고치지 않는다 — 값만 갈아 끼워 apply 하면 다음 회차에 원본을 그대로 다시 쓴다.

</Steps>

### A-3. :badge[함정]{variant=danger}

1. **KEDA Pod Pending** → 차트 tolerations 스키마 확인: `helm show values kedacore/keda --version 2.20.1 | grep -n -A3 tolerations`. 버전에 따라 키가 최상위/컴포넌트별로 바뀐다.
2. **addon 노드 용량 초과** → Karpenter requests 0.5/512Mi 축소 설치. 그래도 Pending이면 KEDA metricServer/webhooks requests도 축소.
3. **scaleDown stabilizationWindowSeconds(15)·consolidateAfter(60s)를 늘리면** 스케일인 채점(150초 창) 실패. ScaledObject에 pollingInterval은 두지 않는다 — min ≥ 1이면 스케일링이 HPA sync 주기를 따라 이 값이 감지 속도를 바꾸지 못한다.
4. **deployment env는 리터럴 3개만** — valueFrom/추가 금지 (name=value 정확 비교).
5. NodePool보다 deployment를 먼저 apply하면 앱 Pod가 스케줄될 노드가 없다 — 번호 순서 준수.
6. 디스커버리 태그 누락(서브넷 `karpenter.sh/discovery`, SG `aws:eks:cluster-name`) → 노드가 영원히 안 뜬다.
7. **Karpenter `helm --wait`가 안 끝나면 replicas부터** — 기본 2 + required podAntiAffinity라 addon 노드 1대에선 구조적으로 불가(`--set replicas=1`). 행 상태에서 중단했다면 release가 `pending-upgrade`로 잠긴다 → `helm uninstall karpenter -n kube-system` 후 재설치.

- [ ] purge: 2.5분 내 Pod 1 / 노드 1

## Part A-이행 — set-08 SQS 스케일링 (us-west-2)

같은 스택(SQS + KEDA + Karpenter)을 다른 세트의 요구로 옮긴다. Part A 를 마친 상태에서 시작한다.

**파일 구조는 양쪽이 같다.** 바뀌는 것은 값이고, **그중 한 값이 다른 필드의 유효성을 뒤집는다.** 이 모듈의 판정 축이 그것이다.

### A이-1. 변동 과제지

**정답 코드를 먼저 열지 않는다.**

| 항목 | set-07 (기준본) | set-08 (변동) |
|---|---|---|
| 리전 | `ap-northeast-2` | **`us-west-2`** |
| 네임스페이스 | `skillsmkt` | `skills-sqs` |
| 큐 설정 | 기본값만 | **가시성 타임아웃을 명시** |
| 유휴 시 파드 수 | **1** | **0** |
| 최대 파드 수 | 5 | 6 |
| 파드 1개당 목표 메시지 | 5 | 2 |
| 트리거 인증 | 스칼라 옵션으로 지정 | **별도 리소스로 분리** |

#### 요구에서 파생되는 것

**"유휴 시 파드 0"** 이 이 이행의 전부다. 나머지는 숫자 교체지만 이 한 줄은 **다른 필드들의 필요성을 뒤집는다.**

파드가 최소 1개면 스케일링 판단을 쿠버네티스의 기본 오토스케일러가 자기 주기로 한다. 그래서 KEDA 쪽 폴링 주기를 적어도 **무효 필드**다 — 웹훅이 경고를 낸다.

파드가 0개가 되면 상황이 다르다. **0에서 1로 깨우는 일은 기본 오토스케일러가 못 한다.** 파드가 없으니 볼 지표도 없다. KEDA 가 직접 큐를 들여다보고 깨워야 하므로 **폴링 주기가 필수가 된다.**

축소 쪽도 같이 뒤집힌다. 최소 1개일 때는 기본 오토스케일러의 축소 동작을 조율해야 하지만, 0까지 내려가는 경우에는 KEDA 자신의 대기 시간이 그 자리를 맡는다.

**"트리거 인증을 별도 리소스로"** 는 도구 세대 문제다. 스칼라 옵션으로 지정하는 방식이 다음 주 버전에서 제거될 예정이라 별도 리소스로 옮겨간다. [03 의 프로바이더 버전 판정](/part-1/03-container-lambda-dynamodb/lab/)과 같은 종류다 — **요구가 코드가 아니라 도구 세대를 지정하는 경우**다.

### A이-2. 이행 (타이머 20분)

타이머를 걸고 시작한다. 아래는 절차가 아니라 **스스로 답해야 할 질문 목록**이다.

- 유휴 시 파드를 0으로 두면 **새로 필요해지는 필드**는 무엇이고, **무효가 되는 필드**는 무엇인가
- 그 판단의 근거를 어디서 확인하나. KEDA 문서인가 웹훅 경고인가
- 트리거 인증을 별도 리소스로 옮기면 리소스 종류 이름은 무엇이고, 트리거 쪽에서 그것을 어떻게 가리키나
- 리전 문자열이 박히는 자리가 몇 군데인가. Terraform 변수 말고 **매니페스트 안**에도 있나
- 네임스페이스를 바꾸면 따라오는 파일이 몇 개인가

**첫 질문에 시간을 쓴다.** 나머지는 문자열 교체다.

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

로그 파이프라인을 끝에서 끝까지 확인한다. 앱에 로그를 일부러 만들게 하고, 수집기 DaemonSet 이 노드 수만큼 떠 있는지, Loki 서비스가 있는지 본다. 마지막은 진짜 확인이다 — port-forward 로 Loki 에 직접 LogQL 을 던져 방금 만든 ERROR 로그가 JSON 원문 그대로 돌아오는지 본다. 본문이 훼손되면 `| json` 파싱이 깨져 여기서 빈 결과가 나온다.

</details>

## 6. 과제지 오독 복구

배포까지 했는데 값이 다르다. 이 모듈의 판정 축은 넷이다.

| 판정 | 무엇으로 아나 | 비용 |
|---|---|---|
| 즉시 수정 | 매니페스트를 고쳐 다시 적용하면 된다 | 초 |
| **조합이 틀렸다** | 값 하나하나는 맞는데 **웹훅이 경고**한다 | 초 — 다만 안 먹는다 |
| 도구 세대 | 필드를 아예 모른다 | 분 — 코드를 고치면 안 된다 |
| 리전 오독 | 아무 도구도 안 잡아 준다 | 전면 재배포 |

두 번째가 이 모듈에서 처음 나온다.

### 6-1. 파드당 목표 메시지를 기준본대로 뒀다

**상황.** 유휴 파드 수와 최대치는 맞췄는데 파드당 목표 메시지를 5 로 뒀다. 메시지 12건을 보내도 파드가 3개까지만 는다.

**판정.** 값 하나만 고쳐 다시 적용한다.

```bash
kubectl apply -f k8s/30-keda-scaledobject.yaml
kubectl get scaledobject -n skills-sqs
```

기대: 경고 없이 적용되고 곧 파드 수가 바뀐다. **오토스케일러 오브젝트는 값 교체가 자유롭다.**

**교훈.** 가장 싼 축이다. 다만 **채점이 파드 수를 직접 세므로** 값이 틀리면 바로 드러난다. 목표 값과 최대치와 보낼 메시지 수를 곱셈으로 맞춰 보고 시작한다.

### 6-2. 유휴 파드를 1로 둔 채 폴링 주기만 넣었다

**상황.** 새 요구를 읽고 폴링 주기를 넣었는데 유휴 파드 수는 기준본의 1 로 남겨 뒀다. 적용은 된다.

**판정.** 적용해 보면 안다.

```bash
kubectl apply --dry-run=server -f k8s/30-keda-scaledobject.yaml
```

기대: **경고가 나온다.** 유휴 파드가 1 이상이면 스케일링 판단을 기본 오토스케일러가 하므로 KEDA 쪽 폴링 주기가 **무효 필드**다. 적용은 되는데 그 값은 아무 일도 하지 않는다.

**여기가 이 모듈의 핵심이다.** 값 하나하나는 전부 유효한데 **조합이 틀렸다.** 문법 오류도 아니고 오타도 아니라서, 값만 훑어서는 못 찾는다.

**복구.** 유휴 파드를 0 으로 내린다. 그러면 폴링 주기가 필수가 되고 경고가 사라진다.

**파급.** 0 으로 내리면 축소 쪽 설정도 함께 봐야 한다. 기준본이 기본 오토스케일러의 축소 동작을 조율하고 있었다면 그 블록은 더 이상 맞지 않는다.

**교훈.** **한 값이 다른 필드의 유효성을 정하는 경우가 있다.** 요구를 읽을 때 "이 값이 바뀌면 무엇이 함께 의미를 잃나"를 묻는다. 그리고 **웹훅 경고를 무시하지 않는다** — 적용이 됐다고 먹은 것은 아니다.

  ```bash
  kubectl get crd | grep keda
  kubectl -n keda get deploy -o jsonpath='{.items[0].spec.template.spec.containers[0].image}'
  ```
  </TabItem>
</Tabs>

기대: CRD 목록에 트리거 인증 리소스가 있고, 이미지 태그로 버전을 확인할 수 있다.

**복구.** 인증을 별도 리소스로 분리하고 트리거에서 그것을 가리킨다. 코드 구조가 바뀌는 것이지 값 교체가 아니다.

**교훈.** [03 의 프로바이더 버전](/part-1/03-container-lambda-dynamodb/lab/)과 같은 자리다. **과제지가 도구 세대를 지정하는 경우**가 있고, 그때는 코드를 고치는 것이 아니라 방식을 옮긴다. 판정 순서는 ① 오타인가 ② 도구가 아는가 ③ 그다음 문서다.

## 7. 장애 진단

정상으로 선 상태에서 일부러 고장을 내고 증상만 보고 좁혀 간다. **주입 명령과 복구 명령이 짝으로 있다.**

### 7-1. 메시지를 넣어도 파드가 안 는다

**주입.** KEDA 가 큐를 못 보게 한다. 운영자 서비스 계정의 신원 연결을 끊는다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl -n keda get sa keda-operator -o yaml | Select-String -Pattern 'role-arn'
  kubectl -n keda annotate sa keda-operator eks.amazonaws.com/role-arn- --overwrite
  kubectl -n keda rollout restart deploy keda-operator
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl -n keda get sa keda-operator -o yaml | grep role-arn
  kubectl -n keda annotate sa keda-operator eks.amazonaws.com/role-arn- --overwrite
  kubectl -n keda rollout restart deploy keda-operator
  ```
  </TabItem>
</Tabs>

첫 명령의 출력을 적어 둔다 — 복구할 때 그 값을 되돌린다.

**증상.** 큐에 메시지가 쌓이는데 파드가 그대로다. 오토스케일러 오브젝트는 존재하고 앱도 정상이다.

**좁히는 순서.** 판단하는 쪽에서 대상 쪽으로 간다.

<Steps>

1. **오토스케일러 오브젝트가 준비됐나** — `kubectl get scaledobject -n <ns>`. `READY` 가 `False` 면 트리거를 못 읽는 것이다. **이 한 열이 갈림이다**

2. **왜 준비가 안 됐다고 하나** — `kubectl describe scaledobject -n <ns> <이름>`. 조건에 이유가 글자로 적혀 있다

3. **판단하는 쪽 로그** — `kubectl logs -n keda deploy/keda-operator --tail=50`. 큐 조회 실패면 여기에 찍힌다. `AccessDenied` 계열이면 신원 문제다

4. **신원이 붙어 있나** — 운영자 서비스 계정의 역할 연결을 본다. 없으면 여기가 원인이다

5. 신원이 있는데도 막히면 그때 역할의 정책과 **큐가 다른 리전에 있는지**를 본다

</Steps>

마지막 줄이 이 모듈 특유다. **트리거에 적은 리전이 큐의 리전과 다르면 조회가 조용히 빈다** — 권한 문제처럼 보이지만 아니다.

**복구.** 적어 둔 역할을 다시 붙인다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl -n keda annotate sa keda-operator eks.amazonaws.com/role-arn=<적어-둔-ARN> --overwrite
  kubectl -n keda rollout restart deploy keda-operator
  kubectl get scaledobject -n skills-sqs
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl -n keda annotate sa keda-operator eks.amazonaws.com/role-arn=<적어-둔-ARN> --overwrite
  kubectl -n keda rollout restart deploy keda-operator
  kubectl get scaledobject -n skills-sqs
  ```
  </TabItem>
</Tabs>

기대: `READY` 가 `True` 로 돌아오고 곧 파드가 늘어난다.

### 7-2. 큐를 비웠는데 파드가 안 줄어든다

**주입.** 메시지를 소비하지 못하게 막는다. 워커의 이미지를 없는 태그로 바꿔 새 파드가 못 뜨게 한다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl set image deployment/sqs-worker -n skills-sqs sqs-worker=nosuchimage:v0 
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl set image deployment/sqs-worker -n skills-sqs sqs-worker=nosuchimage:v0
  ```
  </TabItem>
</Tabs>

컨테이너 이름은 `kubectl get deploy sqs-worker -n skills-sqs -o jsonpath='{.spec.template.spec.containers[0].name}'` 로 확인한다.

**증상.** 큐를 비웠는데 파드 수가 오래 그대로다. 또는 메시지를 넣었는데 처리가 안 되고 계속 쌓인다.

**좁히는 순서.**

<Steps>

1. **큐가 정말 비었나** — 가시성 타임아웃 때문에 **처리 중인 메시지는 목록에서 안 보인다.** `ApproximateNumberOfMessagesNotVisible` 까지 함께 본다. 이것을 모르면 "비웠는데 왜"에서 막힌다

2. **파드가 뜨긴 하나** — `kubectl get pod -n <ns>`. `ImagePullBackOff` 면 소비자가 없어 메시지가 안 줄어드는 것이다

3. **축소가 대기 중인가** — 축소에는 대기 시간이 있다. 방금 비웠으면 그 시간만큼 기다린다

4. **노드까지 줄어드나** — 파드가 줄어도 노드는 별도 판단이다. 노드 정리 대기 시간이 따로 있다

</Steps>

**1번이 이 모듈 고유의 함정이다.** 큐의 "보이는 메시지"만 보면 비어 있는데, 처리 중인 것이 남아 있으면 오토스케일러는 아직 일이 있다고 본다. **가시성 타임아웃을 명시하라는 요구가 여기와 이어진다** — 값이 길면 실패한 처리가 오래 묶여 있다.

**복구.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl rollout undo deployment/sqs-worker -n skills-sqs
  kubectl rollout status deployment/sqs-worker -n skills-sqs
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl rollout undo deployment/sqs-worker -n skills-sqs
  kubectl rollout status deployment/sqs-worker -n skills-sqs
  ```
  </TabItem>
</Tabs>

**교훈.** 큐 기반 스케일링의 진단은 **"큐에 무엇이 남아 있나"와 "소비자가 살아 있나"를 나눠 묻는 것**에서 시작한다. 둘을 합쳐 보면 원인을 못 짚는다.
