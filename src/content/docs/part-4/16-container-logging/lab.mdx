- [ ] 순서 의존(LBC → TargetGroupBinding, Loki → OTel)을 지키고, 어겼을 때의 증상을 안다
- [ ] 제공 Dockerfile 의 결함을 찾아 자기 Dockerfile 로 대체한다
- [ ] 값을 잘못 읽었을 때 고칠지 다시 만들지 판정한다

- [ ] 클러스터와 VPC 를 정리한다

## 1. 배포와 검증

:::note[정답지가 들어왔다 — 이 절차의 근거가 코드로 바뀌었다]
`set-07/task-2/module-4-container-logging` 에 구현이 있다. 이 파트의 순서와 값은 그 구현에 맞춰 두었으니, 막히면 정답지의 `README.md` 와 `cs-deploy.sh` 를 연다.

구성은 본 PC 가 `terraform`·`eksctl` 만 쓰고 **이미지 빌드·helm·kubectl·채점은 전부 ap-northeast-1 CloudShell** 에서 하는 2분할이다. 정답지가 공식 OTel Helm 차트 대신 **원시 매니페스트**를 쓴다는 점이 이 모듈의 갈림길이다.
:::

### 1-1. 절차 (순서 요약 — 순서 의존이 많다)

<Steps>

1. **본 PC**: `module-4-container-logging/terraform` apply (VPC + **이름 고정 ALB/TG** + ECR + LBC IAM) → zip 으로 올린다.
2. **CloudShell**: `~/.o11y-env` → `eksctl create cluster`(~20분) → 노드 2대가 AZ a/c로 분산됐는지 확인.
3. 이미지 빌드: 제공 `app.py` 는 그대로 두고 **`app/Dockerfile` 만 직접 쓴다** — 제공 Dockerfile 은 flask 를 설치하지 않아 파드가 CrashLoop 한다. 베이스·tzdata·비루트 패턴은 [모듈 08 의 Dockerfile](/part-1/08-container-lambda-dynamodb/lab/)을 그대로 가져오고, 바뀌는 것은 의존성 설치 줄과 진입점이다.
4. **LBC 차트 3.4.3 설치** ← TGB CRD가 여기서 생긴다. 이후에만 TGB apply 가능.
5. namespace/StorageClass/앱 apply + 앱 TGB.
6. **Loki 차트 18.7.1** (`grafana-community` 저장소 — `grafana/loki`는 GEL 전용) → svc `o11y-loki` 3100 확인.
7. **OTel DaemonSet apply는 Loki 이후** (otlphttp 전송 대상 먼저).
8. **Grafana 차트 12.10.0** + 대시보드 ConfigMap + Grafana TGB.

</Steps>

### 1-2. 검증 + 기대 출력

```bash
curl -s "http://$APP_ALB/healthz"                     # {"status":"ok"}
curl -s "http://$APP_ALB/log?level=error&count=3"     # {"generated":3,"level":"error"}
kubectl get ds o11y-otel -n monitoring                # DESIRED 2 / READY 2
kubectl get svc o11y-loki -n monitoring               # ClusterIP 3100

# LogQL 직접 조회 (port-forward)
kubectl port-forward -n monitoring svc/o11y-loki 3100:3100 & sleep 2
curl -s -G http://localhost:3100/loki/api/v1/query_range \
  --data-urlencode 'query={k8s_namespace_name="o11y"} | json | level="ERROR"' \
  --data-urlencode "start=$(date -d '3 minutes ago' +%s)000000000" \
  --data-urlencode "end=$(date +%s)000000000" | jq -r '.data.result[].values[][1]' | head -3
# 기대: {"ts":...,"level":"ERROR",...} JSON 원문 라인들
kill %1
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

로그 파이프라인을 끝에서 끝까지 확인한다. 앱에 로그를 일부러 만들게 하고, 수집기 DaemonSet 이 노드 수만큼 떠 있는지, Loki 서비스가 있는지 본다. 마지막은 진짜 확인이다 — port-forward 로 Loki 에 직접 LogQL 을 던져 방금 만든 ERROR 로그가 JSON 원문 그대로 돌아오는지 본다. 본문이 훼손되면 `| json` 파싱이 깨져 여기서 빈 결과가 나온다.

</details>

채점 전 마지막 준비: `/log?level=info`, `/log?level=warn`, `/log?level=error` 각각 호출 → Grafana Log Overview 3패널 모두 데이터 확인(범례 INFO/WARN/ERROR). 채점: `bash ~/skills-2026/set-07/task-2/mark/mark4.sh` (4-6은 Grafana 웹 수동 채점).

### 1-3. :badge[함정]{variant=danger}

1. **제공 Dockerfile로 빌드 → CrashLoop.** 자체 Dockerfile 사용, app.py 수정 금지.
2. **TGB를 LBC 설치 전에 apply → CRD 없음 오류.** 순서: LBC → TGB.
3. **ALB를 Ingress로 만들면 이름 채점 실패** — 이름 고정이 필요하므로 terraform ALB + TGB.
4. **level은 대문자 ERROR** — LogQL `| json | level="ERROR"`. 소문자로 찍히게 가공하면 오답.
5. **범례는 plain text**(`ERROR`)여야 한다 — `{level="ERROR"}` 형태로 뜨면 오답. `sum by (level)` + legendFormat `{{level}}`.
6. **No Data 패널 1개라도 있으면 오답** — 채점 전 3레벨 호출.
7. **로그 확인(4-5)은 부분 일치**로 완화됐다(배포본 v5) — "3분 이내로 기록된 로그가 있으면 득점"이라 본문을 맞출 필요 없이 **검증 직전 트래픽을 한 번 흘려 최근 로그를 만들어 두면** 된다. 모든 노드 TZ는 KST로 설정한다.
7. OTel이 body를 가공하면 `| json` 파싱 깨짐 — container 파서 외 본문 변형 금지.
8. mark4.sh의 `rm -rf ~/.aws`는 CloudShell(관리형 세션)에선 무해 — bastion에서 돌리지 말 것.

### 1-4. 통과 기준

- [ ] /healthz ok, ds 2/2, svc 3100
- [ ] LogQL ERROR 조회에 원본 JSON 라인 반환
- [ ] Grafana 3패널 데이터 + 범례 INFO/WARN/ERROR
- [ ] mark4.sh 자동 항목 PASS

## 2. 과제지 오독 복구

배포까지 끝낸 상태에서, 값을 잘못 읽었다는 것을 뒤늦게 아는 상황이다. 질문은 언제나 같다 — **고쳐서 살리나, 부수고 다시 만드나, 몇 분 걸리나.**

### 2-1. 네임스페이스를 잘못 읽었다

채점 질의가 `{k8s_namespace_name="o11y"}` 인데 앱을 다른 네임스페이스에 올렸다.

<Steps>

1. **무엇이 걸리는지 먼저 센다.** 네임스페이스는 이름이자 라벨이고, 수집 경로의 파일 이름에도 들어간다.

   ```bash
   kubectl get ns
   kubectl get pods -A -l app=log-generator -o jsonpath='{range .items[*]}{.metadata.namespace}{"\t"}{.metadata.name}{"\n"}{end}'
   ```

2. **판정한다.** 네임스페이스는 **바꿀 수 없는 값**이다 — 리소스를 옮기는 것이 아니라 새 네임스페이스에 다시 만들고 옛 것을 지운다.

   | 손댈 곳 | 왜 |
   |---|---|
   | 매니페스트의 `metadata.namespace` | 앱·서비스·TargetGroupBinding 전부 |
   | 수집기의 수집 대상 필터 | 파일 경로에 네임스페이스가 들어간다 |
   | 대시보드 질의 | 라벨 값이 바뀐다 |

3. **고친 뒤 라벨이 실제로 바뀌었는지 확인한다.** 매니페스트만 고치고 옛 파드가 남아 있으면 두 값이 동시에 흐른다.

   ```bash
   kubectl delete ns <옛 네임스페이스> --ignore-not-found
   kubectl -n o11y get pods
   ```

</Steps>

**교훈.** 라벨은 로그 본문이 아니라 **파일 경로에서 만들어진다.** 그래서 네임스페이스를 바꾸면 수집기 설정까지 같이 움직인다 — 값 하나가 세 곳을 끈다.

### 2-2. 시간대를 안 맞췄다

로그 시각이 한국 시간보다 아홉 시간 이르다.

<Steps>

1. **어디가 UTC 인지 가른다.** 앱, 노드, 대시보드 셋 중 하나다.

   ```bash
   kubectl -n o11y exec deploy/log-generator -- date
   kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.labels.topology\.kubernetes\.io/zone}{"\n"}{end}'
   ```

2. **컨테이너가 UTC 면 이미지 문제다** — 시간대 데이터가 없거나 환경 변수가 없다. [05 컨테이너 이론](/part-0/05-container/theory/)의 시간대 절이 그 원인을 다룬다.

3. **노드까지 맞추라는 요구가 붙은 배포본이 있다.** 요구가 있으면 노드 쪽도 함께 본다.

</Steps>

**교훈.** 정확히 아홉 시간 차이는 계산 실수가 아니라 **시간대 설정의 부재**다. 값이 어긋난 게 아니라 기준이 없는 것이다.

## 3. 장애 진단

### 3-1. 대시보드 패널이 비었다

파이프라인이 네 고리라 어디서 끊겼는지부터 좁힌다. **끝에서부터 거슬러 올라가지 않는다** — 앞에서부터 확인하면 한 번에 끝난다.

<Steps>

1. **앱이 로그를 내고 있나.**

   ```bash
   kubectl -n o11y logs deploy/log-generator --tail=5
   ```

   비어 있으면 앱을 호출해 로그를 만들고 다시 본다.

2. **수집기가 읽고 있나.**

   ```bash
   kubectl -n monitoring get ds o11y-otel
   kubectl -n monitoring logs ds/o11y-otel --tail=20 | grep -iE 'error|refused|dial'
   ```

   `refused` 나 `dial` 이 보이면 **보낼 곳이 없는 것**이다 — 저장소가 아직 안 떴거나 주소가 틀렸다.

3. **저장소에 도착했나.** 대시보드를 거치지 않고 직접 묻는다.

   ```bash
   kubectl -n monitoring port-forward svc/o11y-loki 3100:3100 &
   sleep 2
   curl -s -G http://localhost:3100/loki/api/v1/labels | head -c 200
   kill %1
   ```

   라벨 목록에 `k8s_namespace_name` 이 없으면 **승격이 안 된 것**이다. 로그는 들어갔는데 인덱스가 없으니 질의가 비어 나온다.

4. **대시보드 질의가 맞나.** 여기까지 왔으면 남은 것은 질의 문자열뿐이다 — 라벨 이름, 레벨 값의 대소문자, 시간 범위.

</Steps>

:::tip[순서가 진단 시간을 정한다]
네 단계 중 **앞에서 끊긴 것을 뒤에서 찾으면** 멀쩡한 설정을 계속 고치게 된다. 위 순서는 각 단계가 다음 단계의 입력이라는 사실을 그대로 따른 것이다.

각 단계의 실패 신호도 다르다 — 1번은 출력 없음, 2번은 연결 오류, 3번은 라벨 없음, 4번은 빈 결과. **증상 문구만 보고도 몇 번인지 알 수 있어야 한다.**
:::

### 3-2. TargetGroupBinding 을 apply 했더니 없는 종류라고 한다

```
error: unable to recognize "30-tgb-app.yaml": no matches for kind "TargetGroupBinding"
```

**컨트롤러가 아직 없어서 그 종류를 클러스터가 모르는 것이다.** 매니페스트 문제가 아니다.

```bash
kubectl get crd | grep -i targetgroupbinding
kubectl -n kube-system get deploy aws-load-balancer-controller
```

컨트롤러를 먼저 설치하면 종류가 생긴다. **순서 의존이 이 모듈에 둘 있다** — 컨트롤러가 먼저, 그리고 저장소가 수집기보다 먼저.
