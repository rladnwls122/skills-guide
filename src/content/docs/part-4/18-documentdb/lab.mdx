원리와 채점 관점은 [18 이론 — DocumentDB NoSQL](/part-4/18-documentdb/theory/)에 있다.

**방식**: 기준본을 손으로 세워 동작을 확인한 뒤, **엔진이 통째로 바뀐 요구로 이행한다.** 이 커리큘럼에서 가장 큰 변동이다.

이 실습 절차는 문제지·지급 코드(`docdb_client.py`)와 2026-08-01 정정본의 판정 기준을 근거로 한다. 같은 구성의 Terraform 정답은 [`set-08/task-2/module-1-nosql`](https://github.com/ishs-cloud-computing/skills-2026/tree/main/set-08/task-2/module-1-nosql)이다 — 이 실습은 콘솔·CLI로 손에 익히는 경로이므로 먼저 스스로 만든 뒤 대조한다. 저장소가 아직 없다면 [사전 준비 §4 저장소 클론](/start/#4-저장소-클론)을 먼저 한다. 명령은 PowerShell·bash 두 탭으로 두었고 기준본 리전은 `ap-northeast-2`(서울)다. 지급 파일 경로는 1단계에서 `PROVIDED` 변수 하나로 잡고 그 뒤로는 변수만 쓴다 — 실제 대회에서는 그 한 줄만 대회 플랫폼이 지급한 경로로 바꾼다.

## 실습 목표

- [ ] DocumentDB 클러스터+인스턴스를 KMS 암호화·백업보존 1일 이상으로 배포한다
- [ ] Secret 3키(`username`/`password`/`host`)를 스킴·포트 없는 값으로 채운다
- [ ] Client EC2에 CA 번들과 지급 코드를 올리고 `0.0.0.0:8080`으로 서비스를 띄운다
- [ ] `POST /v1/admin/seed`로 데이터를 적재하고 `dateFieldTypes`가 전부 `datetime`인지 확인한다
- [ ] 인덱스 8개(unique·복합·TTL)를 직접 만들어 `/v1/admin/indexes` 채점을 통과시킨다
- [ ] 조회 4종을 전부 HTTP 200 + 기대 데이터로 재현한다
- [ ] (이행) 같은 "NoSQL" 요구를 **서버 있는 엔진에서 서버 없는 엔진으로** 옮긴다
- [ ] (이행) 옮겨 쓸 것과 **버릴 것**을 판정한다 — 리소스 넷이 통째로 사라진다
- [ ] 조회 요구에서 키 구조를 역산하고, 그것이 왜 만들기 전에 확정할 값인지 확인한다
- [ ] 변경 스트림처럼 **켠 시점부터 흐르는** 요구의 시간 축을 복구 계획에 넣는다
- [ ] 실습 종료 시 전 리소스를 destroy한다

선행 지식과 목표는 [모듈 개요](/part-4/18-documentdb/)에.

1. **사전 준비 — 서브넷·보안 그룹**

   DocumentDB 서브넷 그룹은 서로 다른 AZ의 서브넷 2개 이상이 필요하다. 새 VPC를 만들지 않고 리전 기본 VPC의 기본 서브넷을 쓴다(계정에 기본 VPC가 없다면 [vpc-basics](/start/vpc-basics/)대로 서브넷 2개 이상을 먼저 만든다).

   지급 파일(`docdb_client.py`·`retail_dataset.json`)이 놓인 폴더를 변수 하나로 잡아 둔다. 뒤의 `scp` 가 이 변수를 쓴다 — 대회에서는 대회 플랫폼이 내려 준 폴더로 값만 바꾼다.

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     $env:AWS_DEFAULT_REGION = "ap-northeast-2"
     $PROVIDED = "$HOME\Downloads\2과제\모듈1_지급파일"   # 본인 지급 파일 폴더로 교체
     Get-ChildItem $PROVIDED                              # 기대: docdb_client.py, retail_dataset.json

     $subnets = aws ec2 describe-subnets --filters "Name=default-for-az,Values=true" --query "Subnets[].SubnetId" --output json | ConvertFrom-Json
     $SUBNET_1 = $subnets[0]
     $SUBNET_2 = $subnets[1]
     $VPC_ID = aws ec2 describe-subnets --subnet-ids $SUBNET_1 --query "Subnets[0].VpcId" --output text

     $DOCDB_SG = aws ec2 create-security-group --group-name skills-nosql-docdb-sg --description "DocumentDB - client only" --vpc-id $VPC_ID --query GroupId --output text
     $CLIENT_SG = aws ec2 create-security-group --group-name skills-nosql-client-sg --description "Client EC2 - app + SSH" --vpc-id $VPC_ID --query GroupId --output text

     aws ec2 authorize-security-group-ingress --group-id $DOCDB_SG --protocol tcp --port 27017 --source-group $CLIENT_SG
     aws ec2 authorize-security-group-ingress --group-id $CLIENT_SG --protocol tcp --port 8080 --cidr 0.0.0.0/0
     aws ec2 authorize-security-group-ingress --group-id $CLIENT_SG --protocol tcp --port 22 --cidr 0.0.0.0/0
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     export AWS_DEFAULT_REGION=ap-northeast-2
     PROVIDED=~/Downloads/2과제/모듈1_지급파일     # 본인 지급 파일 폴더로 교체
     ls "$PROVIDED"                                # 기대: docdb_client.py, retail_dataset.json

     SUBNET_1=$(aws ec2 describe-subnets --filters "Name=default-for-az,Values=true" --query 'Subnets[0].SubnetId' --output text)
     SUBNET_2=$(aws ec2 describe-subnets --filters "Name=default-for-az,Values=true" --query 'Subnets[1].SubnetId' --output text)
     VPC_ID=$(aws ec2 describe-subnets --subnet-ids "$SUBNET_1" --query 'Subnets[0].VpcId' --output text)

     DOCDB_SG=$(aws ec2 create-security-group --group-name skills-nosql-docdb-sg --description "DocumentDB - client only" --vpc-id "$VPC_ID" --query GroupId --output text)
     CLIENT_SG=$(aws ec2 create-security-group --group-name skills-nosql-client-sg --description "Client EC2 - app + SSH" --vpc-id "$VPC_ID" --query GroupId --output text)

     aws ec2 authorize-security-group-ingress --group-id "$DOCDB_SG" --protocol tcp --port 27017 --source-group "$CLIENT_SG"
     aws ec2 authorize-security-group-ingress --group-id "$CLIENT_SG" --protocol tcp --port 8080 --cidr 0.0.0.0/0
     aws ec2 authorize-security-group-ingress --group-id "$CLIENT_SG" --protocol tcp --port 22 --cidr 0.0.0.0/0
     ```
     </TabItem>
   </Tabs>

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   기본 VPC 의 서브넷 두 개를 골라 두고 보안 그룹 둘을 만든다. 요점은 DB 쪽 규칙이다 — 27017 을 CIDR 이 아니라 `--source-group` 으로 클라이언트 보안 그룹에만 연다. 클라이언트 IP 가 바뀌어도 규칙이 그대로 살고, 채점이 요구하는 "클라이언트만 접근"을 만족한다. 클라이언트 쪽 8080·22 는 밖에서 들어와야 해서 CIDR 로 연다.

   </details>

   SSH(22)는 채점 대상이 아니다. 본인 IP만 허용하도록 `--cidr`를 좁힐 수 있으면 좁힌다.

3. **DocumentDB 서브넷 그룹 + 클러스터 + 인스턴스**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws docdb create-db-subnet-group --db-subnet-group-name skills-nosql-docdb-subnets --db-subnet-group-description "DocumentDB subnets" --subnet-ids $SUBNET_1 $SUBNET_2

     aws docdb create-db-cluster --db-cluster-identifier skills-nosql-docdb-cluster --engine docdb --master-username skillsadmin --master-user-password $DOCDB_PASSWORD --db-subnet-group-name skills-nosql-docdb-subnets --vpc-security-group-ids $DOCDB_SG --storage-encrypted --kms-key-id alias/skills-nosql-docdb --backup-retention-period 1 --port 27017

     aws docdb create-db-instance --db-instance-identifier skills-nosql-docdb-instance-1 --db-instance-class db.t3.medium --engine docdb --db-cluster-identifier skills-nosql-docdb-cluster

     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">

     ```bash
     DOCDB_PASSWORD='<본인이 정한 12자 이상 비밀번호>'

     aws docdb create-db-instance --db-instance-identifier skills-nosql-docdb-instance-1 --db-instance-class db.t3.medium --engine docdb --db-cluster-identifier skills-nosql-docdb-cluster
     ```

     </TabItem>
   </Tabs>

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   DocumentDB 클러스터와 인스턴스를 만든다. 서브넷 그룹이 먼저 있어야 하고, 클러스터에 `--storage-encrypted` 와 KMS 별칭, 백업 보존 기간을 함께 준다 — 세 가지가 각각 채점 항목이다. 클러스터는 껍데기라 실제로 쿼리를 받는 것은 인스턴스이고, `wait db-instance-available` 이 끝나야 접속이 된다.

   </details>

   `username`/`password` 값 자체는 채점 대상이 아니다(Secret에 값이 채워져 있는지만 본다) — 대신 비밀번호를 잊지 않게 적어 둔다.

4. **Secret 생성**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     $DOCDB_ENDPOINT = aws docdb describe-db-clusters --db-cluster-identifier skills-nosql-docdb-cluster --query 'DBClusters[0].Endpoint' --output text

     $secretObj = @{ username = "skillsadmin"; password = $DOCDB_PASSWORD; host = $DOCDB_ENDPOINT }
     aws secretsmanager create-secret --name skills-nosql-docdb-secret --secret-string ($secretObj | ConvertTo-Json -Compress)
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     DOCDB_ENDPOINT=$(aws docdb describe-db-clusters --db-cluster-identifier skills-nosql-docdb-cluster --query 'DBClusters[0].Endpoint' --output text)

     SECRET_JSON=$(jq -nc --arg u skillsadmin --arg p "$DOCDB_PASSWORD" --arg h "$DOCDB_ENDPOINT" \
       '{username:$u, password:$p, host:$h}')
     aws secretsmanager create-secret --name skills-nosql-docdb-secret --secret-string "$SECRET_JSON"
     ```
     </TabItem>
   </Tabs>

   `describe-db-clusters`의 `Endpoint` 필드는 이미 스킴·포트가 없는 순수 호스트명이다. 콘솔에서 연결 문자열을 복사해 붙여넣지 않는다 — `mongodb://host:27017` 형태가 그대로 들어가면 `docdb_client.py`가 즉시 `RuntimeError`를 던진다.

   검증 (mark 1-2 Secret 부분):

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws secretsmanager describe-secret --secret-id skills-nosql-docdb-secret --query '{Name:Name,ARN:ARN,KmsKeyId:KmsKeyId}' --output table
     (aws secretsmanager get-secret-value --secret-id skills-nosql-docdb-secret --query SecretString --output text | ConvertFrom-Json) | Select-Object username, host, @{N='password_set'; E={ -not [string]::IsNullOrEmpty($_.password) }}
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     aws secretsmanager describe-secret --secret-id skills-nosql-docdb-secret --query '{Name:Name,ARN:ARN,KmsKeyId:KmsKeyId}' --output table
     aws secretsmanager get-secret-value --secret-id skills-nosql-docdb-secret --query SecretString --output text \
       | jq '{username, host, password_set: (.password != null and .password != "")}'
     ```
     </TabItem>
   </Tabs>

5. **Client EC2 — IAM 역할 → 키 페어 → 인스턴스**

   IAM 역할(Secrets Manager 읽기 전용) → 인스턴스 프로파일 → 키 페어 순서로 준비한다.

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     $SECRET_ARN = aws secretsmanager describe-secret --secret-id skills-nosql-docdb-secret --query ARN --output text

     aws iam create-role --role-name skills-nosql-client-ec2-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
     aws iam put-role-policy --role-name skills-nosql-client-ec2-role --policy-name secret-read --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Action\":\"secretsmanager:GetSecretValue\",\"Resource\":\"$SECRET_ARN\"}]}"
     aws iam create-instance-profile --instance-profile-name skills-nosql-client-ec2-profile
     aws iam add-role-to-instance-profile --instance-profile-name skills-nosql-client-ec2-profile --role-name skills-nosql-client-ec2-role
     Start-Sleep -Seconds 15   # 인스턴스 프로파일 전파 대기 — 너무 빨리 run-instances 하면 실패한다

     aws ec2 create-key-pair --key-name skills-nosql-key --query "KeyMaterial" --output text | Out-File -Encoding ascii skills-nosql-key.pem
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     SECRET_ARN=$(aws secretsmanager describe-secret --secret-id skills-nosql-docdb-secret --query ARN --output text)

     aws iam create-role --role-name skills-nosql-client-ec2-role --assume-role-policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ec2.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
     aws iam put-role-policy --role-name skills-nosql-client-ec2-role --policy-name secret-read --policy-document "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",\"Action\":\"secretsmanager:GetSecretValue\",\"Resource\":\"$SECRET_ARN\"}]}"
     aws iam create-instance-profile --instance-profile-name skills-nosql-client-ec2-profile
     aws iam add-role-to-instance-profile --instance-profile-name skills-nosql-client-ec2-profile --role-name skills-nosql-client-ec2-role
     sleep 15   # 인스턴스 프로파일 전파 대기 — 너무 빨리 run-instances 하면 실패한다

     aws ec2 create-key-pair --key-name skills-nosql-key --query KeyMaterial --output text > skills-nosql-key.pem
     chmod 400 skills-nosql-key.pem   # 권한이 넓으면 ssh 가 키를 거부한다
     ```
     </TabItem>
   </Tabs>

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   EC2 가 비밀번호를 코드 없이 읽게 하는 준비다. 역할에 그 시크릿 하나만 읽는 정책을 붙이고, 인스턴스 프로파일로 감싸 EC2 에 붙일 수 있게 만든다. `Start-Sleep 15` 가 필요한 이유는 프로파일 전파가 즉시가 아니어서 바로 `run-instances` 를 하면 실패하기 때문이다. 마지막 줄은 SSH 키를 만들어 파일로 저장한다.

   </details>

   다음 내용을 `user-data.sh`로 저장한다 — 부팅 시 의존성 설치와 CA 번들 다운로드, systemd 유닛 등록까지 한다(앱 파일은 아직 없으므로 서비스는 등록만 하고 시작하지 않는다).

   **이 스크립트는 통째로 재사용한다.** 의존성 설치·CA 번들·systemd 유닛은 과제가 바뀌어도 같은 모양이고([모듈 19](/part-4/19-vpc-lattice/lab/)의 user-data 도 이 뼈대다), 실제로 바뀌는 것은 `ExecStart` 의 스크립트 경로와 서비스 이름 두 줄뿐이다. 외워서 다시 쓰지 말고 이 블록을 복사해 그 두 줄만 고친다.

   ```bash title="user-data.sh"
   #!/bin/bash
   dnf install -y python3-pip
   pip3 install boto3 pymongo
   ```

9. **인덱스 생성**

   `docdb_client.py`는 인덱스를 만들지 않는다. 같은 연결 패턴(URI·TLS·CA 번들)을 재사용하는 별도 스크립트를 하나 실행한다. 로컬에서 다음을 `create_indexes.py`로 저장한다.

   **접속 부분(첫 `db = ...` 줄까지)은 정형구다** — 시크릿 조회, `quote_plus` URI 조립, `replicaSet=rs0`·`retryWrites=false`, `tlsCAFile` 은 DocumentDB 라면 어느 과제에서나 같다. 이 블록을 복사해 두고, 과제지에 따라 바꾸는 것은 **아래 `create_index` 줄들과 시크릿·DB 이름**이다.

   ```python title="create_indexes.py"
   import json
   from urllib.parse import quote_plus

   import boto3
   from pymongo import ASCENDING, DESCENDING, MongoClient

   AWS_REGION = "ap-northeast-2"
   SECRET_NAME = "skills-nosql-docdb-secret"

   sec = json.loads(
       boto3.client("secretsmanager", region_name=AWS_REGION)
       .get_secret_value(SecretId=SECRET_NAME)["SecretString"]
   )
   uri = (
       f'mongodb://{quote_plus(sec["username"])}:{quote_plus(sec["password"])}'
       f'@{sec["host"]}:27017/?replicaSet=rs0&readPreference=secondaryPreferred&retryWrites=false'
   )
   db = MongoClient(uri, tls=True, tlsCAFile="/opt/skills-nosql/global-bundle.pem")["skills_retail"]

   db.orders.create_index([("orderId", ASCENDING)], unique=True)
   db.orders.create_index([("customerId", ASCENDING), ("createdAt", DESCENDING)])
   db.orders.create_index([("status", ASCENDING), ("dueAt", ASCENDING)])

   db.products.create_index([("productId", ASCENDING)], unique=True)
   db.products.create_index([("warehouseId", ASCENDING), ("stock", ASCENDING)])

   db.sessions.create_index([("sessionId", ASCENDING)], unique=True)
   db.sessions.create_index([("expiresAt", ASCENDING)], expireAfterSeconds=0)
   db.sessions.create_index([("customerId", ASCENDING), ("lastSeen", DESCENDING)])

   print("indexes created")
   ```

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   인덱스를 만드는 스크립트다. 접속 정보는 Secrets Manager 에서 받아 URI 를 조립하는데, 비밀번호에 특수문자가 있어도 깨지지 않게 `quote_plus` 로 감싼다. `replicaSet=rs0` 와 CA 번들 TLS 는 DocumentDB 접속의 필수 조건이고, `retryWrites=false` 는 DocumentDB 가 지원하지 않는 옵션을 끄는 것이다. 인덱스는 세 종류다 — 고유 인덱스, 조회 축에 맞춘 복합 인덱스, 그리고 `expireAfterSeconds=0` 인 TTL 인덱스로 세션을 만료 시각에 자동 삭제한다.

   </details>

   Client EC2는 이미 pymongo·CA 번들·Secrets Manager 권한을 전부 갖고 있으므로 그 위에서 실행한다:

## 함정 :badge[함정]{variant=danger}

- **Secret의 `host`에 스킴·포트가 섞이면** — `mongo_client()`가 URI를 만들기도 전에 `RuntimeError`. 모든 조회 API가 500. `describe-db-clusters`의 `Endpoint` 값을 그대로 쓴다.
- **`retail_dataset.json`을 mongoimport로 직접 적재하면** — 날짜가 문자열로 들어가 `dateFieldTypes`가 `"str"`이 되고 `pending` 범위 조회가 빈다. 반드시 `POST /v1/admin/seed`.
- **인덱스는 코드가 만들지 않는다** — `list_indexes()`만 있고 `create_index()`는 없다. 8단계를 건너뛰면 `/v1/admin/indexes`가 `_id_`만 보여준다.
- **`global-bundle.pem` 없이 접속 시도** — `os.path.exists(CA_FILE)` 체크에서 즉시 `RuntimeError`. user-data 로그(`cloud-init-output.log`)로 다운로드 성공 여부부터 확인한다.
- **인스턴스 프로파일을 만들자마자 `run-instances`** — 전파 지연으로 첫 시도가 실패할 수 있다. 몇 초 기다렸다 재시도한다.
- **systemd 서비스를 앱 파일 없이 `enable --now`** — 실패 상태로 남는다. user-data는 `enable`까지만 하고, 파일을 올린 뒤 `systemctl start`를 따로 호출하는 순서를 지킨다.
- **DocumentDB 인스턴스는 stop이 없다** — 잠깐 쉴 때도 삭제 아니면 계속 과금된다.

## 이행 — set-07 모듈1 로 엔진을 바꾼다 (ap-southeast-1)

기준본이 선 상태에서 시작한다. **이 커리큘럼에서 가장 큰 변동이다** — 값이 아니라 서비스 자체가 바뀐다.

### 변동 과제지

**정답 코드를 먼저 열지 않는다.**

| 항목 | set-08 (기준본) | set-07 (변동) |
|---|---|---|
| 리전 | `ap-northeast-2` | **`ap-southeast-1`** |
| 데이터 저장소 | 클러스터 + 인스턴스 | **테이블 2개** |
| 서버 | 있다 — 인스턴스 크기를 고른다 | **없다** |
| 위치 | VPC 안 | **VPC 밖 관리형 엔드포인트** |
| 접속 | 사용자명·비밀번호 | **IAM 신원** |
| 자격증명 보관 | Secrets Manager + 전용 키 | **불필요** |
| 네트워크 통제 | 보안 그룹 | **불필요** |
| 스키마·인덱스 | 접속해서 명령으로 만든다 | **선언으로 만든다** |
| 변경 감지 | 없다 | **변경 스트림 + 소비 함수** |
| 클라이언트 | 전용 EC2 가 CA 번들로 TLS 접속 | 함수가 SDK 로 호출 |

#### 요구에서 파생되는 것

**"서버가 없다"** 가 나머지 전부를 끌고 온다. 서버가 없으면 크기를 고를 필요가 없고, VPC 안에 둘 것이 없으니 보안 그룹도 서브넷 그룹도 없다. 접속 주소와 비밀번호가 없으니 그것을 보관할 곳도 없다.

**그래서 이 이행은 고칠 자리를 찾는 것이 아니라 지우고 새로 쓰는 것이다.** 기준본에서 옮겨 쓸 수 있는 것이 거의 없다 — 그것을 판정하는 것 자체가 훈련이다.

**"선언으로 만든다"** 도 성격이 다르다. 기준본은 저장소를 만든 뒤 접속해서 인덱스를 만들었다. 타깃은 **키 구조를 처음부터 선언**하고, 그 선언이 곧 조회 가능한 축을 정한다. 나중에 바꿀 수 있는 것과 없는 것이 갈린다.

**"변경 스트림"** 은 기준본에 아예 없던 요구다. 데이터가 바뀔 때마다 그것을 흘려보내고 받아 처리하는 경로가 새로 생긴다.

### 이행 (타이머 30분)

타이머를 걸고 시작한다. 아래는 절차가 아니라 **스스로 답해야 할 질문 목록**이다.

- 기준본에서 **지울 리소스 목록**은 무엇인가. 저장소 말고 몇 개가 더 사라지나
- 조회 요구를 읽고 **무엇을 파티션 키로, 무엇을 정렬 키로** 둘지 어떻게 정하나
- 기본 키로 못 푸는 조회가 있으면 어디에 무엇을 더 만드나
- 변경 스트림을 켜는 것과 그것을 함수에 잇는 것은 같은 리소스인가 다른 리소스인가
- 스트림이 흘려보내는 내용에 **바뀌기 전 값**이 필요한가. 그것을 정하는 설정은 무엇인가
- 클라이언트가 IAM 으로 접근하면 **어떤 액션**이 필요한가. 테이블과 인덱스가 같은 권한인가

**두 번째 질문에 시간을 쓴다.** 나머지는 그 결정에서 따라 나온다.

## 6. 과제지 오독 복구

배포까지 했는데 값이 다르다. 판정 축은 셋이다.

| 판정 | 무엇으로 아나 | 비용 |
|---|---|---|
| in-place | `plan` 에 `~ update in-place` | 초 |
| 재생성 | `plan` 에 `forces replacement` | 분 — **데이터가 사라진다** |
| **나중에 켤 수 있으나 과거는 안 온다** | 켜지긴 하는데 이전 변경은 흘러가지 않았다 | 초 + 재시드 |
| 지웠어야 하는 것 | 도구가 안 잡아 준다 | 초 + **시간당 과금 손실** |

### 6-1. 키 구조를 잘못 읽었다

**상황.** 조회 요구를 뒤집어 읽어 정렬 축이 될 속성을 파티션 키로 뒀다.

**판정.** 고치고 `plan` 을 낸다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  terraform plan -no-color | Select-String -Pattern 'forces replacement|# aws_dynamodb'
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  terraform plan -no-color | grep -E 'forces replacement|# aws_dynamodb'
  ```
  </TabItem>
</Tabs>

기대: 키 줄에 `forces replacement`. **키 구조는 테이블의 정체성이라 바꿀 수 없다.**

**파급.** **테이블 안의 데이터가 전부 사라진다.** 검증용 시드를 다시 넣어야 하고, 스트림을 켜 두었다면 그 스트림도 새로 만들어진다 — 소비 함수의 연결도 다시 걸린다.

**교훈.** [08 의 파티션 키](/part-1/08-container-lambda-dynamodb/lab/)와 같은 자리다. **조회 요구를 먼저 종이에 적고 키를 정한 뒤에 만들기 시작한다.**

### 6-2. 변경 스트림을 안 켜고 만들었다

**상황.** 테이블은 요구대로 만들었는데 변경 스트림 요구를 놓쳤다. 나중에 발견했다.

**판정.** 스트림은 **나중에 켤 수 있다.** 테이블이 재생성되지 않는다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  terraform plan -no-color | Select-String -Pattern 'stream|forces replacement'
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  terraform plan -no-color | grep -E 'stream|forces replacement'
  ```
  </TabItem>
</Tabs>

기대: `~ update in-place` 로 스트림 설정이 붙고 `forces replacement` 는 없다.

**파급.** 값은 싼데 **시간 축이 붙는다.** 스트림은 켠 시점부터 흐른다 — **켜기 전에 일어난 변경은 영원히 안 온다.** 소비 함수가 그 변경들을 처리하기로 되어 있었다면 그 결과물이 비어 있다.

**복구가 두 단계다.**

<Steps>

1. 스트림을 켜고 소비 함수를 잇는다 — 초 단위

2. **데이터를 다시 써서 변경을 새로 만든다** — 그래야 소비 함수가 처리한 결과가 생긴다

</Steps>

**교훈.** [11 의 로그 그룹](/part-2/11-observability/lab/)과 같은 종류다. **흘러가는 것을 다루는 요구는 "고친 시각"이 아니라 "흐르기 시작한 시각"이 기준이다.** 채점 직전에 켜면 켜도 늦는다.

### 6-3. 기준본 저장소를 안 지웠다

**상황.** 새 저장소는 요구대로 만들었는데 기준본의 클러스터가 그대로 돌고 있다.

**판정.** 채점에 그것을 검사하는 항목이 없다. **없다는 사실이 근거다.** 그리고 이번엔 근거가 하나 더 있다 — **돈이 계속 나간다.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws docdb describe-db-clusters --region ap-northeast-2 --query "DBClusters[].DBClusterIdentifier" --output text
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws docdb describe-db-clusters --region ap-northeast-2 --query "DBClusters[].DBClusterIdentifier" --output text
  ```
  </TabItem>
</Tabs>

기대: 빈 출력.

**복구.** 정리 절의 의존 순서대로 지운다. 인스턴스 먼저, 그다음 클러스터다.

**교훈.** 다른 모듈의 삭제 판단은 감점만 걸려 있었다. 여기는 **잔존 리소스가 시간당 과금**이라 잊으면 값이 계속 커진다. 그리고 **이 저장소는 정지가 없다** — 잠깐 쉬는 선택지가 없어서 지우거나 계속 내거나 둘 중 하나다.

## 7. 장애 진단

정상으로 선 상태에서 일부러 고장을 내고 증상만 보고 좁혀 간다. **주입 명령과 복구 명령이 짝으로 있다.**

### 7-1. 소비 함수가 스트림을 못 읽는다

**주입.** 함수와 스트림을 잇는 연결을 끈다. 연결 ID 는 첫 명령이 알려준다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws lambda list-event-source-mappings --region ap-southeast-1 --query "EventSourceMappings[].[UUID,State,EventSourceArn]" --output text
  aws lambda update-event-source-mapping --region ap-southeast-1 --uuid <uuid> --no-enabled
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws lambda list-event-source-mappings --region ap-southeast-1 --query "EventSourceMappings[].[UUID,State,EventSourceArn]" --output text
  aws lambda update-event-source-mapping --region ap-southeast-1 --uuid <uuid> --no-enabled
  ```
  </TabItem>
</Tabs>

**증상.** 데이터를 써도 소비 함수가 안 돈다. **함수 로그에 새 줄이 하나도 안 생긴다.** 테이블 쓰기는 정상이다.

**좁히는 순서.**

<Steps>

1. **쓰기는 됐나** — 테이블을 조회해 항목이 들어갔는지 본다. 안 들어갔으면 스트림 이전 문제다

2. **로그가 있나 없나** — 함수 로그에 새 줄이 아예 없으면 **함수 안으로 못 들어간 것이다.** 있으면 들어가서 실패한 것이라 코드·권한 문제다. [08 의 7-2](/part-1/08-container-lambda-dynamodb/lab/)와 같은 갈림이다

3. **연결이 살아 있나** — 이벤트 소스 연결의 상태를 본다. `Disabled` 나 목록에 없으면 여기가 원인이다

4. **연결은 있는데 안 돌면** 그때 함수 역할의 스트림 읽기 권한을 본다. 테이블 읽기 권한과 **다른 액션**이다

</Steps>

4번이 이 모듈 고유다. 테이블을 읽는 권한과 그 테이블의 스트림을 읽는 권한은 **서로 다른 액션이고 리소스 ARN 도 다르다.** 테이블 권한만 주고 끝내면 연결이 만들어지지도 않는다.

**복구.**

```bash
aws lambda update-event-source-mapping --region ap-southeast-1 --uuid <uuid> --enabled
```

또는 코드로 되돌린다.

```bash
terraform plan
terraform apply
```

### 7-2. 조건부 쓰기가 항상 실패한다

**주입.** 조건식이 참조하는 속성 이름을 바꾼다. 애플리케이션 쪽 설정이라면 환경 변수 하나로 재현한다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws lambda get-function-configuration --region ap-southeast-1 --function-name <함수> --query "Environment.Variables" --output json
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws lambda get-function-configuration --region ap-southeast-1 --function-name <함수> --query "Environment.Variables" --output json
  ```
  </TabItem>
</Tabs>

받아 둔 값을 적어 두고 하나를 틀린 이름으로 바꿔 재현한다.

**증상.** 쓰기 요청이 전부 실패하는데 에러가 권한 거부가 아니다. 조건이 만족되지 않았다는 응답이 온다.

**좁히는 순서.**

<Steps>

1. **에러 종류를 가른다** — 권한 거부인가 조건 불만족인가. **둘은 완전히 다른 방향이다.** 조건 불만족이면 권한은 정상이고 데이터·조건식 쪽이다

2. **조건이 무엇을 보고 있나** — 조건식이 참조하는 속성 이름을 실제 항목의 속성 이름과 대조한다

3. **키 속성과 헷갈리지 않았나** — 키 이름과 조건에 쓰는 속성은 다를 수 있다. 키 구조를 다시 읽는다

4. **항목이 실제로 있나** — "없을 때만 쓴다"류 조건은 항목이 이미 있으면 정상적으로 실패한다. **실패가 정상 동작인 경우를 구분한다**

</Steps>

4번이 함정이다. 조건부 쓰기는 **실패하라고 만든 장치**라 실패 자체가 고장이 아니다. 같은 키로 두 번 쓰면 두 번째가 실패하는 것이 설계대로다.

**복구.** 적어 둔 값으로 되돌린다.

**교훈.** **"에러가 났다"와 "설계대로 거절됐다"를 가르는 것**이 이 진단의 전부다. 조건부 쓰기·중복 방지·멱등 처리는 전부 실패를 내장한 장치라, 로그에 실패가 보인다고 고장이라 단정하지 않는다.
