## 0. 기준본 세우기

[Lab 29](/part-4/29-gitops-rollouts/lab/)를 마친 상태에서 시작한다. 클러스터와 ArgoCD·Rollouts·External Secrets 가 서 있어야 한다.

섰는지 한 줄로 확인한다.

```bash
kubectl argo rollouts get rollout red-rollout -n skills | egrep "Strategy|Status"
```

`Strategy: BlueGreen` 과 정상 상태가 나오면 시작한다.

:::danger[클러스터가 시간당 과금한다]
EKS 컨트롤 플레인과 노드가 계속 과금한다. **타이머를 걸고 6절까지 한 번에 끝낸다.**
:::

## 1. 변동 과제지

**정답 코드를 먼저 열지 않는다.**

> 새 버전을 한 번에 전환하지 않고 **소수의 사용자에게 먼저 노출한 뒤 단계적으로 늘리도록** 배포 전략을 바꾼다. 트래픽은 20% → 50% → 100% 로 올리고, 각 단계 사이에 **자동으로 상태를 검사해 실패하면 이전 버전으로 되돌아가야** 한다. 사람이 명령을 치지 않아도 끝까지 진행되어야 한다.

기준본과의 차이다.

| 항목 | Lab 29 (기준본) | 이 드릴 (타깃) |
|---|---|---|
| 전략 | Blue/Green | **Canary** |
| 트래픽 배분 | 0% 또는 100% | **20 → 50 → 100** |
| 서비스 | active · preview 둘 | **하나로 충분한가?** |
| 분석 시점 | 승격 전 한 번 | **단계마다** |
| 실패 시 | 미리보기에 머문다 | **자동 롤백** |
| 사람의 개입 | 승격 판단 | 없다 |

### 요구에서 파생되는 것

**"단계적으로 늘린다"** 는 한 줄이 나머지를 결정한다.

Blue/Green 은 트래픽이 두 값 중 하나다 — 새 버전이 0% 거나 100% 다. Canary 는 그 사이에 값이 생기므로 **트래픽을 비율로 나눌 수 있는 무엇**이 필요하다. 서비스 두 개를 셀렉터로 가르던 방식으로는 20% 를 표현할 수 없다.

"각 단계 사이에 자동으로 검사"는 분석을 **몇 번 도느냐**의 문제다. 기준본은 승격 직전 한 번이었다. 단계마다 돌면 분석 대상이 그때그때 달라진다 — 무엇을 향해 질의할지가 단계별로 정해져야 한다.

기준본의 미리보기 서비스는 **지울 후보다.** 남겨 두면 아무도 안 쓰는 서비스가 남는다.

## 2. 이행 (타이머 25분)

타이머를 걸고 시작한다. 아래는 절차가 아니라 **스스로 답해야 할 질문 목록**이다.

- `strategy` 아래에서 `blueGreen` 을 무엇으로 바꾸나. 그 블록이 받는 하위 키는 무엇인가
- 20% 를 표현하는 키와 "다음 단계로 넘어가기 전 기다린다"를 표현하는 키는 각각 무엇인가
- 트래픽을 실제로 비율대로 나누려면 무엇이 더 필요한가. **아무것도 안 붙이면 비율이 어떻게 근사되나**
- 단계마다 분석을 돌리는 블록의 이름은 무엇이고, Blue/Green 의 승격 전 분석과 키 이름이 같은가
- 분석이 실패하면 자동으로 되돌아가나, 아니면 멈추고 기다리나. 그것을 정하는 값이 있나
- 기준본의 **미리보기 서비스는 남기나 지우나.** 판단의 근거는 무엇인가
- ArgoCD 가 이 변경을 언제 가져가나. 커밋 후 반영까지 무엇이 시간을 먹나

:::note[막히면 여기]
- [Argo Rollouts — Canary](https://argo-rollouts.readthedocs.io/en/stable/features/canary/)
- [Analysis 와 Progressive Delivery](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/)
- 개념이 흔들리면 [이론 3절](/part-4/29-gitops-rollouts/theory/)
:::

## 3. 통과 기준

<Steps>

1. **옛 전략 잔존 0건**

   ```bash
   grep -rn "blueGreen\|previewService" gitops/
   ```

   빈 출력이어야 한다.

2. **매니페스트가 유효하다**

   ```bash
   kubectl apply --dry-run=server -f gitops/rollout.yaml
   ```

3. **전략과 단계가 등록됐다**

   ```bash
   kubectl argo rollouts get rollout red-rollout -n skills | egrep "Strategy|Step|SetWeight"
   ```

   `Canary` 와 세 단계가 보여야 한다.

4. **실제로 단계가 돈다**

   이미지 태그를 올리고 커밋한 뒤 지켜본다.

   ```bash
   kubectl argo rollouts get rollout red-rollout -n skills --watch
   ```

   비율이 20 → 50 → 100 으로 올라가고 **사람이 promote 를 치지 않아도** 끝나야 한다.

5. **실패하면 되돌아간다**

   없는 태그로 커밋해 본다. 분석이 실패하고 이전 버전으로 돌아가는지 본다.

   ```bash
   kubectl argo rollouts get rollout red-rollout -n skills | egrep "Status|Message"
   ```

</Steps>

## 4. 복기

다섯 개를 통과시킨 뒤에 연다.

<details>
<summary>정답 구성 — 열기 전에 자기 답을 적어 둔다</summary>

```yaml title="gitops/rollout.yaml"
spec:
  strategy:
    canary:
      steps:
        - setWeight: 20
        - pause: { duration: 60s }
        - analysis:
            templates:
              - templateName: red-health
        - setWeight: 50
        - pause: { duration: 60s }
        - analysis:
            templates:
              - templateName: red-health
        - setWeight: 100
      analysis:
        templates:
          - templateName: red-health
        startingStep: 1
```

세 가지가 걸린다.

**첫째, 트래픽 분리 장치가 없으면 비율이 파드 수로 근사된다.** `trafficRouting` 을 붙이지 않으면 20% 는 "복제본 5개 중 1개"로 흉내 낼 뿐이다. 요구가 비율의 정확성을 말하면 ALB 나 서비스 메시 쪽 설정이 함께 필요하다.

**둘째, 분석 실패 시 동작이 전략마다 다르다.** Canary 의 인라인 `analysis` 는 실패하면 롤아웃을 `Degraded` 로 만들고 되돌린다. `steps` 안의 `analysis` 는 그 단계에서 멈춘다 — "자동으로 되돌아가야" 라는 요구에는 앞쪽이 맞다.

**셋째, 미리보기 서비스는 지운다.** Canary 에는 그 개념이 없다. 남기면 아무 파드도 안 가리키는 서비스가 남는다.

</details>

놓친 곳을 분류한다.

| 분류 | 뜻 | 다음에 할 것 |
|---|---|---|
| 몰라서 못 했다 | `steps` 문법 | 그 문서 한 쪽만 다시 읽는다 |
| 알았는데 빠뜨렸다 | 미리보기 서비스 삭제 | 지울 목록을 먼저 적는 습관 |
| 근사를 정답으로 봤다 | 비율이 파드 수로 흉내 난 것을 통과로 판단 | 요구가 무엇을 재는지 다시 읽는다 |

## 5. 고장 진단

기준본을 되살린 뒤 아래를 심고 **증상만 보고 원인을 좁힌다.** 둘 다 [이론](/part-4/29-gitops-rollouts/theory/)에 실측으로 기록된 것이다.

### 5-1. 시크릿이 동기화되지 않는다

ServiceAccount 의 IRSA 애노테이션에서 역할 ARN 한 글자를 바꾼다.

```
증상: ExternalSecret 이 SecretSyncedError. 앱 파드는 뜨지도 못한다.
```

무엇부터 보나. 순서를 적고 나서 연다.

<details>
<summary>볼 곳의 순서</summary>

고리가 넷이고 **앞에서부터** 끊긴 자리를 찾는다.

1. ServiceAccount 에 애노테이션이 있나 — `kubectl get sa -n skills -o yaml`
2. 그 ARN 의 역할이 실제로 있나 — `aws iam get-role`
3. 신뢰 정책의 `sub` 가 이 네임스페이스·이 SA 를 가리키나
4. Operator 로그 — `kubectl logs -n external-secrets deploy/external-secrets`

앱 파드 로그를 먼저 보면 시간을 버린다. **시크릿이 없어 뜨지도 못했으므로 거기엔 아무것도 없다.**

</details>

### 5-2. 권한은 줬는데 거부된다

IAM 정책의 Resource 에서 Secrets Manager ARN 끝 여섯 자를 지운다.

```
증상: AccessDenied. 정책에 GetSecretValue 는 분명히 있다.
```

<details>
<summary>볼 곳의 순서</summary>

Action 이 아니라 **Resource** 를 본다. Secrets Manager 의 ARN 은 끝에 임의 6자가 붙는다.

```bash
aws secretsmanager describe-secret --secret-id <이름> --query ARN
```

정책에 적힌 문자열과 이 값을 문자 단위로 대조한다. 이름까지만 적으면 안 맞는다. 와일드카드를 쓰려면 `-??????` 형태로 끝을 열어 둔다.

</details>
