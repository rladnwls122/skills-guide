## 0. 기준본 세우기

[Lab 30](/part-4/30-stepfunctions-apigw/lab/)을 마친 상태를 되살린다.

```bash
cd ~/sfn-lab
terraform apply -auto-approve
```

동작하는지 한 줄로 확인한다.

```bash
aws dynamodb put-item --table-name inventory --item '{"name":{"S":"stock"},"value":{"N":"50"}}'
aws dynamodb get-item --table-name inventory --key '{"name":{"S":"stock"}}' --query Item.value.N --output text
```

`50` 이 나오면 시작한다.

---

## 1. 변동 과제지

**정답 코드를 먼저 열지 않는다.**

> 현재 API 는 요청받은 판매량을 검사 없이 재고에서 뺀다. 재고보다 많이 팔면 **재고가 음수가 된다.**
>
> 판매 요청이 현재 재고를 넘으면 **아무것도 바꾸지 않고** HTTP `409` 와 `{"message":"insufficient stock"}` 을 돌려주도록 고친다. 동시에 여러 요청이 들어와도 재고가 음수가 되지 않아야 한다.

먼저 기준본이 실제로 그런지 확인한다.

```bash
aws dynamodb put-item --table-name inventory --item '{"name":{"S":"stock"},"value":{"N":"5"}}'
SM_ARN=$(aws stepfunctions list-state-machines --query 'stateMachines[0].stateMachineArn' --output text)
aws stepfunctions start-execution --state-machine-arn "$SM_ARN" --input '{"sales": 20}'
sleep 5
aws dynamodb get-item --table-name inventory --key '{"name":{"S":"stock"}}' --query Item.value.N --output text
```

`-15` 가 나온다. **취약함을 먼저 확인하는 것이 순서다.**

기준본과의 차이다.

| 항목 | Lab 30 (기준본) | 이 드릴 (타깃) |
|---|---|---|
| 검사하는 것 | `sales` 가 1~30 인가 | **+ 재고보다 작은가** |
| 재고를 읽는 상태 | 없다 | 필요한가? |
| 부족할 때 | 그냥 뺀다 | **아무것도 바꾸지 않는다** |
| 응답 | 200 만 | **409 + 메시지** |
| 동시 요청 | 고려하지 않음 | **음수가 되면 안 된다** |

### 요구에서 파생되는 것

**"아무것도 바꾸지 않는다"** 가 첫 번째 함정이다. 재고 차감과 잔고 증가가 두 상태로 나뉘어 있으므로, 앞이 성공하고 뒤가 실패하면 절반만 반영된 상태가 남는다.

**"동시에 여러 요청"** 이 두 번째다. 읽고 → 판단하고 → 쓰는 사이에 남이 끼어들 수 있다. 읽은 값이 판단 시점에 이미 낡았다면 검사는 통과했는데 결과는 음수가 된다. **읽어서 판단하는 방식으로 이 요구를 만족시킬 수 있는지**부터 생각한다.

## 2. 이행 (타이머 25분)

타이머를 걸고 시작한다. 아래는 절차가 아니라 **스스로 답해야 할 질문 목록**이다.

- 재고를 읽어 비교하는 방식으로 가면 상태가 몇 개 늘어나나. 그 방식이 동시 요청 요구를 만족하나
- DynamoDB 가 **쓰기 시점에** 조건을 검사하게 하는 인자는 무엇인가. 조건이 거짓이면 어떤 오류가 오나
- 그 오류를 상태 머신이 잡으려면 어느 필드에 무엇을 적나. 오류 이름의 정확한 문자열은 어디서 확인하나
- 실패 경로에서 잔고 증가로 넘어가지 않게 하려면 어디를 끊나
- API Gateway 가 409 를 낼 수 있으려면 **응답 템플릿 말고 무엇을 먼저 등록**해야 하나
- 상태 머신의 실패를 API 응답 상태코드로 옮기는 자리는 통합 응답인가 메서드 응답인가
- 성공 경로의 200 은 그대로 유지되나

:::note[막히면 여기]
- [Choice · Catch — Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)
- [ConditionExpression — DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Expressions.ConditionExpressions.html)
- 개념이 흔들리면 [이론 2절](/part-4/30-stepfunctions-apigw/theory/)
:::

## 3. 통과 기준

<Steps>

1. **정의가 유효하다**

   ```bash
   terraform validate && terraform plan
   ```

2. **충분하면 그대로 된다**

   ```bash
   aws dynamodb put-item --table-name inventory --item '{"name":{"S":"stock"},"value":{"N":"50"}}'
   curl -s -o /dev/null -w '%{http_code}\n' -X POST "$API_URL" -d '{"sales": 20}'
   aws dynamodb get-item --table-name inventory --key '{"name":{"S":"stock"}}' --query Item.value.N --output text
   ```

   `200` 과 `30` 이 나온다.

3. **모자라면 409 이고 값이 그대로다**

   ```bash
   curl -s -w '\n%{http_code}\n' -X POST "$API_URL" -d '{"sales": 100}'
   aws dynamodb get-item --table-name inventory --key '{"name":{"S":"stock"}}' --query Item.value.N --output text
   ```

   `insufficient stock` 과 `409`, 그리고 재고가 **`30` 그대로**여야 한다.

4. **잔고도 안 움직였다**

   ```bash
   aws dynamodb get-item --table-name inventory --key '{"name":{"S":"balance"}}' --query Item.value.N --output text
   ```

   실패한 요청이 잔고를 올렸다면 절반만 반영된 것이다.

5. **동시에 던져도 음수가 없다**

   ```bash
   aws dynamodb put-item --table-name inventory --item '{"name":{"S":"stock"},"value":{"N":"10"}}'
   for i in $(seq 1 10); do curl -s -o /dev/null -X POST "$API_URL" -d '{"sales": 3}' & done; wait
   aws dynamodb get-item --table-name inventory --key '{"name":{"S":"stock"}}' --query Item.value.N --output text
   ```

   **0 이상**이어야 한다.

</Steps>

## 4. 복기

다섯 개를 통과시킨 뒤에 연다.

<details>
<summary>정답 구성 — 열기 전에 자기 답을 적어 둔다</summary>

읽어서 비교하는 방식은 5번을 통과하지 못한다. **판단을 쓰기 시점으로 옮긴다.**

```json title="상태 머신 — DecreaseStock"
"DecreaseStock": {
  "Type": "Task",
  "Resource": "arn:aws:states:::aws-sdk:dynamodb:updateItem",
  "Parameters": {
    "TableName": "inventory",
    "Key": { "name": { "S": "stock" } },
    "UpdateExpression": "SET #v = #v - :sales",
    "ConditionExpression": "#v >= :sales",
    "ExpressionAttributeNames": { "#v": "value" },
    "ExpressionAttributeValues": { ":sales": { "N.$": "States.Format('{}', $.sales)" } }
  },
  "Catch": [{
    "ErrorEquals": ["DynamoDb.ConditionalCheckFailedException"],
    "Next": "InsufficientStock"
  }],
  "Next": "IncreaseBalance"
},
"InsufficientStock": {
  "Type": "Fail",
  "Error": "InsufficientStock",
  "Cause": "insufficient stock"
}
```

세 가지가 걸린다.

**첫째, 조건은 쓰기와 한 번에 평가된다.** 읽고 판단하면 그 사이에 남이 끼어들 수 있지만, `ConditionExpression` 은 갱신과 같은 연산에서 검사되므로 경합이 없다.

**둘째, 실패가 `Catch` 로 잡혀 `IncreaseBalance` 로 넘어가지 않는다.** 절반 반영이 여기서 막힌다.

**셋째, API Gateway 는 메서드 응답에 등록한 상태코드만 낼 수 있다.** 통합 응답에서 409 를 만들어도 메서드 응답에 409 가 없으면 무시되거나 500 이 난다.

```hcl
resource "aws_api_gateway_method_response" "conflict" {
  # ...
  status_code = "409"
}
```

</details>

놓친 곳을 분류한다.

| 분류 | 뜻 | 다음에 할 것 |
|---|---|---|
| 몰라서 못 했다 | 조건부 쓰기·오류 이름 | 그 문서 한 쪽만 다시 읽는다 |
| 통과했지만 경합에 약하다 | 읽고 판단하는 방식 | 5번 같은 동시 요청 검사를 습관으로 |
| 응답이 안 바뀐다 | 메서드 응답 미등록 | 상태코드는 두 자리에 등록한다 |

## 5. 고장 진단

기준본을 되살린 뒤 아래를 심고 **증상만 보고 원인을 좁힌다.** 둘 다 [이론](/part-4/30-stepfunctions-apigw/theory/)에 기록된 함정이다.

### 5-1. 숫자 대신 글자가 저장된다

`ExpressionAttributeValues` 의 키에서 `.$` 를 뗀다.

```
증상: 실행은 성공한다. 그런데 DynamoDB 에 $.sales 라는 글자가 들어 있다.
```

<details>
<summary>볼 곳의 순서</summary>

**오류가 나지 않는 것이 이 함정의 성질이다.** 값이 경로로 해석되지 않고 문자열 그대로 들어간다.

키 이름 끝에 `.$` 가 붙어야 그 값을 경로로 읽는다. 실행 이력의 입력·출력을 보면 어느 상태에서 값이 글자로 바뀌었는지 보인다.

```bash
aws stepfunctions get-execution-history --execution-arn <arn> --reverse-order --max-items 5
```

</details>

### 5-2. 403 을 썼는데 200 이 온다

메서드 응답에서 403 등록만 지운다(통합 응답은 그대로 둔다).

```
증상: 응답 템플릿은 분명히 403 을 내는데 클라이언트는 200 을 받는다.
```

<details>
<summary>볼 곳의 순서</summary>

VTL 문법 오류와 구분한다 — 문법이 틀리면 500 이 나거나 본문이 깨진다. 200 이 온다는 것은 템플릿이 돌았다는 뜻이다.

```bash
aws apigateway get-method --rest-api-id <id> --resource-id <r> --http-method POST \
  --query 'methodResponses'
```

등록된 상태코드 목록에 403 이 없으면 그것이 답이다.

</details>
