## 1. Macie 가 하는 일

S3 에 저장된 데이터를 훑어 민감 정보가 있는지 찾는다. 사람이 정규식을 쓰지 않아도 AWS 가 미리 만들어 둔 **관리형 데이터 식별자**가 찾아 준다.

| 개념 | 뜻 |
|---|---|
| 분류 작업(Classification Job) | "이 버킷의 이 범위를 검사해라"라는 한 건의 지시 |
| 관리형 데이터 식별자 | AWS 가 제공하는 탐지 규칙. 카드번호·주민번호·이메일 등 |
| 사용자 지정 식별자 | 직접 만든 정규식 규칙 |
| 발견 항목(Finding) | 검사 결과. 어느 객체에서 무엇을 몇 건 찾았는지 |

### 1-1. 무엇을 찾는가

2025 배포 파일 여섯 종과 관리형 식별자의 대응이다.

| 파일 | 식별자 | 비고 |
|---|---|---|
| `credit_cards.txt` | `CREDIT_CARD_NUMBER` | 체크섬까지 검증한다 |
| `emails.txt` | 이메일 계열 | 형식으로 판단 |
| `phones.txt` | 전화번호 계열 | 국가별 형식 |
| `ssns.txt` | `USA_SOCIAL_SECURITY_NUMBER` 등 | 형식이 미국 SSN 과 같다 |
| `names.txt` | `NAME` | 사람 이름 패턴 |
| `uuids.txt` | 사용자 지정이 필요할 수 있다 | 관리형 목록에 없을 수 있다 |

:::caution[UUID 는 관리형 식별자가 없을 수 있다]
관리형 목록은 개인 식별 정보 위주다. UUID 는 그 자체로 민감 정보가 아니라 목록에 없을 수 있다.

그러면 **사용자 지정 데이터 식별자**를 만든다.

```
정규식: [0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{12}
```

문제지는 "배포 파일 내의 모든 민감한 정보를 정확히 감지할 수 있어야" 한다고만 썼다. 관리형으로 안 되면 사용자 지정으로 채운다.
:::

### 1-2. 작업 범위를 좁힌다

요구를 그대로 읽는다.

> Job 생성 시 S3 버킷 내 masked 접두어(prefix)를 가진 객체들에 대해서만 민감한 데이터를 감지하도록 설정하고, Job 은 한 번만 실행되도록 구성해야 합니다.

두 가지다.

**첫째, `masked/` 만 검사한다.** 작업의 범위 조건에 접두사 필터를 건다.

```json
{
  "scoping": {
    "includes": {
      "and": [{
        "simpleScopeTerm": {
          "comparator": "STARTS_WITH",
          "key": "OBJECT_KEY",
          "values": ["masked/"]
        }
      }]
    }
  }
}
```

**둘째, 한 번만 실행한다.** 작업 유형이 `ONE_TIME` 이다. `SCHEDULED` 로 두면 반복 실행되어 과금이 계속 늘어난다.

:::note[왜 `masked/` 만 검사하나]
채점 방식 때문이다. 채점자가 이 작업을 **복사해서** 쓴다. 마스킹 결과에 민감 정보가 남아 있으면 발견 항목이 생기고, 그것이 곧 마스킹 실패의 증거다.

`incoming/` 은 원본이라 당연히 감지된다. 검사할 이유가 없다.
:::

### 1-3. 결과 읽기

```bash
aws macie2 list-findings --query 'findingIds'
aws macie2 get-findings --finding-ids <ID> \
  --query 'findings[*].{type:type,resource:resourcesAffected.s3Object.key,counts:classificationDetails.result.sensitiveData}'
```

`sensitiveData` 에 유형별 건수가 나온다. **마스킹이 완전하면 이 목록이 비어야 한다.**

어느 유형이 남았는지 보면 어느 정규식이 부족한지 바로 안다.

## 2. S3 이벤트가 Lambda 를 부르는 경로

```mermaid
flowchart LR
    UP["파일 업로드"] --> IN["S3 incoming/"]
    IN -->|"이벤트 알림<br/>(접두사 incoming/)"| LAM["Lambda<br/>wsc2025-masking-start"]
    LAM -->|"읽기"| IN
    LAM -->|"마스킹 후 쓰기"| MK["S3 masked/"]
    MK -.->|"검사 대상"| MAC["Macie 작업"]
```

<details class="diagram-note">
<summary>이 도식이 보여주는 것</summary>

같은 버킷 안에서 읽고 쓴다는 점이 위험 지점이다. 트리거 조건을 `incoming/` 으로 좁히지 않으면 `masked/` 에 쓴 파일이 다시 트리거를 불러 끝없이 돈다. 점선이 채점 경로다 — Macie 는 `masked/` 만 본다.

</details>

### 2-1. 무한루프를 막는 두 겹

**첫 겹은 접두사 필터다.**

```hcl
resource "aws_s3_bucket_notification" "this" {
  bucket = aws_s3_bucket.sensitive.id

  lambda_function {
    lambda_function_arn = aws_lambda_function.masking.arn
    events              = ["s3:ObjectCreated:*"]
    filter_prefix       = "incoming/"      # 이것이 없으면 무한루프
  }
}
```

**둘째 겹은 코드에서 확인하는 것이다.**

```python
key = record["s3"]["object"]["key"]
if not key.startswith("incoming/"):
    return {"statusCode": 200, "skipped": key}
```

:::danger[필터 하나만 믿지 않는다]
설정을 고치다 필터가 빠질 수 있다. 코드의 확인이 마지막 안전장치다. 무한루프가 나면 Lambda 호출과 S3 요청이 폭증해 과금이 급격히 는다.

이미 돌기 시작했다면 이벤트 알림을 지워 끊는다.

```bash
aws s3api put-bucket-notification-configuration \
  --bucket <버킷> --notification-configuration '{}'
```
:::

### 2-2. Lambda 를 부를 권한

두 방향이 모두 필요하다.

| 방향 | 무엇 |
|---|---|
| S3 → Lambda | Lambda 리소스 기반 정책에 S3 호출 허용 |
| Lambda → S3 | 실행 역할에 `s3:GetObject` · `s3:PutObject` |

첫 번째를 빠뜨리는 일이 흔하다.

```hcl
resource "aws_lambda_permission" "s3" {
  statement_id  = "AllowS3Invoke"
  action        = "lambda:InvokeFunction"
  function_name = aws_lambda_function.masking.function_name
  principal     = "s3.amazonaws.com"
  source_arn    = aws_s3_bucket.sensitive.arn
}
```

없으면 이벤트 알림 설정 자체가 실패한다.

```
Unable to validate the following destination configurations
```

## 3. 마스킹 정규식 여섯 종

여기가 이 모듈의 본론이다. 표의 여섯 줄을 정확히 만족시켜야 한다.

### 3-1. 규칙마다 살릴 부분과 가릴 부분

| 유형 | 살린다 | 가린다 |
|---|---|---|
| 이름 | 성(첫 단어) | 나머지 단어를 글자 수만큼 `*` |
| 이메일 | 로컬부 첫 글자 + `@도메인` | 로컬부 나머지를 글자 수만큼 `*` |
| 전화 | 앞 두 마디 | 마지막 네 자리를 `****` |
| 주민번호 | 앞 두 마디 | 마지막 네 자리를 `****` |
| 카드 | 앞 세 마디 | 마지막 네 자리를 `****` |
| UUID | 앞 네 마디 | 마지막 12자리를 `************` |

**뒤 네 개는 같은 모양이다.** "마지막 마디를 별표로"라는 한 가지 규칙이다.

### 3-2. 자릿수를 세는 것과 고정 개수의 차이

표를 자세히 본다.

```
Crystal White        -> Crystal *****      (White 5글자 -> * 5개)
davisjesus@...       -> d*********@...     (avisjesus 9글자 -> * 9개)
010-7658-5153        -> 010-7658-****      (언제나 * 4개)
```

앞 둘은 **원래 길이만큼** 별표를 찍고, 뒤 넷은 **고정 개수**다. 구현 방식이 달라진다.

```python
# 길이에 맞춰 — 함수를 넘긴다
def mask_name(text):
    def repl(m):
        first, rest = m.group(1), m.group(2)
        return first + " " + "*" * len(rest)
    return re.sub(r"(\w+)\s+(\w+)$", repl, text)

# 고정 개수 — 치환 문자열로 충분하다
re.sub(r"(\d{2,3}-\d{3,4}-)\d{4}", r"\1****", text)
```

### 3-3. 겹침 문제

전화번호와 주민번호 규칙이 서로 걸린다.

```
전화 규칙:     (\d{2,3}-\d{3,4}-)\d{4}
주민번호:      887-07-7325
```

`887-07-7325` 에서 `\d{2,3}` 이 `887`, `\d{3,4}` 가 `07` 에 맞지 않는다(`{3,4}` 는 최소 3자리). 이번 예에서는 안 걸린다. 그런데 카드는 다르다.

```
카드:          4468-6779-7028-4776
전화 규칙 적용: 4468-6779-**** 부분이 걸릴 수 있다
```

`\d{2,3}` 은 최대 3자리인데 `4468` 은 4자리다. 앞에서부터 맞추면 `468-6779-7028` 이 전화 형식과 맞아 잘못 걸린다.

:::danger[경계를 명시하지 않으면 긴 숫자의 일부가 걸린다]
`\b` 로 단어 경계를 붙인다.

```python
(r"\b(\d{2,3}-\d{3,4}-)\d{4}\b", r"\1****")
```

`\b` 는 단어 문자와 그렇지 않은 것의 경계다. `4468-6779-7028-4776` 안쪽에서는 하이픈 양쪽이 모두 숫자라 경계가 성립하지 않아 걸리지 않는다.
:::

**순서도 정한다. 가장 긴 것부터.**

```python
PATTERNS = [
    # 1. UUID — 가장 길고 형식이 독특하다
    (r"\b([0-9a-fA-F]{8}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-[0-9a-fA-F]{4}-)[0-9a-fA-F]{12}\b",
     r"\1************"),
    # 2. 카드 — 네 마디
    (r"\b(\d{4}-\d{4}-\d{4}-)\d{4}\b", r"\1****"),
    # 3. 전화 — 세 마디, 마지막 4자리
    (r"\b(\d{2,3}-\d{3,4}-)\d{4}\b", r"\1****"),
    # 4. 주민번호 — 세 마디, 마지막 4자리
    (r"\b(\d{3}-\d{2}-)\d{4}\b", r"\1****"),
]
```

긴 것부터 처리하면 짧은 규칙이 그 안쪽을 건드릴 기회가 없다. 이미 별표로 바뀌어 숫자가 아니기 때문이다.

### 3-4. 이름의 어려움

`names.txt` 의 실제 내용을 보면 형태가 여럿이다.

```
Nicole Huff
Crystal White
Mrs. Brianna Rodriguez
```

세 번째는 경칭이 붙어 세 토막이다. 표의 예시(`Crystal White` → `Crystal *****`)만 보고 "두 번째 단어를 가린다"로 만들면 세 토막에서 결과가 달라진다.

**판단이 필요하다.** 표의 규칙을 "첫 단어만 남기고 나머지를 가린다"로 읽을지, "마지막 단어를 가린다"로 읽을지다.

| 해석 | `Mrs. Brianna Rodriguez` 결과 |
|---|---|
| 첫 단어만 남긴다 | `Mrs. ******* *********` |
| 마지막 단어를 가린다 | `Mrs. Brianna *********` |

:::note[채점 기준이 Macie 다]
어느 쪽이든 **Macie 가 이름으로 감지하지 않으면 통과**다. `Mrs. Brianna *********` 가 여전히 이름으로 감지되면 첫 번째 해석을 써야 한다.

돌려 보고 결정하는 것이 정답이다. 이 모듈은 추론보다 실측이 빠르다.
:::

### 3-5. 이메일

```python
def mask_email(text):
    def repl(m):
        local, domain = m.group(1), m.group(2)
        return local[0] + "*" * (len(local) - 1) + "@" + domain
    return re.sub(r"\b([\w.+-]+)@([\w.-]+\.[\w.-]+)\b", repl, text)
```

`local[0]` 이 첫 글자다. 로컬부가 한 글자면 `len(local) - 1` 이 0 이라 별표가 없고 결과가 원본과 같다. 드문 경우지만 **한 글자 로컬부는 마스킹이 무의미**하다는 점을 알아 둔다.

## 4. 대용량 파일

배포 파일이 각 10,000줄이다. 전부 메모리에 올려 처리하면 문제가 생긴다.

| 제한 | 기본값 | 넘기면 |
|---|---|---|
| 실행 시간 | 3초 | `Task timed out` |
| 메모리 | 128MB | `Runtime exited with error` |
| 응답 크기 | 6MB | 동기 호출에서만 문제 |

### 4-1. 먼저 늘린다

```hcl
resource "aws_lambda_function" "masking" {
  timeout     = 60
  memory_size = 512
  ...
}
```

**메모리를 늘리면 CPU 도 함께 늘어난다.** 정규식 처리는 CPU 작업이므로 512MB 가 128MB 보다 네 배쯤 빠르다. 시간이 줄어 오히려 비용이 비슷하거나 싸진다.

### 4-2. 줄 단위로 흘려보낸다

파일 전체를 문자열 하나로 만들지 않는다.

```python
import boto3, re

s3 = boto3.client("s3")


def handler(event, context):
    record = event["Records"][0]
    bucket = record["s3"]["bucket"]["name"]
    key = record["s3"]["object"]["key"]

    if not key.startswith("incoming/"):
        return {"statusCode": 200, "skipped": key}

    body = s3.get_object(Bucket=bucket, Key=key)["Body"]

    out = []
    for raw in body.iter_lines():
        out.append(mask_all(raw.decode("utf-8")))

    s3.put_object(
        Bucket=bucket,
        Key=key.replace("incoming/", "masked/", 1),
        Body=("\n".join(out) + "\n").encode("utf-8"),
    )
    return {"statusCode": 200, "lines": len(out)}
```

`iter_lines()` 가 한 줄씩 준다. 10,000줄이면 여전히 메모리에 다 모이지만, 훨씬 큰 파일이면 S3 멀티파트 업로드로 흘려보내야 한다.

`key.replace("incoming/", "masked/", 1)` 의 마지막 인자 `1` 이 **첫 번째만 바꾸라**는 뜻이다. 파일 이름에 `incoming` 이 들어 있어도 안전하다.

## 5. 확인하는 순서

**Macie 작업은 즉시 끝나지 않는다.** 데이터 양에 따라 수 분에서 수십 분 걸린다. 그동안 마스킹이 맞는지 다른 방법으로 먼저 확인한다.

### 5-1. 먼저 눈으로 본다

```bash
aws s3 cp s3://<버킷>/masked/emails.txt - | head -5
```

표의 예시와 형태가 같은지 본다. 이것이 가장 빠른 되먹임이다.

### 5-2. 정규식으로 잔존을 센다

```bash
aws s3 cp s3://<버킷>/masked/credit_cards.txt - \
  | grep -cE '[0-9]{4}-[0-9]{4}-[0-9]{4}-[0-9]{4}'
```

`0` 이 나와야 한다. 하나라도 남으면 그 줄을 본다.

```bash
aws s3 cp s3://<버킷>/masked/credit_cards.txt - \
  | grep -nE '[0-9]{4}-[0-9]{4}-[0-9]{4}-[0-9]{4}' | head -5
```

**이 단계에서 대부분의 오류가 잡힌다.** Macie 를 돌리는 것은 마지막 확인이다.

### 5-3. 마지막에 Macie

```bash
aws macie2 describe-classification-job --job-id <ID> --query 'jobStatus'
aws macie2 list-findings --query 'findingIds'
```

발견 항목이 없으면 통과다.

## 6. 안 될 때 좁히는 순서

### 6-1. `masked/` 에 파일이 안 생긴다

```bash
aws logs tail /aws/lambda/wsc2025-masking-start --since 10m
```

| 로그 상태 | 원인 |
|---|---|
| 로그 그룹 자체가 없다 | Lambda 가 한 번도 호출되지 않았다 |
| 호출됐는데 오류 | 코드나 권한 |
| `skipped` 를 반환 | 접두사 확인에 걸렸다 |

호출되지 않았다면 이벤트 알림을 본다.

```bash
aws s3api get-bucket-notification-configuration --bucket <버킷>
```

비어 있으면 설정이 안 된 것이고, 있는데 안 불리면 `aws_lambda_permission` 을 확인한다.

### 6-2. Lambda 가 실패한다

| 오류 | 원인 |
|---|---|
| `AccessDenied` (GetObject) | 실행 역할에 읽기 권한 |
| `AccessDenied` (PutObject) | 실행 역할에 쓰기 권한 |
| `Task timed out` | 타임아웃을 늘린다 |
| `KeyError: 'Records'` | 테스트 이벤트 형식이 다르다 |
| `UnicodeDecodeError` | 인코딩. `errors="replace"` 를 쓴다 |

### 6-3. Macie 가 여전히 감지한다

발견 항목의 유형을 본다.

```bash
aws macie2 get-findings --finding-ids $(aws macie2 list-findings --query 'findingIds[0]' --output text) \
  --query 'findings[0].classificationDetails.result.sensitiveData[*].{cat:category,detections:detections[*].type}'
```

어느 유형이 남았는지 나온다. 그 유형의 정규식만 고친다.

| 남은 유형 | 흔한 원인 |
|---|---|
| 카드 | `\b` 경계가 없어 전화 규칙이 먼저 걸렸다 |
| 이름 | 세 토막 이름을 처리하지 못했다 |
| 이메일 | 도메인 부분까지 가려야 하는지 재확인 |
| 전화 | 국가 코드가 붙은 형식(`+82-10-...`)을 놓쳤다 |

### 6-4. 무한루프가 났다

Lambda 호출 수가 폭증하면 즉시 끊는다.

```bash
# 1. 이벤트 알림 제거
aws s3api put-bucket-notification-configuration --bucket <버킷> --notification-configuration '{}'

# 2. 동시 실행을 0으로 — 즉시 멈춘다
aws lambda put-function-concurrency \
  --function-name wsc2025-masking-start --reserved-concurrent-executions 0
```

두 번째가 더 빠르다. 원인을 고친 뒤 되돌린다.

```bash
aws lambda delete-function-concurrency --function-name wsc2025-masking-start
```

## 7. 30% 변형에 대비하기

| 변형 | 무엇이 바뀌나 |
|---|---|
| 마스킹 문자가 `#` | 치환 문자열만 |
| 가리는 자릿수가 다름 | 정규식의 그룹 경계 |
| 다른 버킷으로 출력 | 무한루프 위험이 사라진다. 권한은 두 버킷에 |
| 암호화된 채로 저장 | `put_object` 에 `ServerSideEncryption` |
| 유형이 추가됨 | `PATTERNS` 목록에 한 줄 |
| 사용자 지정 식별자 필수 | Macie 에 정규식 등록 |
| 작업이 주기 실행 | `SCHEDULED` 와 주기 설정 |

**정규식 목록을 자료 구조로 빼 둔 이유가 이것이다.** 유형이 늘거나 규칙이 바뀌어도 목록 한 줄만 고친다.

## 정리

- Macie 는 관리형 식별자로 민감 정보를 찾는다. 없는 유형은 **사용자 지정**으로 만든다
- 작업 범위를 `masked/` 로 좁히고 **한 번만** 실행한다. Macie 가 마스킹의 채점자다
- S3 이벤트는 접두사 필터로 좁히고, **코드에서 한 번 더** 확인한다
- S3 가 Lambda 를 부르려면 **리소스 기반 정책**이 따로 필요하다
- 마스킹 규칙 여섯 중 둘은 길이에 맞춰, 넷은 고정 개수로 가린다
- 정규식에 **`\b` 경계**를 붙이고 **긴 것부터** 적용한다
- 확인은 눈 → `grep` 잔존 세기 → Macie 순서다. Macie 는 느리다
- 무한루프가 나면 **동시 실행 0** 으로 즉시 끊는다

<Quiz title="정규식이 카드번호에 걸린다">
