> 문서 유형: how-to

앞의 세 편은 코드와 콘솔의 관계를 다뤘다. PART-4 는 **리전**이다.

2과제는 모듈마다 리전이 다르고 **틀리면 그 모듈이 0점**이다. 그런데 콘솔은 리전이 화면 위 드롭다운 하나이고, **한 번 잘못 고르면 그 뒤 모든 작업이 그 리전에서 일어난다.** 도구가 알려 주지 않는 유일한 종류의 실수라 따로 다룬다.

:::note[클릭 순서는 적지 않는다]
콘솔 화면은 자주 바뀐다. **무엇을 확인하는지**만 적는다.
:::

## 1. 리전을 먼저 맞춘다

[14](/part-4/14-serverless-event/lab/)~[20](/part-4/20-cdn-function/lab/)의 리전을 한 장에 모으면 이렇다. :badge[실측]{variant=note}

| 모듈 | 기준본 리전 | 이행 타깃 리전 |
|---|---|---|
| 09 | `eu-west-1` | `ap-southeast-1` |
| 10 | `ap-northeast-2` | `us-west-2` |
| 11 | `ap-northeast-2` | `ap-southeast-1` |
| 12 | `ap-northeast-1` | 자체 제작 |
| 13 | `us-east-1` | 동일 |

**전부 다르다.** PART-1~3 은 서울 고정이라 이 축이 아예 없었다.

### 지금 어느 리전을 보고 있나

콘솔에서 작업하기 전에 CLI 로 먼저 확인한다. **두 곳이 같은 리전을 보고 있어야 헷갈리지 않는다.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws configure get region
  $env:AWS_DEFAULT_REGION
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws configure get region
  echo "$AWS_DEFAULT_REGION"
  ```
  </TabItem>
</Tabs>

기대: 두 값이 지금 모듈의 리전이다. **환경 변수가 설정 파일을 이긴다** — 둘이 다르면 환경 변수 쪽이 실제로 쓰인다.

모듈을 시작할 때마다 이것부터 세운다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  $env:AWS_DEFAULT_REGION = "ap-southeast-1"   # 이 모듈의 리전으로 바꾼다
  aws sts get-caller-identity --query Account --output text
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  export AWS_DEFAULT_REGION=ap-southeast-1     # 이 모듈의 리전으로 바꾼다
  aws sts get-caller-identity --query Account --output text
  ```
  </TabItem>
</Tabs>

### 콘솔 쪽은 URL 로 확인한다

콘솔 화면의 드롭다운 위치는 바뀌지만 **주소창의 `region=` 파라미터는 안 바뀐다.** 지금 보고 있는 리전을 가장 빨리 확인하는 방법이다.

새 탭을 열 때 그 값이 따라오므로, **탭을 여러 개 띄워 놓고 모듈을 오가면 탭마다 리전이 다를 수 있다.** 2과제에서 특히 위험하다.

## 2. 콘솔이 몰래 만드는 것 — 로그 그룹

2과제 리소스를 콘솔로 만들 때 가장 자주 딸려 오는 것이 **로그 그룹**이다.

함수를 만들고 한 번 실행하면 로그 그룹이 자동으로 생긴다. 이름은 서비스의 기본 규칙을 따른다 — 사람이 정한 것이 아니다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  aws logs describe-log-groups --query "logGroups[].{Name:logGroupName,Retention:retentionInDays,Kms:kmsKeyId}" --output table
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  aws logs describe-log-groups --query 'logGroups[].{Name:logGroupName,Retention:retentionInDays,Kms:kmsKeyId}' --output table
  ```
  </TabItem>
</Tabs>

기대: 로그 그룹 목록. **세 열을 함께 본다.**

| 열 | 자동 생성이면 | 왜 문제인가 |
|---|---|---|
| 이름 | 서비스 기본 규칙 | 과제지가 이름을 지정했으면 **틀린다** |
| 보존 기간 | 비어 있다(무기한) | 보존을 요구하는 과제가 있다 |
| 암호화 키 | 비어 있다 | **암호화를 요구하면 못 맞춘다** |

[08 실습 6-1](/part-1/08-container-lambda-dynamodb/lab/)이 이 상황을 다룬다 — 로그 그룹을 지정하지 않으면 기본 규칙 이름이 나와 채점이 틀린다.

**자동 생성된 그룹은 나중에 이름을 못 바꾼다.** 지우고 올바른 이름으로 다시 만든 뒤, 함수가 그것을 쓰도록 지정해야 한다. 그리고 [08 의 교훈](/part-1/08-container-lambda-dynamodb/lab/)대로 **이미 흘러간 로그는 옛 그룹에 남는다.**

### 그 밖에 딸려 오는 것

| 콘솔에서 만들면 | 함께 생기는 것 | 잔존 위험 |
|---|---|---|
| 함수 | 실행 역할 · 로그 그룹 | 높다 — 역할은 남는다 |
| API | 스테이지 · 로그 그룹 | 중간 |
| 큐 | (없음) | 낮다 |
| 규칙 | 대상 호출 권한 | 낮다 — 규칙과 함께 사라진다 |

## 3. drift 판단 — 다른 리전은 코드도 상태도 모른다

**이 절이 이 문서의 존재 이유다.**

앞의 세 편에서 다룬 drift 는 전부 "같은 리전 안에서 값이 다르다"였다. 리전이 틀리면 성격이 완전히 달라진다.

### `plan` 이 조용한 이유

Terraform 은 프로바이더에 설정된 리전만 본다. **다른 리전의 리소스는 존재 자체를 모른다.**

| | 같은 리전, 값이 다름 | **다른 리전에 만듦** |
|---|---|---|
| `plan` 이 알려 주나 | **알려 준다** | **아니다 — 아무 말도 없다** |
| 상태 파일에 있나 | 있다 | 없다 |
| `destroy` 가 지우나 | 지운다 | **아니다** |
| 채점이 찾나 | 찾는다 | **못 찾는다 — 0점** |
| 과금되나 | 된다 | **된다** |

**가장 나쁜 조합이다.** 점수는 안 나오는데 돈은 나가고, 도구는 아무 말도 안 한다.

### 찾는 방법은 리전을 바꿔 가며 조회하는 것뿐이다

코드가 모르므로 사람이 세는 수밖에 없다. 2과제에 나오는 리전들을 돌며 확인한다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  foreach ($r in 'ap-northeast-1','ap-northeast-2','ap-southeast-1','ap-southeast-2','eu-west-1','us-east-1','us-west-2') {
    $n = aws ec2 describe-instances --region $r --filters Name=instance-state-name,Values=running --query "length(Reservations[].Instances[])" --output text
    $v = aws ec2 describe-vpcs --region $r --query "length(Vpcs[?IsDefault==``false``])" --output text
    "{0,-16} EC2 {1,-4} VPC(비기본) {2}" -f $r, $n, $v
  }
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  for r in ap-northeast-1 ap-northeast-2 ap-southeast-1 ap-southeast-2 eu-west-1 us-east-1 us-west-2; do
    n=$(aws ec2 describe-instances --region "$r" --filters Name=instance-state-name,Values=running --query 'length(Reservations[].Instances[])' --output text)
    v=$(aws ec2 describe-vpcs --region "$r" --query 'length(Vpcs[?IsDefault==`false`])' --output text)
    printf '%-16s EC2 %-4s VPC(비기본) %s\n' "$r" "$n" "$v"
  done
  ```
  </TabItem>
</Tabs>

기대: 지금 작업 중인 리전에만 숫자가 있고 나머지는 `0` 이다.

**엉뚱한 리전에 숫자가 있으면 그것이 틀린 리전에 만든 것이다.** 이 조회를 모듈을 끝낼 때마다 돌리면 늦기 전에 잡힌다.

:::caution[이 조회에도 한계가 있다]
EC2 와 VPC 만 센다. 함수·큐·테이블처럼 VPC 밖 리소스는 안 잡힌다.

서비스별로 다 돌리려면 오래 걸리므로, **작업 중에 리전을 먼저 맞추는 쪽이 훨씬 싸다.** 이 조회는 사후 확인이지 예방책이 아니다.
:::

### 선택지는 하나뿐이다

| 선택 | 가능한가 |
|---|---|
| 리전을 옮긴다 | **불가능하다.** 리전은 리소스의 주소다 |
| import 로 살린다 | 무의미하다. 채점이 다른 리전을 본다 |
| **틀린 리전에서 지우고 맞는 리전에서 다시 만든다** | **이것뿐이다** |

그래서 이 실수의 복구 비용은 **전면 재배포**다. [14 실습 6-1](/part-4/14-serverless-event/lab/)이 같은 판정을 다룬다.

**예방이 유일한 대응이다.** 모듈을 시작할 때 리전을 세우고, 파트를 넘어갈 때 다시 세운다.

## 4. 판단표 — 콘솔이 옳은 때, 코드가 옳은 때

| 상황 | 고르는 쪽 | 이유 |
|---|---|---|
| 리소스가 실제로 만들어졌나 눈으로 본다 | **콘솔** | 목록을 훑는 데는 화면이 빠르다 |
| **어느 리전에 있나 확인한다** | **CLI** | 콘솔은 지금 보는 리전만 보여 준다 |
| 함수 코드 한 줄을 급히 고친다 | **콘솔** | 편집기가 붙어 있어 빠르다 |
| 값 하나를 급히 바꾼다 | **콘솔** | 앞의 세 편과 같다 |
| 모듈 하나를 통째로 만든다 | **코드** | 리전이 변수 하나로 고정된다 |
| 여러 모듈을 오간다 | **코드** | **모듈마다 디렉터리가 갈려 리전이 안 섞인다** |
| 정리한다 | **코드** | `destroy` 가 그 리전 것만 정확히 지운다 |

마지막에서 두 번째가 이 파트의 핵심이다. **코드로 하면 리전이 파일에 박혀 있어 실수하기 어렵다.** 콘솔은 리전이 화면 상태라 사람 기억에 의존한다.

### 한 줄로

**2과제에서 콘솔은 보는 도구지 만드는 도구가 아니다.**

리전이 화면 상태에 얹혀 있다는 것 하나 때문이다. 만드는 것은 리전이 파일에 적히는 쪽으로 하고, 콘솔은 만든 것을 확인할 때 쓴다.

## 정리

이 문서는 리소스를 만들지 않는다. 조회만 했다.

다만 **위 3절의 리전별 조회는 습관으로 만든다.** 모듈을 끝낼 때마다 돌리면 틀린 리전에 남긴 것을 그날 안에 잡는다.

각 모듈의 정리 절과 [잔존 리소스 점검](/reference/cleanup-check/)을 함께 쓴다 — 그 문서는 **한 리전**을 훑으므로, 2과제에서는 리전마다 돌려야 한다는 것을 기억한다.
