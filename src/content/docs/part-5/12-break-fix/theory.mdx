이 PART는 적용이 전부다. 원칙만 짧게.

## 원칙 1 — 추측으로 고치지 않는다

증상을 보면 손이 먼저 나간다 — 그게 시간을 태운다. **증상 → 1순위 확인 명령 → 출력 해석 → 조치.** 확인 명령이 원인을 말해주기 전에는 아무것도 바꾸지 않는다. [../../reference/troubleshooting.md](/reference/troubleshooting/)의 표가 그 순서 그대로다.

## 원칙 2 — 경로를 분리해서 진단한다

CloudFront 403처럼 다층 경로의 오류는 **오리진 직접 curl로 계층을 분리**한다: S3 presign / ALB 직접 / Function URL 직접. 어느 계층에서 처음 깨지는지 찾으면 원인 후보가 1~2개로 준다.

## 원칙 3 — Events와 로그가 1차 소스다

- k8s: `kubectl describe pod` Events 최하단 → 그 다음 `kubectl logs --previous`
- AWS: 해당 서비스의 CloudWatch Logs / CloudTrail (IAM 계열은 AssumeRole 오류 검색)
- LB: `aws elbv2 describe-target-health` reason 필드

## 원칙 4 — 시간 지연을 오류로 착각하지 않는다

TG healthy 2~3분, CloudFront 전파 수 분, Config 첫 평가 5~10분 — [../../reference/timings.md](/reference/timings/). "고장"의 절반은 그냥 아직 안 된 것이다. 대기해야 하는 상황인지부터 판단.

## 원인 순위(빈도순)로 확인한다

troubleshooting.md의 각 항목은 원인을 실측 빈도순(①②③)으로 나열한다. ①부터 확인 — 대회장 통계적으로 가장 빠른 경로다.

## 훈련이 만드는 것

같은 증상을 **자기 손으로 만들어보면** 확인 명령의 출력이 어떻게 생겼는지(정상 vs 고장) 기억에 박힌다. 대회장에서는 출력을 보는 순간 원인이 떠올라야 한다.

## 퀴즈 (5문)

1. Pod가 Pending이다. 가장 먼저 칠 명령은?
2. ALB에서 Lambda 오리진이 502를 뱉는다. 원인은? 응답에 필수인 필드 3개는?
3. CloudFront가 OAC S3 오리진에 403 — Origin Request Policy `AllViewerExceptHostHeader`가 의심되는 이유는?
4. `kubectl get nodes`가 Unauthorized. 확인 명령과 비교 대상은?
5. DynamoDB에 시간이 UTC로 저장된다. 원인 두 요소는?

### 정답

1. `kubectl describe pod <pod>` — Events 최하단 (taint/toleration → 용량 → nodeSelector 오타 순으로 해석).
2. ALB 통합 응답 포맷 위반. `statusCode` / `statusDescription` / `body`.
3. AllViewer 계열은 **Authorization 헤더를 오리진에 전달**해 OAC의 SigV4 서명과 충돌 — OAC 오리진엔 QueryString-only ORP.
4. `aws sts get-caller-identity` ↔ 클러스터를 **생성한 신원**과 비교. 다르면 같은 신원으로 update-kubeconfig 또는 Access Entry 추가.
5. 컨테이너에 **tzdata 부재 + `TZ=Asia/Seoul` env 누락** (Go 바이너리는 tzdata 미내장). 실측 확인은 `aws dynamodb scan --max-items 1`.
