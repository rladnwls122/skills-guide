> 문서 유형: 개요

3과제는 리소스 존재 여부를 세지 않는다. 트래픽을 주입하고 **결과 로그(`results_<비번호>.log`)의 4개 비율**만 본다 — 비정상 요청 처리·가용성·성능·비용 ratio 40점. 배포는 입장권이고, 점수는 T+60분 트래픽 개시 이후 2시간의 운영에서 갈린다.

이 모듈은 배포를 T+50분 안에 끝내고, 부하 중 4축을 동시에 지키는 튜닝·감시·복구를 훈련한다.

:::caution[이 모듈의 근거는 예상 풀이다]
3과제 공식 과제지·채점지는 아직 공개되지 않았다. 이 모듈의 배점 40점·SLO 수치·비용 ratio 밴드는 전부 `skills-2026/task-3`(예상 풀이, 파일명 그대로 `task-sample.md`·`mark-sample.md`)에서 가져온 예측이며 실제 대회에서 달라질 수 있다. 40점이라는 총점은 1·2과제 각 30점·전체 100점에서 역산되므로 비교적 안정적이지만, 그 안의 구성은 예상이다. 반면 이 모듈이 훈련하는 SLO 기반 HPA 튜닝·RDS Proxy 풀링·인덱스 설계·비용을 게이트로 다루는 사고는 배점이 달라져도 그대로 쓸 수 있다.
:::

:::note[협의회(2026-07-31)에서 확인된 것 — 예상의 골격이 맞았다]
변별력은 3과제로 판단한다. 채점 플랫폼은 **선수 트래픽 점수를 실시간 대시보드로 보여 주고**, 평가 목적은 "요청을 처리하면서 리소스는 최대한 적게"(대회 기간 **전체** 기준)이며, **악의적 트래픽이 유입되어 WAF 대응이 요구된다** — 이 모듈의 4축(비정상 요청·가용성·성능·비용)과 방향이 일치한다. 기존 문제의 전면 변경은 없고 배점 수정과 추가 문제가 가능하다(예시: CloudWatch 모니터링 로그가 적재되면 Firehose를 통해 S3로 저장). 실시간 점수가 보이므로 부하 중 "지표 확인 → 노브 조정 → 재확인" 루프를 대회장에서도 그대로 쓴다 — 비용 축이 전 기간 누적이라, 부하가 없는 시간대에 노드·리소스를 줄여 두는 운영까지 점수다.
:::

## 목표

- [ ] 정답지(`skills-2026/task-3`) 런북으로 CloudFront 스택을 **T+50분 내** 배포하고 스모크 6종 통과
- [ ] 부하 드릴에서 user·product `p(90) < 200ms`, stress `p(90) < 1000ms`, 실패율 < 10% 달성
- [ ] 부하 전 구간에서 노드 2~9대 밴드 유지 (비용 ratio 0.5~3.75)
- [ ] 부하 중 장애 10종 중 7개 이상을 확인 명령 → 조치 순서로 5분 내 복구
- [ ] 노브 1개를 변경 → 재측정해 지표 변화를 원인과 결과로 설명한다

## 소요 / 일차

- Day 13~14, 각 8~10시간 (배포 1시간 + 부하 드릴 3회 + 장애 드릴). 배점 40점으로 세 과제 중 가장 크다 — 2주 일정 안에 넣는다.

## 과금 / destroy

:::caution[시간당 과금이 가장 비싼 모듈]
EKS + NAT GW + ALB + CloudFront + RDS Multi-AZ(db.t3.micro) + 노드 최대 9대.

- 드릴 1회는 배포~부하~정리까지 3시간 안에 끝내고 **당일 destroy**한다.
- k6 부하는 자기 CloudFront로만 주입한다. 종료 시 부하부터 멈추고 스택을 지운다.
- 정리 순서: k6 중지 → `kubectl delete` → `eksctl delete cluster` → `terraform destroy` → [잔존 리소스 점검](/reference/cleanup-check/).
:::
