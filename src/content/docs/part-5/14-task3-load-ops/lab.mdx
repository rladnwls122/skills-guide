:::caution[두 값은 반드시 같아야 한다]
`terraform.tfvars` 의 `db_password` 는 RDS 와 RDS Proxy 가 **실제로 만드는** 비밀번호다. 셸의 `DB_PASSWORD` 는 STEP 8 에서 매니페스트의 `<DB_PASSWORD>` 자리를 치환할 때만 쓰인다. 두 값이 어긋나면 인프라는 정상으로 뜨는데 앱만 DB 인증에 실패한다 — 증상이 배포 실패가 아니라 런타임 500 이라 원인을 찾는 데 시간이 든다. 대회 당일 과제지가 다른 비밀번호를 지정하면 **두 곳을 함께** 바꾼다.

새 셸 창을 열 때마다 `DB_PASSWORD` 는 사라진다. 창을 열면 이 한 줄부터 다시 실행한다.
:::

  c() { curl -s -o /dev/null -w "%{http_code} %{time_total}s $1\n" "$1"; }

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

스택이 제대로 섰는지 경로별로 한 번씩 친다. 함수 `c` 는 상태 코드와 응답 시간을 한 줄로 찍는다. 확인 항목은 넷이다 — 정상 API 가 200 이고 0.2초를 넘지 않는지, 이미지가 S3 에서 오는지, 정의되지 않은 경로가 ALB 기본 액션의 404 인지, SQL 주입 모양의 요청이 WAF 의 403 인지다. 403 과 404 를 내는 주체가 다르다는 점이 요점이다.

</details>

## 관측 준비 (스모크 통과 직후, 트래픽 전)

지표와 로그가 없으면 부하 중 조정은 추측이 된다. 배포 검증이 끝나면 트래픽 전에 수집기 두 갈래를 세운다.

### Container Insights 활성화

<Steps>

1. **추가 기능을 설치한다**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws eks create-addon --cluster-name <클러스터명> --addon-name amazon-cloudwatch-observability
     kubectl -n amazon-cloudwatch get pods
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash

     kubectl -n amazon-cloudwatch get pods
     ```
     </TabItem>
   </Tabs>

   데몬셋 두 개(`cloudwatch-agent`, `fluent-bit`)가 노드 수만큼 Running이면 정상이다.

2. **콘솔에서 데이터가 뜨는지 본다**

   CloudWatch → Container Insights에서 클러스터·노드·파드 사용률을 연다. 파드 사용률이 비어 있으면 매니페스트의 `resources.requests` 부터 확인한다 — 사용률은 requests를 분모로 계산한다([이론](/part-5/14-task3-load-ops/theory/)의 requests 절).

3. **비어 있으면 에이전트 로그를 먼저 읽는다**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     kubectl -n amazon-cloudwatch logs daemonset/cloudwatch-agent --tail 50
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     kubectl -n amazon-cloudwatch logs daemonset/cloudwatch-agent --tail 50
     ```
     </TabItem>
   </Tabs>

   `AccessDenied` 가 보이면 수집은 되고 전송만 막힌 상태다. 에이전트가 쓰는 역할에 정책을 붙인다.

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws iam attach-role-policy --role-name <에이전트가 쓰는 역할> `
       --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy
     kubectl -n amazon-cloudwatch rollout restart daemonset cloudwatch-agent
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     aws iam attach-role-policy --role-name <에이전트가 쓰는 역할> \
       --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy
     kubectl -n amazon-cloudwatch rollout restart daemonset cloudwatch-agent
     ```
     </TabItem>
   </Tabs>

</Steps>

:::caution[역할을 잘못 짚는 실수]
클러스터에는 노드 역할과 서비스 계정용 역할이 함께 있어 엉뚱한 역할의 정책을 보며 시간을 쓰기 쉽다. **에이전트 파드가 실제로 assume한 역할 ARN을 먼저 특정한다.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl -n amazon-cloudwatch describe sa cloudwatch-agent   # annotation 의 role-arn
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl -n amazon-cloudwatch describe sa cloudwatch-agent   # annotation 의 role-arn
  ```
  </TabItem>
</Tabs>

그리고 `rollout restart` 는 **데몬셋·디플로이먼트 단위**다. 파드를 지정하면 명령 자체가 성립하지 않는다.
:::

### WAF 로깅 활성화

WAF는 로깅이 꺼진 채로 만들어진다. 켜 두지 않으면 부하 중 "정상 요청이 403"을 진단할 근거가 없다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  # 로그 그룹 이름은 반드시 aws-waf-logs- 로 시작. CLOUDFRONT 스코프는 us-east-1
  aws logs create-log-group --log-group-name aws-waf-logs-task3 --region us-east-1

  $acl = aws wafv2 list-web-acls --scope CLOUDFRONT --region us-east-1 `
    --query 'WebACLs[0].ARN' --output text
  $lg  = aws logs describe-log-groups --log-group-name-prefix aws-waf-logs-task3 `
    --region us-east-1 --query 'logGroups[0].arn' --output text

  aws wafv2 put-logging-configuration --region us-east-1 `
    --logging-configuration "ResourceArn=$acl,LogDestinationConfigs=$lg"
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  # 로그 그룹 이름은 반드시 aws-waf-logs- 로 시작. CLOUDFRONT 스코프는 us-east-1
  aws logs create-log-group --log-group-name aws-waf-logs-task3 --region us-east-1

  acl=$(aws wafv2 list-web-acls --scope CLOUDFRONT --region us-east-1 \
    --query 'WebACLs[0].ARN' --output text)
  lg=$(aws logs describe-log-groups --log-group-name-prefix aws-waf-logs-task3 \
    --region us-east-1 --query 'logGroups[0].arn' --output text)

  aws wafv2 put-logging-configuration --region us-east-1 \
    --logging-configuration "ResourceArn=$acl,LogDestinationConfigs=$lg"
  ```
  </TabItem>
</Tabs>

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

WAF 평가 로그를 CloudWatch Logs 로 흘린다. 로그 그룹 이름의 `aws-waf-logs-` 접두어는 규칙이라 다른 이름이면 마지막 명령이 거부된다. Web ACL 과 로그 그룹을 각각 조회해 변수에 담은 뒤 둘을 연결하는 순서이고, CloudFront 에 붙은 ACL 이므로 세 명령 모두 us-east-1 이다.

</details>

**검증**: SQL 주입 모양의 요청을 한 번 던지고 `aws logs tail aws-waf-logs-task3 --region us-east-1 --since 2m` 에 그 요청이 잡히는지 본다. 로그가 비면 배달 권한을 확인한다.

## 사전 워밍 (트래픽 개시 5분 전)

노드 프로비저닝 2~3분을 트래픽 개시 시점에서 앞으로 당긴다. 낮은 우선순위 placeholder 파드로 노드를 미리 띄우고, 트래픽이 오면 0으로 줄여 실제 파드에 자리를 내준다.

```yaml
# warm.yaml — 드릴용. 채점 대상 리소스가 아니므로 트래픽 개시 직후 삭제한다.
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: warm
value: -10
preemptionPolicy: Never
globalDefault: false
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: warm
spec:
  replicas: 3
  selector:
    matchLabels: { app: warm }
  template:
    metadata:
      labels: { app: warm }
    spec:
      priorityClassName: warm
      terminationGracePeriodSeconds: 0
      containers:
        - name: pause
          image: registry.k8s.io/pause:3.9
          resources:
            requests: { cpu: 600m, memory: 768Mi }
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

노드를 미리 확보하는 워밍업 리소스다. 우선순위를 음수로 두고 `preemptionPolicy: Never` 로 잡아, 실제 앱 파드가 뜰 때 이 파드들이 밀려나되 남을 자리를 만들어 둔다. 요청량을 실제 앱과 비슷하게 잡는 이유는 그래야 같은 크기의 노드가 준비되기 때문이다. 채점 대상 리소스가 아니므로 트래픽 시작 직후 지운다.

</details>

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl apply -f warm.yaml
  kubectl get nodes -w          # 노드가 목표 수만큼 Ready 되면 다음 줄
  # 트래픽 개시 시각에:
  kubectl delete -f warm.yaml   # 자리를 실제 파드에 넘긴다
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl apply -f warm.yaml
  kubectl get nodes -w          # 노드가 목표 수만큼 Ready 되면 다음 줄
  # 트래픽 개시 시각에:
  kubectl delete -f warm.yaml   # 자리를 실제 파드에 넘긴다
  ```
  </TabItem>
</Tabs>

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

워밍업을 실제로 쓰는 순서다. 적용한 뒤 노드가 목표 수만큼 Ready 가 되기를 기다리고, 트래픽이 시작되는 시각에 삭제한다. 노드 부팅에 2분 가까이 걸리므로, 이 단계를 건너뛰면 첫 스텝에서 응답 시간이 그만큼 튄다.

</details>

워밍 노드는 그대로 두면 비용 ratio를 올린다. `consolidateAfter: 30s`가 회수하므로 **삭제 후 노드 수가 실제 부하를 따라가는지** 감시 루프로 확인한다.

## 드릴 B — k6 3단 프로파일

정답지의 `script/load.js`를 그대로 쓴다. 임계값이 채점표와 같아 빨간불이 곧 감점이다.

<Steps>

1. **BASE_URL 지정**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     $env:BASE_URL = $CF
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     export BASE_URL="$CF"
     ```
     </TabItem>
   </Tabs>

2. **① Ramp** — 정상 부하에서 SLO를 지키는지

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     $env:VUS='20'; $env:DURATION='2m'; k6 run script/load.js
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     VUS=20 DURATION=2m k6 run script/load.js
     ```
     </TabItem>
   </Tabs>

   관찰: `kubectl get hpa -w` — 정상 부하에서 이용률이 목표(75%) 근방에서 안정되는지.

3. **② Spike** — 스텝 증가에 스케일이 따라붙는지

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     $env:VUS='80'; $env:DURATION='1m'; k6 run script/load.js
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     VUS=80 DURATION=1m k6 run script/load.js
     ```
     </TabItem>

## 운영 대시보드 (선택 드릴)

감시 루프를 터미널 세 창으로 도는 대신 한 화면으로 모으는 훈련이다. 채점 대상이 아니라 **조정 속도를 위한 도구**이므로, 부하 드릴을 두 번 이상 돌려 무엇을 보게 되는지 안 뒤에 만든다.

| 묶음 | 패널 | 데이터 소스 |
|---|---|---|
| 트래픽 판정 | 2xx·4xx·5xx 개수, 응답시간 평균·최대 | ALB·타깃그룹 지표 |

:::

## 판정 기준

- 배포: 스모크 6종 통과를 **T+50분 내**
- 성능: soak 구간에서 user·product `p(90) < 200ms`, stress `p(90) < 1000ms`
- 가용성: 3회차 전체 `http_req_failed < 10%`
- 비용: 부하 전 구간 노드 2~9대, 부하 종료 5분 내 2대로 회수
- 복구: 10종 중 7개 이상을 5분 내 복구

## 변형 셀프 체크

당일 과제의 약 30% 가 수정된다. 재배포 없이, 각 질문에 먼저 답한 뒤 펼쳐 확인한다. 3과제는 mark 스크립트가 없고 네 축으로 채점한다 — 비정상 요청 처리·고가용성 및 안정성·성능 효율성·비용 최적화다(`task-3/mark-sample.md`).

1. 과제지가 비번호와 DB 비밀번호를 다른 값으로 지정하면 무엇을 고치나?

   <details>
   <summary>답 확인</summary>

   `terraform/terraform.tfvars` 의 `player_number`·`db_password` 와, 셸의 `$env:DB_PASSWORD` 를 함께 바꾼다. tfvars 쪽은 RDS 와 RDS Proxy 가 실제로 만드는 값이고, 환경 변수는 매니페스트의 `<DB_PASSWORD>` 자리를 치환할 때만 쓰인다. 두 값이 어긋나면 인프라는 정상으로 뜨는데 앱만 DB 인증에 실패해 배포 실패가 아니라 런타임 500 으로 나타난다.

   </details>

2. 노드 상한을 9대에서 12대로 올리라면 어디를 고치고, 어디를 그대로 두나?

   <details>
   <summary>답 확인</summary>

   `k8s/01-nodepool.yaml` 의 `limits.cpu` 와 앱 매니페스트 HPA 의 `maxReplicas` 를 함께 올린다. 상한 하나만 올리면 파드가 안 늘어 노드도 안 는다. 인스턴스 타입 목록은 `requirements` 한 곳이고 Auto Mode 가 vCPU 1개 이하를 거부하므로 t3.medium 아래로는 못 내린다. 필드 이름은 `kubectl explain nodepool.spec.limits` 로 확인하고, 동선은 [검색 가이드](/reference/search-guide/)에 있다.

   </details>

3. 그 변경은 어느 판정 축에 닿나?

   <details>
   <summary>답 확인</summary>

   두 축이 반대로 움직인다. 고가용성·성능 효율성 축은 로드 처리 비율과 응답 시간 구간으로 배점되므로 오르고, 비용 최적화 축은 노드 수의 함수라 내려간다. 그래서 노브는 한 번에 하나만 바꾸고 같은 조건으로 재측정한다.

   </details>

4. user API 응답 시간 기준이 0.2초에서 0.1초로 강화되면 어디부터 보나?

   <details>
   <summary>답 확인</summary>

   `db/02-index.sql` 의 `email` 인덱스다. 성능 효율성 축은 "응답 시간 기준 이하 비율" 을 구간별로 나눠 배점하므로 기준이 내려가면 데이터 계층이 먼저 걸린다. 확인은 DB 에서 `EXPLAIN SELECT ... WHERE email=` 이고, 그다음이 파드 CPU limit 유무다.

   </details>
