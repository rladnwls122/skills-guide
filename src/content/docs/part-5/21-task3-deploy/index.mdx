> 문서 유형: 개요

3과제는 리소스 존재 여부를 세지 않는다. 트래픽을 주입하고 **결과 로그(`results_<비번호>.log`)의 4개 비율**만 본다 — 비정상 요청 처리·가용성·성능·비용 ratio 40점. 배포는 입장권이고, 점수는 T+60분 트래픽 개시 이후 2시간의 운영에서 갈린다.

이 모듈은 **배포를 T+50분 안에 끝내고 트래픽 전에 관측을 세우는 데까지**를 훈련한다. 부하가 시작된 뒤의 측정·조정·복구는 [22. 부하 운영](/part-5/22-task3-tuning/)이 이어받는다.

:::danger[실기출은 ECS 를 강제하고 EKS 를 금지했다 — 둘 다 준비한다]
이 모듈은 **EKS 경로**다. 그런데 [2025 실기출 3과제](/reference/past-exams/#3-3-2025-3과제--운영-40점)는 "컨테이너 오케스트레이션 툴로는 ECS 를 사용합니다. EKS 를 사용할 수 없습니다"라고 못 박았다. 컴퓨팅도 c5.large 만 허용하고 Lambda 는 리전 무관 생성 시 감점이다.

한편 EKS 기반 3과제도 출제된 적이 있다. 어느 쪽이 나올지 모르므로 **양쪽을 다 준비한다.**

- ECS 경로 — [32. 3과제 ECS 경로](/part-5/32-task3-ecs/)
- 두 경로가 공유하는 판단(인덱스·캐싱·WAF·비용 ratio)은 [32번 이론 7절](/part-5/32-task3-ecs/theory/#7-두-경로의-공통-사고)에 대조표로 있다

달라지는 것은 컴퓨팅 계층뿐이고 데이터·엣지 계층은 완전히 같다.
:::

:::caution[이 모듈의 근거는 예상 풀이다]
3과제 공식 과제지·채점지는 아직 공개되지 않았다. 이 모듈의 배점 40점·SLO(서비스 수준 목표 — p95 응답 0.2초 같은 지표별 상한선) 수치·비용 ratio 밴드는 전부 `skills-2026/task-3`(예상 풀이, 파일명 그대로 `task-sample.md`·`mark-sample.md`)에서 가져온 예측이며 실제 대회에서 달라질 수 있다. 40점이라는 총점은 1·2과제 각 30점·전체 100점에서 역산되므로 비교적 안정적이지만, 그 안의 구성은 예상이다. 반면 이 모듈이 훈련하는 SLO 기반 HPA 튜닝·RDS Proxy 풀링·인덱스 설계·비용을 게이트로 다루는 사고는 배점이 달라져도 그대로 쓸 수 있다.
:::

:::note[협의회(2026-07-31)에서 확인된 것 — 예상의 골격이 맞았다]
변별력은 3과제로 판단한다. 확인된 것 셋:

- 채점 플랫폼이 **선수 트래픽 점수를 실시간 대시보드로 보여 준다.**
- 평가 목적은 "요청을 처리하면서 리소스는 최대한 적게"다(대회 기간 **전체** 기준).
- **악의적 트래픽이 유입되어 WAF 대응이 요구된다.**

이 모듈의 4축(비정상 요청·가용성·성능·비용)과 방향이 일치한다. 기존 문제의 전면 변경은 없고 배점 수정과 추가 문제가 가능하다(예시: CloudWatch 모니터링 로그가 적재되면 Firehose를 통해 S3로 저장).

실시간 점수가 보이므로 부하 중 "지표 확인 → 노브 조정 → 재확인" 루프를 실전에서도 그대로 쓴다. 비용 축이 전 기간 누적이라, 부하가 없는 시간대에 노드·리소스를 줄여 두는 운영까지 점수다.

회의록이 더한 것:

- **EC2 인스턴스 수는 주기적으로 확인해** 전체 경기 시간 기준으로 산정한다. 제시된 구성 외 EC2에는 패널티가 붙는다(bastion도 개수에 든다).
- Product App의 PUT 업로드는 Content-Type·Body 같은 기본 형식만 문제지에 나온다. **S3 저장 경로는 당일 앱 동작과 요청을 분석해 알아내는 과제의 일부**다.
- 취약점 위치·엔드포인트 성격을 묻는 질의는 "정답 요구"로 분류돼 답변되지 않았다. 3과제는 요구사항 구현 확인이 아니라 **분석과 운영**이다.
:::

## 소요 시간

- 약 4~5시간 (배포 1시간 + 관측 준비 + 재현 2회). 배점 40점으로 세 과제 중 가장 크고, 뒤의 [22. 부하 운영](/part-5/22-task3-tuning/)과 함께 Week 4 를 채운다.

## 과금 / destroy

:::caution[시간당 과금이 가장 비싼 모듈]
EKS + NAT GW + ALB + CloudFront + RDS Multi-AZ(db.t3.micro) + 노드 최대 9대.

- 드릴 1회는 배포~부하~정리까지 3시간 안에 끝내고 **당일 destroy**한다.
- k6 부하는 자기 CloudFront로만 주입한다. 종료 시 부하부터 멈추고 스택을 지운다.
- 정리 순서: k6 중지 → `kubectl delete` → `eksctl delete cluster` → `terraform destroy` → [잔존 리소스 점검](/reference/cleanup-check/).
:::
