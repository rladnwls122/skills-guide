:::caution[두 값은 반드시 같아야 한다]
`terraform.tfvars` 의 `db_password` 는 RDS 와 RDS Proxy 가 **실제로 만드는** 비밀번호다. 셸의 `DB_PASSWORD` 는 STEP 8 에서 매니페스트의 `<DB_PASSWORD>` 자리를 치환할 때만 쓰인다. 두 값이 어긋나면 인프라는 정상으로 뜨는데 앱만 DB 인증에 실패한다 — 증상이 배포 실패가 아니라 런타임 500 이라 원인을 찾는 데 시간이 든다. 실전 과제지가 다른 비밀번호를 지정하면 **두 곳을 함께** 바꾼다.

새 셸 창을 열 때마다 `DB_PASSWORD` 는 사라진다. 창을 열면 이 한 줄부터 다시 실행한다.
:::

</details>

### 배포 직후 확인 6종 (하나라도 실패면 트래픽 전에 고친다)

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  $CF = "https://$(terraform -chdir=terraform output -raw cloudfront_domain)"
  $Q  = "requestid=999999999999&uuid=7c5a3c6a-758f-4bc5-9bdf-3e573a0ad729"
  function c($url) { curl.exe -s -o NUL -w "%{http_code} %{time_total}s $url`n" $url }

  c "$CF/v1/user?email=dbdump500001@example.org&$Q"   # 200, 0.2s 미만
  c "$CF/v1/product?id=dbdump500001&$Q"               # 200
  c "$CF/images/<업로드한 키>"                          # 200
  c "$CF/v1/none?$Q"                                  # 404 (ALB 기본 액션)
  c "$CF/v1/user?email=%27%20OR%201=1--&$Q"           # 403 (WAF)
  kubectl get targetgroupbindings                     # 3개 모두 등록
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash

  Q="requestid=999999999999&uuid=7c5a3c6a-758f-4bc5-9bdf-3e573a0ad729"
  c() { curl -s -o /dev/null -w "%{http_code} %{time_total}s $1\n" "$1"; }

  c "$CF/v1/user?email=dbdump500001@example.org&$Q"   # 200, 0.2s 미만
  c "$CF/v1/product?id=dbdump500001&$Q"               # 200
  c "$CF/images/<업로드한 키>"                          # 200
  c "$CF/v1/none?$Q"                                  # 404 (ALB 기본 액션)

  kubectl get targetgroupbindings                     # 3개 모두 등록
  ```
  </TabItem>
</Tabs>

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

스택이 제대로 섰는지 경로별로 한 번씩 친다. 함수 `c` 는 상태 코드와 응답 시간을 한 줄로 찍는다. 확인 항목은 넷이다. 정상 API 가 200 이고 0.2초를 넘지 않는지, 이미지가 S3 에서 오는지를 본다. 이어서 정의되지 않은 경로가 ALB 기본 액션의 404 인지, SQL 주입 모양의 요청이 WAF 의 403 인지를 본다. 403 과 404 를 내는 주체가 다르다는 점이 요점이다.

</details>

## 관측 준비 (스모크 통과 직후, 트래픽 전)

지표와 로그가 없으면 부하 중 조정은 추측이 된다. 배포 검증이 끝나면 트래픽 전에 수집기 두 갈래를 세운다.

### Container Insights 활성화

<Steps>

1. **추가 기능을 설치한다**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws eks create-addon --cluster-name <클러스터명> --addon-name amazon-cloudwatch-observability
     kubectl -n amazon-cloudwatch get pods
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     aws eks create-addon --cluster-name <클러스터명> --addon-name amazon-cloudwatch-observability
     kubectl -n amazon-cloudwatch get pods
     ```
     </TabItem>
   </Tabs>

   데몬셋 두 개(`cloudwatch-agent`, `fluent-bit`)가 노드 수만큼 Running이면 정상이다.

2. **콘솔에서 데이터가 뜨는지 본다**

   CloudWatch → Container Insights에서 클러스터·노드·파드 사용률을 연다. 파드 사용률이 비어 있으면 매니페스트의 `resources.requests` 부터 확인한다 — 사용률은 requests를 분모로 계산한다([이론](/part-5/21-task3-deploy/theory/)의 requests 절).

3. **비어 있으면 에이전트 로그를 먼저 읽는다**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     kubectl -n amazon-cloudwatch logs daemonset/cloudwatch-agent --tail 50
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     kubectl -n amazon-cloudwatch logs daemonset/cloudwatch-agent --tail 50
     ```
     </TabItem>
   </Tabs>

   `AccessDenied` 가 보이면 수집은 되고 전송만 막힌 상태다. 에이전트가 쓰는 역할에 정책을 붙인다.

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     aws iam attach-role-policy --role-name <에이전트가 쓰는 역할> `
       --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy
     kubectl -n amazon-cloudwatch rollout restart daemonset cloudwatch-agent
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     aws iam attach-role-policy --role-name <에이전트가 쓰는 역할> \
       --policy-arn arn:aws:iam::aws:policy/CloudWatchAgentServerPolicy
     kubectl -n amazon-cloudwatch rollout restart daemonset cloudwatch-agent
     ```
     </TabItem>
   </Tabs>

</Steps>

:::caution[역할을 잘못 짚는 실수]
클러스터에는 노드 역할과 서비스 계정용 역할이 함께 있어 엉뚱한 역할의 정책을 보며 시간을 쓰기 쉽다. **에이전트 파드가 실제로 assume한 역할 ARN을 먼저 특정한다.**

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  kubectl -n amazon-cloudwatch describe sa cloudwatch-agent   # annotation 의 role-arn
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  kubectl -n amazon-cloudwatch describe sa cloudwatch-agent   # annotation 의 role-arn
  ```
  </TabItem>
</Tabs>

그리고 `rollout restart` 는 **데몬셋·디플로이먼트 단위**다. 파드를 지정하면 명령 자체가 성립하지 않는다.
:::

### WAF 로깅 활성화

WAF는 로깅이 꺼진 채로 만들어진다. 켜 두지 않으면 부하 중 "정상 요청이 403"을 진단할 근거가 없다.

<Tabs syncKey="shell">
  <TabItem label="PowerShell">
  ```powershell
  # 로그 그룹 이름은 반드시 aws-waf-logs- 로 시작. CLOUDFRONT 스코프는 us-east-1
  aws logs create-log-group --log-group-name aws-waf-logs-task3 --region us-east-1

  $acl = aws wafv2 list-web-acls --scope CLOUDFRONT --region us-east-1 `
    --query 'WebACLs[0].ARN' --output text
  $lg  = aws logs describe-log-groups --log-group-name-prefix aws-waf-logs-task3 `
    --region us-east-1 --query 'logGroups[0].arn' --output text

  aws wafv2 put-logging-configuration --region us-east-1 `
    --logging-configuration "ResourceArn=$acl,LogDestinationConfigs=$lg"
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash
  # 로그 그룹 이름은 반드시 aws-waf-logs- 로 시작. CLOUDFRONT 스코프는 us-east-1
  aws logs create-log-group --log-group-name aws-waf-logs-task3 --region us-east-1

  acl=$(aws wafv2 list-web-acls --scope CLOUDFRONT --region us-east-1 \
    --query 'WebACLs[0].ARN' --output text)
  lg=$(aws logs describe-log-groups --log-group-name-prefix aws-waf-logs-task3 \
    --region us-east-1 --query 'logGroups[0].arn' --output text)

  aws wafv2 put-logging-configuration --region us-east-1 \
    --logging-configuration "ResourceArn=$acl,LogDestinationConfigs=$lg"
  ```
  </TabItem>
</Tabs>

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

WAF 평가 로그를 CloudWatch Logs 로 흘린다. 로그 그룹 이름의 `aws-waf-logs-` 접두어는 규칙이라 다른 이름이면 마지막 명령이 거부된다. Web ACL 과 로그 그룹을 각각 조회해 변수에 담은 뒤 둘을 연결하는 순서다. CloudFront 에 붙은 ACL 이므로 세 명령 모두 `us-east-1` 이다.

</details>

**검증**: SQL 주입 모양의 요청을 한 번 던지고 `aws logs tail aws-waf-logs-task3 --region us-east-1 --since 2m` 에 그 요청이 잡히는지 본다. 로그가 비면 배달 권한을 확인한다.

## 사전 워밍 (트래픽 개시 5분 전)

노드 프로비저닝 2~3분을 트래픽 개시 시점에서 앞으로 당긴다. 낮은 우선순위 placeholder 파드로 노드를 미리 띄우고, 트래픽이 오면 0으로 줄여 실제 파드에 자리를 내준다.

```yaml
# warm.yaml — 드릴용. 채점 대상 리소스가 아니므로 트래픽 개시 직후 삭제한다.
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: warm
value: -10
preemptionPolicy: Never
globalDefault: false
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: warm
spec:
  replicas: 3
  selector:
    matchLabels: { app: warm }
  template:
    metadata:
      labels: { app: warm }
    spec:
      priorityClassName: warm
      terminationGracePeriodSeconds: 0
      containers:
        - name: pause
          image: registry.k8s.io/pause:3.9
          resources:
            requests: { cpu: 600m, memory: 768Mi }
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

노드를 미리 확보하는 워밍업 리소스다. 우선순위를 음수로 두고 `preemptionPolicy: Never` 로 잡아, 실제 앱 파드가 뜰 때 이 파드들이 밀려나되 남을 자리를 만들어 둔다. 요청량을 실제 앱과 비슷하게 잡는 이유는 그래야 같은 크기의 노드가 준비되기 때문이다. 채점 대상 리소스가 아니므로 트래픽 시작 직후 지운다.

</details>

  ```powershell
  # 트래픽 개시 시각에:
  kubectl delete -f warm.yaml   # 자리를 실제 파드에 넘긴다
  ```
  </TabItem>
  <TabItem label="Bash (Linux/CloudShell)">
  ```bash

  kubectl get nodes -w          # 노드가 목표 수만큼 Ready 되면 다음 줄
  # 트래픽 개시 시각에:
  kubectl delete -f warm.yaml   # 자리를 실제 파드에 넘긴다
  ```
  </TabItem>
</Tabs>

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

워밍업을 실제로 쓰는 순서다. 적용한 뒤 노드가 목표 수만큼 Ready 가 되기를 기다리고, 트래픽이 시작되는 시각에 삭제한다. 노드 부팅에 2분 가까이 걸리므로, 이 단계를 건너뛰면 첫 스텝에서 응답 시간이 그만큼 튄다.

</details>

워밍 노드는 그대로 두면 비용 ratio를 올린다. `consolidateAfter: 30s`가 회수하므로 **삭제 후 노드 수가 실제 부하를 따라가는지** 감시 루프로 확인한다.



## 오독 복구 — 배포 시점에 확정되는 값

3과제의 오독은 성격이 다르다. 과제지에 없는 값을 **앱 동작에서 알아내야 하는** 과제라, 잘못 읽는 대상이 이름이 아니라 **구성 자체**다. 그리고 대부분 배포 시점에 확정돼 뒤에 못 고친다.

먼저 표로 감각을 잡는다.

| 잘못 읽은 값 | 나중에 고칠 수 있나 | 되돌리는 비용 |
|---|---|---|
| 인스턴스 타입 | 노드는 교체 가능하나 설정을 고치고 **노드를 다 갈아야** 한다 | 수 분 + 그동안의 가용성 손실 |
| DB 배치(단일/다중 AZ) | 변경은 되지만 **재시작을 동반**한다 | 부하 중이면 그 구간 실패 |
| DB 인스턴스 등급 | 변경 가능, 재시작 동반 | 위와 같음 |
| 엔드포인트 단일화 | 앞단을 새로 세우는 일 | 크다 — 채점 플랫폼에 등록한 주소가 바뀐다 |
| 리전 | **불가** | 전부 다시 |

### 1. 인스턴스 타입을 다른 것으로 띄웠다

<Steps>

1. **무엇이 떠 있는지 센다.**

   ```bash
   kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.metadata.labels.node\.kubernetes\.io/instance-type}{"\n"}{end}'
   ```

2. **정의를 고친다.** 노드는 선언에서 만들어지므로 선언을 먼저 고치지 않으면 지워도 같은 것이 다시 뜬다.

   ```bash
   grep -n 'instance-type\|instance-category\|instance-size' ~/skills-2026/task-3/k8s/01-nodepool.yaml
   ```

3. **기존 노드를 회수시킨다.** 고친 선언은 **새로 뜨는 노드에만** 적용된다. 이미 뜬 노드는 그대로 남는다.

4. **판정.** 트래픽 전이면 그냥 갈면 된다. 트래픽 중이면 **한 대씩** 갈아 가용성을 지킨다 — 한꺼번에 지우면 그 구간이 통째로 실패로 잡힌다.

</Steps>

**교훈.** 선언형에서 "고쳤다"는 것은 **다음에 만들어질 것**을 고쳤다는 뜻이다. 이미 있는 것은 따로 회수해야 바뀐다.

### 2. 엔드포인트를 여러 개로 냈다

과제지는 사용자에게 주는 주소를 **하나로 단일화**하라고 한다. 앱마다 주소를 따로 내면 그 자체로 요구 미충족이다.

<Steps>

1. **밖으로 열려 있는 것을 전부 센다.**

   ```bash
   kubectl get ingress,svc -A -o wide | grep -iE 'loadbalancer|hostname'
   ```

2. **경로로 나눈다.** 주소를 늘리는 대신 **한 주소 안에서 경로로** 앱을 가른다. 그 정의가 [21 이론](/part-5/21-task3-deploy/theory/)의 확인 블록에서 본 라우팅 파일 한 곳이다.

3. **채점 플랫폼에 넣는 형식을 확인한다.** 프로토콜과 주소까지만 넣고 **경로는 넣지 않는다.** 형식이 틀리면 그 뒤 채점이 전부 무의미해진다.

</Steps>

**교훈.** "여러 개를 만들었다"가 아니라 **"하나로 모으라는 요구를 못 읽었다"** 가 실점의 이유다. 요구가 금지형일 때는 만든 것이 아니라 **안 만든 것**이 점수다.

### 3. 정적 파일 경로를 앱으로 보냈다

이미지 다운로드가 앱을 거치면 앱이 그 부하를 다 받는다. 요구는 같은 주소로 제공하되 **다른 곳에서** 오는 것이다.

<Steps>

1. **지금 어디로 가는지 본다.**

   ```bash
   curl -s -o /dev/null -w 'status=%{http_code} time=%{time_total}\n' "$CF/images/없는파일.jpg"
   ```

2. **403 이 나오면 접근 정책 문제이고, 404 면 의도대로다.** 없는 파일에 403 을 내는 것은 저장소가 키 존재 여부를 숨기기 때문이다 — [21 이론](/part-5/21-task3-deploy/theory/)의 엣지 계층 절이 그 경로를 다룬다.

3. **판정.** 경로 분기는 앞단에서 끝내야 앱 부하가 줄고 응답도 빨라진다. 앱을 거치게 두면 성능 축과 비용 축을 같이 잃는다.

</Steps>
