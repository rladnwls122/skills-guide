## 규칙

- 조정은 반드시 **관측 → 노브 1개 변경 → 재측정** 순서로 한다. 부하 중에 두 개를 동시에 바꾸면 어느 쪽이 들었는지 알 수 없다.
- 부하는 자기 CloudFront 도메인에만 주입한다. 드릴이 끝나면 **부하부터 멈추고** 스택을 지운다.
- 드릴 1회는 배포부터 정리까지 3시간 안에 끝낸다([모듈 개요](/part-5/22-task3-tuning/)의 과금 절차).

:::note[실전 참조 — 막히면 여는 곳]
- k6 옵션·임계값 문법: [k6 문서](https://grafana.com/docs/k6/latest/)
- 대시보드에 칠 쿼리: [PromQL 기초](https://prometheus.io/docs/prometheus/latest/querying/basics/)
- 노브의 실제 필드 이름: `kubectl explain hpa.spec.behavior` · `kubectl explain nodepool.spec.limits`
- 부하 중 증상별 확인 명령: [트러블슈팅](/reference/troubleshooting/)

## 드릴 B — k6 3단 프로파일

부하 스크립트는 **저장소에 없다.** 직접 쓴다 — 그리고 그게 맞다. 실전에서 트래픽을 넣는 것은 채점 플랫폼이고, 여기서 만드는 스크립트는 그 트래픽을 **미리 흉내 내 내 시스템의 한계를 찾는 도구**다. 임계값을 채점 기준과 같게 두면 스크립트의 빨간불이 곧 감점 예고가 된다.

아래를 `load.js` 로 저장한다. 임계값은 샘플 과제지의 서비스 수준 목표에서 그대로 가져왔다 — user·product 는 0.2초, stress 는 1초, 그리고 최소 가용성 상한이 5초다.

```javascript title="load.js"
import http from 'k6/http';
import { check, group } from 'k6';

const BASE = __ENV.BASE_URL;
const VUS = Number(__ENV.VUS || 20);
const DURATION = __ENV.DURATION || '2m';

export const options = {
  vus: VUS,
  duration: DURATION,
  thresholds: {
    // 서비스 수준 목표 — 여기가 빨간불이면 성능 ratio 를 잃는다
    'http_req_duration{api:user}': ['p(90)<200'],
    'http_req_duration{api:product}': ['p(90)<200'],
    'http_req_duration{api:stress}': ['p(90)<1000'],
    // 최소 가용성 — 5초를 넘기면 그 요청은 실패로 친다
    http_req_duration: ['p(99)<5000'],
    http_req_failed: ['rate<0.01'],
  },
};

// 변조 방지용 쿼리스트링. 값 자체는 검사되지 않지만 빠지면 요청이 거부된다
const hex = (n) => Array.from({ length: n }, () => Math.floor(Math.random() * 16).toString(16)).join('');
const uuid = () => [hex(8), hex(4), hex(4), hex(4), hex(12)].join('-');
const rid = () => ({ requestid: String(Date.now()).slice(-12), uuid: uuid() });

export default function () {
  const id = `k6-${__VU}-${__ITER}`;
  const q = rid();

  group('user', () => {
    const body = JSON.stringify({ ...q, username: id, email: `${id}@example.org` });
    const post = http.post(`${BASE}/v1/user`, body,
      { headers: { 'Content-Type': 'application/json' }, tags: { api: 'user' } });
    check(post, { 'user 201': (r) => r.status === 201 });

    const get = http.get(`${BASE}/v1/user?email=${id}@example.org&requestid=${q.requestid}&uuid=${q.uuid}`,
      { tags: { api: 'user' } });
    check(get, { 'user 200': (r) => r.status === 200 });
  });

  group('product', () => {
    // 같은 id 를 반복 조회한다 — 캐시가 듣는 구간인지 여기서 갈린다
    const get = http.get(`${BASE}/v1/product?id=k6-fixed&requestid=${q.requestid}&uuid=${q.uuid}`,
      { tags: { api: 'product' } });
    check(get, { 'product 200 or 404': (r) => r.status === 200 || r.status === 404 });
  });

  group('stress', () => {
    const body = JSON.stringify({ ...q, length: 256 });
    const res = http.post(`${BASE}/v1/stress`, body,
      { headers: { 'Content-Type': 'application/json' }, tags: { api: 'stress' } });
    check(res, { 'stress 201': (r) => r.status === 201 });
  });
}
```

:::caution[앱이 바뀌면 스크립트도 바뀐다]
경로·필드·응답코드는 **당일 배부되는 앱**이 정본이다. 위 값은 샘플 과제지 기준이므로, 당일에는 앱을 먼저 한 번 호출해 실제 응답을 보고 스크립트를 맞춘다. 3과제는 요구사항을 구현하는 과제가 아니라 **주어진 앱을 분석해 운영하는 과제**다.
:::

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

시험 중 상태를 30초마다 한 화면에 모으는 감시 루프다. HPA 의 현재·목표 이용률, 노드와 파드의 실제 사용량, 노드 수, 타깃 헬스를 함께 본다. 응답이 느려질 때 원인이 파드 부족인지 노드 부족인지 타깃 등록 지연인지를 이 네 지표의 조합으로 가른다.

</details>

CloudWatch에서는 Container Insights(파드 CPU)와 RDS Proxy 지표(`DatabaseConnections`, `DatabaseConnectionsBorrowLatency`)를 함께 연다.

읽는 순서는 RED 다음 USE로 고정한다([이론](/part-5/21-task3-deploy/theory/)의 USE·RED 절).

1. **RED** — k6 콘솔의 요청 수·오류율·`http_req_duration` p90으로 증상을 확인한다.
2. **USE** — `kubectl top`(사용률), HPA 이용률과 Pending 파드·Proxy borrow latency(포화), Events와 타깃 상태(오류)로 원인 계층을 좁힌다.
3. 좁혀진 계층에 해당하는 노브를 튜닝 노브 표에서 하나만 고른다.

## 운영 대시보드 (선택 드릴)

감시 루프를 터미널 세 창으로 도는 대신 한 화면으로 모으는 훈련이다. 채점 대상이 아니라 **조정 속도를 위한 도구**이므로, 부하 드릴을 두 번 이상 돌려 무엇을 보게 되는지 안 뒤에 만든다.

담을 것은 부하 중 실제로 손이 가는 값들이다.

| 묶음 | 패널 | 데이터 소스 |
|---|---|---|
| 트래픽 판정 | 2xx·4xx·5xx 개수, 응답시간 평균·최대 | ALB·타깃그룹 지표 |
| 차단 실적 | 메서드·응답 코드·URI별 건수, 차단된 요청 | WAF 로그(Logs Insights) |
| 자원 | 클러스터·노드·파드 CPU·메모리 사용률 | Container Insights |
| 규모 | 레플리카 수, 노드 수 추이 | Container Insights·Karpenter 이벤트 |
| 앱 로그 | 키워드·에러 필터 | CloudWatch Logs Insights |

:::caution[남이 만든 대시보드를 그대로 쓰지 않는다]
값이 어떤 쿼리로 계산되는지 모르면, 부하 중 숫자가 이상할 때 대시보드가 틀린 것인지 시스템이 틀린 것인지 가를 수 없다. 패널 하나를 추가할 때마다 **그 값이 어느 API·쿼리에서 나오는지** 한 줄로 적어 둔다.

AI로 골격을 받는 것은 괜찮다 — 받은 뒤 쿼리를 직접 읽고 고치는 것이 조건이다([AI 기반 과제 풀이 훈련](/part-6/26-ai-assisted-drill/)).
:::

## 튜닝 노브 표

증상을 보면 **노브 하나만** 돌린다. 위 행부터 검토한다 — 아래로 갈수록 효과 대비 위험이 크다.

| 증상 | 1순위 확인 | 노브 | 파일 |
|---|---|---|---|
| user GET p90이 수백 ms | DB에서 `EXPLAIN SELECT ... WHERE email=` | `email` 인덱스 생성 | `db/02-index.sql` |
| 부하 개시 직후만 5xx·타임아웃 | `kubectl get hpa` 이용률 급등 + 파드 수 정체 | `minReplicas` 상향, `scaleUp` 정책 공격적으로 | 앱 매니페스트 HPA |
| 파드는 늘었는데 Pending | `kubectl describe pod` Events | NodePool `limits.cpu` 상향 | `k8s/01-nodepool.yaml` |
| CPU 여유가 있는데 p99만 튐 | 파드에 CPU limit이 걸렸는지 | CPU limit 제거 | 앱 매니페스트 `resources` |
| DB 커넥션 에러·borrow latency 상승 | RDS Proxy 지표 | `max_connections_percent` 상향(최대 100) | `terraform/rds-proxy.tf` |
| 스케일다운 직후 502/503 | `describe-target-health`의 draining | `deregistration_delay` 축소, `preStop` sleep 정렬 | `terraform/alb.tf`, 앱 매니페스트 |
| 이미지가 갱신 전 내용으로 나감 | 해당 키를 직접 GET, `x-cache` 헤더 | 무효화 실행 또는 short TTL 캐시 정책 | `terraform/cloudfront.tf` |
| 정상 요청이 403 | WAF 콘솔(us-east-1) sampled requests | 문제 룰을 Count로 내리거나 `RuleActionOverrides` | `terraform/waf.tf` |
| 비용 ratio 상단 초과 | 노드 수 추이 | HPA `maxReplicas`·NodePool `limits.cpu` 하향, `consolidateAfter` 단축 | `k8s/01-nodepool.yaml` |
| 유휴인데 노드가 2대 이상 | `kubectl get nodeclaims` 와 노드그룹 크기 | 차트 `replicas` 1 확인, zone spread 를 `ScheduleAnyway` 로, PDB 삭제 | `scripts/*.sh`, `k8s/1X-*.yaml` |
| 부하 중에도 노드가 안 늘어 하한 미달 | `kubectl get hpa` 이용률이 목표 아래 | HPA 목표를 60%에서 40%로 하향 — 하한 0.50 아래는 0점 | 앱 매니페스트 HPA |
| HPA 이용률이 `<unknown>` | `kubectl top pods` 응답 여부 | 파드에 `requests` 선언 (없으면 계산 불가) | 앱 매니페스트 `resources` |
| Container Insights 사용률 패널이 빔 | 에이전트 로그의 `AccessDenied` | 에이전트 역할에 `CloudWatchAgentServerPolicy` 후 데몬셋 재시작 | IAM 역할 |
| 캐시가 갱신 전 이미지를 계속 냄 | `x-cache` 헤더, 캐시 정책의 TTL | 무효화 후 short TTL 정책으로 교체 | `terraform/cloudfront.tf` |
| 쿼리스트링이 다른데 같은 응답 | 캐시 정책의 캐시 키 구성 | 쿼리스트링을 캐시 키에 포함하거나 그 경로를 캐시 제외 | `terraform/cloudfront.tf` |

## 드릴 C — 노브 조정 루프 (관찰 → 노브 1개 → 재측정)

드릴 B의 한 프로파일(예: Spike)을 부하를 건 채로 반복하며 이어지는 순서를 돈다. **노브는 한 번에 하나만** 바꾼다. 두 개를 같이 바꾸면 다음 회차에서 어느 쪽이 개선의 원인인지 알 수 없다.

     ```bash
     VUS=80 DURATION=1m k6 run load.js
     ```
     </TabItem>
   </Tabs>

5. **변경 전/후를 기록하고 판정한다**

   p90·실패율·최대 노드 수가 의도한 방향으로 움직였으면 유지한다. 아니면 되돌리고 다음 노브로 — 여전히 한 번에 하나씩. 회차마다 이 문서 끝의 회고 양식에 한 줄씩 남긴다.

</Steps>

## 드릴 D — 부하 중 장애 10종

부하를 돌린 채로 [트러블슈팅](/reference/troubleshooting/)의 "부하 운영(3과제)" 10개 항목을 하나씩 재현하고 복구한다. 규칙은 모듈 24과 같다 — **확인 명령 → 원인 → 조치**, 추측 수리는 실패 처리.

부하 중 복구는 정지 상태 복구와 다르다. 각 항목마다 두 가지를 함께 기록한다.

- 복구까지 걸린 시간
- 그 사이 k6 실패율이 얼마나 올랐는지 (= 실전에서 잃었을 availability)

## 드릴 E — 환경 분리와 경로 라우팅 (추가 문항 대비)

:::caution[정답지에 없는 패턴이다]
`skills-2026/task-3` 는 앱 3종을 한 벌만 띄운다. 이 드릴의 스테이징·프로덕션 분리와 Ingress 경로 라우팅은 **2026-08 실습 강의**에서 다룬 구성이다. 추가 바이너리 배포 같은 요구가 붙었을 때 쓸 형태다. 기본 드릴 A~D를 통과한 뒤에 한다.
:::

<Steps>

1. **같은 앱을 두 환경으로 띄운다**

   매니페스트를 복사해 네임스페이스와 이름만 바꾼다. 이미지·포트·헬스체크 경로는 그대로 둔다 — 바뀌는 것이 적을수록 두 환경의 차이가 원인 추적에 쓸모 있다.

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     kubectl create namespace staging
     kubectl create namespace production
     kubectl -n staging apply -f k8s/10-user.yaml
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     kubectl create namespace staging
     kubectl create namespace production
     kubectl -n staging apply -f k8s/10-user.yaml
     ```
     </TabItem>
   </Tabs>

2. **프로덕션에만 붙는 것을 챙긴다**

   두 환경의 차이는 셋이다 — 환경변수·시크릿 값, `ServiceAccount`, 그 서비스 계정에 붙는 IAM 권한(IRSA 또는 Pod Identity).

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     kubectl -n production create serviceaccount user
     kubectl -n production annotate serviceaccount user `
       eks.amazonaws.com/role-arn=arn:aws:iam::<계정ID>:role/<역할명>
     # Deployment 의 spec.template.spec.serviceAccountName 에 user 를 넣고 재적용
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     kubectl -n production create serviceaccount user
     kubectl -n production annotate serviceaccount user \
       eks.amazonaws.com/role-arn=arn:aws:iam::<계정ID>:role/<역할명>
     # Deployment 의 spec.template.spec.serviceAccountName 에 user 를 넣고 재적용
     ```
     </TabItem>
   </Tabs>

   서비스 계정만 만들고 파드 스펙에 연결하지 않는 것이 흔한 누락이다. 파드는 뜨는데 AWS 호출만 `AccessDenied` 로 실패한다.

3. **Ingress로 경로를 가른다**

   ```yaml
   # ingress.yaml — 경로 두 개 + 매칭 실패용 기본 백엔드
   apiVersion: networking.k8s.io/v1
   kind: Ingress
   metadata:
     name: app
     annotations:
       alb.ingress.kubernetes.io/scheme: internet-facing
   spec:
     ingressClassName: alb
     defaultBackend:
       service:
         name: response
         port: { number: 8080 }
     rules:
       - http:
           paths:
             - path: /staging
               pathType: Prefix
               backend:
                 service:
                   name: user-staging
                   port: { number: 8080 }
             - path: /production
               pathType: Prefix
               backend:
                 service:
                   name: user-production
                   port: { number: 8080 }
   ```

   <details class="diagram-note">
   <summary>이 블록이 하는 일</summary>

   ALB 하나를 두 경로로 나눈다. `/staging` 과 `/production` 은 각각의 서비스로 가고, 둘 중 어디에도 걸리지 않는 요청은 `defaultBackend` 로 간다. 기본 백엔드가 없으면 매칭되지 않은 요청의 응답이 컨트롤러 기본값에 맡겨지므로, 어떤 코드가 나갈지 과제지가 요구한 값과 어긋날 수 있다.

   </details>

4. **없는 경로의 응답 코드를 확인한다**

   <Tabs syncKey="shell">
     <TabItem label="PowerShell">
     ```powershell
     curl.exe -s -o NUL -w "%{http_code}`n" "http://<ALB DNS>/none"     # 기대: 404
     curl.exe -s -o NUL -w "%{http_code}`n" "http://<ALB DNS>/staging"  # 기대: 200
     ```
     </TabItem>
     <TabItem label="Bash (Linux/CloudShell)">
     ```bash
     curl -s -o /dev/null -w "%{http_code}\n" "http://<ALB DNS>/none"     # 기대: 404
     curl -s -o /dev/null -w "%{http_code}\n" "http://<ALB DNS>/staging"  # 기대: 200
     ```
     </TabItem>
   </Tabs>

   기본 백엔드로 보낸 서비스가 실제로 그 코드를 내는지까지 본다 — 서비스가 없으면 404가 아니라 502·503이 나간다.

</Steps>

**판정**: 두 환경이 각 경로에서 응답하고, 정의되지 않은 경로가 과제지가 지정한 코드로 끝난다. 프로덕션 파드가 AWS API를 호출하는 동작(예: S3 업로드)이 권한 오류 없이 성공한다.

## 판정 기준

- 배포: 스모크 6종 통과를 **T+50분 내**
- 성능: soak 구간에서 user·product `p(90) < 200ms`, stress `p(90) < 1000ms`
- 가용성: 3회차 전체 `http_req_failed < 10%`
- 비용: 부하 전 구간 노드 1~7대, 부하 종료 5분 내 1대로 회수
- 복구: 10종 중 7개 이상을 5분 내 복구

네 개 중 세 개를 만족하면 통과, 두 개 이하면 실패 축만 다음 드릴에서 재도전한다.

## 변형 셀프 체크

요구가 바뀌면 아래 자리가 움직인다. 재배포 없이, 각 질문에 먼저 답한 뒤 펼쳐 확인한다. 3과제는 mark 스크립트가 없고 네 축으로 채점한다 — 비정상 요청 처리·고가용성 및 안정성·성능 효율성·비용 최적화다(`task-3/mark-sample.md`).

1. 과제지가 비번호와 DB 비밀번호를 다른 값으로 지정하면 무엇을 고치나?

   <details>
   <summary>답 확인</summary>

   `terraform/terraform.tfvars` 의 `player_number`·`db_password` 와, 셸의 `$env:DB_PASSWORD` 를 함께 바꾼다. tfvars 쪽은 RDS 와 RDS Proxy 가 실제로 만드는 값이고, 환경 변수는 매니페스트의 `<DB_PASSWORD>` 자리를 치환할 때만 쓰인다. 두 값이 어긋나면 인프라는 정상으로 뜨는데 앱만 DB 인증에 실패해 배포 실패가 아니라 런타임 500 으로 나타난다.

   </details>

2. 노드 상한을 6대에서 8대로 올리라면 어디를 고치고, 어디를 그대로 두나?

   <details>
   <summary>답 확인</summary>

   `k8s/01-nodepool.yaml` 의 `limits.cpu` 와 앱 매니페스트 HPA 의 `maxReplicas` 를 함께 올린다. 상한 하나만 올리면 파드가 안 늘어 노드도 안 는다. 인스턴스 타입 목록은 `requirements` 한 곳이고 Auto Mode 가 vCPU 1개 이하를 거부하므로 t3.medium 아래로는 못 내린다. 필드 이름은 `kubectl explain nodepool.spec.limits` 로 확인하고, 동선은 [검색 가이드](/reference/search-guide/)에 있다.

   </details>

3. 그 변경은 어느 판정 축에 닿나?

   <details>
   <summary>답 확인</summary>

   두 축이 반대로 움직인다. 고가용성·성능 효율성 축은 로드 처리 비율과 응답 시간 구간으로 배점되므로 오르고, 비용 최적화 축은 노드 수의 함수라 내려간다. 그래서 노브는 한 번에 하나만 바꾸고 같은 조건으로 재측정한다.

   </details>

4. user API 응답 시간 기준이 0.2초에서 0.1초로 강화되면 어디부터 보나?

   <details>
   <summary>답 확인</summary>

   `db/02-index.sql` 의 `email` 인덱스다. 성능 효율성 축은 "응답 시간 기준 이하 비율" 을 구간별로 나눠 배점하므로 기준이 내려가면 데이터 계층이 먼저 걸린다. 확인은 DB 에서 `EXPLAIN SELECT ... WHERE email=` 이고, 그다음이 파드 CPU limit 유무다.

   </details>
