> 문서 유형: explanation

선행 지식과 학습 경로는 [모듈 개요](/part-6/16-break-fix/)에.

이 PART는 적용이 전부다. 원칙만 짧게.

## 원칙 1 — 추측으로 고치지 않는다

증상을 보면 손이 먼저 나간다 — 그게 시간을 태운다. **증상 → 1순위 확인 명령 → 출력 해석 → 조치.** [트러블슈팅](/reference/troubleshooting/)의 표가 그 순서 그대로다.

:::danger[추측 수리 금지]
확인 명령이 원인을 말해주기 전에는 아무것도 바꾸지 않는다.
:::

## 원칙 2 — 경로를 분리해서 진단한다

CloudFront 403처럼 다층 경로의 오류는 **오리진 직접 curl로 계층을 분리**한다: S3 presign / ALB 직접 / Function URL 직접. 어느 계층에서 처음 깨지는지 찾으면 원인 후보가 1~2개로 준다.

## 원칙 3 — Events와 로그가 1차 소스다

- k8s: `kubectl describe pod` Events 최하단 → 그 다음 `kubectl logs --previous` ([k8s-basics](/start/k8s-basics/)에 Pod·Event 를 읽는 기본기가 있다)
- AWS: 해당 서비스의 CloudWatch Logs / CloudTrail (IAM 계열은 AssumeRole 오류 검색)
- LB: `aws elbv2 describe-target-health` reason 필드

## 원칙 4 — 시간 지연을 오류로 착각하지 않는다

TG healthy 2~3분, CloudFront 전파 수 분, Config 첫 평가 5~10분 — [소요 시간표](/reference/timings/). "고장"의 절반은 그냥 아직 안 된 것이다. 대기해야 하는 상황인지부터 판단.

## 원인 순위(빈도순)로 확인한다

[트러블슈팅 문서](/reference/troubleshooting/)의 각 항목은 원인을 실측 빈도순(①②③)으로 나열한다. ①부터 확인 — 대회장 통계적으로 가장 빠른 경로다.

## 훈련이 만드는 것

같은 증상을 **자기 손으로 만들어보면** 확인 명령의 출력이 어떻게 생겼는지(정상 vs 고장) 기억에 박힌다. 대회장에서는 출력을 보는 순간 원인이 떠올라야 한다.

## 퀴즈 (5문)

<Quiz title="Pod Pending — 1순위 명령">
Pod가 Pending에서 안 나온다. 가장 먼저 칠 명령은?

- [x] `kubectl describe pod <pod>` — Events 최하단을 본다
- [ ] `kubectl logs <pod>`
  > Pending은 컨테이너가 시작조차 안 한 상태다. 로그가 존재하지 않으므로 아무것도 안 나온다.
- [ ] `kubectl delete pod <pod>` 로 재생성을 유도한다
  > 원칙 1 위반 — 추측 조치다. 스케줄 불가 원인이 그대로면 새 파드도 똑같이 Pending이고 시간만 태운다.
- [ ] `kubectl get nodes -o wide` 로 노드 용량부터 확인한다
  > 용량은 원인 후보 중 하나일 뿐이다. describe의 Events가 용량인지 taint인지 셀렉터 오타인지를 한 줄로 알려주므로 순서가 뒤집혔다.

`kubectl describe pod <pod>` — **Events 최하단**이 1차 소스다. 해석 순서는 실측 빈도순으로 taint/toleration 불일치 → 용량 부족 → nodeSelector 오타. 확인 명령이 원인을 말해주기 전에는 아무것도 바꾸지 않는다.
</Quiz>

<Quiz title="ALB → Lambda 502">
ALB 타깃그룹이 Lambda인 구성에서 502가 돌아온다. 원인과 조치는?

- [x] 함수 응답이 ALB 통합 포맷을 어겼다 — `statusCode`·`headers`·`isBase64Encoded` 세 필드를 갖춘 객체를 반환하도록 고친다
- [ ] 타깃그룹 헬스체크 경로가 틀렸다 — health check path를 고친다
  > Lambda 타깃그룹은 HTTP 헬스체크로 상태를 보지 않는다. 경로를 고쳐도 502는 그대로다.
- [ ] 보안그룹이 Lambda 아웃바운드를 막고 있다 — 규칙을 연다
  > ALB→Lambda는 보안그룹 경로를 타지 않는다(서비스 호출). 네트워크를 의심하기 전에 함수 응답 본문부터 본다.
- [ ] Lambda 동시성이 부족하다 — reserved concurrency를 올린다

**ALB 통합 응답 포맷 위반.** AWS 가 요구하는 필수 항목은 `statusCode` / `headers` / `isBase64Encoded` 셋이다 — `body` 는 생략할 수 있고 `statusDescription` 은 필수가 아니다. 1차 소스는 해당 함수의 CloudWatch Logs — 함수가 200으로 끝났는데 ALB가 502면 포맷 문제로 거의 확정된다.
</Quiz>

<Quiz title="OAC S3 오리진 403">
CloudFront가 OAC로 붙인 S3 오리진에서 403을 낸다. Origin Request Policy가 `AllViewerExceptHostHeader`인 것이 1순위 의심 대상인 이유는?

- [x] AllViewer 계열이 뷰어의 `Authorization` 헤더를 오리진에 그대로 전달해 OAC가 붙인 SigV4 서명과 충돌한다 — OAC 오리진에는 QueryString-only ORP를 쓴다
- [ ] Host 헤더가 제외돼 S3가 어떤 버킷인지 판별하지 못한다
  > 이름 때문에 그럴싸하지만, S3 REST 엔드포인트로 가는 요청의 Host는 CloudFront가 오리진 도메인으로 다시 채운다. 403의 원인이 아니다.
- [ ] 버킷 정책의 `AWS:SourceArn` 이 배포 ARN과 다르다
  > 실제로 403을 내는 별개 원인이 맞다. 다만 ORP가 AllViewer 계열이면 정책을 고쳐도 계속 403이므로, 서명 충돌을 먼저 걷어내고 재확인한다.
- [ ] OAC와 레거시 OAI가 동시에 설정돼 서명이 이중으로 붙는다

**Authorization 헤더 전달이 SigV4 서명과 충돌**하기 때문이다. OAC 오리진에는 QueryString-only ORP를 붙인다. 다층 경로 오류이므로 원칙 2대로 **계층을 분리**해 확인한다 — S3 presign URL 직접 호출이 200이면 S3·정책은 정상이고 범인은 CloudFront 쪽 설정이다.
</Quiz>

<Quiz title="kubectl Unauthorized">
`kubectl get nodes` 가 Unauthorized를 낸다. 현재 신원을 확인하는 명령은 `aws sts` [[get-caller-identity]] 이고, 이 결과를 클러스터를 **생성한** 신원과 비교한다.

---

`aws sts get-caller-identity` ↔ **클러스터를 생성한 신원** 대조. EKS는 생성자에게만 자동으로 cluster-admin을 준다. 다르면 두 갈래다 — 같은 신원으로 `aws eks update-kubeconfig` 를 다시 하거나, 현재 신원에 Access Entry를 추가한다.

대회장에서 특히 잘 나는 경로: CloudShell과 로컬 터미널이 서로 다른 신원이거나, 역할을 assume한 세션으로 클러스터를 만들어놓고 베이스 유저로 kubectl을 치는 경우. 채점 직전 리셋 체크리스트에 "채점 신원 = 클러스터 생성자 확인"이 들어 있는 이유가 이것이다.
</Quiz>

<Quiz title="DynamoDB 시간이 UTC">
DynamoDB에 적재된 시각이 KST가 아니라 UTC로 저장돼 있다. 원인이 되는 요소를 모두 고르라.

- [x] 컨테이너 이미지에 tzdata 패키지가 없다
- [x] 컨테이너에 `TZ=Asia/Seoul` 환경변수가 지정되지 않았다
- [ ] DynamoDB 테이블이 다른 리전에 있다
  > DynamoDB는 넘어온 문자열을 그대로 저장할 뿐 시간대 변환을 하지 않는다. 리전은 무관하다.
- [ ] 노드(EC2)의 시스템 시계가 UTC다
  > 노드 시계를 KST로 바꿔도 컨테이너는 자기 tzdata와 `TZ`를 본다. 호스트를 고치는 건 증상 회피이자 재현 불가능한 조치다.

**tzdata 부재 + `TZ=Asia/Seoul` env 누락**, 둘 다 필요하다. `TZ`만 줘도 tzdata가 없으면 zone을 못 찾고, tzdata만 있어도 `TZ`가 없으면 UTC로 동작한다. Go 바이너리는 tzdata를 내장하지 않으므로 특히 잘 걸린다(`time/tzdata` 임포트 또는 이미지에 tzdata 설치).

실측 확인 명령은 `aws dynamodb scan --max-items 1` — 저장된 값을 직접 눈으로 본다. 앱 로그의 시각이 아니라 **저장된 항목**이 1차 소스다.
</Quiz>
