## 규칙

- **타이머를 켠다.** 이 모듈이 재는 것은 정확도가 아니라 초안부터 검증 완료까지의 시간이다.
- 검증은 **Q가 아닌 곳**에서 한다 — 공식 문서, `validate`, `--dry-run=server`, `kubectl explain`.
- Q에게 되묻는 횟수를 세 둔다. 3회를 넘으면 그 주제는 손으로 쓰는 편이 빠르다는 신호다.

원리와 실패 유형은 [이론](/part-6/18-ai-assisted-drill/theory/)에.

:::note[실전 참조 — 막히면 여는 곳]
- Terraform 인자 정본: [AWS Provider Registry](https://registry.terraform.io/providers/hashicorp/aws/latest/docs)
- 쿠버네티스 필드 존재 확인: `kubectl explain <리소스>.spec`
- 찾는 동선 자체가 막히면 [실전 문서 검색 가이드](/reference/search-guide/)
:::

## 프롬프트 형식

세 요소를 한 덩어리로 붙인다. 드릴마다 이 형식을 쓴다.

```text
[버전] AWS provider 5.x, 리전 ap-northeast-2
[요구] 과제지 문장 그대로 붙여넣기 — 이름·포트·임계값 포함
[요청] 위 요구를 만족하는 리소스 블록과, 만들어진 뒤 이 구성을 확인할 CLI 명령을 함께.
       요구에 없는 리소스는 만들지 마.
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

프롬프트의 세 조각이다. 버전이 인자 이름을 고정하고, 과제지 문장을 그대로 붙여 이름과 수치를 넘기며, 마지막 줄이 확인 명령까지 요구한다. "요구에 없는 리소스는 만들지 마"를 붙이는 이유는 Q 가 모범 구성을 얹으려 하기 때문이다 — 요구되지 않은 리소스는 감점이다.

</details>

## 드릴 A — Terraform 리소스 초안 (목표 3분)

<Steps>

1. **과제를 하나 고른다**

   기존 실습에서 이미 답을 아는 것을 고른다 — 정답을 알아야 Q의 오류가 보인다. 예: S3 버킷 + 퍼블릭 차단 4종 + SSE-KMS.

2. **프롬프트 형식대로 요청하고 시각을 적는다**

3. **값싼 순서로 검증한다**

   ```powershell
   # ── Windows PowerShell ──
   terraform fmt -check
   terraform validate
   terraform plan
   ```

   `validate` 가 통과하고 `plan` 에서 인자 오류가 나면 옛 인자명이다. Registry 문서의 인자 목록과 대조한다.

4. **과제지와 이름을 한 글자씩 대조한다**

   버킷 이름, 로그 그룹 이름, alias 이름이 채점 조회 키다. Q가 지어낸 이름이 하나라도 남으면 그 항목은 0점이다.

5. **요구에 없는 리소스를 지운다**

   `plan` 출력의 생성 목록을 과제지 요구와 1:1로 맞춘다. 남는 것이 있으면 지운다.

</Steps>

**기록**: 초안 도착까지 걸린 시간, 검증 완료까지 걸린 시간, 발견한 오류를 실패 유형 4종 중 하나로 분류.

## 드릴 B — 매니페스트 초안 (목표 3분)

Deployment·Service·HPA 한 벌을 요청한다. 이 드릴의 검증은 클러스터에게 묻는다.

```powershell
# ── Windows PowerShell ──
kubectl apply -f draft.yaml --dry-run=server
kubectl explain hpa.spec.behavior          # 필드가 실제로 있는지
kubectl explain deployment.spec.template.spec.containers.resources
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

서버 쪽 스키마로 검사한다. `--dry-run=server` 는 클러스터에 보내되 저장하지 않으므로, 그 클러스터 버전이 모르는 필드를 그 자리에서 거른다. `explain` 은 반대 방향이다 — 필드가 있는지 클러스터에게 직접 묻는다. Q 의 답과 어긋나면 클러스터가 맞다.

</details>

확인할 것 셋:

- Service의 셀렉터가 Deployment의 라벨과 **정확히** 같은가. 한 글자만 달라도 엔드포인트가 비고, 증상은 타깃 unhealthy로 나타난다.
- 컨테이너 포트와 Service의 대상 포트가 맞는가. `port` 와 `targetPort` 를 바꿔 쓰는 실수가 잦다.
- 헬스체크 경로가 과제지가 지정한 경로 그대로인가.

## 드릴 C — WAF 규칙과 CloudFront Function (목표 5분)

두 가지는 Q의 정확도가 높은 영역이다 — 입출력이 프롬프트 안에 다 들어가기 때문이다. 대신 **적용 절차**를 사람이 챙긴다.

<Steps>

1. **규칙을 요청한다**

   차단 조건을 문장으로 준다. 예: "쿼리스트링에 SQL 주입 패턴이 있으면 차단, URL 디코드 후 검사, CloudFront 스코프".

2. **Terraform 이면 `plan`, 콘솔이면 규칙 편집 화면에서 구조를 대조한다**

   `statement` 종류와 `text_transformation` 순서가 요구와 맞는지 본다. 관리형 그룹을 함께 얹었다면 요구에 있는지 확인한다.

3. **Function 은 게시하고 Behavior 에 연결한다**

   작성만 하고 게시(Publish)하지 않으면 반영되지 않는다. 연결까지 끝난 뒤에 경로를 실제로 호출해 확인한다.

   ```powershell
   curl.exe -s -o NUL -w "%{http_code}`n" "https://<cf도메인>/images/<키>"
   curl.exe -s -o NUL -w "%{http_code}`n" "https://<cf도메인>/v1/user?email=%27%20OR%201=1--"
   ```

4. **정상 요청이 막히지 않는지 확인한다**

   차단 규칙은 넓게 잡으면 정상 요청까지 먹는다. 차단 확인과 통과 확인을 항상 한 쌍으로 친다.

</Steps>

## 드릴 D — 변형 요구 반영 (목표 15분)

[변동 드릴](/part-6/15-mutation-drill/)의 변형 카드 하나를 뽑아 Q와 함께 반영한다. 재는 것은 **반영 완료까지의 시간**이다.

<Steps>

1. 바뀐 요구를 프롬프트 형식으로 옮긴다 — 바뀐 값과 바뀌지 않은 값을 함께 준다.
2. Q에게 **영향 파일 목록**을 먼저 묻는다. 그다음 각 파일의 수정 조각을 받는다.
3. 받은 목록을 `Select-String` 으로 검증한다 — Q가 빠뜨린 파일이 있는지 본다.

   ```powershell
   # ── Windows PowerShell ──
   Select-String -Path .\**\*.tf,.\**\*.yaml -Pattern '<옛 이름>'
   ```

4. 수정 후 같은 검색으로 잔여 0건을 확인하고 `plan`·`--dry-run=server` 로 닫는다.

</Steps>

:::caution[영향 파일 목록은 Q를 믿지 않는다]
Q는 레포 전체를 보지 못한다. 이름이 숨는 곳(대시보드 JSON, 스크립트 리터럴, eksctl 설정)을 빠뜨린다 — 검증은 문자열 검색이 한다. 숨는 곳 목록은 [변동 드릴](/part-6/15-mutation-drill/)에 있다.
:::

## 판정 기준

- 드릴 A·B: 초안부터 검증 완료까지 각 5분 이내, 발견 오류를 유형으로 분류
- 드릴 C: 차단 확인과 통과 확인을 한 쌍으로 통과
- 드릴 D: 변형 반영 후 잔여 문자열 0건, 15분 이내
- 전체: Q에게 되묻기 3회 이하

## 변형 셀프 체크

1. Q가 준 매니페스트가 `kubectl apply` 는 되는데 파드가 트래픽을 못 받는다. 먼저 볼 곳은?

   <details>
   <summary>답 확인</summary>

   Service 의 셀렉터와 Deployment 의 라벨이다. 둘이 어긋나면 엔드포인트가 비고, 증상은 타깃 unhealthy 로 나타난다. `kubectl get endpoints <서비스명>` 이 비어 있으면 확정이다. 스키마 오류가 아니라 값의 불일치이므로 `--dry-run` 으로는 잡히지 않는다.

   </details>

2. Q가 `terraform validate` 를 통과하는 코드를 줬는데 `plan` 에서 알 수 없는 인자로 실패한다. 무엇을 본 것인가?

   <details>
   <summary>답 확인</summary>

   옛 인자명이다. `validate` 는 구문과 스키마의 일부만 보고, 프로바이더 스키마 대조는 `plan` 단계에서 일어난다. 고치는 곳은 Registry 의 해당 리소스 문서이고, 프롬프트에 프로바이더 메이저 버전을 넣지 않은 것이 원인일 때가 많다.

   </details>

3. 대회 중 응답이 느려졌다. Q에게 무엇을 묻고 무엇을 묻지 않나?

   <details>
   <summary>답 확인</summary>

   지금 시스템 상태는 묻지 않는다 — Q 는 그 클러스터의 지표를 모른다. 원인 후보와 순위는 [트러블슈팅](/reference/troubleshooting/) 표에 있고 판단에 필요한 것은 현재 값이다. Q 에게 맡길 수 있는 것은 조치에 필요한 조각이다 — 예를 들어 지표를 뽑는 Logs Insights 쿼리나 수정할 매니페스트 조각이다.

   </details>
