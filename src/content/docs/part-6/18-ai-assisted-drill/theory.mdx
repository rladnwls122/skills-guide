선행 지식과 학습 경로는 [모듈 개요](/part-6/18-ai-assisted-drill/)에.

Q를 쓰면 타이핑이 빨라진다. 그런데 채점을 통과시키는 것은 타이핑이 아니라 **이름과 값의 정확 일치**다. 이 둘 사이의 간격이 이 모듈이 다루는 전부다.

## Q가 잘하는 것과 못하는 것은 갈린다

같은 도구가 어떤 요청에는 거의 정확하고 어떤 요청에는 반복해서 틀린다. 경계는 "그 정보가 어디에 있는가"로 갈린다.

| 요청 | 결과 | 이유 |
|---|---|---|
| 리소스 블록의 **골격**을 써 달라 | 대체로 맞다 | 공개 문서와 예제가 많은 형태다 |
| 정규식·Lua·JavaScript 같은 **작은 변환 코드** | 대체로 맞다 | 입출력이 프롬프트 안에 다 들어간다 |
| 특정 인자의 **최신 이름·기본값** | 자주 틀린다 | 버전마다 달라지고 옛 예제가 섞여 있다 |
| 과제지가 지정한 **이름·수치** | 프롬프트에 없으면 반드시 틀린다 | 대회 자료는 학습 데이터에 없다 |
| "이 구성이 채점을 통과하나" | 판정할 수 없다 | 채점 스크립트를 볼 수 없다 |

그래서 역할을 나눈다. **골격과 변환 코드는 Q에게, 이름·값·판정은 사람이.** 이 경계를 지키면 Q는 시간을 벌어 주고, 넘으면 그럴듯한 오답을 빠르게 만들어 준다.

## 프롬프트에 반드시 넣는 세 가지

Q의 출력이 일반 예제로 돌아오는 것은 프롬프트가 일반적이기 때문이다. 셋을 넣으면 답의 범위가 좁아진다.

1. **버전** — AWS provider 메이저 버전, 쿠버네티스 API 버전(`autoscaling/v2` 등), 앱 런타임. 인자 이름이 갈리는 축이다.
2. **과제지가 준 이름과 값** — 리소스 이름, 포트, 경로, 임계값. 프롬프트에 없으면 Q가 지어낸다.
3. **판정 방법** — "이 구성을 어떤 명령으로 확인할 것인지"까지 요구한다. 확인 명령이 함께 오면 검증이 곧바로 시작된다.

세 번째가 특히 남는다. Q가 제안한 확인 명령이 틀렸다면 그 자리에서 드러나고, 맞다면 검증 절차를 하나 얻는다.

## 검증은 값싼 순서로 한다

Q의 출력을 확인하는 수단은 비용이 다르다. 싼 것부터 쓴다.

| 순서 | 수단 | 걸리는 시간 | 잡히는 오류 |
|---|---|---|---|
| 1 | `terraform validate` · `kubectl apply --dry-run=server` | 초 | 문법, 없는 필드 |
| 2 | 공식 문서의 인자 목록 | 1~3분 | 옛 인자명, 필수 인자 누락 |
| 3 | `terraform plan` · `kubectl explain` | 수십 초 | 타입 불일치, 스키마 차이 |
| 4 | 실제 적용과 동작 확인 | 분~수십 분 | 런타임 동작, 권한 |

`--dry-run=server` 는 클러스터의 스키마로 검사하므로 없는 필드를 그 자리에서 거른다. `kubectl explain <리소스>.spec` 은 그 클러스터 버전이 실제로 아는 필드만 보여 준다 — Q의 답과 어긋나면 클러스터가 맞다.

:::caution[apply 로 검증하지 않는다]
가장 흔한 낭비가 "일단 적용해 보고 에러를 읽는" 방식이다. 인프라는 되돌리는 데 시간이 들고, 절반만 만들어진 상태가 다음 오류의 원인이 된다. 1~3단계에서 걸리는 오류를 4단계로 미루지 않는다.
:::

## Q 출력의 실패 유형 넷

반복해서 나타나는 형태가 있다. 이름을 붙여 두면 검토가 빨라진다.

| 유형 | 증상 | 첫 확인 |
|---|---|---|
| 옛 인자명 | `validate` 는 통과하는데 `plan` 에서 알 수 없는 인자 | Registry 리소스 문서의 인자 목록 |
| 없는 필드 | 매니페스트 적용 시 스키마 오류 | `kubectl explain <리소스>.spec` |
| 이름 불일치 | 적용은 되는데 채점 조회가 실패 | 과제지의 이름과 한 글자씩 대조 |
| 과잉 리소스 | 요구되지 않은 로그 그룹·키·정책이 함께 생성됨 | 과제지에 그 이름이 있는지 |

넷째가 감점으로 직결되는데 가장 눈에 안 띈다. Q는 "모범 구성"을 만들려 하므로 요구되지 않은 리소스를 얹는다. 과제는 **요구된 것만** 만드는 것이 규칙이다 — 이름이 과제지에 없으면 지운다.

## 무엇을 Q에게 맡기면 시간이 남는가

3과제처럼 시간이 지배하는 과제에서는 어디에 Q를 쓰는지가 곧 배분이다.

- **초반 배포 구간** — 반복적인 리소스 골격과 매니페스트. Q가 벌어 주는 시간이 가장 크다.
- **부하 운영 구간** — 지표 해석과 노브 선택은 사람이 한다. Q는 그 클러스터의 지금 상태를 모른다.
- **추가 문항 구간** — 새 규칙·함수·작은 코드. Q의 변환 코드 정확도가 높은 영역이다.

부하 중에 Q에게 "왜 느린가"를 묻는 것은 시간을 버리는 쪽이다. 원인 후보는 [트러블슈팅](/reference/troubleshooting/) 표에 이미 순위로 있고, 판단에 필요한 것은 지금 지표다.

- [ ] "이 구성으로 채점을 통과할 수 있는지 판정해 줘"

- [ ] "지금 응답이 느린데 원인이 뭔지 알려 줘"

경계는 **정보가 어디에 있는가**다. 공개 문서에 있는 형태(리소스 골격, 변환 코드)는 Q가 잘 맞히고, 대회 자료와 현재 시스템 상태에만 있는 정보(지정된 이름, 지금 지표)는 프롬프트에 넣지 않는 한 지어낸다.

<Quiz title="검증 순서">
Q가 준 Terraform 리소스 블록을 검증한다. 가장 먼저 할 일은?

- [x] `terraform validate` 로 문법과 없는 인자를 초 단위로 거른다
- [ ] `terraform apply` 로 실제로 만들어 보고 에러를 읽는다
  > 인프라는 되돌리는 데 시간이 들고 절반만 만들어진 상태가 다음 오류의 원인이 된다. 값싼 수단에서 걸릴 오류를 apply 로 미루지 않는다.
- [ ] Registry 문서를 먼저 정독한다
  > 문서 대조는 2순위다. 문법 오류가 있으면 문서를 읽는 시간이 통째로 낭비된다.
- [ ] Q에게 "이 코드 맞아?"라고 되묻는다
  > 같은 출처에 다시 물으면 같은 오류가 확인처럼 돌아온다. 검증은 다른 출처에서 한다.

수단마다 비용이 다르므로 싼 것부터 쓴다 — `validate`·`--dry-run=server`(초) → 공식 문서 인자 목록(1~3분) → `plan`·`kubectl explain`(수십 초) → 실제 적용(분 단위).
</Quiz>

<Quiz title="과잉 리소스">
Q가 WAF 구성을 만들어 주면서 요청하지 않은 로그 그룹과 KMS 키까지 함께 생성했다. 어떻게 하나?

- [x] 과제지에 그 이름이 있는지 확인하고, 없으면 지운다 — 요구되지 않은 리소스 생성은 감점 사유다
- [ ] 보안상 더 나은 구성이므로 그대로 둔다
  > 채점 기준은 모범 구성이 아니라 과제지 요구다. 요구되지 않은 리소스는 감점 항목으로 명시된 세트가 있다.
- [ ] 이름만 과제지 형식에 맞게 바꿔 남긴다
  > 이름을 맞춰도 요구되지 않은 리소스라는 사실은 그대로다. 게다가 다른 항목의 이름 조회와 충돌할 수 있다.
- [ ] 로그 그룹만 남기고 KMS 키는 지운다

Q는 "모범 구성"을 만들려 하므로 요구되지 않은 리소스를 얹는다. 판단 기준은 언제나 **과제지의 이름 명시 여부**다 — 이름이 없으면 만들지 않는다.

이 유형이 위험한 이유는 오류로 보이지 않는다는 점이다. apply 는 성공하고 동작도 정상이라, 감점을 채점 결과에서야 알게 된다.
</Quiz>
