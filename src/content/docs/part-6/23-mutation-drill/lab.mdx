## 훈련 ① — 30분 치환 드릴

타이머 30분. 변형 과제지를 받는 순간 시작.

<Steps>

1. **변경 분류** — 변경 목록을 훑고 **접두어 변경 / 개별 이름 변경 / 스펙 변경**으로 나눈다 (2분)

2. **기계 치환** — 이름 변경 건별로

   ```bash
   grep -rl --exclude-dir=.terraform '옛이름' . | xargs sed -i 's/옛이름/새이름/g'
   ```

3. **스펙 변동 직접 수정** — `terraform.tfvars` 열어 CIDR·타입·개수 수정 (sed로 안 잡히는 것)

4. **숨는 곳 8종 순회 점검** — tfvars / YAML 리터럴(라벨 키 `wsc2026/node` 류) / JS 코드(쿠키명 `x-sp-ab`, KVS 키명) / Grafana dashboard JSON / mark.sh / eksctl cluster.yaml / userdata 템플릿 / Lambda env

5. **최종 검증** — 옛이름 전부에 대해

   ```bash
   grep -rn --exclude-dir=.terraform '옛이름' .   # 0건이어야 함
   ```

6. **`terraform fmt && terraform validate` 통과**

7. **(스택이 떠 있으면) apply 후 mark.sh 재실행**

</Steps>

### 판정 기준

| 항목 | 기준 |
|---|---|
| 시간 | **30분 내** 5번(누락 0건 확인)까지 도달 |
| 누락 | 옛이름 잔존 grep **0건** |
| 채점 | mark.sh **재통과** (스택 미기동 시 validate + mark 리터럴 대조로 대체) |

미달이면 변경 목록을 새로 받아 재도전. 통과 기록 2회가 목표.

## 훈련 ①-2 — 문항이 늘었을 때: 키트를 고른다

30% 변동은 **값만 바뀌는 것이 아니라 문항이 붙는 형태**로도 온다. 값 치환이 손에 익었으면 다음은 이쪽이다.

정답지 저장소의 `shared/addons/` 에 부착 키트 36개가 있다. 기존 세트의 Terraform 상태를 건드리지 않고 파일만 얹는 구조라, **기존 문항을 다시 배포하지 않고** 새 문항만 붙일 수 있다.

<Steps>

1. **명사 하나를 뽑는다** (3분). 새로 붙은 문장에서 서비스나 기능을 가리키는 명사를 하나만 고른다 — `TTL`, `액세스 로그`, `CMK`, `관리형 룰 그룹`, `VPC 엔드포인트`.

   여러 개가 보이면 **채점 문장이 확인 명령을 어디로 던질지**로 고른다. 확인 대상이 곧 붙일 자리다.

2. **키트를 정하고 부착 파일을 확인한다** (2분). 키트 README 는 전부 같은 순서다 — 언제 쓰나 → 고칠 값 → 그대로 둘 값 → 계정·리전 확인 → 실행 → 검증 → 문제 해결.

3. **치환 자리를 채운다** (10분). 꺾쇠 표기가 하나라도 남으면 `validate` 에서 걸린다. `<기존>` 은 표를 찾지 말고 자기 세트에서 직접 뽑는다.

   ```bash
   grep -rn 'resource "aws_s3_bucket"' set-XX/task-1/terraform/
   # -> resource "aws_s3_bucket" "web"  ->  web
   ```

4. **`plan` 으로 안전 확인** (5분). **끝 조건은 하나다 — 기존 리소스에 replace 나 delete 가 0건.**

   :::danger[replace 가 뜨면 apply 하지 않는다]
   추가 문항 하나를 붙이려다 이미 점수를 받은 리소스를 다시 만들게 된다. 이름이 충돌하면 **기존 것을 지우지 말고 키트 쪽 변수를 리네임**한다.

   사전 제공 리소스에는 삭제를 막는 정책이 걸려 있을 수 있고, 지우는 행위 자체가 대회 규칙 위반이 될 수 있다.
   :::

5. **apply 후 세트 `mark.sh` 로 확인** (10분).

</Steps>

### 판정 기준

| 항목 | 기준 |
|---|---|
| 시간 | 명사 뽑기부터 apply 까지 **30분 내** |
| 안전 | `plan` 에 기존 리소스 replace/delete **0건** |
| 채점 | 해당 항목 통과. 기존 항목의 점수가 그대로인지도 함께 확인 |

**기존 항목이 깨지지 않았는지 확인하는 것이 이 훈련의 핵심이다.** 새 문항을 맞히고 원래 맞던 것을 잃으면 손해다.

### 어떤 문장이 어떤 키트로 가는가

전체 색인은 정답지의 `KIT-INDEX.md` 에 있다. 자주 나오는 것만 익혀 둔다.

| 과제지에 새로 붙은 말 | 붙일 자리 |
|---|---|
| TTL · PITR · 스트림 · 온디맨드 백업 | `dynamodb.tf` |
| 버저닝 · 수명주기 · 퍼블릭 차단 강화 | `s3.tf` |
| 액세스 로그 S3 저장 · 리스너 규칙 · 삭제 보호 | `alb.tf` |
| 이미지 스캔 · 태그 불변성 · lifecycle policy | `ecr.tf` |
| 지리적 제한 · 캐시 정책 · 에러 페이지 | `cloudfront.tf` |
| 관리형 룰 그룹 · Rate limit · WAF 로깅 | `waf.tf` |
| CMK 로 암호화 · 키 회전 · alias | `kms.tf` |
| CloudWatch 경보 · SNS 알림 · 대시보드 | `cloudwatch.tf` |
| VPC 엔드포인트 · PrivateLink | `endpoints.tf` |
| Control Plane 로깅 · Secret 암호화 | `eksctl/cluster.yaml` |
| Grafana 패널 · Prometheus Alert Rule | `k8s/monitoring/` |

## 훈련 ② — 아키텍처 이해 검증 (종이 먼저)

<Steps>

1. **에디터를 열기 전에** 새 변형 과제지를 받고 종이에 답한다

   - 각 변경이 닿는 컴포넌트는? (예: 헤더 값 변경 → CloudFront 커스텀 헤더 + ALB 리스너 룰)
   - 각 변경이 닿는 파일 경로는? (terraform/*.tf, k8s/*.yaml, app/*, eksctl/*)

2. **대조** — 종이 목록 완성 후 grep으로 실제 영향 파일을 뽑아 맞춰본다

3. **누락 기록** — 종이에서 빠뜨린 파일마다 "왜 못 봤는가"를 한 줄로

4. **수정 진행** — 그 다음에 훈련 ①과 동일 절차

</Steps>

**판정**: 종이 목록과 실제 영향 파일의 일치율 80% 이상. 이해했으면 바뀐 요구사항이 닿는 파일이 즉시 보인다 — 안 보이면 해당 컴포넌트의 PART-2~4 모듈로 돌아간다.

## 훈련 ③ — mark 스크립트 표 만들기

[mark 스크립트 가이드](/reference/mark-script-guide/)의 읽기 절차를 그대로 사용해 mark 스크립트 **3개**(set-02/task-1 mark.sh, set-02/task-2 mark2-2.sh, set-07/task-2 mark2.sh)를 표로 정리한다.

<Steps>

1. **항목(N-N) 단위로 자른다**

2. **표 작성** — **항목 | 검사 명령 | 기대값(리터럴)**

   예시 (set-02 mark.sh 7-2):

   | 항목 | 검사 명령 | 기대값 |
   |---|---|---|
   | 7-2-A | `aws elbv2 describe-rules ... HttpHeaderConfig.Values[]` + `curl http://$ALB_DNS/book` | 커스텀 헤더 값 + `403` |
   | 6-1-A | `aws lambda get-function-configuration --function-name wskorea26-book-lambda` | 이름·런타임·`TABLE_NAME` env |

3. **기대값의 모든 리터럴을 구현 체크리스트로 옮긴다**

4. **환경 준비 라인 표시** — sleep/재시도 항목과 `rm -rf ~/.aws` 같은 줄 (set-07 mark2.sh 첫머리 실측 — 반드시 CloudShell에서)

</Steps>

**판정**: 3개 스크립트 전 항목이 표에 있고, 각 표의 리터럴만 보고 "무엇을 만들어야 하는지" 재구성이 가능하면 통과.
