## 왜 30% 변동인가

사전 공개된 과제는 대회 당일 **전체 채점 점수의 30% 범위 안에서** 수정·추가된다. 지도교사 협의회 회의록에 1·2·3과제 공통으로 못 박힌 수치다. 수정은 기존 문제를 전면 교체하는 방식이 아니라 추가 문제를 얹는 방향이다. 항목이 늘어난 만큼 **기존 항목의 배점이 조정될 수 있다**.

과제별 범위도 공지됐다.

| 과제 | 변동 범위 |
|---|---|
| 1과제 | 아키텍처 교체 없이 기존 구성 위 추가만. EKS를 ECS로 바꾸는 식의 서비스 교체는 불가 |
| 2과제 | 최대 2개 모듈 추가(추첨 세트 4개 + 2 = 최대 6개). **추가 시간 없음** |
| 3과제 | 배점 수정·추가 문제. 추가 바이너리 배포, 새 Lambda 함수 개발 후 운영이 예시로 언급됐다 |

주로 바뀌는 축은 **이름 접두어**(`wskorea26-` → 다른 접두어), CIDR, 인스턴스 타입, 개수, 경로·헤더 값이다. 아키텍처 구조가 유지된다는 것이 공식 확인된 셈이다.

따라서 승부는 "새로 설계하는 능력"이 아니라 **바뀐 값을 코드베이스 전체에서 누락 없이 빠르게 갈아끼우는 능력**이다.

## 판단 원칙 3가지

1. **mark 스크립트가 1순위.** 과제지와 채점지가 다르면 mark를 따른다. set-02에서 처리 Lambda 이름이 task엔 없고 mark에만 등장 — mark 이름으로 생성해야 득점.
2. **오타처럼 보여도 적힌 그대로 쓴다.** 변동 반영 시에도 새 과제지의 오타를 "교정"하지 말 것. 단 **정정 공지가 먼저다** — 오타의 대표 사례였던 set-02 역할명 `wsc2026-alaytics-ec2-role`(analytics 오타)은 이의 제기로 수정됐고 채점 대상도 아니다.
3. **둘 다 애매하면 합집합 구현.** 함수 6개·룰 6개 전부 생성하고 mark가 그중 일부만 채점하게 둔다. 빼는 쪽이 잃는다.

상세는 [mark 스크립트 가이드](/reference/mark-script-guide/).

## 이름이 숨는 곳 (치환 누락 다발 지점)

`grep -rl`이 못 잡는 곳은 없지만, **어디에 있는지 알아야 grep 결과를 믿을 수 있다.** 실측 목록:

| 위치 | 예시 (실측) |
|---|---|
| `terraform.tfvars` | 접두어·CIDR·리전 변수값 |
| YAML 리터럴 | 라벨 키 `wsc2026/node`, `node-type` 셀렉터 값 |
| JS/앱 코드 | 쿠키명 `x-sp-ab`, KVS 키명 `weight` (set-07 CDN 함수) |
| Grafana dashboard JSON | 대시보드 uid/title `wskorea26-monitoring`, 패널 쿼리 내 라벨 |
| mark.sh 자체 | `--names wskorea26-book-alb` 등 리터럴 수십 개 — 변동 과제지의 새 mark와 대조 |
| eksctl `cluster.yaml` | 클러스터명 `wskorea26-cluster`, 노드그룹명 `wskorea26-app-ng`, 라벨 |
| userdata 템플릿 | 유닛명, 버킷/스트림 이름이 셸 스크립트 안에 문자열로 |
| Lambda env | `TABLE_NAME=wskorea26-data-table` 같은 환경변수 값 |

## 방법론 — 기계 치환 + 사람 검증

```bash
grep -rl '옛이름' . | xargs sed -i 's/옛이름/새이름/g'   # 기계가 치환
grep -rn '옛이름' .                                      # 사람이 0건 확인
```

- 접두어 단위(`wskorea26` 전체)와 개별 이름 단위(경로가 바뀐 것)를 구분해서 돌린다.
- 바이너리·`.terraform/`은 제외 (`--exclude-dir=.terraform`).
- `grep`·`sed`·`xargs` 의 옵션이 헷갈리면 [shell-basics](/start/shell-basics/)에 쓰임이 정리돼 있다.

:::caution[grep 0건이 곧 정답은 아니다]
tfvars는 sed에 걸리지만 **의미 확인** 필수 — CIDR·타입 변동은 이름 치환으로 안 잡힌다. 접두어가 다 바뀌었는데 CIDR이 옛 값 그대로면 grep은 0건을 내면서도 틀린 상태다.
:::

## 아키텍처 이해가 치환 속도를 결정한다

요구사항 변경 → 영향 파일이 즉시 보이는가? "헬스체크 경로가 `/health`→`/healthz`로 변경"이면 deployment probe + TG 헬스체크 + (있다면) mark의 curl 세 곳. 이 매핑이 머리에 없으면 grep 결과를 해석하는 데 시간을 다 쓴다. 훈련 ②가 이걸 검증한다.

<Quiz title="과제지 vs mark 충돌">
변동 과제지의 리소스 이름과 mark 스크립트 안의 리터럴 이름이 서로 다르다. 어느 이름으로 리소스를 생성하는가?

- [x] mark 스크립트의 이름
- [ ] 과제지의 이름 — 과제지가 공식 사양이므로 mark 쪽을 오기로 본다
  > 채점을 실행하는 것은 mark다. 과제지가 아무리 공식이어도 mark가 찾지 못하는 이름은 0점이다.
- [ ] 두 이름으로 리소스를 각각 하나씩 만들어 합집합을 노린다
  > 합집합 원칙은 어느 쪽도 확정할 수 없을 때의 보험이다. mark에 이름이 박혀 있으면 애매한 상황이 아니다 — 중복 리소스는 개수 검사와 비용만 늘린다.
- [ ] 감독관 질의 후 답이 올 때까지 해당 리소스는 보류한다

**mark 스크립트를 따른다.** 채점은 mark가 한다. set-02 실측: 처리 Lambda 이름이 과제지엔 아예 없고 mark에만 등장했다 — mark의 이름으로 생성해야 득점했다. 판단 원칙 1순위.
</Quiz>

<Quiz title="오타처럼 보이는 이름">
변동 과제지에 IAM 역할명이 `wsc2026-alaytics-ec2-role`처럼 오타로 보이는 철자로 적혀 있고, 정정 공지에는 아무 언급이 없다. 어떻게 생성하는가?

- [x] 적힌 그대로 생성한다 — 채점은 문자열 정확 일치이고, 공지가 없으면 그 철자가 사양이다
- [ ] `analytics`로 교정해서 생성한다
  > 교정하는 순간 mark의 `--names` 리터럴과 어긋나 오답이 된다. 읽는 사람이 판단할 자리가 아니다.
- [ ] 오타본으로 생성하되 교정본도 하나 더 만들어 둔다
  > 합집합은 두 문서의 요구가 갈릴 때 쓴다. 철자 하나는 갈림이 아니라 확정된 값이다.
- [ ] 정정 공지가 나올 때까지 해당 역할 생성을 보류한다
  > 공지를 확인하는 것과 작업을 멈추는 것은 다르다. 확인은 이미 끝났고(언급 없음), 남은 선택은 적힌 대로 만드는 것뿐이다.

**그대로 쓴다.** 다만 순서가 중요하다 — **정정 공지를 먼저 확인하고, 언급이 없을 때 적힌 대로 쓴다.** 실제 set-02의 `alaytics`는 이의 제기로 오타가 수정되고 채점 대상에서도 빠졌다. 공지를 안 보면 이미 고쳐진 오타를 사양으로 착각한다.
</Quiz>

<Quiz title="치환 후 검증">
기계 치환이 끝났으면 `grep -rn '옛이름' .` 의 결과가 [[0]]건이어야 치환이 완료된 것이다. 이때 바이너리와 함께 `--exclude-dir=` 로 제외해야 할 디렉터리는 [[.terraform]] 이다.

---

기계가 치환하고 **사람이 0건을 확인한다.**

```bash
grep -rl '옛이름' . | xargs sed -i 's/옛이름/새이름/g'   # 기계가 치환
grep -rn '옛이름' .                                      # 사람이 0건 확인
```

접두어 단위(`wskorea26` 전체)와 개별 이름 단위(경로가 바뀐 것)를 구분해서 각각 돌린다. `.terraform/` 캐시와 바이너리는 제외하지 않으면 잔존 건수가 노이즈로 가득 차 진짜 누락이 묻힌다.
</Quiz>

<Quiz title="sed가 못 잡는 변동 축">
접두어 sed 치환으로는 잡히지 않아 `terraform.tfvars`를 의미 단위로 직접 대조해야 하는 변동 축을 모두 고르라.

- [x] VPC·서브넷 CIDR 대역
- [x] 인스턴스 타입과 노드 개수
- [ ] eksctl `cluster.yaml`의 클러스터명·노드그룹명
  > 이건 문자열이라 sed에 그대로 걸린다. 다만 라벨 값까지 걸렸는지는 grep으로 확인해야 한다.
- [ ] Lambda 환경변수 `TABLE_NAME=wskorea26-data-table` 의 값
  > 값 안에 접두어가 들어 있으므로 sed가 잡는다. 숨는 위치일 뿐 치환이 안 되는 축은 아니다.

**CIDR·인스턴스 타입·개수·스펙** 등 이름이 아닌 값은 이름 치환으로 안 잡힌다. tfvars는 sed에 걸리긴 하지만 **의미 확인**이 따로 필요하다 — 접두어가 다 바뀌었는데 CIDR이 옛 과제지 값 그대로면 grep은 0건을 내면서도 틀린 상태다.
</Quiz>

<Quiz title="Grafana에 숨은 이름">
접두어를 전부 갈아끼웠는데 모니터링만 옛 이름이 남았다. 어디를 고쳐야 하는가? (모두 고르라)

- [x] dashboard JSON의 대시보드 uid / title (`wskorea26-monitoring`)
- [x] 패널 쿼리 문자열 안의 라벨 셀렉터
- [ ] 실행 중인 Grafana UI에서 대시보드 이름만 rename 후 저장
  > UI 저장은 코드베이스와 어긋나고 재배포하면 되돌아간다. 채점은 배포된 정의를 본다 — 소스인 JSON을 고쳐야 한다.
- [ ] Grafana Helm values의 admin 비밀번호

**dashboard JSON**의 uid/title과 **패널 쿼리 안의 라벨 셀렉터 문자열** 두 곳. JSON은 grep에 걸리지만, 쿼리 문자열 안쪽까지 봐야 한다는 걸 모르면 "대시보드는 떴는데 패널이 No data"로 끝난다. 같은 부류의 다발 지점: YAML 라벨 키(`wsc2026/node`), JS 쿠키명·KVS 키명, userdata 셸 스크립트 안의 유닛·버킷 이름, 그리고 mark.sh 자체의 `--names` 리터럴.
</Quiz>
