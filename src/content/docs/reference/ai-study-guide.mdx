> 문서 유형: how-to

AI에게 물어서 얻는 것은 둘 중 하나다 — **개념**이거나 **초안**이다. 둘은 다루는 법이 다르다.

개념을 물을 때는 AI가 과외 선생이다. 문서가 설명하지 못하고 지나간 자리를 채운다. 초안을 받을 때는 AI가 신입이다. 그럴듯한데 틀린 인자를 섞어 내므로, **받은 즉시 공식 문서로 대조하는 손**이 있어야 쓸 수 있다.

:::note[초안의 틀린 곳을 3분 안에 잡는 훈련]
AI는 Terraform·YAML·WAF 규칙 같은 코드를 곧잘 만들어 준다. 문제는 존재하지 않는 인자나 옛 버전의 문법이 섞여 나온다는 것이고, 그것을 **읽어서 알아채는 눈**은 따로 길러야 한다.

대조 절차는 [실전 문서 검색 가이드](/reference/search-guide/)에, 초안을 받아 고치는 훈련은 [AI 기반 과제 풀이 훈련](/part-6/26-ai-assisted-drill/)에 있다.
:::

## 언제 쓰고 언제 금지인가

| 상황 | AI 사용 |
|---|---|
| theory.md를 읽어도 개념·동작 원리가 이해 안 될 때 | **권장** |
| lab 완료 후 "왜 이렇게 동작했는지" 복기할 때 | **권장** |
| 오답 노트 정리하며 원인의 원리를 파고들 때 | **권장** |
| lab 진행 중 막혔을 때 | **조건부** — 먼저 확인 명령→Events→로그 순서로 15분 자력, 그 후에만 |
| 모듈 24 break-fix, 모듈 25 모의 대회 중 | **Amazon Q와 공식 문서로 한정** — 실전과 같은 도구 구성으로 맞춘다 |
| 변형 카드 생성(모의 대회 전날 저녁) | 권장 — AI에게 출제시키는 용도 |

:::danger[모듈 24·17 — 도구 구성을 실전과 같게]
break-fix(모듈 24)와 모의 대회(모듈 25)는 실전과 같은 도구만 열고 돈다 — Amazon Q와 공식 문서다. 평소 쓰던 학습용 AI를 함께 열면 조건이 달라져, 그 판정으로 실전 결과를 예측할 수 없다.

두 모듈이 재는 것은 진단과 복구의 사슬이므로, Q에게도 **원인 판단을 맡기지 않는다**. Q에게 받는 것은 조치에 쓸 조각(명령·매니페스트 일부)이다.
:::

## 질문 공식 — 맥락 + 현상 + 구체 질문

나쁜 질문: "IRSA가 뭐야?" → 문서 수준의 일반 답만 돌아온다.
좋은 질문은 3요소를 붙인다:

```text
[맥락] 전국기능경기대회 클라우드컴퓨팅 준비 중. EKS 1.35, eksctl로 만든 클러스터,
       IRSA로 ServiceAccount에 역할을 연결했다.
[현상/근거] 이 yaml과 이 에러가 있다: (yaml 붙여넣기) (에러 전문 붙여넣기)
[구체 질문] Pod Identity 대신 IRSA를 쓸 때 OIDC provider가 정확히 어느 시점에
       어떤 검증을 하는지 순서대로 설명해줘. 내 설정에서 검증이 실패할 수 있는
       지점을 짚어줘.
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

질문 템플릿의 세 부분이다. 맥락(버전·구성), 현상과 근거(YAML·에러 전문), 구체 질문 순이다. 앞의 둘이 없으면 답이 일반론으로 돌아오고, 마지막이 "왜 안 되나요" 수준이면 추측이 돌아온다 — 검증 순서를 물으면 확인할 지점이 답으로 나온다.

</details>

- **자료를 붙여라**: 관련 yaml/tf/에러 전문/`kubectl describe` 출력. 붙인 만큼 정확해진다.
- **범위를 좁혀라**: "설명해줘" 대신 "순서대로", "차이 3가지만", "내 설정 기준으로".
- **수준을 밝혀라**: "AWS 기초만 아는 상태다. 비유 먼저, 그다음 정확한 용어로."

## 목적별 질문 패턴 5종

1. **개념이 안 잡힐 때** — "X를 모르는 사람에게 비유로 설명하고, 그 비유가 깨지는
   지점(비유의 한계)도 알려줘. 그다음 정확한 동작 순서를 번호로."
2. **왜 이 구성인지 모를 때** — "이 가이드는 A 방식(예: TargetGroupBinding)을 쓴다.
   B 방식(예: Ingress)과 비교해서 이 대회 조건(이름 고정 채점)에서 A여야 하는 이유를
   반박 포함으로 설명해줘."
3. **두 개념이 헷갈릴 때** — "IRSA vs Pod Identity를 표로: 인증 주체, trust 조건,
   설치물, 채점에서 걸리는 지점. 그다음 내가 구분 못 하고 있는 지점을 질문으로 확인해줘."
4. **에러 복기(사후)** — "이미 해결했다. 원인은 X였다. 그런데 왜 증상이 Y로 나타났는지
   내부 동작으로 설명해줘. 같은 원인이 다르게 나타나는 증상 2가지도."
5. **이해 검증(역방향)** — "내가 설명해볼게: (자기 언어 설명). 틀린 부분을 지적하고,
   이해 확인 질문 3개를 내줘." ← **오해를 가장 많이 잡아낸다. 매 theory 퀴즈 후 이걸로 마무리한다.**

## 답을 받은 뒤 — 3단계 소화

<Steps>

1. **검증**: 리소스 이름·옵션·버전이 나오면 AWS 공식 문서/`--help`로 대조한다.
   AI는 그럴듯한 오답(환각)을 낸다 — 특히 helm 차트 옵션, eksctl 필드명.

2. **기록**: 답을 복사하지 말고 **자기 언어로 3줄 요약**해서 오답 노트나 theory 여백에.
   복사한 지식은 실전에서 안 나온다.

3. **재도전**: lab 중 막혀서 물었다면, 답을 본 뒤 **그 부분을 되돌리고 안 보고 다시**.

</Steps>

## 대회용 Amazon Q — 학습용 AI와 쓰는 법이 다르다

학습용 AI에게는 "원리를 설명해 줘"라고 묻는다. 실전의 Q에게는 **지금 쓸 코드**를 요구하고, 그 코드를 공식 문서로 검증한다. 두 용도를 같은 습관으로 다루면 검증 없이 붙여넣게 된다.

| | 학습용(Claude·Gemini) | 대회용(Amazon Q) |
|---|---|---|
| 묻는 것 | 개념·원리·오해 교정 | 리소스 블록·매니페스트·규칙의 초안 |
| 받은 뒤 | 자기 언어로 3줄 요약 | 인자 이름·기본값을 공식 문서로 대조 |
| 실패 형태 | 이해했다는 착각 | 그럴듯한 옛 인자명으로 apply 실패 |
| 훈련 시점 | 학습 전 기간 | 모듈 24·17과 [모듈 26](/part-6/26-ai-assisted-drill/) |

Q에게 코드를 받을 때 프롬프트에 세 가지를 반드시 넣는다 — **프로바이더·API 버전**(예: AWS provider 5.x, `autoscaling/v2`), **과제지가 준 이름과 값**, **판정 방법**(어떤 명령으로 확인할 것인지). 셋이 빠지면 Q는 일반 예제를 돌려주고, 그 예제의 이름은 채점 기준과 다르다.

## 의존 방지 룰

- 같은 질문을 두 번 하게 되면 — 기록이 안 된 것. 오답 노트부터 다시.
- lab에서 "다음 명령이 뭐야"는 금지 질문. 절차는 런북(lab)이 담당, AI는 원리만.
- 주 1회(중간 지점, 모의 대회 전날) AI 사용 로그를 훑어라 — 반복 주제가 곧 취약 모듈. 재실습 대상 선정에 쓴다.
- 대회 D-2부터 학습용 AI는 5번 패턴(이해 검증)만 사용 — 입력을 끊고 출력만 남긴다. Amazon Q는 대회 도구이므로 이 제한과 무관하게 계속 훈련한다.
