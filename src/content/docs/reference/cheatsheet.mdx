> 문서 유형: reference

**만들 줄 아는 것과 만들어졌는지 확인할 줄 아는 것은 다른 능력이다.** 이 문서는 뒤쪽이다 — 리소스가 실제로 요구대로 섰는지 묻는 명령과, 안 될 때 원인을 좁히는 명령을 모았다.

검증 스크립트가 치는 형태(`describe` · `jsonpath` · `jq`)를 그대로 따른다. 스크립트가 보는 자리를 손으로 먼저 보면 무엇이 어긋났는지가 같은 자리에서 드러난다.

이 문서의 명령은 전부 Bash 기준이다. 본 PC(Windows)에서 칠 때 달라지는 것만 먼저 정리한다.

<Tabs syncKey="shell">
  <TabItem label="Bash (CloudShell · Git Bash)">

  ```bash
  curl -s "http://$ALB_DNS/health"
  export TF_VAR_player_number=07
  grep -rl "old-name" . | xargs sed -i 's/old-name/new-name/g'
  aws ecr describe-images --repository-name repo --query 'imageDetails[].imageTags'
  ```

  </TabItem>
  <TabItem label="PowerShell 7 (본 PC)">

  ```powershell
  curl.exe -s "http://$env:ALB_DNS/health"   # curl 은 Invoke-WebRequest 별칭
  $env:TF_VAR_player_number = '07'           # $ 포함 문자열은 작은따옴표
  # grep/sed 는 PowerShell 에 없다 — Git Bash 나 CloudShell 에서 친다
  aws ecr describe-images --repository-name repo --query 'imageDetails[].imageTags'
  ```

  </TabItem>
</Tabs>

:::caution[PowerShell 5.1 금지]
5.1 은 CP949 인코딩이라 jq·terraform 출력이 깨진다. **PowerShell 7** 을 쓴다.
:::

## kubectl

### 조회·진단 (막히면 이 순서)

```bash
kubectl get pods -A -o wide                       # 전체 NS + 노드 배치 확인 (mark 5-4 대비)
kubectl describe pod <pod>                        # Events 최하단부터 읽기
kubectl logs <pod> --previous                     # CrashLoop 죽기 직전 로그
kubectl get events --sort-by='.lastTimestamp'     # 클러스터 최근 이벤트
kubectl get nodes --show-labels                   # label/taint 배치 검증
kubectl describe node <node>                      # taint, Allocated resources
kubectl top pods -A --sort-by=memory              # metrics-server 필요
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

상태를 읽는 조회 명령들이다. 배치가 맞는지는 `-o wide` 와 `--show-labels`, 실패 원인은 `describe pod` 의 Events, 크래시 원인은 `logs --previous` 로 본다. `describe node` 는 taint 와 할당된 자원을 함께 보여 줘 스케줄 실패를 가른다.

</details>

### 리소스 다루기

```bash
kubectl apply -f manifests/                       # 디렉토리 일괄
kubectl delete -f manifests/ --ignore-not-found
kubectl rollout status deploy/<name>              # 배포 완료 대기
kubectl rollout restart deploy/<name>             # ConfigMap 변경 반영
kubectl rollout undo deploy/<name>                # 롤백
kubectl scale deploy/<name> --replicas=2
kubectl set image deploy/<name> <ctr>=<image>:<tag>
kubectl exec -it <pod> -- sh                      # 컨테이너 내부 확인
kubectl port-forward svc/<svc> 8080:80            # Grafana/Prometheus 로컬 확인
kubectl run dbg --rm -it --image=alpine -- sh     # 임시 디버그 Pod (쓰고 지워짐)
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

리소스를 바꾸는 명령들이다. `rollout status` 는 배포 완료를 기다리고, `rollout restart` 는 ConfigMap 변경을 순차 교체로 반영하며, `rollout undo` 는 되돌린다. 마지막 두 줄은 임시 확인용이다 — port-forward 로 대시보드를 로컬에서 열고, 디버그 파드는 쓰고 나면 자동으로 사라진다.

</details>

### 출력 추출 (mark.sh 스타일)

```bash
kubectl get pods -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.nodeName}{"\n"}{end}'
kubectl get deploy <name> -o jsonpath='{.spec.template.spec.containers[0].image}'
kubectl get sa <sa> -o jsonpath='{.metadata.annotations}'          # IRSA annotation 확인
kubectl get nodes -o custom-columns=NAME:.metadata.name,TAINTS:.spec.taints
kubectl config current-context                    # 엉뚱한 클러스터 방지
kubectl auth can-i list pods                      # 신원/RBAC 빠른 점검
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

출력에서 필요한 값만 뽑는 형태들이다. `jsonpath` 로 파드와 노드의 짝, 이미지 태그, IRSA 애노테이션을 각각 꺼낸다. 마지막 두 줄은 사고 예방용이다 — 지금 어느 클러스터에 붙어 있는지, 지금 신원으로 그 동작이 되는지를 미리 확인한다.

</details>

### 안 뜰 때 (Pending · CrashLoop · ImagePull)

```bash
kubectl get events -n <ns> --sort-by=.lastTimestamp | tail -20   # 원인은 대개 여기 이미 적혀 있다
kubectl describe pod <pod> -n <ns> | sed -n '/Events:/,$p'       # Events 절만 잘라 본다
kubectl logs <pod> -n <ns> --previous                            # 재시작했으면 죽기 직전 로그
kubectl logs <pod> -n <ns> -c <container>                        # 컨테이너가 여럿일 때
kubectl get pod <pod> -n <ns> -o jsonpath='{.status.containerStatuses[*].state}'
kubectl debug -it <pod> -n <ns> --image=busybox --target=<container>   # 셸 없는 이미지 안을 본다
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

파드가 안 뜰 때 보는 순서다. `events` 가 가장 싸고 자주 맞는다 — 스케줄 실패·이미지 pull 실패는 여기에 문장으로 남는다. `--previous` 는 이미 재시작된 컨테이너의 **죽기 직전** 로그라, 지금 로그가 비어 있을 때 유일한 단서다.

마지막 `debug` 는 distroless 처럼 셸이 없는 이미지를 다룰 때 쓴다. `exec` 는 셸이 없어 실패하지만, 임시 컨테이너를 같은 네임스페이스에 붙이면 그 안을 들여다볼 수 있다.

</details>

:::caution[증상마다 볼 곳이 다르다]
| 상태 | 뜻 | 먼저 볼 곳 |
|---|---|---|
| `Pending` | 배치할 노드가 없다 | `describe pod` 의 Events — 자원 부족인지 taint 인지 |
| `ImagePullBackOff` | 이미지를 못 받는다 | 태그 오타 · ECR 권한 · 프라이빗 경로 |
| `CrashLoopBackOff` | 떴다가 죽는다 | `logs --previous` |
| `Running` 인데 트래픽이 안 옴 | 준비되지 않았다 | readiness probe · TG 상태 |
:::

### 권한과 통신 (RBAC · NetworkPolicy)

```bash
kubectl auth can-i list pods -n <ns>                              # 지금 신원으로 되나
kubectl auth can-i delete pods -n <ns> --as=<user>                # 남의 신원으로 확인
kubectl auth can-i --list -n <ns>                                 # 이 네임스페이스에서 가능한 것 전부
kubectl get rolebinding,clusterrolebinding -A -o wide | grep <name>

aws eks list-access-entries --cluster-name <c>                    # 클러스터가 아는 IAM 주체
aws eks list-associated-access-policies --cluster-name <c> --principal-arn <arn>
kubectl get configmap aws-auth -n kube-system -o yaml > aws-auth.backup.yaml   # 고치기 전 백업

kubectl get networkpolicy -A
kubectl get pods -n calico-system                                 # 정책을 강제할 플러그인이 있나
kubectl exec -it <pod> -n <ns> -- curl -m 5 http://<svc>/healthcheck   # 막혔으면 응답이 아니라 침묵이다
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

권한이 두 겹이라 확인도 두 겹이다. `auth can-i` 는 쿠버네티스 RBAC 만 보고, `list-access-entries` 는 그 앞단인 "클러스터가 이 IAM 역할을 아는가"를 본다. 오류 문구가 `Unauthorized` 면 뒤쪽, `Forbidden` 이면 앞쪽이 통과한 것이다.

마지막 세 줄은 네트워크 계층이다. NetworkPolicy 는 목록에 보여도 강제할 플러그인이 없으면 **조용히 무시된다** — 그래서 실제 통신으로 확인하고, 차단된 연결은 오류가 아니라 무응답이므로 `-m` 으로 시간 제한을 건다.

</details>

## eksctl

```bash
eksctl create cluster -f cluster.rendered.yaml    # 생성 ~20분, 먼저 던지고 다른 작업
eksctl get cluster --region ap-northeast-2
eksctl get nodegroup --cluster <name>
eksctl scale nodegroup --cluster=<name> --name=<ng> --nodes=2
eksctl get addon --cluster <name>
eksctl get iamserviceaccount --cluster <name>     # IRSA 확인
eksctl utils describe-stacks --cluster <name>     # 생성 실패 시 CFN 스택 진단
eksctl delete cluster -f cluster.rendered.yaml    # destroy는 만든 파일로
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

eksctl 명령들이다. 생성은 20분이 걸리므로 먼저 던져 두고 다른 작업을 한다. 조회 계열로 노드그룹·애드온·IRSA 를 확인하고, 생성이 실패하면 `utils describe-stacks` 로 CloudFormation 쪽 오류를 본다. 삭제는 만들 때 쓴 파일을 그대로 넘긴다.

</details>

kubeconfig 등록(채점 신원과 동일 신원으로):

```bash
aws eks update-kubeconfig --name <cluster> --region ap-northeast-2
```

## helm

```bash
helm repo add <name> <url> && helm repo update
helm search repo <keyword>
helm show values <repo>/<chart> > values.yaml     # 기본값 뽑아서 수정
helm upgrade --install <release> <repo>/<chart> -n <ns> --create-namespace -f values.yaml
helm list -A                                      # 설치된 릴리즈 전체
helm status <release> -n <ns>
helm template <release> <repo>/<chart> -f values.yaml > rendered.yaml   # 렌더만 (검토용)
helm uninstall <release> -n <ns>
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

helm 명령들이다. `show values` 로 기본값을 뽑아 고친 뒤 `-f` 로 넘기는 흐름이 기본이고, `upgrade --install` 은 처음이든 두 번째든 같은 명령으로 끝난다. `template` 은 클러스터에 적용하지 않고 렌더 결과만 파일로 내므로 무엇이 바뀌는지 먼저 볼 때 쓴다.

</details>

## aws cli

### 신원·클러스터

```bash
aws sts get-caller-identity                       # 매 세션 첫 명령 습관
aws eks describe-cluster --name <c> --query 'cluster.{status:status,endpoint:endpoint,private:resourcesVpcConfig.endpointPrivateAccess}'
```

### ECR

```bash
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
aws ecr get-login-password --region ap-northeast-2 \
  | docker login --username AWS --password-stdin "${ACCOUNT_ID}.dkr.ecr.ap-northeast-2.amazonaws.com"
aws ecr describe-images --repository-name <repo>              # 태그·푸시 확인
aws ecr describe-image-scan-findings --repository-name <repo> --image-id imageTag=<tag> \
  --query 'imageScanFindings.findingSeverityCounts'           # Critical/High 확인
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

ECR 로그인과 이미지 확인이다. 계정 ID 를 조회해 레지스트리 주소를 만들고, 토큰을 표준 입력으로 넘겨 로그인한다. 뒤의 두 명령은 태그가 제대로 올라갔는지와 취약점 스캔에 Critical·High 가 없는지를 본다.

</details>

### ALB·TG (mark가 가장 자주 치는 곳)

```bash
aws elbv2 describe-load-balancers --query 'LoadBalancers[].[LoadBalancerName,DNSName,Scheme]' --output table
aws elbv2 describe-listeners --load-balancer-arn <lb-arn> \
  --query 'Listeners[].DefaultActions'                        # 기본 403 확인
aws elbv2 describe-rules --listener-arn <listener-arn> | jq '.Rules[].Conditions'
aws elbv2 describe-target-health --target-group-arn <tg-arn> \
  --query 'TargetHealthDescriptions[].TargetHealth.State'     # healthy 대기 2~3분
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

ALB 를 계층 순서대로 조회한다. 로드밸런서 이름·주소·스킴 → 리스너 기본 액션 → 규칙 조건 → 타깃 상태다. 타깃이 healthy 가 되기까지 2~3분 걸리므로 마지막 조회는 시간을 두고 다시 친다.

</details>

</details>

### S3 (퍼블릭 차단 · 암호화 · 정책)

```bash
aws s3api get-public-access-block --bucket <b>                # 4종이 전부 true 여야 한다
aws s3api get-bucket-encryption --bucket <b>                  # SSE-KMS 인지 SSE-S3 인지
aws s3api get-bucket-policy --bucket <b> --query Policy --output text | jq .
aws s3api get-bucket-versioning --bucket <b>
aws s3api get-bucket-notification-configuration --bucket <b>  # 어떤 접두사가 무엇을 부르나
aws s3 ls s3://<b>/<prefix>/ --recursive --human-readable
```

:::caution[`get-public-access-block` 은 없으면 오류를 낸다]
설정한 적이 없으면 `NoSuchPublicAccessBlockConfiguration` 이 난다. **값이 false 인 것과 설정 자체가 없는 것은 다르다** — 오류가 곧 "차단 안 됨"이라는 답이다.
:::

### KMS

```bash
aws kms describe-key --key-id alias/<alias> --query 'KeyMetadata.{Id:KeyId,Manager:KeyManager,State:KeyState,MultiRegion:MultiRegion}'
aws kms get-key-policy --key-id alias/<alias> --policy-name default --output text | jq .
aws kms get-key-rotation-status --key-id alias/<alias>
```

키 정책을 읽을 때는 `Principal` 이 root 를 담는지부터 본다. root 가 빠진 정책은 그 키를 만든 신원만 쓸 수 있다.

### WAF

```bash
aws wafv2 list-web-acls --scope CLOUDFRONT --region us-east-1   # CloudFront 는 항상 us-east-1
aws wafv2 list-web-acls --scope REGIONAL --region ap-northeast-2 # ALB·API GW 는 그 리전
aws wafv2 get-web-acl --name <n> --id <id> --scope REGIONAL \
  --query 'WebACL.Rules[].{Name:Name,Priority:Priority,Action:Action}'
aws wafv2 get-sampled-requests --web-acl-arn <arn> --rule-metric-name <metric> \
  --scope REGIONAL --max-items 20 \
  --time-window StartTime=$(date -u -d '30 min ago' +%s),EndTime=$(date -u +%s)
```

마지막 명령이 **무엇이 실제로 걸렸는지**를 보여 준다. 규칙을 붙였는데 안 막힌다면 여기가 비어 있다.

### Lambda

```bash
aws lambda get-function-configuration --function-name <f> \
  --query '{Runtime:Runtime,Timeout:Timeout,Memory:MemorySize,Role:Role,Env:Environment.Variables}'
aws lambda list-event-source-mappings --function-name <f> \
  --query 'EventSourceMappings[].{Src:EventSourceArn,State:State,Pos:StartingPosition,Batch:BatchSize}'
aws lambda get-policy --function-name <f> | jq -r .Policy | jq .   # 누가 이 함수를 부를 수 있나
aws lambda invoke --function-name <f> --payload file://event.json \
  --cli-binary-format raw-in-base64-out out.json && cat out.json
aws logs tail /aws/lambda/<f> --since 10m --follow
```

:::danger[`--cli-binary-format` 을 빼면 payload 가 깨진다]
AWS CLI v2 는 `--payload` 를 base64 로 해석한다. 그대로 JSON 파일을 주면 `Could not parse request body into json` 이 난다. **v2 에서는 이 플래그가 사실상 필수다.**

그리고 S3 가 Lambda 를 부르려면 실행 역할이 아니라 **함수 쪽 리소스 정책**이 있어야 한다 — `get-policy` 가 비어 있으면 이벤트 알림 설정 자체가 검증에서 막힌다.
:::

### DynamoDB

```bash
aws dynamodb describe-table --table-name <t> \
  --query 'Table.{Keys:KeySchema,Mode:BillingModeSummary.BillingMode,GSI:GlobalSecondaryIndexes[].{Name:IndexName,Keys:KeySchema,Proj:Projection.ProjectionType}}'
aws dynamodb query --table-name <t> --index-name <gsi> \
  --key-condition-expression "#k = :v" \
  --expression-attribute-names '{"#k":"concert_name"}' \
  --expression-attribute-values '{":v":{"S":"foo"}}' \
  --no-scan-index-forward --max-items 5                    # 최신순 5건
aws dynamodb scan --table-name <t> --max-items 1           # 저장된 타입·시간 형식 실측
aws dynamodb describe-time-to-live --table-name <t>
aws cloudwatch get-metric-statistics --namespace AWS/DynamoDB \
  --metric-name ThrottledRequests --dimensions Name=TableName,Value=<t> \
  --start-time $(date -u -d '30 minutes ago' +%Y-%m-%dT%H:%M:%S) \
  --end-time $(date -u +%Y-%m-%dT%H:%M:%S) --period 300 --statistics Sum
```

`scan --max-items 1` 한 줄이 많은 것을 알려 준다 — 숫자가 `N` 인지 `S` 인지, 시간이 epoch 인지 ISO 인지가 여기서 갈린다.

## terraform

```bash
terraform init

```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

Terraform 흐름이다. `plan -out` 으로 계획을 파일에 담아 그대로 apply 하면 계획과 실행 사이에 상태가 바뀌어도 의도한 것만 적용된다. `output -json` 은 다음 단계 치환의 입력이고, `state list`·`state show` 는 실제로 무엇이 만들어졌는지 확인한다. destroy 는 삭제방지를 먼저 해제해야 통과한다.

## 제공물 읽기 (수정할 수 없는 바이너리·덤프)

```bash
file app                                          # 아키텍처 · 정적 링크 여부
go version -m app | head -20                      # Go 바이너리면 모듈·빌드 정보가 그대로 나온다
strings -n 6 app | grep -E '^/(v1|health|api)'    # 라우트 후보
strings -n 4 app | grep -E '^[A-Z][A-Z0-9_]{3,}$' | sort -u | head -30   # 환경변수 후보
strings -n 6 app | grep -iE 'select |insert |index'                       # 질의·인덱스 흔적
head -40 dump.sql && grep -c '^INSERT' dump.sql   # 스키마와 행 수
```

<details class="diagram-note">
<summary>이 블록이 하는 일</summary>

고칠 수 없는 제공물에서 사양을 되짚는 순서다. `file` 이 먼저인 이유는 아키텍처가 안 맞으면 그 뒤가 전부 의미 없기 때문이다 — x86-64 바이너리는 ARM 노드에서 `exec format error` 로 죽는다.

`strings` 로 뽑은 대문자 토큰이 환경변수 후보다. **문제 설명에 없는 이름이 여기서 나오면 그것이 곧 요구사항이다** — 인덱스 이름을 받는 변수가 대표적이다.

</details>

## 부하와 데이터베이스

```bash
k6 run --vus 50 --duration 60s script.js          # 부하
k6 run --summary-trend-stats='avg,p(95),p(99)' script.js

mysql -h <host> -u <user> -p<pw> <db> -e "SHOW TABLES; DESCRIBE <t>;"
mysql -h <host> ... -e "EXPLAIN SELECT * FROM t WHERE user_id=1\G"        # type·key·rows 를 본다
mysql -h <host> ... -e "SHOW INDEX FROM <t>;"
mysql -h <host> ... -e "SHOW VARIABLES LIKE 'max_connections'; SHOW STATUS LIKE 'Threads_connected';"
mysql -h <host> ... < dump.sql                    # 적재는 인덱스를 만들기 전에
```

`EXPLAIN` 의 `type: ALL` + `key: NULL` 이면 인덱스를 안 쓰고 전체를 훑는 중이다. 조건 열에 인덱스를 만들면 `type` 이 `ref` 로 바뀐다.

## curl · jq

```bash
curl -sI https://<host>/                          # 상태코드와 헤더만
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' https://<host>/v1/user?id=1
curl -s -m 5 http://<svc>/health                  # 차단된 연결은 오류가 아니라 침묵이다
curl -s -X POST https://<host>/v1/user -H 'Content-Type: application/json' -d '{"email":"a@b.c"}' -i
for i in $(seq 1 30); do curl -s -o /dev/null -w '%{http_code} ' https://<host>/; done; echo   # rate 규칙 확인

jq -r '.Items[] | [.id.S, .created_at.S] | @tsv' out.json
jq '.. | objects | select(has("Effect"))' policy.json         # 중첩 정책에서 문장만
jq -s 'add | length' *.json
```

`-w '%{http_code} %{time_total}s'` 조합이 응답 시간 요구를 확인하는 가장 짧은 방법이다. 눈으로 재지 않는다.
