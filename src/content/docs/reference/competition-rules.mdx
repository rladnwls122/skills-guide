## 과제 수정 범위 :badge[협의회]{variant=note}

제1·2·3과제 모두 **전체 채점 점수의 30% 범위 안에서** 수정된다.

수정은 기존 문제를 전면 교체하는 방식이 아니라 **추가 문제를 얹는 방향**이다. 과다 비용·중복 문제처럼 기존 문제를 꼭 고쳐야 하는 구체적 사유가 있을 때만 기존 문제를 바꾼다. 추가 문제가 나오면 채점 항목이 늘어나므로 **기존 항목의 배점이 조정될 수 있다.**

| 과제 | 범위 | 예시로 언급된 것 |
|---|---|---|
| 제1과제 | 기존 문제를 최대한 바꾸지 않고 추가 출제. EKS를 ECS로 바꾸는 **서비스 교체는 특별한 사유가 없는 한 없다** | 모니터링 도구 설치 |
| 제2과제 | 하위 문제 **최대 2개 추가**. 기존 4개 + 2 = 최대 6개이고 **추가 시간은 주지 않는다** | — |
| 제3과제 | 전면 변경 없이 추가 문항 | 추가 바이너리 배포, 새 Lambda 함수 개발 후 시스템 운영 |

대응 절차는 [변동 드릴](/part-6/23-mutation-drill/), 후보 밖 개념은 [변동 대비](/reference/variation-drill/)에 있다.

## 과제 분량 :badge[협의회]{variant=note}

문제지 외에 선수가 확인해야 하는 자료가 늘 수 있다 — 추가 Markdown 파일, 바이너리의 `help` 출력 등. 이를 전부 제한하기는 어려우므로 **선정된 문제지의 분량은 유지**한다. 추가 파일과 추가 문제의 설명은 간결하게 작성하되, 전체 분량을 특정 기준으로 제한하거나 확정하지는 않는다.

즉 요구사항은 과제지 한 장으로 끝나지 않는다. 첨부 Markdown과 바이너리 `--help`까지 읽어야 요구사항이 모인다.

## EKS 접근과 채점 :badge[협의회]{variant=note}

- 쿠버네티스 관련 채점은 **선수의 AWS CloudShell에서** 진행한다.
- CloudShell에서 EKS에 접근하는 방식은 제한하지 않는다. Access Entry·aws-auth ConfigMap 등 무엇을 써도 되고, **채점 시점에 kubectl로 클러스터에 접근되는 상태**이기만 하면 된다.
- 채점 중 클러스터에 접근할 수 없는 경우에 한해 다음 명령을 **1회** 실행할 수 있다.

  ```bash
  aws eks update-kubeconfig --name <클러스터명> --region <리전>
  ```

- 이 명령 외에 AWS CLI용 자격 증명을 입력하거나 다른 명령을 실행하는 것은 허용되지 않는다.

### Bastion EC2

| 항목 | 규칙 |
|---|---|
| 사용 근거 | 과제지에 명시가 없어도 필요하면 만들어 kubectl에 쓸 수 있다 |
| 불이익 | 생성으로 생기는 채점·풀이 시간 등의 불이익은 선수가 감수한다 |
| 생성·수정 시점 | **경기 중에만**. 채점 시 새로 만들거나 중지된 인스턴스를 시작하는 제어는 허용되지 않는다 |
| 용도 | kubectl을 포함한 채점 명령 실행 전용. EKS와 무관한 채점 항목의 명령 실행 서버로 쓰지 못한다 |
| 비용 | 3과제에서는 EC2 개수에 포함돼 비용 점수를 깎는다 |

원활한 운영을 위해 과제지·채점지에 명시된 환경 사용이 권장된다. 세트별 접근 경로 설계는 [프라이빗 EKS 이론](/part-3/13-private-eks-iam/theory/)에 있다.

## 3과제 채점 방식 :badge[협의회]{variant=note}

- EC2 인스턴스 수는 **주기적으로 확인**해 산정한다. 전체 경기 시간 기준으로 적게 쓸수록 높은 점수다.
- 제시된 구성 외에 EC2를 추가하면 패널티 점수가 있다(문제지에 이미 명시).
- Product App이 PUT 요청으로 S3에 이미지를 올릴 때 필요한 Content-Type·Body 등 **기본 형식은 문제지에 제시**된다. **저장 경로**는 당일 애플리케이션 동작과 요청 형식을 선수가 분석해 알아내는 과제의 일부다.
- 취약점은 시스템의 모든 구성 요소에서 발생할 수 있다. 채점 플랫폼이 주는 로그와 정보로 식별해 대응한다.

3과제는 1·2과제처럼 요구사항대로 만들고 구현 여부를 확인하는 형태가 아니다. 당일 제공되는 애플리케이션을 분석해 정상 구동하고, 로그·메트릭·동작 방식을 분석해 효율적이고 안정적으로 운영하는 것이 핵심이다.

### 답변이 거부된 질의

아래는 "문제의 정답을 요구하는 내용"으로 분류돼 답변되지 않았다. 당일 분석으로 판단할 항목이라는 뜻이다.

- `/images` 경로에도 취약점 정보가 전송되는가
- `/healthcheck`가 사용자에게 제공되는 엔드포인트인가
- 특정 요청에 403을 반환해야 하는가

## 3과제 학습 축 :badge[심사위원]{variant=tip}

과제 완수에 신경 쓸 것은 셋이다.

| 축 | 완료·판정 기준 |
|---|---|
| 프로비저닝 | 명시된 인프라를 세운 뒤 테스트 API 호출에 성공 응답이 오는 것 |
| 요청 처리 | 응답 코드가 예상값(200 등)이고 제한 시간 안에 도착하는 것 |
| 비용 | 인스턴스 개수. Bastion을 포함한 **모든 EC2**가 들어가므로 최소 대수로 운영한다 |

상태 판단에는 USE·RED 패턴을 쓴다. 두 패턴으로 현재 인프라와 시스템 상태를 읽고 Scale-in·Scale-out을 결정한다.

| 패턴 | 축 | 보는 값 |
|---|---|---|
| USE | 자원 | Utilization(사용률) · Saturation(대기·큐 포화) · Errors(자원 단의 오류) |
| RED | 요청 | Rate(초당 요청 수) · Errors(오류율) · Duration(지연 분포) |

훈련 절차는 [21. 3과제 배포](/part-5/21-task3-deploy/)와 [22. 부하 운영](/part-5/22-task3-tuning/)에 있다.

## 학습 방법 :badge[심사위원]{variant=tip}

세션에서 나온 질의와 답변 요지다.

| 질의 | 답변 요지 | 이 가이드의 연결 |
|---|---|---|
| 외우는 게 힘들다 | 전 기능 암기가 아니라 **비슷한 서비스 사이의 차이**로 익힌다. IAM 역할은 EC2가 assume할 수 있고 키 방식보다 keyless라 보안이 낫다, EFS는 EBS와 달리 NFS로 마운트돼 네트워크를 타므로 보안 그룹이 붙는다 — 이런 대비가 좋은 예다. "생성 버튼을 누르고 IAM 란에 역할을 넣고 EFS를 하나 만들면 10점"식의 절차 암기가 나쁜 예다 | [선수 지식](/start/) |
| 직종이 얼마 안 돼 과제가 별로 없다 | 서비스 이해가 먼저다. 지방·전국·국제대회 5년치 과제가 쌓여 있고 [aws-samples](https://github.com/aws-samples)에 샘플이 수천 개 있다. 학습한 주제의 샘플 아키텍처를 직접 구축해 본다 | [링크 모음](/reference/links/) |
| 코드 개발이 힘들다 | Claude Code·codex로 앱 하나를 직접 개발해 본다. 과제에 REST API 구현이 있으므로 Lambda에 배포할 수준의 Python은 익힌다 | [모듈 08](/part-1/08-container-lambda-dynamodb/) |
| 트러블 슈팅이 힘들다 | 먼저 로그를 본다. 문제 시스템을 계층별로 나눠 차례로 이상 유무를 확인하는 전략을 익힌다 | [트러블슈팅](/reference/troubleshooting/) |
| 기능이 너무 많다 | 자주 쓰는 서비스부터 익혀도 충분하다. AWS 인기도 상위 서비스가 과제 빈출과 겹친다 | [치트시트](/reference/cheatsheet/) |
| 과제 풀다가 리소스가 한번에 삭제됐다 | IaC 작업 시 삭제에 유의하고, 폴더를 나눠 **apply 단위를 쪼개** 작업 실수에 대비한다 | [모듈 06](/part-1/06-terraform-vpc/) |

## 인터넷 열람

클라우드컴퓨팅 직종은 **예외적으로 대회 중 인터넷 열람이 허용된다.** 공식 문서(Terraform Registry·AWS 문서·kubernetes.io 등)를 열어 값을 찾는 것이 실전 동작의 일부다.

대회 환경이 제공하는 Amazon Q도 함께 쓸 수 있다(아래 Amazon Q 절). 다만 Q의 출력을 확인할 곳은 결국 공식 문서이므로, 훈련은 "모르는 값을 어디서 찾는가"를 같이 연습한다 — [실전 문서 검색 가이드](/reference/search-guide/)가 그 훈련 문서다.

## Amazon Q :badge[강의]{variant=tip}

**대회장에서 Amazon Q를 쓸 수 있다.** 2026-08 실습 강의에서 확인된 사항이고, 협의회(2026-07-31) 시점의 "제공 여부 협의 중, 확정돼도 웹 검색만"을 대체한다.

| 항목 | 내용 |
|---|---|
| 사용 가능 도구 | Amazon Q. 질의뿐 아니라 Terraform·YAML·WAF 규칙·CloudFront Function 같은 **코드 생성**에 쓸 수 있다 |
| 쓰는 자리 | 리소스 골격·매니페스트·변환 코드의 초안. 과제지가 지정한 이름과 수치는 프롬프트로 직접 넘긴다 |
| 훈련 방향 | Q에게 초안을 받고 **공식 문서로 검증해 고치는** 왕복을 속도로 만든다 — [AI 기반 과제 풀이 훈련](/part-6/26-ai-assisted-drill/) |

Q가 답을 대신 써 주는 것과 그 답이 맞는지 판정하는 것은 다른 능력이다. 채점은 리소스 이름·인자값의 정확 일치를 보므로, Q의 출력이 그럴듯해도 인자 하나가 옛 버전이면 그대로 감점이다. 검증 절차와 프롬프트 패턴은 [AI 학습 활용 가이드](/reference/ai-study-guide/)에 있다.

:::caution[공지 확인]
대회 직전에 Amazon Q 제공 형태(모델·플러그인 범위)가 다시 바뀔 수 있다. 최종 공지를 확인하고, Q가 없는 경우에도 손으로 쓸 수 있는 상태를 유지한다.
:::
