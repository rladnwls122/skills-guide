1과제 후보(set-02·03·07)는 **셋 다 EKS**다. 이 문서는 당일 30% 변동으로 컴퓨트가 ECS로 바뀌는 낮은 확률에 대비한 대응표이지, 새로 배울 과정이 아니다. EKS를 아는 상태에서 필요한 건 대응 관계와 함정 몇 개뿐이다 — 평소 학습 순서에서 먼저 붙잡지 않는다.

## EKS ↔ ECS 대응표

| EKS(k8s) | ECS | 비고 |
|---|---|---|
| 클러스터 | 클러스터 | ECS 클러스터는 논리적 묶음일 뿐이다 — Fargate라면 클러스터 자체에 컴퓨트가 딸려 있지 않다 |
| 노드그룹(EC2) | Fargate 또는 EC2 launch type | set-08·set-09 모두 `launch_type = "FARGATE"` — 노드 사이징·AMI·라벨·taint 개념 자체가 없어진다 |
| Deployment | 태스크 정의(Task Definition) + 서비스(Service) | 태스크 정의 = 컨테이너·리소스·역할 스펙, 서비스 = 개수 유지·로드밸런서 연결 |
| Pod | 태스크(Task) | 태스크 하나 = 파드 하나. 사이드카는 같은 태스크 정의 안 컨테이너로 추가 |
| VPC CNI(파드 = VPC IP) | `awsvpc` 네트워크 모드(태스크 = ENI) | 아래 참고 |
| Service + TargetGroupBinding | ALB Target Group(`ip` 타입) 직결 | 서비스 정의의 `load_balancer` 블록이 TG를 바로 문다 |
| ServiceAccount(IRSA) | 태스크 역할(Task Role) | "컨테이너 안 앱의 AWS 자격증명"이라는 역할은 동일 |
| (EKS엔 없음 — 노드 IAM Role이 유사 역할) | 실행 역할(Execution Role) | ECS 고유 개념. 아래 참고 |
| ConfigMap | 태스크 정의 `environment` | 별도 리소스가 아니라 태스크 정의에 인라인 |
| Fluent Bit DaemonSet | `awslogs` 로그 드라이버 | 태스크 정의 `logConfiguration`이 로그 그룹을 직접 지정 |

## 실행 역할(execution role) vs 태스크 역할(task role)

- **실행 역할** — ECS 에이전트가 쓴다: ECR 이미지 pull, CloudWatch Logs 전송. `AmazonECSTaskExecutionRolePolicy` 관리형 정책 하나로 충분하다(set-08 `iam.tf`).
- **태스크 역할** — 컨테이너 안 애플리케이션이 쓴다: 앱 코드가 실제로 호출하는 AWS API만 최소 권한으로(set-08은 `dynamodb:PutItem` + 테이블 CMK용 `kms:Decrypt`/`GenerateDataKey`/`DescribeKey`뿐).
- 왜 갈라야 하나: 하나로 합치면 앱이 이미지 pull·로그 전송 권한까지 갖게 되어 최소 권한 원칙에 어긋난다. **같은 역할로 돌려쓰면 채점에서 탈락한다** — set-08의 채점 스크립트(mark.sh) 5-3/5-4가 태스크 정의의 `executionRoleArn`과 `taskRoleArn`을 나란히 조회해 비교한다.
- 확인:
  ```bash
  aws ecs describe-task-definition --task-definition <family> \
    --query '{Execution:taskDefinition.executionRoleArn,Task:taskDefinition.taskRoleArn}'
  ```

## `awsvpc` 네트워크 모드

Fargate는 `awsvpc` 모드만 지원한다 — 태스크마다 전용 ENI를 받아 **태스크 IP로 직접 라우팅**된다(EC2 인스턴스 IP 뒤에 포트로 물리는 방식이 아니다). 그래서 ALB Target Group은 `target_type = "ip"`여야 한다(`instance` 타입은 태스크 IP를 등록할 수 없다) — EKS에서 파드가 VPC IP를 직접 받으므로 TargetGroupBinding이 `ip` 타입을 쓰는 것과 같은 이유다.

태스크 SG도 EC2 인스턴스 SG가 아니라 **태스크 자신의 SG**다. set-08은 컨테이너 포트 인바운드를 ALB SG 참조 하나로만 열어 그 외 경로를 차단한다(`ecs.tf`의 `aws_security_group.ecs_task`).

## private 서브넷 + `assign_public_ip = false`일 때 ECR pull 경로

private 서브넷의 태스크는 퍼블릭 IP가 없다 — **NAT Gateway 또는 VPC Endpoint 없이는 이미지 pull도 로그 전송도 안 되고 태스크가 기동조차 못 한다.** EKS 프라이빗 클러스터에서 이미 겪은 것과 같은 함정이다 — [vpc-basics](/start/vpc-basics/) 참고.

- **set-08**: private 서브넷 + NAT Gateway로 이 경로를 연다(태스크 SG egress `0.0.0.0/0`, 실제로는 NAT 경유). DynamoDB는 별도로 [게이트웨이 엔드포인트](/start/vpc-basics/)를 붙인다(`vpc.tf`).
- **set-09**: 반대로 public 서브넷 + `assign_public_ip = true`를 택해(`ecs.tf` 주석 "과제 7.4") NAT 없이 태스크가 직접 인터넷으로 나간다 — NAT 비용을 아끼는 대신 태스크가 퍼블릭 IP를 직접 갖는다.

확인:
```bash
aws ecs describe-tasks --cluster <c> --tasks <arn> \
  --query 'tasks[].attachments[].details[?name==`networkInterfaceId`].value'
aws ec2 describe-network-interfaces --network-interface-ids <eni> --query 'NetworkInterfaces[].Association.PublicIp'
```

## `runtime_platform`의 `cpu_architecture`

제공 book 바이너리는 **정적 링크 x86-64 ELF**다. 태스크 정의에 `runtime_platform.cpu_architecture = "X86_64"`를 명시하지 않거나 arm으로 잘못 지정하면 Fargate가 맞지 않는 아키텍처로 태스크를 기동해 즉시 실패하고, 물린 ALB Target Group·서비스까지 연쇄로 unhealthy가 된다. EKS에서 노드그룹 인스턴스 타입(Graviton vs x86)을 맞추던 것과 같은 문제가, ECS에서는 노드가 없으니 **태스크 정의 필드**로 옮겨왔을 뿐이다.

확인: `aws ecs describe-task-definition --task-definition <family> --query 'taskDefinition.runtimePlatform'`

## `container_definitions`를 `jsonencode()`로 쓰는 이유

ECS 태스크 정의의 `container_definitions`는 Terraform 리소스 인자가 아니라 **JSON 문자열 하나**를 받는 API 스펙이다. HCL 블록 문법이 없으므로 컨테이너 이름·이미지·포트·환경변수·로그 설정을 HCL 맵/리스트로 쓴 뒤 `jsonencode()`로 직렬화해 넘긴다.

```hcl
container_definitions = jsonencode([
  {
    name  = local.container_name
    image = "${aws_ecr_repository.book.repository_url}:${var.image_tag}"
    portMappings = [{ containerPort = var.container_port, protocol = "tcp" }]
    environment  = [{ name = "TABLE_NAME", value = var.table_name }]
    logConfiguration = {
      logDriver = "awslogs"
      options = {
        awslogs-group         = aws_cloudwatch_log_group.app.name
        awslogs-region        = var.region
        awslogs-stream-prefix = var.log_stream_prefix
      }
    }
  }
])
```

k8s 매니페스트(YAML)에 익숙하면 위화감이 드는 지점이다 — 이 필드 하나에 컨테이너 스펙 전체가 들어간다는 점만 기억하면 나머지는 set-08·set-09 `ecs.tf` 그대로 따라 쓸 수 있다.

## ALB 오리진 검증 헤더 패턴은 EKS·ECS 공통

CloudFront가 커스텀 헤더를 심고 ALB 리스너 규칙이 그 헤더를 조건으로 검사하며 기본 액션은 `fixed-response` 403으로 막는 패턴은 이미 [k8s 워크로드·ALB 이론](/part-2/05-k8s-workloads-alb/theory/)에서 배운 것과 **완전히 같다**. 컴퓨트가 파드든 ECS 태스크든 ALB 뒤에 무엇이 있는지는 이 패턴과 무관하다. set-08 `alb.tf`도 헤더 조건 리스너 규칙(우선순위 1) + 기본 액션 403 fixed-response로 동일하게 구성한다.
