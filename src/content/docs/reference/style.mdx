> 문서 유형: reference

이 레포의 모든 문서가 따르는 규칙. 새 문서를 쓰거나 고칠 때 이 문서를 기준으로 판단한다.

규칙이 무엇을 위한 것인지는 [H 절](#h-문서가-만들려는-것--이해와-역량)에 있다 — 문서는 개념을 이해시키고, 실습은 역량을 만든다. 세부 규칙끼리 판단이 갈리면 그쪽을 기준으로 정한다.

콘텐츠는 전부 `src/content/docs/` 아래의 `.mdx` 다. Starlight 가 frontmatter 의 `title` 을 제목으로 렌더하므로 본문에 H1 을 따로 쓰지 않는다.

## A. Diátaxis 문서 체계

[Diátaxis](https://diataxis.fr)는 문서를 4유형으로 나눈다.

| 유형 | 목적 | 축 |
|---|---|---|
| tutorial | 학습 — 따라 하며 배운다 | 학습 × 습득 |
| how-to | 과제 해결 — 특정 목표를 달성한다 | 작업 × 적용 |
| reference | 조회 — 사실을 찾아본다 | 작업 × 습득 |
| explanation | 이해 — 원리와 이유를 안다 | 학습 × 적용 |

:::caution[핵심 규칙 — 유형 혼합 금지]
한 문서는 한 유형만 담는다. 설명이 필요한 tutorial 은 explanation 문서로 링크한다. 절차가 필요한 explanation 은 tutorial·lab 으로 링크한다.
:::

### 이 레포 매핑

모듈 디렉터리는 `index` / `theory` / `lab` 세 파일로 이뤄진다.

| 파일 | 유형 | 담는 것 | 금지 |
|---|---|---|---|
| 모듈 `theory.mdx` | explanation (+접이식 실행 블록, 끝의 퀴즈) | 원리·왜·채점 관점 | 산문 본문의 절차(단계별 실행 지시) |
| 모듈 `lab.mdx` (PART-1~4) | tutorial (검증 절차는 how-to 성격) | 변동 이행·배포·복구·진단 | 개념 설명 — theory 링크로 대체 |
| `part-N/console-deploy.mdx` | how-to | 콘솔 경로·drift 판단 | 개념 설명 |
| PART-5~6 `lab.mdx` | how-to | 훈련 절차·판정 기준 | 개념 설명 |
| 모듈 `index.mdx` | 개요 | 목표/소요/비용/경로 | 내용 서술 |
| `reference/*.mdx` | reference | 조회용 표·명령·매핑 | 설명·훈련 지침 |
| `start/*.mdx` | explanation | 선수 지식 요약+퀴즈 | — |

#### theory 의 접이식 실행 블록 — 유형 혼합 금지의 유일한 예외

theory 는 개념 절 끝에 `<details class="build-step">` 를 하나 붙일 수 있다. 읽는 사람이 그 절의
리소스를 눈으로 보게 하는 장치이고, 절마다 열고 따라오면 기준본 인프라가 완성된다.

예외가 성립하는 조건은 둘이다.

- **기본 상태가 접힘이다.** 블록을 열지 않는 사람에게 그 문서는 그대로 explanation 이다.
  `open` 속성을 붙이지 않는다.
- **블록 안이 셋으로 제한된다.** 실행 명령, 기대 출력, 기대와 다를 때 볼 곳 한 줄. 진단
  절차와 원인 분석은 `lab.mdx` 소관이다.

과금이 붙는 리소스를 띄우는 블록은 첫 줄에 과금 사실과 예상 비용을 적는다. 그리고 그 문서
끝에 띄운 것을 지우는 정리 절을 둔다.

### theory 와 start 의 층위 경계

두 유형 모두 explanation 이라 주제가 겹칠 수 있다. "무엇이 중복인가"는 문장 하나 단위로 판정한다.

**실측 코드 없이도 참인 문장은 start, 실측 코드를 가리키는 문장은 theory.** 봉투 암호화의
일반 원리(누가 배워도 같은 문장)는 start 소관이고, "set-02 의 이 키가 이 버킷을 어떻게
암호화하는가"(그 세트 코드를 안 보면 확인할 수 없는 문장)는 theory 소관이다. theory 의
역할은 실제로 쓸 소스를 읽고·쓰고·구축하는 관점에서 동작 원리를 설명하고, 그 값이
바뀌면 어디를 고치는지("④ 변형 포인트")까지 잇는 것이다. 같은 주제를 양쪽이
다뤄도 층위가 다르면 중복이 아니다 — 언어·개념 일반론이 theory 에 남아 있으면 start 로
옮기고 링크로 대체한다.
## B. 문장 규칙 (Google·Microsoft·Apple 종합)

- **능동태·현재형.** 독자를 직접 지칭하는 명령형("~한다/~하라")을 쓴다. "우리는" 금지. [Google]
- **조건이 지시보다 먼저.** "채점 전에 X하려면 Y한다" — 지시 뒤에 조건을 붙이지 않는다. [Google]
- **큰 아이디어, 적은 단어.** 군더더기 삭제: 불필요한 "~할 수 있다", "~하는 것이 가능하다", "기본적으로/사실상". 단, 학습 목표 체크리스트의 "~을 설명할 수 있다"는 달성 기준이므로 유지. [Microsoft]
- **동사로 시작하는 지시 우선, 핵심 먼저(front-load).** [Microsoft]
- **제목: 마침표·콜론 금지.** 부제는 `—` 로 잇는다. 영문 제목·용어는 sentence case. [Microsoft/Google]
- **순차 절차 = 번호 목록, 그 외 = 불릿.** [Google]
- **코드·명령·리소스명 = 코드 폰트, UI 요소 = 굵게.** [Google]
- **의인화 금지.** "채점 스크립트가 원한다/똑똑하다" → "mark.sh는 X를 검사한다". [Apple]
- **사전 예고 금지**("나중에 다룰"). 링크 텍스트는 설명적으로. [Google]
- **한 문단 = 한 아이디어.** 5줄 넘으면 쪼갠다. [Google]
- **방향성 표현 금지.** "아래 표"·"위 명령어" 대신 대상을 직접 지칭한다. [Google]
- **추상어 대신 구체값.** "성능이 향상된다" 금지 — 실제 명령어·파일 경로·수치(예: p99 200ms → 40ms)로 쓴다.
- **코드 요소엔 종류를 밝힌다.** `example.yaml` 단독 대신 "`example.yaml` 파일"처럼 쓴다. [Google]
- **관용구·비유 금지.** ESL 독자 기준 — 계절 비유·속담 없이 짧고 모호하지 않게 쓴다. [Google]

### 용어 표준화 표 [Apple: 한 개념 한 표기]

| 표준 표기 | 규칙 | 금지/변형 예 |
|---|---|---|
| `mark.sh` | 파일당 첫 언급만 "채점 스크립트(mark.sh)" 병기, 이후 `mark.sh` | "채점 스크립트" 단독 반복 |

| 노드그룹 | 붙여쓰기 | "노드 그룹" |
| 채점지 | = `mark.md` | — |
| 과제지 | = `task.md` | — |
| 정답지 | = `skills-2026` 실측 코드 | — |
| 런북 | 자기 배포 절차 문서 | "runbook" |
| 배포 | 스택 전체를 세우는 행위 | — |
| 적용(apply) | `terraform apply`·`kubectl apply` 실행 | "어플라이" |
| 삭제방지 | 붙여쓰기 | "삭제 방지" |

| 치트시트 | 본문 표기 (문서는 `reference/cheatsheet.mdx`) | — |

## C. 파일 상단 유형 라벨

frontmatter(와 컴포넌트 import) 다음 1행에 인용구로 유형을 명시한다. 본문 첫 줄이다.

```mdx
---
title: 05. 이론 — k8s 워크로드와 ALB 연동
description: ...
---

import { Quiz, QuizResults } from 'starlight-quiz/components';

> 문서 유형: explanation
```

값은 `explanation` · `tutorial` · `how-to` · `reference` · `개요` 다섯 중 하나다.

## D. 도식 (mermaid)

도식은 ```` ```mermaid ```` 코드 펜스로 쓴다. 렌더·아이콘·전체화면 뷰어는 전부 사이트 쪽에서
처리하므로 문서에서는 아래 규칙만 지킨다.

### 줄바꿈은 `<br/>`

라벨 안의 `\n` 은 mermaid 11 에서 줄바꿈이 **아니라 글자로 렌더된다**. 반드시 `<br/>` 를 쓴다.

```
DEP["Deployment<br/>replicas 2 · probe 3종"]
```

### AWS 서비스 노드에는 아이콘을 붙인다

서비스·제품을 가리키는 노드는 아이콘 셰이프로 쓴다. 규격(`form`·`pos`·`h`·`w`)은 전 도식 공통이다.

```
S3@{ icon: "logos:aws-s3", form: "square", label: "S3 버킷<br/>정적 호스팅", pos: "b", h: 46, w: 46 }
```

개념·데이터·판단을 가리키는 노드(`{"…?"}` 마름모, `"실제 데이터"` 등)는 아이콘 없이 둔다.

:::caution[아이콘 셰이프는 엣지 문장 안에 못 쓴다]
`CF["CloudFront"] -->|"오리진"| ALB["ALB"]` 처럼 엣지 안에서 선언된 노드는 아이콘화할 수 없다.
노드를 각자 줄에 선언하고 엣지는 id 로만 잇는다.
:::

### subgraph 는 `<span>` 으로 붙인다

subgraph 라벨에는 `@{ icon: }` 문법이 없다. 클래스로 붙인다.

```
subgraph EKS["<span class='icon--logos icon--logos--aws-eks'></span> EKS 클러스터"]
```

라벨 없이 쓰던 `subgraph KMS` 는 대괄호 라벨을 만들어 붙인다.

### 아이콘 고르는 순서

1. `aws:*` — AWS 서비스·리소스. 공식 아키텍처 아이콘 패키지에서 뽑은 자체 팩
2. `logos:aws-*` — 자체 팩에 없는 AWS 로고
3. `k8s:*` — 쿠버네티스 리소스. Deployment·Pod·Service·ConfigMap 처럼 종류를 구분해야 할 때
4. `logos:*` — docker-icon·terraform-icon·helm·prometheus·grafana 등 제품 로고
5. `simple-icons:*` — `logos` 에 없는 브랜드
6. `mdi:*` — 위 어디에도 없는 **개념**일 때만

`logos:kubernetes` 는 로고 하나뿐이라 Deployment 도 Pod 도 Service 도 전부 같아 보인다.
쿠버네티스 리소스에는 `k8s:*` 를 쓴다.

`sequenceDiagram` 은 mermaid 가 아이콘을 지원하지 않는다 — 손대지 않는다.

:::danger[아이콘 이름 오타는 빌드가 안 잡는다]
목록에 없는 아이콘을 쓰면 그 노드만 조용히 깨지고 빌드는 통과한다. 도식을 고쳤으면 반드시 실행한다.

```bash
npm run check:icons
```

새 아이콘을 쓰려면 `src/mermaid-icons.mjs` 의 목록에 이름을 먼저 추가한다.
:::

## E. 금지 목록 (AI slop 차단)

아래 표현은 리뷰에서 반려한다.

| 금지 | 예 |
|---|---|
| 섹션 끝 요약 문장 | "정리하면…", "요약하자면…" |
| 닫는 문장 | "결론적으로", "In conclusion" |
| 마케팅 형용사 | powerful, seamless, robust, comprehensive, leverage, utilize, 강력한, 손쉽게, 완벽하게 |
| 군더더기 문장 | "~하는 것이 중요합니다", "It's important to note that…" |
| 에세이 골격 | "첫째… 둘째… 셋째…" 식 5문단 구조 |
| 수동태 절차문 | "노드가 스케일될 수 있다" → "`kubectl scale`로 스케일한다" |
| 긴 문장 | 문장당 25단어(한글 약 45자) 초과 |
| 검증 안 된 구체성 | 근거 없는 숫자·인용 |

## F. 초심자 가독성 규칙

2026-08 가독성 감사에서 반복된 실패 패턴을 규칙으로 만들었다. 근거는
`docs/superpowers/specs/2026-08-04-beginner-readability-overhaul.md`.

### 용어는 정의가 사용보다 먼저

- 새 기술 용어는 **첫 등장에서 한 줄로 정의**하거나, 정의하는 문서로 그 자리에서 링크한다.
  약어(ARN·CIDR·SSE 등)는 첫 등장에서 풀어 쓴다.
- `start/*` 문서는 읽기 순서상 **자기보다 뒤인 문서의 지식을 전제하지 않는다**. 전제가
  불가피하면 해당 문서 링크를 단다.
- 정책 JSON·매니페스트를 인용하면 낯선 필드는 전부 한 줄씩 푼다. 채점에 걸리는 필드만
  골라 해설하고 나머지를 건너뛰지 않는다.

### 문장 구조

- **괄호 안에 핵심 정의를 넣지 않는다.** "QoS(축출 등급) 확보" 금지 — 정의가 필요한
  개념은 본문 문장으로 꺼낸다. 괄호는 보조 정보(값 예시·영문 병기)만 담는다.
- **부정을 두 겹 이상 쌓지 않는다.** "없으면 못 하게 되는 것을 막으려고 거부한다" —
  긍정형으로 다시 쓴다.
- 한 문장에 **새 개념은 2개까지**. 단 끊어쓰기는 수단이지 목표가 아니다 — 읽기를 실제로
  막는 문장만 풀고, 기계적으로 토막 내지 않는다.
- 지시어("이 값"·"그 리소스")는 직전 명사가 둘 이상이면 대상을 이름으로 다시 쓴다.

### 표는 조회용, 산문은 설명용

- 표 셀에 조건 분기·인과·정의를 압축하지 않는다. 셀에 문장이 두 개 이상 필요하면
  그 내용은 표 밖 산문으로 옮기고 셀은 값만 남긴다.

### 원리와 채점은 함께

- "mark.sh 가 X 를 검사한다"는 문장은 **X 가 왜 그렇게 동작하는지** 설명 없이 단독으로
  쓰지 않는다. 채점 관점은 동작 원리의 대체물이 아니라 우선순위 표시다.

### 공식 문서로 가는 길을 남긴다

- theory 의 코드 해설이 새 Terraform 리소스 타입을 처음 쓰면 Terraform Registry 의 그
  리소스 문서를 링크한다(리소스 타입 단위 — 인자 앵커는 부패하므로 금지).
- lab 은 상단에 그 실습이 참조하는 공식 문서 목록을 두고
  [실전 문서 검색 가이드](/reference/search-guide/)로 링크한다.

## G. 퀴즈

문항은 **props 가 아니라 슬롯 안 작업 목록**으로 쓴다. `question`·`options`·`correct`
같은 속성은 없다 — 넘겨도 무시되고 빈 퀴즈가 렌더되며 **빌드는 통과한다**.

```mdx
<Quiz title="상태 저장의 의미">
보안 그룹으로 인바운드 443 만 열었다. 아웃바운드 규칙은 없다. 클라이언트가 접속하면?

- [x] 정상 동작한다 — 나가는 응답은 상태 추적으로 자동 허용된다
- [ ] 응답이 못 나가 타임아웃된다
  > 그것은 네트워크 ACL 의 동작이다. 보안 그룹은 상태를 기억한다.

**동작한다.** 들어온 연결의 응답은 규칙 없이 나간다.
</Quiz>
```

- `- [x]` 가 정답, `- [ ]` 가 오답이다. 오답 아래 `>` 인용은 **왜 틀렸는지**를 적는다.
- 목록 뒤 마지막 문단이 정답 해설이다.
- **`title` 은 필수다.** 없으면 id 가 전부 `hash('untitled')` 로 같아져 진도 저장이 섞인다.
- 문서 끝에 `<QuizResults />` 를 한 번 둔다.

배치는 `theory` 가 `## 자기 점검 퀴즈`, `start/*` 가 `## ⑦ 자기 점검 퀴즈` 다. 심화 개념이
퀴즈보다 앞에 온다 — 배운 뒤 점검하는 순서다.

## H. 문서가 만들려는 것 — 이해와 역량

이 사이트의 산출물은 **읽은 사람의 이해와 역량**이다. 완결된 참고서가 아니다. 아래 두 규칙이
거기서 나오고, 앞의 규칙들과 판단이 갈리면 이쪽을 기준으로 정한다.

### 깊이의 경계 — 여기까지 쓰고 여기부터 링크한다

문서에는 **왜 그렇게 동작하는지**를 쓴다. 인자 목록·전체 스펙·버전별 차이는 공식 문서 몫이다.

| 여기에 쓴다 | 링크로 넘긴다 |
|---|---|
| 개념이 푸는 문제 | 리소스의 전체 인자 목록 |
| 대안과 갈리는 지점 | 한 인자가 받는 모든 값 |
| 채점·실패로 이어지는 값과 그 이유 | API 응답 필드 전체 표 |
| 틀리기 쉬운 자리와 그때의 증상 | 버전별 변경 이력 |

판단 기준은 하나다. **그 문단을 지웠을 때 독자가 "왜"를 잃으면 남기고, "무엇을"만 잃으면
링크로 바꾼다.**

공식 문서를 옮겨 적은 문단은 부패한다. 원문이 바뀌어도 이쪽은 안 바뀌고, 독자는 틀린 값을
믿는다. 링크는 부패하지 않는다. 링크를 다는 방법은 F 절에 있다.

### 실습은 따라 하기로 끝나지 않는다

명령을 그대로 쳐서 성공하는 경험은 역량을 만들지 않는다. 손이 기억할 뿐 판단은 남지 않는다.
`lab` 은 세 단계를 거친다.

| 단계 | 학습자가 하는 일 | 문서가 주는 것 |
|---|---|---|
| 이행 | 변동 스펙을 읽고 직접 고친다 | 스펙 차이와 타이머 |
| 복기 | 정답과 diff 해 놓친 곳을 분류한다 | 통과 기준과 채점 대응표 |
| 복구·진단 | 망가진 상태에서 원인을 좁힌다 | 증상 하나와 볼 곳의 순서 |

**이행 절에 절차 지시를 쓰지 않는다.** 무엇이 달라졌는지만 주고 방법은 학습자가 정한다.

**정답 코드를 먼저 보여 주지 않는다.** 보고 난 뒤의 diff 는 확인이지 훈련이 아니다.

:::note[이행할 짝이 없는 모듈은 문서를 가른다]
기준본과 타깃이 짝지어지지 않는 모듈이 있다 — 참고할 구현이 한 벌뿐이면 "무엇에서 무엇으로"가
성립하지 않는다. 그때 `lab.mdx` 하나에 구축과 훈련을 섞지 않는다.

| 파일 | sidebar | 담는 것 |
|---|---|---|
| `lab.mdx` | 3 | 구축. 따라 만들며 스택을 세운다 |
| `drill.mdx` | 4 | 훈련. 이행 → 복기 → 진단 |

`drill.mdx` 는 기준본 세우기로 시작한다(`lab` 이 destroy 로 끝나므로). 변동 축은 직접
만들되 **실재하는 기전만** 쓰고, 출제 예측이 아니라 훈련용임을 문서에 적는다. 심는 고장은
그 모듈 `theory.mdx` 의 `:::danger` 에서 가져온다 — 이미 실측된 함정이다.

두 문서의 진단 절은 중복이 아니다. `lab` 쪽은 만들다 막힌 사람에게 원인을 주고,
`drill` 쪽은 일부러 낸 고장에 증상만 준다. 근거는
`docs/superpowers/specs/2026-08-29-drill-lab-split-design.md`.
:::

진단 절은 "이렇게 고친다"가 아니라 **무엇을 보고 어떻게 좁히는가**를 쓴다. 명령 하나의 출력이
갈리는 자리마다 다음에 볼 곳을 적는다 — 그 갈래가 역량이다.

:::note[이행 절은 스크립트가 검사한다]
```bash
npm run check:lab
```

이행 절(제목에 타이머가 붙은 절) 안의 코드 펜스에 실행 명령이 있으면 잡는다. 번호 목록은
세지 않는다 — "종이에 순서를 적는다" 같은 사고 훈련은 절차 지시가 아니다.

이 검사를 손으로 두 번 틀렸다. 범위를 잘못 잡아 통과 기준의 명령을 셌고, 번호 목록을
무조건 절차로 봤다. **스크립트가 정본이다.**
:::

```
로그에 기록이 없다   -> 라우트 테이블
REJECT 가 있다      -> 보안 그룹 · 네트워크 ACL
ACCEPT 인데 무응답   -> 반대 방향 경로
```

근거는 `docs/superpowers/specs/2026-08-11-variation-first-labs-design.md` 와
`docs/superpowers/specs/2026-08-14-debug-first-restructure-design.md`.
