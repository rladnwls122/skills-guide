## ② 핵심 개념

문법이 낯설면 아래 여섯 가지만 잡으면 나머지는 전부 같은 규칙의 반복이다.

### 실행 단위는 파일이 아니라 디렉토리다

`terraform apply` 는 **현재 디렉토리의 모든 `*.tf` 를 한 덩어리로 합쳐서** 읽는다. 파일을 `vpc.tf`·`s3.tf` 로 나누는 것은 사람이 찾기 쉬우라고 하는 것이고, Terraform 입장에서는 이름도 개수도 의미가 없다. 그래서 **파일 안의 순서도 의미가 없다** — 아래에 쓴 리소스를 위에서 참조해도 된다.

정답지도 이 관례를 따른다. `vpc.tf`·`iam.tf`·`s3.tf`·`alb.tf`·`cloudfront.tf`·`dynamodb.tf` 처럼 리소스 종류별로 쪼개 두었고, 세트에 따라 provider 고정 파일이 `versions.tf` 이기도 `providers.tf` 이기도 하다. **파일명은 자유고 내용이 채점 대상이다.**

### 모든 블록은 같은 모양이다

```hcl
resource "aws_vpc" "this" {
  cidr_block = "172.16.0.0/16"
}
```

- `resource` — **블록 타입**. 이 블록이 무엇을 하는지 (`resource` 만들기 / `data` 조회 / `variable` 입력 / `locals` 계산 / `output` 출력).
- `"aws_vpc"` — **첫째 라벨 = AWS 리소스 종류**. provider(`aws`)가 정한 이름이고, 여기 올 수 있는 값과 그 안에 쓸 인자는 provider 문서에 전부 나온다.
- `"this"` — **둘째 라벨 = 내가 붙이는 이름**. AWS 에는 안 올라간다. 코드 안에서 이 리소스를 부르는 별명일 뿐이다. AWS 콘솔에 보이는 이름은 `tags = { Name = ... }` 쪽이다.
- `{ ... }` 안 — **인자(argument)**. `이름 = 값` 형태로만 쓴다.

라벨 개수는 블록 타입마다 고정이다: `resource`·`data` 는 2개, `variable`·`output`·`provider` 는 1개, `locals`·`terraform` 은 0개.

:::caution[둘째 라벨과 Name 태그를 헷갈리지 않는다]
채점 스크립트는 **`Name` 태그**로 리소스를 찾는다. 둘째 라벨은 아무 영향이 없다. `resource "aws_vpc" "this"` 라고 써도 `tags = { Name = "skills-book-vpc" }` 가 맞으면 채점을 통과한다.
:::

### 값을 부르는 이름표(주소)는 5종류뿐이다

| 쓰는 법 | 무엇 | 예 |
|---|---|---|
| `var.<이름>` | `variable` 블록의 입력값 | `var.region` |
| `local.<이름>` | `locals` 블록의 계산값 | `local.account_id` |
| `<타입>.<내이름>.<속성>` | `resource` 가 만든 것 | `aws_vpc.this.id` |
| `data.<타입>.<내이름>.<속성>` | `data` 로 조회한 것 | `data.aws_caller_identity.current.account_id` |
| `each.key` / `each.value` | `for_each` 반복 중인 현재 항목 | `each.value.cidr` |

`locals` 는 선언은 복수형(`locals {}`), 참조는 단수형(`local.x`)이다 — 처음에 가장 많이 틀리는 곳.

### 내가 쓰는 값(argument)과 AWS 가 돌려주는 값(attribute)

```hcl
resource "aws_vpc" "this" {
  cidr_block = var.vpc_cidr      # argument — 내가 넣는 값
}

resource "aws_subnet" "a" {
  vpc_id     = aws_vpc.this.id   # attribute — AWS 가 만들고 나서야 아는 값
  cidr_block = "172.16.1.0/24"
}
```

`id`·`arn`·`dns_name` 처럼 **만들어봐야 정해지는 값**이 attribute 다. `terraform plan` 이 `(known after apply)` 라고 찍는 것이 이것이고, 아직 몰라도 정상이다.

### 실행 순서는 참조가 정한다

위 예에서 서브넷이 `aws_vpc.this.id` 를 참조하므로 Terraform 은 **VPC → 서브넷** 순서를 스스로 세운다. 순서를 내가 쓰는 게 아니라, 참조 관계로 의존성 그래프가 만들어지고 서로 무관한 리소스는 병렬로 생성된다. 참조가 없는데도 순서를 강제해야 할 때만 `depends_on` 을 쓴다 — 남발하면 병렬성이 죽어 배포가 느려진다.

:::danger[함정]
**A 가 B 를 참조하고 B 가 다시 A 를 참조하면 그래프가 고리가 되어 apply 자체가 거부된다**(순환 참조). PART-1 모듈 02 의 KMS·CloudFront·버킷 정책이 정확히 이 함정이다.
:::

### plan 은 세 가지를 비교한다

`terraform plan` = **코드**(`*.tf`) ↔ **상태 파일**(`terraform.tfstate`, 내가 지난번에 만든 것의 기록) ↔ **실제 AWS**. 셋 중 하나만 어긋나도 diff 가 뜬다.

:::caution[콘솔 수정과 섞을 때]
콘솔에서 손으로 고친 리소스는 다음 plan 에서 "되돌리겠다"고 나온다 — 대회에서 콘솔 수정과 코드 수정을 섞을 때 반드시 기억할 것. tfstate 는 로컬에 두고 커밋하지 않는다(계정 정보·시크릿 포함).
:::

## ③ 대회에서 어떻게 쓰이나

**Terraform 은 채점 대상이 아니다.** 1·2과제 문제지·채점지 어디에도 IaC 요구가 없다. 채점은 CloudShell 에서 AWS CLI 로 **배포된 리소스 상태만** 본다. 콘솔로 만들어도 점수는 같다.

그런데도 HCL 을 읽을 줄 알아야 하는 이유는 둘이다.

1. **수상 과제 정답지가 전부 Terraform 이다.** 정답지를 읽고 자기 코드와 대조하는 것이 이 커리큘럼의 학습 방법인데, 문법을 모르면 그 대조가 불가능하다.
2. **당일 30% 변동을 30분에 반영해야 한다.** 이름·CIDR·리전이 바뀌었을 때 콘솔을 다시 클릭하는 것보다 변수 하나 고치고 `apply` 하는 쪽이 빠르다. 그러려면 어디를 고쳐야 하는지 알아야 한다.

즉 HCL 은 **점수가 붙는 지식이 아니라 점수를 빨리 따게 해 주는 도구**다. 이 문서에 시간을 과하게 쓰지 않는다.

## ④ 미니 실습 — `terraform console` (20분, 과금 없음)

`terraform console` 은 표현식을 즉석에서 평가하는 대화형 셸이다. **AWS 자격 증명도 `.tf` 파일도 필요 없다.** 빈 디렉토리에서 그냥 띄우면 된다. 문법이 헷갈릴 때마다 여기서 확인하는 습관이 가장 빠른 피드백이다.

<Steps>

1. 빈 디렉토리에서 콘솔을 띄운다.

   ```bash
   mkdir hcl-play && cd hcl-play
   terraform console
   ```

2. 타입이 어떻게 다른지 본다. 결과의 대괄호·중괄호를 눈에 익힌다.

   ```hcl
   > ["a", "b", "a"]
   > toset(["a", "b", "a"])
   > { name = "vpc", cidr = "10.0.0.0/16" }
   ```

   `toset` 을 통과하면 중복이 사라지고 순서가 없어진다. `for_each` 가 list 를 거부하고 set·map 만 받는 이유가 이것이다.

3. `for` 표현식으로 목록을 만들어 본다. 왼쪽 대괄호면 list, 중괄호면 map 이 나온다.

   ```hcl
   > [for n in ["a", "b"] : upper(n)]
   > { for n in ["a", "b"] : n => "subnet-${n}" }
   ```

4. 정답지에서 자주 보는 함수를 직접 돌려 본다.

   ```hcl
   > merge({ Project = "x" }, { Name = "vpc" })
   > lookup({ html = "text/html" }, "html", "application/octet-stream")
   > lookup({ html = "text/html" }, "png", "application/octet-stream")
   > jsonencode({ Version = "2012-10-17", Statement = [] })
   > regex("[^.]+$", "index.html")
   ```

   `lookup` 의 셋째 인자가 기본값이다. 키가 없을 때 실패하지 않고 그 값을 돌려준다.

5. 조건 표현식과 문자열 보간을 확인한다.

   ```hcl
   > var_is_public = true
   > true ? "public" : "private"
   > "wskorea26-${"pub"}-subnet-c"
   ```

6. `exit` 또는 Ctrl+D 로 나온다. 만든 디렉토리는 지워도 된다 — 아무것도 만들어지지 않았다.

</Steps>

:::tip[막힐 때마다 여기로 온다]
`.tf` 를 고치다 "이 함수가 뭘 돌려주지?" 싶으면 `apply` 로 확인하지 말고 콘솔을 띄운다. `apply` 는 실패해도 시간이 가고, 콘솔은 즉시 답한다.
:::

## ⑤ 심화 개념 (응용력 기르기)

여기부터는 정답지 `.tf` 191개 약 14,000줄에서 **실제로 쓰이는 것만** 골랐다. 쓰이지 않는 문법은 뺐다.

### 타입 — `for_each` 가 set·map 만 받는 이유

기본 타입은 `string`·`number`·`bool` 이고, 묶음 타입이 `list`·`set`·`map`·`object` 다.

| 타입 | 접근 방법 | 중복 |
|---|---|---|
| `list` | 인덱스 `[0]` | 허용 |
| `set` | **인덱스 없음** | 제거됨 |
| `map` | 키 `["name"]` | 키는 유일 |
| `object` | 속성 `.name` | 속성명 고정 |

`for_each` 는 **각 항목에 고유한 이름표를 붙일 수 있어야** 동작한다. list 는 순서가 곧 정체성이라 중간을 빼면 뒤가 전부 밀린다. 그래서 `for_each` 는 set 과 map 만 받고, list 를 주면 `toset()` 으로 감싸라고 요구한다.

정답지는 서브넷 정의를 `map(object({}))` 로 잡는다.

```hcl title="set-02/task-1/terraform/variables.tf" 
variable "subnets" {
  description = "서브넷 정의 (Reference01)"
  type = map(object({
    cidr = string
    az   = string
    tier = string # public | private
  }))
  default = {
    "wskorea26-pub-subnet-c"  = { cidr = "172.16.1.0/24", az = "ap-northeast-2c", tier = "public" }
    "wskorea26-pub-subnet-d"  = { cidr = "172.16.2.0/24", az = "ap-northeast-2d", tier = "public" }
    "wskorea26-priv-subnet-c" = { cidr = "172.16.201.0/24", az = "ap-northeast-2c", tier = "private" }
    "wskorea26-priv-subnet-d" = { cidr = "172.16.202.0/24", az = "ap-northeast-2d", tier = "private" }
  }
}
```

키가 곧 `Name` 태그다. 그래서 사용부가 이렇게 짧아진다.

```hcl title="set-02/task-1/terraform/vpc.tf"
resource "aws_subnet" "this" {
  for_each = var.subnets

  vpc_id                  = aws_vpc.this.id
  cidr_block              = each.value.cidr
  availability_zone       = each.value.az
  map_public_ip_on_launch = each.value.tier == "public"

  tags = { Name = each.key }
}
```

`map_public_ip_on_launch` 우변이 `true`/`false` 가 아니라 **비교식**이라는 데 주목한다. HCL 에서 `==` 는 bool 을 돌려주므로 그대로 인자에 넣을 수 있다.

### 반복 — `count` 와 `for_each` 는 짝이 다르다

두 방식은 만들어진 리소스를 **부르는 법**이 다르고, 그래서 뒤따르는 코드 모양까지 달라진다.

| | `count` | `for_each` |
|---|---|---|
| 받는 것 | 숫자 | set 또는 map |
| 현재 항목 | `count.index` | `each.key` / `each.value` |
| 주소 | `aws_subnet.public[0]` | `aws_subnet.this["이름"]` |
| 전체 뽑기 | splat `aws_subnet.public[*].id` | `for` 표현식 |
| 중간 항목 삭제 | **뒤가 전부 재생성** | 그것만 삭제 |

정답지에서 두 방식이 세트별로 갈린다. EKS 계열(set-02·03·05·07)은 `for_each`, ECS 계열(set-08·09)과 task-3 은 `count` 를 쓴다. 그래서 splat 도 후자에서만 나온다.

```hcl title="set-08/task-1/terraform/alb.tf"
subnets = aws_subnet.public[*].id
```

`for_each` 쪽은 키 목록을 `locals` 에 두고 `for` 표현식으로 뽑는다.

```hcl title="set-02/task-1/terraform/data.tf"
public_subnet_ids  = [for k in local.public_subnet_keys : aws_subnet.this[k].id]
private_subnet_ids = [for k in local.private_subnet_keys : aws_subnet.this[k].id]
```

`for` 표현식은 map 도 만든다. 대괄호로 감싸면 list, 중괄호에 `키 => 값` 이면 map 이다.

```hcl
{ for k in local.private_subnet_keys : k => aws_subnet.this[k].id }
```

:::caution[대회에서 어느 쪽이 유리한가]
**`for_each` 다.** 30% 변동은 보통 "서브넷 하나가 빠지거나 CIDR 이 바뀐다" 형태로 온다. `count` 로 만든 목록에서 중간 하나를 빼면 뒤 항목의 인덱스가 밀려 전부 재생성된다 — apply 시간이 그만큼 길어지고, 이미 다른 리소스가 붙어 있으면 연쇄로 다시 만든다. `for_each` 는 키가 정체성이라 그것만 지운다.
:::

### 조건 표현식 — 리소스를 켜고 끄는 스위치

`조건 ? 참일때 : 거짓일때` 형태다. 값 고르기에도 쓰지만, 정답지에서는 **리소스 자체를 만들지 말지 정하는 데** 더 많이 쓴다.

```hcl
count = var.enable_cdn ? 1 : 0
```

`count = 0` 이면 그 리소스는 만들어지지 않는다. 세트마다 CloudFront 를 쓰기도 안 쓰기도 하는데 코드는 하나로 유지하는 방법이다.

```hcl
app_bootstrap_servers = var.producer_auth_mode == "iam" ? aws_msk_cluster.this.bootstrap_brokers_sasl_iam : aws_msk_cluster.this.bootstrap_brokers_tls
```

### 자주 쓰는 함수 다섯

| 함수 | 하는 일 | 정답지 용례 |
|---|---|---|
| `toset(list)` | list 를 set 으로. 중복 제거 | `for_each = toset(["index.html", "main.jpeg"])` |
| `merge(a, b)` | map 두 개를 합친다. 뒤가 이긴다 | 공통 태그 + 리소스별 태그 |
| `lookup(map, key, 기본값)` | 키를 찾되 없으면 기본값 | 확장자로 `content_type` 결정 |
| `jsonencode(객체)` | HCL 객체를 JSON 문자열로 | EventBridge 이벤트 패턴, IAM 정책 |
| `templatefile(경로, 변수)` | 파일을 읽어 `${}` 를 채운다 | EC2 user data, Step Functions 정의 |

`lookup` 과 `regex` 를 붙여 쓰는 패턴이 정답지에 반복해 나온다.

```hcl
content_type = lookup(local.content_types, regex("[^.]+$", each.value), "application/octet-stream")
```

`regex("[^.]+$", "index.html")` 이 `"html"` 을 뽑고, 그걸 키로 `content_types` 맵을 찾고, 없으면 `application/octet-stream` 을 쓴다.

:::tip[정책 JSON 은 두 가지 방법이 있다]
`jsonencode({...})` 로 직접 쓰는 방법과 `data "aws_iam_policy_document"` 로 쓰는 방법이다. 후자가 오타를 잡아 주고 여러 statement 를 합치기 쉬워 IAM 정책에는 주로 이쪽을 쓴다. EventBridge 이벤트 패턴처럼 IAM 정책이 아닌 JSON 에는 `jsonencode` 를 쓴다.
:::

### `lifecycle` 과 `provider alias`

`lifecycle` 은 리소스의 생성·교체·삭제 방식을 바꾼다. 정답지에서 쓰이는 것은 둘이다.

- `create_before_destroy = true` — 새것을 먼저 만들고 옛것을 지운다. 이름이 겹칠 수 없는 리소스를 교체할 때.
- `ignore_changes = [...]` — 그 인자의 변경을 plan 에서 무시한다. 콘솔이나 오토스케일링이 바꾸는 값을 Terraform 이 되돌리지 않게 할 때.

`provider alias` 는 같은 provider 를 다른 설정으로 하나 더 두는 것이다. CloudFront 용 ACM 인증서와 WAF 는 반드시 `us-east-1` 에 있어야 하므로 정답지가 전부 이 패턴을 쓴다.

```hcl
provider "aws" {
  alias  = "use1"
  region = "us-east-1"
}
```

쓰는 쪽에서 `provider = aws.use1` 로 지정한다.

### 정답지에 없는 것

아래는 Terraform 문법에는 있지만 **정답지 14,000줄에 한 번도 안 나온다.** 시간을 쓰지 않는다.

`module` 블록 · `backend` 블록 · `provisioner` · `cidrsubnet()` · `try()` · `coalesce()` · `format()` · `join()` · `split()` · `flatten()` · `optional()` · `prevent_destroy`

`module` 과 `backend` 가 없다는 것이 이 커리큘럼의 성격을 말해 준다 — 정답지는 전부 flat 한 루트 모듈이고 상태 파일은 로컬에 둔다. 대회는 4시간짜리 단발 배포지 유지보수하는 인프라가 아니다.

## ⑥ 자기 점검 퀴즈

<Quiz title="for_each 가 list 를 거부하는 이유">
`for_each` 에 `["a", "b"]` 를 그대로 주면 오류가 난다. `toset()` 으로 감싸야 하는 근본 이유는?

- [x] list 는 순서가 정체성이라 중간 항목을 빼면 뒤 항목의 주소가 전부 밀린다
- [ ] list 는 문자열만 담을 수 있어 복잡한 값을 못 넣는다
  > list 는 어떤 타입이든 담는다. `list(object({}))` 도 유효하다. 문제는 담는 것이 아니라 **부르는 법**이다.
- [ ] `for_each` 는 원래 map 전용이고 set 도 사실은 내부에서 map 으로 바뀐다
  > set 을 주면 `each.key` 와 `each.value` 가 같은 값이 되는 것은 맞지만, 그건 결과지 이유가 아니다.
- [ ] list 는 `terraform plan` 에서 순서가 무작위로 섞인다
  > list 순서는 보존된다. 섞이는 것은 set 이다.

`for_each` 는 각 항목에 **변하지 않는 이름표**를 붙여 상태 파일에 기록한다. 그래야 다음 apply 에서 "이 항목은 그대로다"를 판단할 수 있다. list 의 이름표는 인덱스뿐인데 인덱스는 중간을 빼면 밀린다 — 그래서 이름표 자격이 없다. set 은 값 자체가, map 은 키가 이름표가 된다.
</Quiz>

<Quiz title="30% 변동이 왔을 때 유리한 쪽">
과제지 변동으로 서브넷 4개 중 하나가 빠졌다. `count` 로 만든 코드와 `for_each` 로 만든 코드의 차이는?

- [x] `count` 는 빠진 것 뒤의 서브넷들이 전부 재생성되고, `for_each` 는 그것만 삭제된다
- [ ] `count` 는 apply 가 실패하고 `for_each` 만 성공한다
  > 둘 다 성공한다. 차이는 성패가 아니라 **얼마나 많이 다시 만드는가**다.
- [ ] 차이가 없다. 어느 쪽이든 Terraform 이 알아서 최소 변경만 한다
  > `count` 의 주소는 `[0]`·`[1]` 같은 인덱스라 중간이 빠지면 뒤가 한 칸씩 당겨진다. Terraform 은 그것을 "다른 리소스"로 본다.
- [ ] `for_each` 는 서브넷 ID 가 바뀌고 `count` 는 유지된다
  > 반대다.

`count` 에서 인덱스 1을 지우면 옛 `[2]` 가 새 `[1]` 이 된다. Terraform 은 주소로 리소스를 식별하므로 이것을 "`[1]` 을 교체하고 `[2]` 를 삭제"로 읽는다. 서브넷이 재생성되면 거기 붙은 RTB 연결·ENI 까지 연쇄로 흔들린다. 4시간짜리 대회에서 이 차이는 크다.
</Quiz>

<Quiz title="채점과 코드의 관계">
`resource "aws_vpc" "this"` 의 둘째 라벨 `"this"` 를 `"main"` 으로 바꿨다. 채점에 미치는 영향은?

- [x] 없다. 채점 스크립트는 `Name` 태그로 리소스를 찾는다
- [ ] VPC 이름이 바뀌므로 채점 스크립트가 못 찾는다
  > 둘째 라벨은 AWS 에 올라가지 않는다. 코드 안에서 부르는 별명일 뿐이다.
- [ ] `terraform apply` 가 거부한다
  > 문법적으로 유효하다. 다만 주소가 바뀌므로 기존 리소스를 삭제하고 새로 만든다.
- [ ] Terraform 상태 파일이 깨져 복구가 불가능해진다
  > 상태는 깨지지 않는다. 옛 주소가 사라지고 새 주소가 생긴 것으로 처리된다.

채점 스크립트가 보는 것은 AWS 에 실제로 올라간 것뿐이다. 둘째 라벨은 안 올라가고, `tags = { Name = ... }` 은 올라간다. 다만 라벨을 바꾸면 Terraform 주소가 바뀌어 **리소스가 재생성**되므로 대회 중에는 건드리지 않는다.
</Quiz>

<Quiz title="lookup 의 셋째 인자">
`lookup(local.content_types, regex("[^.]+$", "photo.jpeg"), "application/octet-stream")` 에서 `content_types` 맵에 `jpeg` 키가 없다면 결과는?

[[application/octet-stream]]

---

`lookup` 의 셋째 인자는 기본값이다. 키가 없으면 오류를 내는 대신 이 값을 돌려준다. 정답지가 S3 객체 업로드에서 이 패턴을 쓰는 이유가 여기 있다 — 예상 못 한 확장자가 와도 apply 가 죽지 않고 범용 MIME 타입으로 올라간다. `regex("[^.]+$", ...)` 는 마지막 점 뒤를 뽑아 `"jpeg"` 를 만든다.
</Quiz>

<Quiz title="plan 에 diff 가 뜨는 이유">
아무 코드도 안 고쳤는데 `terraform plan` 에 변경 사항이 나온다. 가능한 원인을 **모두** 고르시오.

- [x] 콘솔에서 그 리소스를 손으로 고쳤다
- [x] 오토스케일링이나 다른 자동화가 값을 바꿨다
- [ ] 상태 파일이 오래돼서 자동으로 갱신이 필요하다
  > 상태 파일은 시간이 지난다고 낡지 않는다. plan 은 매번 실제 AWS 를 조회해 비교한다.
- [ ] provider 버전이 올라가면 항상 전체 재생성 diff 가 뜬다
  > provider 업그레이드로 기본값이 바뀌면 diff 가 날 수 있지만 "항상 전체 재생성"은 아니다. 그래서 버전을 `~>` 로 고정한다.

`plan` 은 **코드 ↔ 상태 파일 ↔ 실제 AWS** 셋을 비교한다. 코드를 안 고쳤어도 실제 AWS 가 상태 파일과 다르면 diff 가 난다. 대회에서 콘솔 수정과 코드 수정을 섞으면 반드시 겪는다 — 콘솔로 급히 고친 것을 다음 apply 가 되돌린다. 되돌리면 안 되는 값이면 `lifecycle.ignore_changes` 로 빼 둔다.
</Quiz>

<Quiz title="정책 JSON 을 쓰는 방법">
IAM 정책을 코드로 쓸 때 `data "aws_iam_policy_document"` 를 `jsonencode()` 보다 선호하는 이유는?

- [x] 인자 이름을 provider 가 검증해 주고 여러 statement 를 합치기 쉽다
- [ ] `jsonencode()` 는 IAM 정책에 쓸 수 없다
  > 쓸 수 있다. 정답지도 EventBridge 이벤트 패턴 등에는 `jsonencode` 를 쓴다.
- [ ] `jsonencode()` 로 만든 정책은 AWS 가 거부한다
  > 거부하지 않는다. 유효한 JSON 이면 통과한다.
- [ ] data source 쪽이 apply 가 더 빠르다
  > 속도 차이는 사실상 없다.

`aws_iam_policy_document` 는 `statement`·`actions`·`resources`·`principals` 를 HCL 블록으로 쓰게 해 준다. 오타가 나면 plan 단계에서 잡히고, 조건부로 statement 를 넣고 빼기도 쉽다. 반면 `jsonencode` 는 그냥 문자열을 만들 뿐이라 오타가 apply 까지 간다. IAM 정책이 아닌 JSON(이벤트 패턴·Step Functions 정의)에는 `jsonencode` 나 `templatefile` 을 쓴다.
</Quiz>
