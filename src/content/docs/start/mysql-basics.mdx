## ① 학습 목표

- [ ] `CREATE TABLE` 문을 읽고 어떤 열이 어떤 타입인지 말할 수 있다
- [ ] 기본 키(primary key)와 고유 키(unique key)가 무엇을 보장하는지 안다
- [ ] `SELECT` · `WHERE` · `ORDER BY` · `LIMIT` 로 원하는 행을 꺼낼 수 있다
- [ ] 인덱스가 무엇이고 왜 조회를 빠르게 하는지 설명할 수 있다
- [ ] `EXPLAIN` 출력을 읽고 전체 훑기인지 인덱스 조회인지 구분할 수 있다
- [ ] 인덱스를 언제 만들지, 왜 아무 데나 만들면 안 되는지 안다
- [ ] `mysql` 명령으로 접속하고 덤프를 적재할 수 있다
- [ ] 커넥션 풀과 RDS Proxy 가 푸는 문제를 설명할 수 있다

:::note[3과제 점수가 여기서 갈린다]
[실기출 분해](/reference/past-exams/#2-3-2025년-3과제-40점)를 보면 3과제 40점 중 성능 효율성이 12점이고, 그 조건이 "응답 0.2초 이하인 요청의 비율"이다. `user` 앱은 MySQL 을 쓴다.

앱은 수정할 수 없다. 앱이 던지는 질의는 정해져 있다. **선수가 바꿀 수 있는 것은 테이블 구조와 인덱스뿐이다.** 그래서 이 문서의 중심은 인덱스다.
:::

## ② 핵심 개념

### 2-1. 테이블은 열이 정해진 표다

DynamoDB 와 달리 관계형 데이터베이스는 **열을 미리 정한다.** 정하지 않은 열에는 값을 넣을 수 없다.

2025 3과제 문제지가 준 테이블이다.

```sql
CREATE TABLE user (
    id VARCHAR(255) NOT NULL,
    username VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_username (username)
);
```

한 줄씩 읽는다.

| 부분 | 뜻 |
|---|---|
| `id VARCHAR(255)` | `id` 라는 열, 최대 255자 문자열 |
| `NOT NULL` | 비워 둘 수 없다 |
| `PRIMARY KEY (id)` | `id` 가 행을 구분하는 기준. 중복 불가, 비움 불가 |
| `UNIQUE KEY uk_username (username)` | `username` 도 중복 불가. 이름이 `uk_username` 인 제약 |

같은 문제지의 `product` 테이블이다.

```sql
CREATE TABLE product (
    id VARCHAR(255) NOT NULL,
    name VARCHAR(255) NOT NULL,
    price FLOAT(8) NOT NULL,
    image_path VARCHAR(500) DEFAULT NULL,
    PRIMARY KEY (id)
);
```

`DEFAULT NULL` 은 비워 둬도 된다는 뜻이다. `NOT NULL` 의 반대다.

### 2-2. 자주 쓰는 타입

| 타입 | 담는 것 | 비고 |
|---|---|---|
| `INT` | 정수 | 약 ±21억 |
| `BIGINT` | 큰 정수 | 그보다 크면 |
| `VARCHAR(n)` | 가변 길이 문자열 | `n` 은 최대 길이 |
| `CHAR(n)` | 고정 길이 문자열 | 짧고 길이가 일정할 때 |
| `FLOAT` · `DOUBLE` | 실수(근사) | 돈에는 쓰지 않는다 |
| `DECIMAL(m,n)` | 실수(정확) | 돈에 쓴다 |
| `DATE` | 날짜 | `2026-08-28` |
| `DATETIME` · `TIMESTAMP` | 날짜와 시각 | |
| `ENUM('M','F')` | 정해진 값 중 하나 | 2024 3과제 `gender` 가 이것 |

:::caution[`FLOAT` 은 값이 정확하지 않다]
`price FLOAT(8)` 은 문제지가 준 그대로다. 실수를 2진수로 근사하므로 미세한 오차가 남는다. 파이썬에서 `Decimal` 을 쓰는 이유와 같은 문제다([Python·boto3 기초](/start/python-basics/#2-8-decimal-이-필요한-이유)). **다만 제공된 스키마는 그대로 쓴다.** 임의로 바꾸면 앱이 기대하는 것과 어긋날 수 있다.
:::

### 2-3. 조회

```sql
SELECT id, username, email FROM user WHERE email = 'gildong@example.org';
```

| 부분 | 뜻 |
|---|---|
| `SELECT id, username, email` | 이 세 열을 |
| `FROM user` | `user` 테이블에서 |
| `WHERE email = '...'` | 이 조건을 만족하는 행만 |

`SELECT *` 는 모든 열이다. 편하지만 필요 없는 열까지 읽어 오므로 성능이 중요한 자리에서는 필요한 열만 적는다.

**조건에 자주 쓰는 것들.**

```sql
WHERE price > 1000                    -- 초과
WHERE price BETWEEN 1000 AND 5000     -- 사이
WHERE name LIKE '노트북%'              -- 로 시작
WHERE id IN ('a', 'b', 'c')           -- 목록 중 하나
WHERE image_path IS NULL              -- 비어 있음
```

`IS NULL` 을 `= NULL` 로 쓰면 안 된다. `NULL` 은 "값이 없음"이라 무엇과도 같지 않다. `= NULL` 은 항상 거짓이라 아무 행도 나오지 않는다.

**정렬과 개수 제한.**

```sql
SELECT * FROM product ORDER BY price DESC LIMIT 10;
```

`DESC` 가 내림차순, `ASC`(생략 가능)가 오름차순이다. `LIMIT 10` 은 열 행까지만.

### 2-4. 넣고 고치고 지우기

```sql
INSERT INTO user (id, username, email) VALUES ('u-1', 'kim', 'kim@example.org');
UPDATE user SET email = 'new@example.org' WHERE id = 'u-1';
DELETE FROM user WHERE id = 'u-1';
```

:::danger[`WHERE` 없는 `UPDATE` 와 `DELETE`]
`DELETE FROM user;` 는 **모든 행을 지운다.** 대회 3과제는 "삽입한 데이터를 임의로 수정하거나 삭제하지 않도록" 요구한다. 지우면 되돌릴 방법이 없고 점수도 없다. `WHERE` 를 먼저 쓰고 조건을 채우는 습관을 들인다.
:::

### 2-5. 여러 테이블을 잇기

```sql
SELECT o.id, u.username, p.name
FROM orders o
JOIN user u ON o.user_id = u.id
JOIN product p ON o.product_id = p.id;
```

`orders o` 의 `o` 는 별명이다. 아래에서 `o.id` 처럼 짧게 쓴다.

`JOIN ... ON` 은 두 테이블을 어떤 열이 같은 것끼리 이을지 정한다. 대회 과제에서 조인이 필수인 경우는 드물지만, 앱이 던지는 질의에 조인이 있으면 **이은 열 양쪽에 인덱스가 있어야** 빠르다.

## ③ 인덱스 — 3과제의 핵심

### 3-1. 인덱스가 없으면 무슨 일이 일어나나

`user` 테이블에 30만 행이 있고 앱이 이 질의를 던진다고 하자.

```sql
SELECT id, username, email FROM user WHERE email = 'gildong@example.org';
```

`email` 에 인덱스가 없으면 MySQL 은 **첫 행부터 마지막 행까지 전부 읽어** 조건에 맞는지 하나씩 본다. 이것을 전체 훑기(full table scan)라고 한다. 30만 행이면 30만 번 비교한다.

인덱스가 있으면 다르다. 인덱스는 `email` 값을 정렬해 둔 별도의 구조라, 사전에서 단어를 찾듯 몇 단계 만에 위치를 찾는다. 30만 행이어도 비교 횟수는 스무 번 안쪽이다.

**이 차이가 0.2초 목표의 성패를 가른다.**

### 3-2. 인덱스 만들기

```sql
ALTER TABLE user ADD INDEX idx_email (email);
```

`idx_email` 은 인덱스 이름이고 괄호 안이 대상 열이다.

만든 뒤 확인한다.

```sql
SHOW INDEX FROM user;
```

:::danger[덤프 적재 뒤에 만든다]
덤프 파일이 `DROP TABLE` 과 `CREATE TABLE` 을 포함할 수 있다. 인덱스를 먼저 만들면 덤프가 테이블을 다시 만들면서 인덱스가 사라진다. **순서는 덤프 적재가 먼저, 인덱스가 나중이다.**

행이 많을 때 인덱스를 먼저 만들면 적재도 느려진다. 행을 넣을 때마다 인덱스를 갱신해야 하기 때문이다.
:::

### 3-3. EXPLAIN 으로 확인한다

인덱스를 만들었다고 쓰이는 것이 아니다. 확인하는 방법이 `EXPLAIN` 이다.

```sql
EXPLAIN SELECT id, username, email FROM user WHERE email = 'gildong@example.org';
```

**인덱스가 없을 때.**

```
id  select_type  table  type  possible_keys  key   rows    Extra
1   SIMPLE       user   ALL   NULL           NULL  298734  Using where
```

**인덱스가 있을 때.**

```
id  select_type  table  type  possible_keys  key        rows  Extra
1   SIMPLE       user   ref   idx_email      idx_email  1     NULL
```

세 칸만 보면 된다.

| 칸 | 나쁜 값 | 좋은 값 |
|---|---|---|
| `type` | `ALL` (전체 훑기) | `ref` · `eq_ref` · `const` |
| `key` | `NULL` (인덱스 안 씀) | 인덱스 이름 |
| `rows` | 큰 수 | 작은 수 |

`type` 이 `ALL` 이고 `key` 가 `NULL` 이면 인덱스가 쓰이지 않았다는 뜻이다. `rows` 는 MySQL 이 몇 행을 읽을 것으로 추정하는지다. 298734 에서 1 로 줄면 그만큼 빨라진다.

`Extra` 에 `Using filesort` 나 `Using temporary` 가 보이면 정렬이나 임시 테이블에 추가 비용이 든다는 뜻이다.

### 3-4. 인덱스를 만들면 안 되는 경우

인덱스는 공짜가 아니다.

| 비용 | 내용 |
|---|---|
| 쓰기가 느려진다 | `INSERT` · `UPDATE` · `DELETE` 마다 인덱스도 갱신한다 |
| 저장 공간을 쓴다 | 별도 구조라 디스크를 더 쓴다 |
| 안 쓰일 수도 있다 | 값 종류가 적으면 MySQL 이 전체 훑기를 고른다 |

세 번째가 헷갈리는 지점이다. `gender` 처럼 값이 `M` 과 `F` 둘뿐인 열에 인덱스를 만들어도, 조건에 맞는 행이 절반이면 인덱스를 거쳐 가는 것보다 그냥 훑는 편이 빠르다. MySQL 이 그렇게 판단하면 인덱스를 무시한다.

**규칙은 하나다. 앱이 실제로 던지는 질의의 `WHERE` 절에 나오는 열에, 값 종류가 충분히 많을 때 만든다.**

3과제라면 앱이 던지는 질의를 어떻게 아는가. 세 가지 방법이 있다.

1. 문제지의 API 표를 본다. `GET /v1/user?email=...` 이면 `WHERE email = ?` 다
2. 바이너리에서 SQL 문자열을 뽑는다([Go·Gin 앱 읽기](/start/go-app-basics/#3-컴파일된-바이너리-읽기))
3. **느린 질의 로그를 켜서 실제로 들어온 것을 본다** — 가장 확실하다

### 3-5. 느린 질의 로그

RDS 파라미터 그룹에서 켠다.

| 파라미터 | 값 | 뜻 |
|---|---|---|
| `slow_query_log` | `1` | 켜기 |
| `long_query_time` | `0.2` | 0.2초 넘는 질의를 기록 |

`0.2` 로 두면 **목표를 넘긴 질의만** 정확히 모인다. RDS 콘솔의 로그나 CloudWatch Logs 로 보낸 뒤 확인한다.

### 3-6. 복합 인덱스

두 열을 함께 쓰는 조건이면 인덱스도 함께 만든다.

```sql
ALTER TABLE orders ADD INDEX idx_user_created (user_id, created_at);
```

**순서가 중요하다.** 이 인덱스는 다음에 쓰인다.

| 질의 조건 | 쓰이나 |
|---|---|
| `WHERE user_id = ?` | 쓰인다 |
| `WHERE user_id = ? AND created_at > ?` | 쓰인다 |
| `WHERE created_at > ?` | **쓰이지 않는다** |

전화번호부가 성으로 먼저 정렬돼 있으면 성만 알아도 찾을 수 있지만 이름만으로는 찾을 수 없는 것과 같다. **자주 등호로 비교하는 열을 앞에 둔다.**

## ④ 접속과 적재

### 4-1. 접속

```bash
mysql -h <엔드포인트> -P 3306 -u admin -p
```

| 옵션 | 뜻 |
|---|---|
| `-h` | 호스트(엔드포인트) |
| `-P` | 포트. 대문자다 |
| `-u` | 사용자 |
| `-p` | 암호를 물어본다 |

:::caution[`-p` 뒤에 암호를 붙일 때는 공백이 없어야 한다]
`-p Skills53` 는 틀리고 `-pSkills53` 가 맞다. 다만 암호가 셸 기록에 남으므로 가능하면 `-p` 만 쓰고 물어보게 한다.

암호에 `#` 나 `$` 가 들어가면 셸이 먼저 해석한다. 작은따옴표로 감싸거나 역슬래시로 이스케이프한다. 2025 1과제 채점 스크립트도 `-pSkills53#\$%` 처럼 이스케이프했다.
:::

**포트가 3306 이 아닐 수 있다.** 2025 1과제는 3309 를 요구했다. 보안을 위해 기본 포트를 바꾸라는 요구가 자주 나온다.

### 4-2. 어디서 접속하나

RDS 를 사설 서브넷에 두면 인터넷에서 직접 붙을 수 없다. 같은 VPC 안에서 붙어야 한다.

| 방법 | 쓸 때 |
|---|---|
| VPC 안의 EC2·Bastion | 가장 흔하다 |
| VPC CloudShell | 도구 설치 없이 |
| `kubectl run --image=mysql:8` | 클러스터가 이미 있을 때 |

세 번째가 2025 1과제 채점 스크립트가 쓴 방법이다.

```bash
kubectl run proxy-test --image=mysql:8 --restart=Never -- sleep 60
kubectl exec proxy-test -- mysql -h $ENDPOINT -u admin -pSkills53#\$% -e 'SELECT 1'
```

`-e '...'` 는 접속해서 그 SQL 한 줄만 실행하고 나오라는 뜻이다. 연결 확인에 쓴다.

### 4-3. 덤프 적재

```bash
mysql -h <엔드포인트> -u admin -p day1 < load_user.dump
```

`< 파일` 은 파일 내용을 명령의 입력으로 넣는다는 뜻이다. `day1` 은 대상 데이터베이스 이름이다.

**적재 확인.**

```sql
SELECT COUNT(*) FROM user;
```

:::danger[프록시가 아니라 직결 엔드포인트로 적재한다]
RDS Proxy 를 거치면 대량 적재 중 연결이 끊길 수 있다. 덤프는 RDS 인스턴스 엔드포인트로 직접 넣고, 앱만 프록시를 거치게 한다.
:::

### 4-4. 데이터베이스 만들기

```sql
CREATE DATABASE day1 CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE day1;
```

`utf8mb4` 를 쓴다. MySQL 의 `utf8` 은 이름과 달리 3바이트까지만 담아 이모지 같은 4바이트 글자가 들어가지 않는다.

## ⑤ 심화 — 커넥션과 RDS Proxy

### 5-1. 접속 하나가 비싸다

MySQL 에 접속할 때마다 TCP 연결, 인증, 세션 준비가 일어난다. 요청마다 새로 접속하면 이 준비 시간이 응답 시간에 그대로 얹힌다.

그래서 앱은 **커넥션 풀**을 쓴다. 접속을 몇 개 미리 열어 두고 돌려 쓴다. Go 의 `database/sql` 이 기본으로 풀을 관리한다.

### 5-2. 그런데 풀이 늘면 문제가 생긴다

`db.t3.micro` 는 최대 접속 수가 제한적이다. 앱 컨테이너를 열 개로 늘리고 각각 풀을 스무 개씩 열면 200개다. 한도를 넘으면 이 오류가 난다.

```
Error 1040: Too many connections
```

**컨테이너를 늘렸는데 오히려 오류가 늘어나는** 상황이 이렇게 생긴다. 3과제에서 실제로 만나는 함정이다.

### 5-3. RDS Proxy 가 푸는 것

RDS Proxy 는 앱과 DB 사이에 서서 접속을 모아 준다. 앱이 100개를 열어도 프록시가 DB 쪽으로는 훨씬 적은 수를 유지한다.

| | 프록시 없이 | 프록시 있이 |
|---|---|---|
| DB 접속 수 | 앱 수에 비례해 늘어남 | 프록시가 조절 |
| 장애 조치 시간 | 앱이 재연결할 때까지 | 프록시가 흡수 |
| 접속 준비 비용 | 앱마다 | 프록시가 재사용 |

2025 1과제는 "데이터베이스 인스턴스는 RDS 프록시를 통해서만 트래픽을 수신해야 한다"고 요구했다. 보안 그룹으로 프록시만 DB 에 붙을 수 있게 하면 만족한다.

### 5-4. 그 밖에 응답 시간을 줄이는 것들

| 방법 | 효과 | 주의 |
|---|---|---|
| 인덱스 추가 | 가장 크다 | 3-4 참고 |
| 필요한 열만 `SELECT` | 전송량 감소 | |
| 커넥션 풀 크기 조정 | 접속 대기 감소 | 너무 크면 5-2 |
| 읽기 전용 복제본 | 읽기 분산 | **2025 3과제는 금지** |
| 인스턴스 타입 상향 | 확실 | **2025 3과제는 `db.t3.micro` 고정** |

**뒤 두 줄이 막혀 있다는 것이 3과제의 성격을 정한다.** 하드웨어로 밀어붙일 수 없으니 인덱스와 캐싱과 애플리케이션 계층 확장으로 풀어야 한다.

## ⑥ 흔한 실수

| 실수 | 증상 | 고치는 법 |
|---|---|---|
| 덤프 적재 전에 인덱스 생성 | 인덱스가 사라짐 | 적재 먼저, 인덱스 나중 |
| `EXPLAIN` 확인 없이 넘어감 | 인덱스는 있는데 안 쓰임 | `type` 과 `key` 확인 |
| 포트를 3306 으로 가정 | 접속 안 됨 | 문제지의 포트 확인 |
| `= NULL` | 결과가 항상 비어 있음 | `IS NULL` |
| 셸에서 암호의 `#` 미이스케이프 | 인증 실패 | 작은따옴표나 역슬래시 |
| `utf8` 사용 | 일부 글자 깨짐 | `utf8mb4` |
| 프록시로 덤프 적재 | 중간에 끊김 | 직결 엔드포인트로 |
| `WHERE` 없는 `DELETE` | 데이터 소실, 0점 | 조건을 먼저 쓴다 |
