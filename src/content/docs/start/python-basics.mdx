## ② 핵심 개념

### 2-1. 값에는 종류가 있다

Python 에서 값의 종류를 타입이라고 부른다. 대회 Lambda 에서 만나는 것은 다섯 가지다.

| 타입 | 쓰는 법 | 무엇인가 |
|---|---|---|
| 문자열(str) | `"hello"` | 글자 묶음 |
| 정수(int) | `42` | 소수점 없는 수 |
| 실수(float) | `3.14` | 소수점 있는 수 |
| 리스트(list) | `["a", "b"]` | 순서 있는 값들의 묶음 |
| 딕셔너리(dict) | `{"name": "kim"}` | 이름표가 붙은 값들의 묶음 |

**딕셔너리가 가장 중요하다.** JSON 을 주고받는 일이 Lambda 가 하는 일의 거의 전부이고, Python 은 JSON 을 딕셔너리로 다룬다.

```python
item = {"booking_id": "b-001", "username": "kim"}
item["booking_id"]        # "b-001"
item["email"]             # KeyError — 없는 이름표를 꺼내면 오류가 난다
item.get("email")         # None — 없으면 None 을 준다
item.get("email", "없음")  # "없음" — 없을 때 줄 값을 정할 수 있다
```

:::danger[대괄호와 `.get()` 의 차이가 Lambda 를 죽인다]
`item["email"]` 은 이름표가 없으면 `KeyError` 를 내고 Lambda 가 그 자리에서 죽는다. 그러면 ALB 는 502 를 낸다. 채점자가 보는 것은 "응답이 오지 않는다"뿐이라 원인을 찾는 데 시간이 든다. **바깥에서 들어온 값은 항상 `.get()` 으로 꺼낸다.**
:::

### 2-2. 함수와 반환

```python
def calculate_grade(average):
    if average >= 90:
        return "A"
    if average >= 80:
        return "B"
    return "F"
```

`def` 로 시작하고 이름과 괄호 안 입력값을 적는다. 콜론 뒤부터 **들여쓰기된 줄**이 함수의 몸통이다. Python 은 중괄호가 없고 들여쓰기가 곧 구조다. `return` 을 만나면 그 자리에서 값을 돌려주고 함수가 끝난다.

위 함수에서 `average` 가 95 면 첫 `if` 에서 `"A"` 를 돌려주고 나머지 줄은 아예 실행되지 않는다. 이 성질 때문에 `if / return` 을 여러 개 늘어놓는 것만으로 구간 분기가 된다.

### 2-3. 반복

```python
for row in rows:
    error_reason = validate_row(row)
    if error_reason:
        errors += 1
    else:
        processed += 1
```

`rows` 안의 값을 하나씩 꺼내 `row` 에 넣고 몸통을 실행한다. `errors += 1` 은 `errors = errors + 1` 의 줄임이다.

`if error_reason:` 에 비교 연산자가 없다는 점을 본다. Python 은 값 자체를 참·거짓으로 본다. `None` · 빈 문자열 · `0` · 빈 리스트가 거짓이고 나머지는 참이다. `validate_row` 가 오류 이유 문자열을 돌려주면 참, 문제가 없어 `None` 을 돌려주면 거짓이 된다.

### 2-4. import 와 환경변수

```python
import json
import os
import boto3
```

`import` 는 남이 만들어 둔 코드 묶음을 가져온다. `json` 과 `os` 는 Python 에 딸려 오고, `boto3` 는 AWS SDK 로 Lambda 실행 환경에 이미 깔려 있다. 셋 다 따로 설치할 필요가 없다.

```python
table_name = os.environ["TABLE_NAME"]
index_name = os.environ.get("INDEX_NAME", "concert_name-created_at-index")
```

`os.environ` 은 환경변수를 담은 딕셔너리다. Lambda 콘솔이나 Terraform 에서 설정한 값이 여기로 들어온다.

두 줄의 차이가 의도적이다. 첫 줄은 대괄호라 `TABLE_NAME` 이 없으면 **Lambda 가 시작할 때 즉시 죽는다.** 없으면 아무것도 할 수 없는 값이니 조용히 넘어가는 것보다 낫다. 둘째 줄은 기본값이 있어 없어도 굴러간다.

:::caution[테이블 이름을 코드에 직접 쓰지 않는다]
실기출 문제지가 반복해서 요구한다. 연결 정보를 코드에 박으면 이름이 바뀔 때 코드를 다시 배포해야 하고, 채점에서 감점 사유가 되기도 한다. **환경변수로 뺀다.**
:::

### 2-5. boto3 — client 와 resource

boto3 로 AWS 를 부르는 방법이 둘이다.

```python
s3_client = boto3.client("s3")            # 저수준
dynamodb = boto3.resource("dynamodb")     # 고수준
table = dynamodb.Table("my-table")
```

| | `client` | `resource` |
|---|---|---|
| 다루는 모양 | AWS API 그대로 | Python 객체처럼 |
| 타입 표기 | `{"S": "kim"}` 처럼 직접 씀 | `"kim"` 그대로 씀 |
| 지원 범위 | 모든 서비스 | 일부 서비스만 |

DynamoDB 는 `resource` 가 훨씬 편하다. `client` 로 항목을 넣으려면 값마다 타입을 붙여야 한다.

```python
# client — 타입을 직접 붙인다
s3_client.put_item(TableName="t", Item={"name": {"S": "kim"}, "age": {"N": "30"}})

# resource — 파이썬 값을 그대로 넣는다
table.put_item(Item={"name": "kim", "age": 30})
```

S3 는 반대로 `client` 를 쓴다. `get_object` · `put_object` 가 그쪽에 있다.

### 2-6. Lambda 핸들러

```python
def handler(event, context):
    ...
```

Lambda 는 이 이름의 함수를 찾아 부른다. `event` 에 호출한 쪽이 준 정보가, `context` 에 실행 환경 정보가 들어온다. `context` 는 대회에서 거의 쓰지 않는다.

**`event` 의 모양은 누가 불렀느냐로 달라진다.** 이것이 Lambda 를 처음 쓸 때 가장 헷갈리는 지점이다.

| 호출한 쪽 | `event` 에서 꺼내는 법 |
|---|---|
| ALB (Lambda 대상 그룹) | `event["queryStringParameters"]` · `event["path"]` |
| API Gateway REST | `event["queryStringParameters"]` · `event["pathParameters"]` |
| S3 이벤트 알림 | `event["Records"][0]["s3"]["object"]["key"]` |
| Step Functions | 상태 머신이 넘긴 JSON 그대로 |

```python
params = event.get("queryStringParameters") or {}
booking_id = params.get("booking_id")
```

`or {}` 가 붙은 이유가 있다. 쿼리스트링이 아예 없는 요청이 오면 ALB 는 그 자리에 `None` 을 넣는다. `None.get(...)` 은 오류다. `or {}` 는 앞이 거짓일 때 뒤를 쓰라는 뜻이라 빈 딕셔너리로 바뀐다.

### 2-7. ALB 가 요구하는 응답 형식

Lambda 를 ALB 대상 그룹에 붙이면 응답이 정해진 모양이어야 한다. 아니면 ALB 가 502 를 낸다.

```python
{
    "statusCode": 200,
    "statusDescription": "200 OK",
    "isBase64Encoded": False,
    "headers": {"Content-Type": "application/json"},
    "body": json.dumps(body),
}
```

`body` 가 문자열이어야 한다는 점이 핵심이다. 딕셔너리를 그대로 넣으면 안 되고 `json.dumps` 로 문자열로 바꿔야 한다.

| 함수 | 방향 |
|---|---|
| `json.dumps(값)` | 파이썬 값에서 JSON 문자열로 |
| `json.loads(문자열)` | JSON 문자열에서 파이썬 값으로 |

### 2-8. Decimal 이 필요한 이유

DynamoDB 의 숫자를 boto3 `resource` 로 읽으면 `int` 나 `float` 이 아니라 `Decimal` 로 온다. 그리고 **`float` 을 넣으려 하면 boto3 가 거부한다.**

```python
from decimal import Decimal

Decimal("483") / Decimal("5")   # Decimal('96.6')
483 / 5                         # 96.60000000000001
```

컴퓨터는 실수를 2진수로 근사한다. 0.1 을 정확히 담을 수 없어 계산 결과에 미세한 오차가 남는다. 돈이나 점수처럼 **표시한 값이 그대로여야 하는 수**에서는 이 오차가 곧 오답이다. `Decimal` 은 10진수로 계산해 이 문제를 피한다.

:::danger[`Decimal` 은 JSON 으로 바로 바뀌지 않는다]
`json.dumps` 는 `Decimal` 을 만나면 `TypeError` 를 낸다. 읽어서 응답에 담을 때 반드시 변환이 필요하다. 방법이 두 가지인데 뒤에서 실제 코드로 본다.
:::

## ③ 실제 Lambda 세 개 해부

여기부터가 이 문서의 본론이다. `skills-2026` 저장소에 있는 실제 과제 Lambda 를 짧은 것부터 순서대로 읽는다.

### 3-1. 가장 단순한 조회 — `set-07/task-1`

**하는 일.** ALB 로 `GET /v1/book?booking_id=...` 이 오면 DynamoDB 에서 그 항목을 찾아 돌려준다.

```python
import json
import os
from decimal import Decimal

import boto3

dynamodb = boto3.resource("dynamodb")
table = dynamodb.Table(os.environ["TABLE_NAME"])

_STATUS_TEXT = {200: "OK", 400: "Bad Request", 404: "Not Found", 500: "Internal Server Error"}
```

**맨 위 세 줄이 함수 바깥에 있다는 점을 본다.** 이것이 의도적이다. Lambda 는 같은 실행 환경을 재사용하는데, 함수 바깥의 코드는 **처음 한 번만** 실행된다. `boto3.resource` 는 연결 준비에 시간이 걸리므로 바깥에 두면 두 번째 호출부터 그만큼 빨라진다. 안에 두면 매 호출마다 다시 만든다.

`_STATUS_TEXT` 처럼 이름 앞에 밑줄을 붙이는 것은 "이 파일 안에서만 쓰는 것"이라는 관례다. 문법적 강제는 없다.

```python
class _DecimalEncoder(json.JSONEncoder):
    def default(self, obj):
        if isinstance(obj, Decimal):
            return str(obj)
        return super().default(obj)
```

앞에서 말한 `Decimal` 문제의 첫 번째 해법이다. `json.dumps` 가 모르는 타입을 만나면 이 `default` 를 부른다. `Decimal` 이면 문자열로 바꾸고, 그것도 아니면 원래 하던 대로(`super().default`) 오류를 낸다.

`class` 와 상속이 낯설다면 지금은 **"json.dumps 에게 Decimal 을 처리하는 법을 알려주는 부품"** 으로만 이해해도 충분하다.

```python
def _response(status, body):
    return {
        "statusCode": status,
        "statusDescription": f"{status} {_STATUS_TEXT.get(status, '')}",
        "isBase64Encoded": False,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps(body, cls=_DecimalEncoder),
    }
```

응답 만드는 일을 함수 하나로 모았다. 이렇게 해 두면 아래 핸들러가 `_response(400, {...})` 한 줄로 끝난다. 형식을 네 군데에 복사해 두면 한 군데만 고치는 실수가 난다.

`f"{status} {...}"` 는 f-문자열이다. 따옴표 앞에 `f` 를 붙이면 중괄호 안이 값으로 바뀐다.

```python
def handler(event, context):
    params = event.get("queryStringParameters") or {}
    booking_id = params.get("booking_id")

    if not booking_id:
        return _response(400, {"msg": "booking_id is required"})

    item = table.get_item(Key={"booking_id": booking_id}).get("Item")
    if not item:
        return _response(404, {"msg": "Item not found"})
```

핵심 흐름이다. 값이 없으면 400, 찾지 못하면 404, 찾으면 200 을 낸다.

`table.get_item(...)` 은 항목을 바로 주지 않고 응답 딕셔너리를 준다. 찾았으면 그 안에 `"Item"` 이름표가 있고, 못 찾았으면 없다. 그래서 `.get("Item")` 으로 꺼내고 `None` 인지 본다.

**400 과 404 를 나누는 것이 요구사항이다.** 400 은 "요청이 잘못됐다", 404 는 "요청은 맞는데 그런 게 없다"다. 둘 다 404 로 내면 채점 항목 하나를 잃는다.

```python
    for key in ("email", "concert_name"):
        if params.get(key) and item.get(key) != params.get(key):
            return _response(404, {"msg": "Item not found"})
```

선택 조건이다. `email` 이 쿼리에 왔으면 항목의 `email` 과 같아야 하고, 안 왔으면 검사하지 않는다. `params.get(key) and ...` 의 앞부분이 그 "안 왔으면 넘어간다"를 맡는다. `and` 는 앞이 거짓이면 뒤를 아예 보지 않는다.

### 3-2. 인덱스 조회와 정렬 — `set-02/task-1`

**하는 일.** `GET ?concert_name=<이름>` 으로 공연 이름에 해당하는 예매를 **최신순으로 전부** 돌려준다.

앞의 것과 다른 점이 셋이다. 기본 키가 아닌 축으로 찾고, 정렬이 필요하고, 결과가 여러 건이다.

```python
from urllib.parse import unquote_plus

from boto3.dynamodb.conditions import Key

table = boto3.resource("dynamodb").Table(os.environ["TABLE_NAME"])
index_name = os.environ.get("INDEX_NAME", "concert_name-created_at-index")
```

```python
    concert_name = unquote_plus(concert_name)
```

ALB 는 쿼리스트링을 디코딩하지 않고 그대로 넘긴다. 공연 이름이 `2ND TINY_CON` 이면 브라우저가 `2ND%20TINY_CON` 으로 보내고 Lambda 도 그 글자 그대로 받는다. `%20` 을 공백으로 되돌리지 않으면 DynamoDB 에서 아무것도 찾지 못한다. `unquote_plus` 가 그 일을 한다.

```python
    kwargs = {
        "IndexName": index_name,
        "KeyConditionExpression": Key("concert_name").eq(concert_name),
        "ScanIndexForward": False,
    }
    while True:
        page = table.query(**kwargs)
        items.extend(page.get("Items", []))
        if "LastEvaluatedKey" not in page:
            break
        kwargs["ExclusiveStartKey"] = page["LastEvaluatedKey"]
```

세 가지를 한꺼번에 한다.

**첫째, GSI 로 찾는다.** `IndexName` 을 주면 기본 키가 아니라 그 인덱스에서 찾는다. 인덱스가 없으면 `Scan` 으로 테이블 전체를 훑어야 하는데 느리고 비싸다.

**둘째, 정렬을 DynamoDB 에게 맡긴다.** `ScanIndexForward: False` 는 정렬 키 역순, 곧 `created_at` 내림차순이다. 파이썬으로 받아서 `sorted()` 해도 결과는 같지만, 요구사항이 데이터베이스 수준 정렬을 요구하면 그것만으로는 항목을 잃는다.

**셋째, 페이지를 이어 받는다.** DynamoDB 는 한 번에 최대 1MB 만 준다. 남았으면 응답에 `LastEvaluatedKey` 를 넣어 준다. 그것을 다음 요청의 `ExclusiveStartKey` 로 넘겨 이어 받는 반복이 위의 `while` 이다. 이 고리가 없으면 **데이터가 적을 때는 멀쩡히 돌다가 많아지면 조용히 일부만 준다.** 가장 찾기 어려운 종류의 오답이다.

`table.query(**kwargs)` 의 별표 둘은 딕셔너리를 이름 붙은 인자로 펼치라는 뜻이다. `table.query(IndexName=..., KeyConditionExpression=...)` 라고 쓴 것과 같다. 반복마다 키를 하나 더해야 해서 딕셔너리로 들고 있는 것이다.

```python
_KEYS = ["username", "created_at", "email", "booking_id", "client_id", "concert_name"]
...
    return _response(200, [{k: item.get(k) for k in _KEYS} for item in items])
```

마지막 줄에 대괄호와 중괄호가 겹쳐 있다. 안쪽부터 읽는다.

- `{k: item.get(k) for k in _KEYS}` — `_KEYS` 순서대로 이름표와 값을 담은 딕셔너리 하나
- `[... for item in items]` — 그것을 항목마다 만들어 리스트로

**키 순서를 고정한 이유**가 있다. Python 딕셔너리는 넣은 순서를 기억하고 `json.dumps` 가 그 순서로 쓴다. 채점이 출력 문자열을 비교하면 순서가 곧 정답 여부다.

```python
        "body": json.dumps(body, ensure_ascii=False, default=str),
```

여기서는 `Decimal` 을 다른 방법으로 처리한다. `default=str` 은 "모르는 타입은 `str()` 로 바꿔라"라는 뜻이라 앞의 `_DecimalEncoder` 클래스와 결과가 같고 훨씬 짧다.

`ensure_ascii=False` 도 중요하다. `json.dumps` 는 기본적으로 한글을 `안녕` 같은 이스케이프로 바꾼다. 채점이 원문을 기대하면 이 옵션이 없을 때 틀린다.

### 3-3. 파이프라인 — `set-02/task-2 module-1`

**하는 일.** S3 에 올라온 CSV 를 읽어 행마다 검사하고, 정상 행은 평균과 등급을 계산해 DynamoDB 에, 오류 행은 이유를 붙여 S3 `error/` 에 넣는다.

177줄로 앞의 둘보다 훨씬 길지만 **함수가 잘게 나뉘어 있어** 한 번에 한 조각씩 읽으면 된다. 이 나누는 방식 자체가 배울 점이다.

| 함수 | 하는 일 |
|---|---|
| `decode_csv` | 바이트를 글자로 |
| `normalize_header` | 헤더 이름 다듬기 |
| `read_rows` | CSV 를 딕셔너리 목록으로 |
| `validate_row` | 한 행이 성한지 검사 |
| `save_error` | 오류 행을 S3 에 |
| `calculate_grade` | 평균에서 등급으로 |
| `save_student` | 정상 행을 DynamoDB 에 |
| `handler` | 위를 순서대로 부른다 |

```python
def decode_csv(raw):
    for encoding in ("utf-8-sig", "cp949"):
        try:
            return raw.decode(encoding)
        except UnicodeDecodeError:
            continue
    return raw.decode("utf-8", errors="replace")
```

S3 에서 읽은 것은 바이트다. 글자로 바꾸려면 어떤 방식으로 저장됐는지 알아야 한다.

`utf-8-sig` 를 먼저 시도하는 것이 핵심이다. 엑셀이나 메모장이 UTF-8 로 저장하면 파일 맨 앞에 보이지 않는 표식(BOM)을 붙인다. 그냥 `utf-8` 로 읽으면 첫 헤더가 `examDate` 가 아니라 `﻿examDate` 가 되어 **모든 행이 필드 누락으로 떨어진다.** `utf-8-sig` 는 그 표식을 알아서 떼어 낸다.

`try` 와 `except` 는 오류가 날 수 있는 일을 감싼다. `try` 안이 실패하면 프로그램이 죽는 대신 `except` 로 넘어간다. 여기서는 `continue` 로 다음 인코딩을 시도한다.

:::danger[이 함정의 무서운 점]
BOM 때문에 전 행이 떨어져도 **함수는 성공으로 끝난다.** DynamoDB 는 0건인데 상태코드는 200 이라 워크플로가 파일을 `processed/` 로 옮긴다. 겉보기에 전부 정상이고 채점에서만 0건이 드러난다.
:::

```python
def validate_row(row):
    for field in REQUIRED_FIELDS:
        if not (row.get(field) or "").strip():
            return "MISSING_FIELD"

    exam_date = row.get("examDate", "").strip()
    if not re.match(r"^\d{4}-\d{2}-\d{2}$", exam_date):
        return "INVALID_DATE"
    ...
    for field in SCORE_FIELDS:
        value = row.get(field, "").strip()
        if not value.lstrip("+-").isdigit():
            return "INVALID_FORMAT"
        score = int(value)
        if score < 0 or score > 100:
            return "INVALID_SCORE"

    return None
```

**문제가 있으면 이유 문자열을, 없으면 `None` 을 돌려준다.** 부르는 쪽이 `if error_reason:` 한 줄로 갈래를 나눌 수 있다.

`(row.get(field) or "").strip()` 은 세 겹이다. 값이 없으면 `None`, `or ""` 로 빈 문자열, `.strip()` 으로 앞뒤 공백 제거. 결과가 빈 문자열이면 거짓이라 `not` 이 참이 된다. 즉 **없거나 공백뿐이면** 누락으로 본다.

`re.match(r"^\d{4}-\d{2}-\d{2}$", ...)` 는 정규식이다. `\d` 가 숫자 하나, `{4}` 가 네 번, `^` 와 `$` 가 처음과 끝이다. 곧 `2026-08-28` 같은 모양만 통과한다. 따옴표 앞의 `r` 은 역슬래시를 글자 그대로 쓰라는 표시다.

검사 순서가 형식 먼저, 범위 나중이다. `"abc"` 를 `int()` 에 넣으면 오류가 나므로 숫자인지부터 확인해야 한다.

```python
def save_student(table, row):
    scores = {field: int(row[field].strip()) for field in SCORE_FIELDS}
    average = Decimal(str(sum(scores.values()))) / Decimal(len(SCORE_FIELDS))
```

앞에서 본 `Decimal` 이 여기서 실전으로 나온다. 483 을 5로 나누면 `float` 은 96.60000000000001 을 주고, 채점은 96.6 을 기대하며, 애초에 boto3 가 `float` 저장을 거부한다. 세 이유가 겹친다.

`Decimal(str(...))` 처럼 문자열을 거치는 것도 이유가 있다. `Decimal(0.1)` 은 이미 부정확해진 `float` 을 받아 오차를 그대로 물려받는다. `Decimal("0.1")` 은 정확하다.

분모를 `5` 라고 쓰지 않고 `len(SCORE_FIELDS)` 로 쓴 점을 본다. 과목이 바뀌면 목록 한 곳만 고치면 된다. **같은 사실을 두 곳에 적어 두면 한 곳만 고치는 실수가 반드시 난다.**

```python
    last_modified = response.get("LastModified") or datetime.now(timezone.utc)
    timestamp = last_modified.astimezone(timezone.utc).strftime("%Y%m%d%H%M%S")
```

오류 파일 이름에 쓸 시각을 **현재 시각이 아니라 S3 객체의 최종 수정 시각**에서 뽑는다. Step Functions 가 Lambda 를 재시도하면 현재 시각은 매번 달라져 오류 파일이 계속 늘어난다. 채점이 "오류 파일이 정확히 4개"를 본다면 재시도 한 번에 8개가 되어 틀린다. 객체의 시각은 재시도해도 같으므로 같은 이름에 덮어써진다.

```python
    if rows and processed == 0:
        print("[processor] every row rejected — reporting failure")
        return {"statusCode": 500, "processed": processed, "errors": errors}
```

마지막이 이 파일에서 가장 중요한 다섯 줄이다. **행은 읽혔는데 한 건도 저장하지 못했으면 실패로 보고한다.** 200 을 돌려주면 워크플로가 파일을 `processed/` 로 옮겨 성공처럼 보인다. 실패를 발견하는 시점이 채점 직후가 된다.

`print` 로 남긴 것은 CloudWatch Logs 로 간다. Lambda 에서 화면이 없으니 `print` 가 곧 로그다.

### 4-1. S3 이벤트를 받는 Lambda

[실기출 2025 2과제](/reference/past-exams/#3-2-2025-2과제--small-challenge-4시간)의 Macie 마스킹 모듈이 이 모양이다. S3 `incoming/` 에 파일이 올라오면 민감정보를 가리고 `masked/` 에 넣는다.

```python
import boto3
import re

s3 = boto3.client("s3")


def mask_email(text):
    # davisjesus@example.org -> d*********@example.org
    def repl(m):
        local, domain = m.group(1), m.group(2)
        return local[0] + "*" * (len(local) - 1) + "@" + domain
    return re.sub(r"([\w.+-]+)@([\w.-]+\.[\w.-]+)", repl, text)


def handler(event, context):
    record = event["Records"][0]
    bucket = record["s3"]["bucket"]["name"]
    key = record["s3"]["object"]["key"]

    body = s3.get_object(Bucket=bucket, Key=key)["Body"].read().decode("utf-8")
    masked = mask_email(body)

    s3.put_object(
        Bucket=bucket,
        Key=key.replace("incoming/", "masked/"),
        Body=masked.encode("utf-8"),
    )
    return {"statusCode": 200}
```

두 가지를 본다.

**`event["Records"][0]`** — S3 이벤트는 여러 건이 묶여 올 수 있어 목록이다. 실무에서는 `for record in event["Records"]` 로 도는 편이 안전하다.

**`re.sub` 에 함수를 넘길 수 있다.** 찾은 부분마다 그 함수를 부르고 돌려준 값으로 바꾼다. `m.group(1)` 은 정규식의 첫 괄호에 걸린 부분이다.

:::danger[같은 버킷에 쓰면 무한루프가 난다]
`incoming/` 에 반응하는 트리거인데 결과를 같은 버킷에 넣는다. 트리거 조건을 접두사 `incoming/` 으로 좁혀 두지 않으면 `masked/` 에 쓴 파일이 다시 트리거를 부르고 끝없이 돈다. **S3 이벤트 알림에 접두사·접미사 필터를 반드시 건다.**
:::

### 4-2. 마스킹 정규식 여섯 종

[2025 2과제 표](/reference/past-exams/#3-2-2025-2과제--small-challenge-4시간)의 요구를 정규식으로 옮기면 이렇다.

```python
PATTERNS = [
    # 전화 010-7658-5153 -> 010-7658-****
    (r"(\d{2,3}-\d{3,4}-)\d{4}", r"\1****"),
    # 주민번호 887-07-7325 -> 887-07-****
    (r"(\d{3}-\d{2}-)\d{4}", r"\1****"),
    # 카드 4468-6779-7028-4776 -> 4468-6779-7028-****
    (r"(\d{4}-\d{4}-\d{4}-)\d{4}", r"\1****"),
    # UUID 뒤 12자리
    (r"([0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-)[0-9a-f]{12}", r"\1************"),
]


def mask_all(text):
    for pattern, replacement in PATTERNS:
        text = re.sub(pattern, replacement, text)
    return text
```

`\1` 은 첫 괄호에 걸린 부분을 그대로 다시 쓴다는 뜻이다. 앞부분은 살리고 뒤만 별표로 바꾼다.

:::caution[순서가 결과를 바꾼다]
전화번호 규칙 `(\d{2,3}-\d{3,4}-)\d{4}` 가 주민번호 `887-07-7325` 에도 걸릴 수 있다. 좁은 규칙을 먼저 적용하거나 규칙에 경계를 넣어 서로 겹치지 않게 한다. 실제로 돌려 보고 표의 여섯 줄이 전부 기대대로 바뀌는지 확인하는 것이 유일한 검증이다.
:::

### 4-3. 저장된 시간 형식이 하나가 아니다

앱이 `created_at` 에 무엇을 넣는지는 문제지에 안 적혀 있을 때가 있다. [set-03 1과제 정답지](/reference/links/)의 조회 Lambda 가 이 문제를 그대로 만났다 — 같은 칸에서 epoch 숫자와 ISO 8601 문자열이 둘 다 나왔다.

한쪽만 가정하면 다른 쪽에서 터진다.

```python
datetime.fromisoformat("1721000000")   # ValueError — 숫자는 ISO 가 아니다
float("2024-07-15T02:13:20Z")          # ValueError — 문자열은 숫자가 아니다
```

둘 다 받게 만든다.

```python
from datetime import datetime, timedelta, timezone

KST = timezone(timedelta(hours=9))


def to_kst(value):
    """epoch(초·밀리초) · ISO 8601 · 'YYYY-MM-DD HH:MM:SS' 를 모두 받는다."""
    if value is None:
        return ""
    s = str(value)                        # DynamoDB 숫자는 Decimal 로 온다

    dt = None
    try:
        num = float(s)                    # 숫자로 읽히면 epoch 이다
        if num > 1e12:                    # 13자리 이상은 밀리초
            num /= 1000.0
        dt = datetime.fromtimestamp(num, tz=timezone.utc)
    except (ValueError, OverflowError):
        pass

    if dt is None:
        try:
            dt = datetime.fromisoformat(s.replace("Z", "+00:00"))
        except ValueError:
            return s                      # 모르는 형식은 원본 그대로 둔다

    if dt.tzinfo is None:                 # 시간대 표기가 없으면 UTC 로 본다
        dt = dt.replace(tzinfo=timezone.utc)
    return dt.astimezone(KST).strftime("%Y-%m-%d %H:%M:%S KST")
```

세 가지를 본다.

**`str(value)` 로 먼저 문자열을 만든다.** DynamoDB 의 숫자는 `Decimal` 로 돌아온다([2-8 절](#2-8-decimal-이-필요한-이유)). `Decimal` 을 그대로 `float()` 에 넣어도 되지만, 숫자든 문자열이든 한 갈래로 다루려면 문자열로 맞추는 편이 짧다.

**`1e12` 가 초와 밀리초를 가른다.** epoch 초는 지금 10자리(`1721000000`), 밀리초는 13자리(`1721000000000`)다. 이 기준은 2001년부터 2286년까지 성립한다.

**모르는 형식은 원본을 그대로 돌려준다.** 예외를 던지면 항목 하나 때문에 응답 전체가 500 이 된다. 파싱에 실패해도 값은 보이게 둔다.

한 줄씩 확인한다.

```python
assert to_kst(1721000000) == to_kst("1721000000000")   # 초와 밀리초가 같은 시각
assert to_kst("2024-07-15T02:13:20Z").endswith("KST")
assert to_kst("모름") == "모름"
```

:::caution[`Z` 는 `fromisoformat` 이 파이썬 3.11 부터 읽는다]
3.10 이하에서는 `datetime.fromisoformat("2024-07-15T02:13:20Z")` 가 `ValueError` 다. 위 코드가 `Z` 를 `+00:00` 으로 바꿔 두는 이유다. Lambda 런타임을 3.12 로 잡아도 이 치환은 그대로 두는 편이 안전하다.
:::

:::danger[정렬 키에 두 형식이 섞이면 최신순이 깨진다]
`created_at` 이 정렬 키인데 어떤 항목은 `1721000000`, 어떤 항목은 `2024-07-15T02:13:20Z` 로 들어가 있으면 문자열 비교에서 `1...` 이 `2...` 보다 항상 앞선다. `ScanIndexForward: False` 로 뽑아도 최신순이 아니다.

**표시할 때 고치는 것과 저장할 때 통일하는 것은 다른 문제다.** `to_kst` 는 읽는 쪽만 구한다. 정렬이 채점 항목이면 넣는 쪽에서 형식을 하나로 맞춰야 한다([3-2 절](#3-2-인덱스-조회와-정렬--set-02task-1)).
:::

| `float` 로 계산해 DynamoDB 에 넣음 | `Float types are not supported` | `Decimal` 사용 |
| `Decimal` 을 그대로 `json.dumps` | `TypeError` | `default=str` 또는 인코더 |
| 페이지 나눔 처리 없음 | 적을 땐 정상, 많아지면 일부만 | `LastEvaluatedKey` 반복 |
| 테이블 이름 하드코딩 | 이름 바뀌면 재배포, 감점 | `os.environ` |
| 들여쓰기가 섞임 | `IndentationError` | 스페이스 4칸으로 통일 |
| 한글이 `\uXXXX` 로 나감 | 채점 문자열 불일치 | `ensure_ascii=False` |

:::note[Lambda 가 죽었는지 어떻게 아나]
CloudWatch Logs 에서 그 함수의 로그 그룹(`/aws/lambda/<함수이름>`)을 본다. 오류가 나면 파이썬 역추적이 통째로 찍힌다. 마지막 줄이 오류 종류와 메시지다.

```bash
aws logs tail /aws/lambda/my-function --follow
```
:::

## ⑦ 자기 점검 퀴즈

<Quiz title="event 에서 값을 꺼내는 법">
ALB 가 호출하는 Lambda 에서 `event['queryStringParameters']` 대신 `event.get('queryStringParameters') or {}` 를 쓰는 이유는?

- [ ] 성능이 더 빠르기 때문
  > 차이가 없다. 안전성의 문제다.
- [x] 쿼리스트링이 없는 요청에서 값이 None 이 되어 .get() 호출이 오류를 내기 때문
- [ ] ALB 가 대괄호 접근을 막기 때문
  > ALB 는 파이썬 문법에 관여하지 않는다.
- [ ] json 직렬화에 필요하기 때문
  > 직렬화와 무관하다. 값을 꺼내는 시점의 이야기다.

쿼리스트링이 없으면 ALB 는 그 자리에 None 을 넣는다. None.get() 은 AttributeError 이고 Lambda 가 죽어 ALB 는 502 를 낸다. or {} 로 빈 딕셔너리를 대신 쓴다.
</Quiz>

<Quiz title="평균값을 DynamoDB 에 넣기">
483 을 5로 나눈 평균을 DynamoDB 에 넣어야 한다. 올바른 것은?

- [ ] 483 / 5 를 그대로 넣는다
  > `float` 이라 boto3 가 저장을 거부한다.
- [ ] round(483 / 5, 1) 을 넣는다
  > 반올림해도 여전히 `float` 이다. 타입이 문제다.
- [x] Decimal(str(483)) / Decimal(5) 를 넣는다
- [ ] str(483 / 5) 로 문자열로 바꿔 넣는다
  > 저장은 되지만 숫자가 아니라 문자열(`S`)로 들어가 비교·정렬이 깨진다.

483/5 는 96.60000000000001 이 되고 boto3 는 float 저장 자체를 거부한다. round 를 써도 결과는 여전히 float 이다. 문자열로 바꾸면 숫자 속성이 아니게 되어 숫자 비교나 정렬이 깨진다.
</Quiz>

<Quiz title="LastEvaluatedKey 의 뜻">
DynamoDB Query 응답에 LastEvaluatedKey 가 들어 있다는 것은 무슨 뜻인가?

- [ ] 조회에 실패했다
  > 실패면 예외가 난다. 이것은 정상 응답에 붙는 값이다.
- [x] 결과가 더 남아 있고 이어 받아야 한다
- [ ] 인덱스가 없다
  > 인덱스 유무와 무관하다. 한 번에 못 담았다는 뜻이다.
- [ ] 정렬이 적용되지 않았다
  > 정렬은 `ScanIndexForward` 가 정한다.

DynamoDB 는 한 번에 최대 1MB 만 준다. 남았으면 LastEvaluatedKey 를 주고, 그것을 다음 요청의 ExclusiveStartKey 로 넘겨 이어 받는다. 이 처리를 빼면 데이터가 적을 때는 정상으로 보인다.
</Quiz>

<Quiz title="CSV 가 전부 필드 누락으로 떨어진다">
CSV 를 utf-8 로 읽었더니 모든 행이 필드 누락으로 떨어졌다. 가장 먼저 의심할 것은?

- [ ] CSV 구분자가 쉼표가 아니다
  > 그 경우 열이 통째로 하나로 붙어 증상이 다르다.
- [x] 파일 맨 앞에 BOM 이 붙어 첫 헤더 이름이 달라졌다
- [ ] DynamoDB 권한이 없다
  > 권한 문제면 읽기가 아니라 쓰기에서 막힌다.
- [ ] 행 수가 너무 많다
  > 많아서 실패하면 일부는 성공한다. 전부 떨어지는 것은 헤더 문제다.

엑셀이나 메모장이 UTF-8 로 저장하면 BOM 을 붙인다. utf-8 로 읽으면 첫 헤더가 ﻿examDate 가 되어 필수 필드 검사를 통과하지 못한다. utf-8-sig 로 읽으면 BOM 을 떼어 낸다.
</Quiz>

<Quiz title="ScanIndexForward 를 False 로">
ScanIndexForward 를 False 로 두면?

- [ ] 인덱스를 사용하지 않는다
  > 인덱스는 그대로 쓴다. 읽는 방향만 바뀐다.
- [x] 정렬 키 기준 내림차순으로 읽는다
- [ ] 결과를 역순으로 뒤집어 반환한다
  > 받아서 뒤집는 것이 아니라 **읽는 방향**이 바뀐다. `Limit` 과 함께 쓰면 결과가 달라진다.
- [ ] Scan 으로 동작한다
  > `Query` 그대로다.

DynamoDB 가 정렬 키 역순으로 읽는다. created_at 이 정렬 키면 최신순이 된다. 파이썬에서 받아 정렬하는 것과 결과는 같지만 데이터베이스 수준 정렬을 요구하는 항목에서는 그것만으로 부족하다.
</Quiz>

<Quiz title="전부 거부하고 200 을 돌려준다">
파이프라인 Lambda 가 모든 행을 거부했는데도 statusCode 200 을 돌려주면 무엇이 문제인가?

- [ ] 비용이 더 든다
  > 비용은 거의 같다. 문제는 실패가 성공으로 보인다는 것이다.
- [x] 워크플로가 성공으로 보고 원본을 processed/ 로 옮겨 실패를 늦게 발견한다
- [ ] CloudWatch 로그가 남지 않는다
  > 로그는 남는다. 다만 아무도 안 본다.
- [ ] S3 트리거가 다시 돈다
  > 다시 돌지 않는다. 오히려 조용히 넘어가는 것이 문제다.

겉보기에 모두 정상이고 DynamoDB 만 비어 있다. 채점 시점에야 드러난다. 행은 읽혔는데 저장이 0건이면 500 으로 보고해 그 자리에서 멈추게 한다.
</Quiz>

<Quiz title="epoch 과 ISO 가 한 칸에 섞여 있다">
`created_at` 을 읽어 KST 로 보여 주는 Lambda 다. 어떤 항목은 `1721000000`, 어떤 항목은 `2024-07-15T02:13:20Z` 로 저장돼 있다. 어떻게 다루나?

- [x] 숫자로 읽히면 epoch, 아니면 ISO 로 파싱하고 둘 다 실패하면 원본을 그대로 돌려준다
- [ ] `datetime.fromisoformat` 하나로 통일한다
  > 숫자 문자열에서 `ValueError` 가 난다. 잡지 않으면 항목 하나 때문에 응답 전체가 500 이 된다.
- [ ] 문제지에서 앱이 넣는 형식을 확인하고 그것만 처리한다
  > 문제지에 안 적혀 있을 때가 있다. 배포하고 실제 값을 찍어 보는 것이 유일한 근거다.
- [ ] 전부 문자열로 두고 변환하지 않는다
  > 표시 형식이 채점 항목이면 그대로는 통과하지 못한다.

**두 갈래로 받는다.** `float()` 이 되면 epoch, 아니면 `fromisoformat` 이다. `1e12` 를 넘으면 밀리초라 1000 으로 나눈다. 모르는 형식은 예외를 던지지 말고 원본을 돌려준다.

DynamoDB 의 숫자는 `Decimal` 로 오므로 `str()` 로 한 번 맞추면 숫자와 문자열을 한 갈래로 다룰 수 있다.
</Quiz>
